# Project Knowledge Pipeline

## Canonical Domain Layer

Текущий канонический доменный слой состоит из:

- `Wiki/` — термины, понятия, участники, внешние системы, сущности, объекты-значения, команды, доменные и системные события, правила, спецификации, конфликты, вопросы и их реестры.
- `DDD_Wiki/` - DDD-проекция модели: domains, subdomains, bounded contexts, context map, aggregates, state machines, invariants, use cases, integration patterns и `model_health.md`.
- `Code_wiki/` - техническая wiki; продолжает наполняться через `/ingest repository-snapshot` и `/ingest repository-change`.

`/ingest` без параметров выбирает для обработки новые файлы в `RAW_inputs/`, которых ещё нет в журнале обработанных источников. Сверка с исходной моделью не запускает повторную обработку её источника. Изменённый ранее обработанный RAW требует уточнения. Новым входом может быть документ любого типа.

`/discover` и `/discover --wide` ищут вопросы по всей модели редактора инженерной сети. Из пула до 150 кандидатов выбрать до 15 разных подтверждённых пробелов. При меньшем числе подходящих вопросов вернуть фактическое число. [Правила отбора](../../.agents/skills/source-command-discover/SKILL.md).

`/plan-sprint` помогает выбрать результат, который можно продемонстрировать через 14 дней. Агент сверяет модель и код, отбирает 15 из 150 вопросов о цели, объёме, порядке работ и приёмке. В первом содержательном ответе задаёт пользователю все 15 одним нумерованным списком. Если ответы частичные, уточняет оставшиеся пункты. После ответов на все 15, включая явно делегированные решения, составляет минимальный сквозной сценарий, календарь, проверки и допустимое сокращение объёма. Обе команды можно запускать самостоятельно. [Порядок планирования спринта](../../.agents/skills/source-command-plan-sprint/SKILL.md).

Wiki ведется на русском языке. Пути, команды, идентификаторы и имена файлов не переводятся.

## Утро

1. Выполнить `/sync-vision`.
2. Проверить `memory/project-state.md`.
3. Проверить новые файлы в `RAW_inputs/`.
4. Если появились новые RAW inputs, выполнить `/ingest`. Без параметров `/ingest` обрабатывает 1-5 однозначных новых RAW-файлов по очереди. Если файлов больше 5 или есть неоднозначность, агент показывает список и просит подтверждение.

## `/ingest` Без Параметров

Когда путь не указан, агент ищет новые или измененные файлы в `RAW_inputs/`, которых еще нет в обработанных source-записях wiki/state.

- Если новых RAW-кандидатов нет, агент ничего не меняет и сообщает, что ingest не выполнен.
- Если найдено 1–5 однозначных RAW-файлов, агент обрабатывает их в одном запуске. По анализу и ответам одного исследования агент сначала читает оба файла, затем принимает общие решения и отмечает каждый источник в `RAW_inputs/index.md`.
- Если найдено больше 5 RAW-кандидатов, агент показывает список по папкам и просит подтверждение.
- Если есть неоднозначность, агент просит подтверждение до обработки. Неоднозначность: непонятный тип источника, слишком большой файл, неясно, поступил ли новый источник или другая версия уже обработанного документа, возможный конфликт с документацией, потенциальные секреты или персональные данные.

## Полнота доменного ingest

Для каждого доменного RAW проверить вклад во все содержательные разделы `Wiki/` и `DDD_Wiki/`. Для анализа и ответов одного исследования выполнить общую сверку. Взять актуальный состав разделов из обоих каталогов, включая разделы, в которых пока есть только `_info.md`. Сопоставить эпизоды с существующими узлами и решениями. Для каждого существенного вывода установить, что изменилось в работе с сетью и кто за это отвечает.

| Где искать вклад | Что требуется установить по эпизоду |
| --- | --- |
| `Wiki/glossary`, `concepts`, `actors`, `external_systems` | Как участники называют явление, что оно означает, кто принимает решение и кто поставляет или получает сведения? |
| `Wiki/entities`, `value_objects` | Какой объект сохраняет идентичность после изменения? Какие значения взаимозаменяемы, из чего они состоят и какие сочетания допустимы? |
| `Wiki/commands`, `domain_events`, `system_events` | Кто намерен что изменить? Какой совершившийся факт имеет предметные последствия? Какое техническое уведомление лишь сообщает о доставке или обработке? |
| `Wiki/policies`, `specifications`, `questions`, `conflicts` | Какое правило приводит к решению, какое условие можно проверить, что остаётся неизвестным и какие свидетельства действительно противоречат друг другу? |
| `DDD_Wiki/domains`, `subdomains`, `bounded_contexts`, `context_map`, `integration_patterns` | Меняется ли предметная задача или ответственность? Где различается смысл данных? Кто владеет фактом, кто его получает и что известно о способе согласования? |
| `DDD_Wiki/aggregates`, `invariants`, `state_machines` | Что меняется вместе, какое сочетание запрещено и какая операция его предотвращает? Установлены ли корень, допустимый переход, основание перехода и результат отказа? |
| `DDD_Wiki/use_cases` и его каталог кандидатов | Какую цель и проверяемый результат получает участник? Применить правила отбора сценариев ниже. Знакомый сценарий всё ещё может дать новый инвариант, событие или переход. |

Обоснованное уточнение внести в узел, которому принадлежит правило, со ссылкой на эпизод и с указанием происхождения. Уже описанный результат связать с действующим разделом. Для существенной гипотезы указать недостающее свидетельство или различающий случай. Например, один наряд с тремя замерами ещё не определяет границу агрегата. Проверить, можно ли принять один замер при спорной привязке другого. При повторном ingest переиспользовать ранее записанные выводы.

В итогах показать ссылки на изменившиеся части обеих wiki, подтверждения и существенные открытые вопросы. Разделы без предметного прироста можно перечислить вместе с общей причиной. Обновлять относящиеся к изменениям `_registry/`, `_info.md`, `index.md`, `model_health.md` и очередь вопросов. Шаблоны задают оформление новых узлов. Для целиком смежного материала достаточно объяснения в журнале RAW.

Проверять наличие самих узлов по эпизодам. Для принятого агрегата создать или дополнить собственную страницу с `type: aggregate`: указать корень, совместно изменяемые данные, ссылки на внешних владельцев, операции, защищаемые условия и пример отказа. Из каталога и из относящейся к операции команды, сущности или события должен быть путь к этой странице. Если практики описывают поведение, а выбор владельца сделан для GeoService, указать основание выбора через `expert_repson`. В `_info.md` оставить навигацию и действительно нерешённые варианты. Ту же проверку выполнить для других выявленных элементов по их предметной ответственности.

При обновлении состояния различать очередь открытых доменных вопросов и очередь задач на выполнение. Для первой актуальны статусы в реестре вопросов. Для второй сохранять рабочие ссылки на [бэклог разработки](../planning/network-editor-backlog.md) в корневом индексе, состоянии проекта и разделе Current Sprint Planning Queue. Новое доменное решение само по себе не меняет приоритет разработки.

В очереди планирования каждый предметный результат связывать с действующим сценарием каталога, участником, получателем и приёмочным примером. У частичного этапа указывать, какой результат всего сценария ещё предстоит получить. При изменении каталога сверять содержание очереди с этими результатами. Приоритет и срок следующего спринта меняются по отдельному решению о планировании. [Каталог](../../DDD_Wiki/use_cases/_info.md) · [Очередь по сценариям](../planning/network-editor-backlog.md#что-предстоит-реализовать-по-сценариям).

## Как исследование пополняет каталог сценариев

Исследование ответов начинается по отдельному поручению пользователя. Когда готовы RAW с ответами, наблюдениями практиков или выводами, агент выполняет `/ingest` этих файлов в рамках исследовательской задачи. Анализ и ответы одного исследования рассматриваются вместе. Если поручение ограничено сбором или анализом, работа завершается передачей запрошенных материалов. Список вопросов, сохранённый при `/discover`, сам по себе не запускает `/ingest`.

При доменном `/ingest` агент через `expert_repson` сопоставляет эпизоды источника с задачами редактора инженерной сети. Исходная граница определена в разделах о целях, рабочих процессах и данных [UtilityGisEditor.md](../../RAW_inputs/documents/UtilityGisEditor.md). В неё входят ведение и проверка сети, трассировка и обмен сведениями, нужными для решения по сети.

1. Для каждой цели, в том числе вне исходной анкеты, связать эпизод RAW с разделом исходного документа или принятым узлом, восходящим к нему. Указать, кто решает какую задачу с помощью редактора, над какими данными сети и кто получает наблюдаемый результат. В смешанном эпизоде рассмотреть решения участников по отдельности.
2. Прочитать ближайшие страницы [каталога DDD](../../DDD_Wiki/use_cases/_info.md) и прежние решения по кандидатам. Сравнить основной ход, ответственность и условия завершения. Дополнительный пример уже описанной работы связать с существующей страницей в обзоре. Если такой эпизод уже был предложен автором как кандидат, отметить «уже покрыт» и сослаться на раздел с тем же результатом.
3. Для каждого кандидата выбрать один исход. В обзоре исследования или реестре решений указать место в источнике, ближайший сценарий или его отсутствие, различие и причину выбора.

| Решение | Результат в wiki |
| --- | --- |
| Принят | В источнике прослеживается самостоятельная задача редактора. Показано, какой результат ещё не покрывает ближайший сценарий и как он расширяет исходную модель. Описать задачу, повод, участников, данные сети, ход работы, развилки, получателя, ожидаемый результат и его проверку. Включить страницу в каталог. |
| Включён как вариант | Цель уже покрыта. Конкретный раздел действующего сценария дополнен новым условием, действием и исходом. В решении дана ссылка на раздел. |
| Уже покрыт | Для предложенного в исследовании кандидата даны ссылка на действующий раздел и совпадающий результат. Новая страница не требуется. |
| Отложен | Возможна предметная связь, но неизвестно, какое решение или результат принадлежит редактору. Указать недостающее свидетельство и условие пересмотра. |
| За границей модели | У решения есть внешний владелец и результат. Зафиксировать относящийся к редактору обмен, если он описан. |

Разбор сценариев завершён, когда по каждому кандидату есть обоснование, принятые страницы доступны из каталога, а варианты можно найти в соответствующих разделах. Весь доменный ingest завершается после [проверки обеих wiki](#полнота-доменного-ingest), в том числе при нулевом числе новых сценариев. В отчёте дать ссылки на решения. При повторном разборе указать новое основание, если прежнее решение пересмотрено. [Пример разбора кандидатов](../../DDD_Wiki/use_cases/candidates/_info.md).

Практику из источника, решение GeoService и открытую гипотезу фиксируют раздельно. Для отдельно запрошенного исследования ответы обосновывают относящимися к вопросу источниками. Обязательного минимума нет. [Инструкция доменного ingest](../../.agents/skills/source-command-ingest/SKILL.md).

Единственный источник начального среза — `RAW_inputs/documents/UtilityGisEditor.md`. Четыре исходных сценария служат отправной точкой. Новое предметное свидетельство может уточнить правило, добавить вариант или обосновать самостоятельную цель. Код приложения и RAW с пометкой «Обработан ранее» не дают такого основания сами по себе.

## Перед Встречей

1. Для обычного `/discover` просмотреть принятые узлы, сценарии и передачу работы между участниками. Начать с исходного документа и прослеживаемых доменных уточнений. `--context` и `--phase` сужают поиск внутри предметной границы.
2. Связать рабочий эпизод с конкретным узлом или предлагаемым дополнением к модели. Сравнить два возможных ответа и назвать, какое предметное правило, состояние, связь или действие с сетью они определяют по-разному. Сверить развилку с принятыми ответами и реестром, убрать повторы.
3. Из прошедших отбор выбрать до 15 вопросов по последствиям и неопределённости. Для каждого сохранить в реестре ссылку на основание и указать, что изменит ответ. В чате выдать нумерованный список с рабочими ситуациями. Если ни одного нового вопроса нет, сообщить об этом одной строкой. Исследование ответов относится к отдельному поручению.

Сверить Current Discovery Queue, реестр и `memory/project-state.md` с уже принятыми решениями. Новые вопросы оставить открытыми до появления ответов.

## После Встречи

1. Положить транскрипт или заметки в `RAW_inputs/meetings/`.
2. Выполнить `/ingest`.
3. Зафиксировать результат разбора в `RAW_inputs/index.md`. Если материал уточняет или расширяет модель, обновить соответствующий узел, указать источник в поле `source` и ссылку на результат в журнале. Для целиком смежного материала достаточно причины в журнале.
4. Зафиксировать конфликты и follow-up'ы.
5. Согласовать реестр вопросов, саму Current Discovery Queue в `DDD_Wiki/model_health.md` и следующий шаг `memory/project-state.md`. Одной новой сводки над устаревшей очередью недостаточно. Отличать прирост модели от дополнительных подтверждений; новые URL не доказывают новизну правила.

## Раз В Неделю

1. Выполнить `/lint-wiki`.
2. Выполнить `/audit-memory`.
3. Выполнить `/sync-vision`.
4. Подготовить отчет о здоровье wiki и памяти.
5. Показать кандидатов memory cleanup пользователю и не удалять/объединять их
   без подтверждения.

## Repository-Change Ingest

Перед ingest агент должен определить только наличие нового устойчивого
технического знания, которое требуется отразить в `Code_wiki`.

Конкретные target nodes заранее указывать не требуется.
`Repository Change Ingest` самостоятельно:

1. анализирует новое знание и его источники;
2. определяет, нужно создать новую ноду или обновить существующие;
3. создаёт или обновляет соответствующие ноды `Code_wiki`;
4. добавляет строки об изменённых нодах в компактный реестр.

Если нового устойчивого технического знания нет, ingest не вызывается. Размер
задачи, завершение plan, commit, успешные tests и изменения только index/state
сами по себе не являются triggers.

Pre-commit не запускает и не проверяет repository-change ingest. `repository-change ingest` не меняет код, конфигурацию, миграции и тесты. Он пишет только knowledge-документацию.

## Repository-Snapshot Ingest

`/ingest repository-snapshot` используется для первичного добавления уже существующего, неизмененного состояния репозитория в `Code_wiki`. Это не diff и не commit workflow: агент строит карту проекта, читает ключевые файлы и создает технические wiki-ноды о текущей архитектуре, dev setup, сборке, deployment, API, моделях, тестах, правилах и рисках.

Вызывать:

1. При первом наполнении `Code_wiki` для существующего проекта.
2. Если в проекте были крупные изменения вне текущей агентской задачи.
3. Если `Code_wiki` явно отстает от реальной структуры репозитория.

Результат фиксируется в `Code_wiki/состояние_проекта/repository_snapshot.md`, а `memory/project-state.md` получает отметку о последнем snapshot. Snapshot не меняет код, конфигурацию, миграции и тесты.

## Post-Ingest Correction

После `/ingest` можно исправлять только конфликты, которые уже есть в `Wiki/_registry/conflicts.md`, связаны с `Code_wiki` и требуют синхронизации старой документации с новым знанием. Другие Markdown-документы, код, конфигурация, миграции и тесты требуют отдельного явного запроса или implementation task.
