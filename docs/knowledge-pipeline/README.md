# Project Knowledge Pipeline

Wiki ведется на русском языке. Пути, команды, идентификаторы и имена файлов не переводятся.

## Утро

1. Выполнить `/sync-vision`.
2. Проверить `memory/project-state.md`.
3. Проверить новые файлы в `RAW_inputs/`.
4. Если появились новые RAW inputs, выполнить `/ingest`. Без параметров `/ingest` обрабатывает 1-5 однозначных новых RAW-файлов по очереди. Если файлов больше 5 или есть неоднозначность, агент показывает список и просит подтверждение.

## `/ingest` Без Параметров

Когда путь не указан, агент ищет новые или измененные файлы в `RAW_inputs/`, которых еще нет в обработанных source-записях wiki/state.

- Если новых RAW-кандидатов нет, агент ничего не меняет и сообщает, что ingest не выполнен.
- Если найдено 1-5 однозначных RAW-кандидатов, агент обрабатывает их по очереди в одном запуске `/ingest`.
- Если найдено больше 5 RAW-кандидатов, агент показывает список по папкам и просит подтверждение.
- Если есть неоднозначность, агент просит подтверждение до обработки. Неоднозначность: непонятный тип источника, слишком большой файл, несколько версий одного документа, похожая уже существующая wiki-нода, возможный конфликт с документацией, потенциальные секреты или персональные данные.

## Перед Встречей

1. Выполнить `/discover --context "..." --phase "..."`.
2. Подготовить 10-15 вопросов.
3. Подготовить чек-лист встречи.

## Первый `/discover`

Если `/discover` запускается впервые, он не готовит обычный чек-лист встречи. Он должен:

1. Задать стартовую анкету из 5-7 вопросов о проекте, стейкхолдере, стадии, RAW-материалах и желаемых артефактах.
2. Создать недостающие пустые solution-артефакты: `Vision_wiki/solution/USM.md`, `roadmap.md`, `nfr.md`, `architecture_vision.md`.
3. Проверить наличие `Общие_принципы/Фазы наполнения wiki.md`.
4. Не заполнять продуктовые факты без ответов пользователя.
5. После ответов предложить следующие 3 шага и обновить `memory/project-state.md`.

## После Встречи

1. Положить транскрипт или заметки в `RAW_inputs/meetings/`.
2. Выполнить `/ingest`.
3. Обновить `Vision_wiki`.
4. Зафиксировать конфликты и follow-up'ы.
5. Обновить `memory/project-state.md`.

## Раз В Неделю

1. Выполнить `/lint-wiki`.
2. Выполнить `/sync-vision`.
3. Подготовить отчет о здоровье wiki.
4. При крупных изменениях в репозитории проверить, что агент вызвал `/ingest repository-change` и изменения отражены в `Code_wiki`.

## Repository-Change Ingest

После полного завершения реализации плана или крупной задачи в репозитории агент должен вызвать `/ingest repository-change` перед финальным отчетом пользователю. Не вызывать после каждого мелкого шага плана. Это правило не привязано к commit.

Этот режим выполняется агентом по `.agents/skills/source-command-ingest/SKILL.md`: агент смотрит `git status`, `git diff --stat`, при необходимости точечные diffs, затем создает или обновляет knowledge entry в `Code_wiki/состояние_проекта/repository_change_ingest.md`.

Pre-commit не запускает и не проверяет repository-change ingest. `repository-change ingest` не меняет код, конфигурацию, миграции и тесты. Он пишет только knowledge-документацию.

## Repository-Snapshot Ingest

`/ingest repository-snapshot` используется для первичного добавления уже существующего, неизмененного состояния репозитория в `Code_wiki`. Это не diff и не commit workflow: агент строит карту проекта, читает ключевые файлы и создает технические wiki-ноды о текущей архитектуре, dev setup, сборке, deployment, API, моделях, тестах, правилах и рисках.

Вызывать:

1. При первом наполнении `Code_wiki` для существующего проекта.
2. Если в проекте были крупные изменения вне текущей агентской задачи.
3. Если `Code_wiki` явно отстает от реальной структуры репозитория.

Результат фиксируется в `Code_wiki/состояние_проекта/repository_snapshot.md`, а `memory/project-state.md` получает отметку о последнем snapshot. Snapshot не меняет код, конфигурацию, миграции и тесты.

## Post-Ingest Correction

После `/ingest` можно исправлять только конфликты, которые уже есть в `Vision_wiki/decisions/followups/index.md`, связаны с `Code_wiki` и требуют синхронизации старой документации с новым знанием. Другие Markdown-документы, код, конфигурация, миграции и тесты требуют отдельного явного запроса или implementation task.
