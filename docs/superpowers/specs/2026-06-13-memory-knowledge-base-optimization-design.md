# Оптимизация Памяти И Базы Знаний

Date: 2026-06-13
Status: Approved for implementation planning

## Цель

Снизить процессный шум и дублирование между `docs/agent-memory/`,
`Code_wiki/`, `Vision_wiki/`, `memory/project-state.md` и Git.

Память должна сохранять важные события в жизни репозитория, а не вести
хронологический лог каждого изменения. Техническая wiki должна описывать
актуальное устойчивое знание о системе, а история изменений должна оставаться
в Git.

## Наблюдаемая Проблема

На момент проектирования в `docs/agent-memory/` находится 47 Markdown-файлов,
из которых 35 являются session-записями. Файл
`Code_wiki/состояние_проекта/repository_change_ingest.md` содержит 19 событий
и вырос примерно до 53 КБ. В нём фиксируются не только изменения технических
нод, но также planning, discovery, результаты проверок и факты завершения
работы.

Из-за этого:

- одно событие может одновременно появляться в design/plan, session memory,
  `repository_change_ingest.md`, индексах и `project-state`;
- релевантное долговременное знание сложнее находить среди хронологии;
- agents тратят время и контекст на обслуживание документов без нового знания;
- Git и knowledge base частично выполняют одну и ту же функцию истории.

## Выбранный Подход

Применяется жизненный цикл знаний с явным разделением ответственности,
строгими критериями записи и периодическим аудитом.

Альтернативы:

1. Только ужесточить триггеры без очистки накопленного шума. Подход дешевле,
   но не устраняет существующие дубли.
2. Почти полностью перенести память в wiki. Подход упрощает структуру, но
   ухудшает хранение локальных agent-oriented patterns, root causes и
   неочевидных связей.

Выбранный подход сохраняет полезное различие между памятью и wiki, но
запрещает использовать их как параллельные журналы работ.

## Границы Хранилищ

### `docs/agent-memory/`

Хранит только контекст, который помогает следующему agent понять причины,
ограничения или неочевидные отношения:

- решения с альтернативами и последствиями;
- root causes нетривиальных дефектов;
- устойчивые технические patterns;
- неочевидные связи компонентов и файлов;
- важные команды, ограничения среды и operational knowledge, если они ещё не
  представлены в подходящем runbook.

`sessions/` не используется по умолчанию. Новая session-запись допустима
только для передачи незавершённой работы или уникального итога, которому нет
подходящей decision, pattern, bugfix или wiki-ноды. При дальнейшем развитии
процесса `sessions/` может быть упразднена.

### `Code_wiki/`

Хранит актуальное техническое знание: архитектуру, API, модели данных,
runbooks, ADR, dev setup, build/deploy, testing strategy и устойчивые
ограничения.

`Code_wiki` не хранит подробную хронологию реализации, перечни изменённых
файлов и результаты каждого запуска тестов.

### `Vision_wiki/`

Хранит продуктовые знания, решения, assumptions, conflicts, stakeholders,
исследования и follow-up'ы. Техническая память не должна пересказывать
содержимое существующих продуктовых нод.

### `memory/project-state.md`

Хранит только живое текущее состояние pipeline и проекта. Завершённые события
не накапливаются как хронология, если они больше не нужны для определения
следующего действия.

### Git

Является архивом изменений, удалённых записей и историей реализации. Для
сохранения хронологии не создаются дополнительные Markdown-журналы.

## Критерии Записи Памяти

Новая memory-запись создаётся только при одновременном выполнении двух условий:

1. Знание с высокой вероятностью останется полезным минимум неделю.
2. Знание отсутствует в актуальной документации либо добавляет существенное
   объяснение причин, компромиссов или последствий.

Если подходящая запись уже существует, она обновляется вместо создания новой.

Не сохраняются:

- факт завершения задачи, plan, test run или commit;
- простой перечень изменённых файлов;
- содержание design или plan, уже сохранённое в исходном документе;
- результаты `/sync-vision`, `/lint-wiki` или `/ingest`;
- временный статус и последовательность действий;
- знание, очевидное из кода или уже отражённое в wiki;
- verification logs без устойчивого диагностического значения.

Перед созданием записи agent должен ответить:

1. Какое уникальное знание будет потеряно без этой записи?
2. Почему ссылки на существующий design, plan, code или wiki недостаточно?
3. В какой ситуации будущий agent должен найти эту запись?

Если на вопросы нет конкретного ответа, запись не создаётся.

## `repository-change` Ingest

`/ingest repository-change` вызывается только тогда, когда завершённая
реализация содержит новое устойчивое техническое знание, которое требуется
отразить в `Code_wiki`.

Факт крупной задачи, полного implementation plan, commit, успешных тестов или
изменения множества файлов сам по себе не является триггером.

До ingest agent определяет только наличие нового устойчивого технического
знания. Сам ingest анализирует знание и источники, выбирает между созданием
новой ноды и обновлением существующих нод, выполняет изменения и обновляет
реестр. Изменение только `Code_wiki/index.md`, `memory/project-state.md` или
реестра не создаёт основание для ingest.

### Реестр Изменений Нод

`Code_wiki/состояние_проекта/repository_change_ingest.md` преобразуется из
журнала задач в компактный реестр содержательных изменений нод.

Одна запись содержит только:

- дату;
- ссылку на созданную или обновлённую ноду;
- краткую причину изменения;
- источник знания: implementation, repository snapshot, RAW source или
  другой проверяемый источник.

Реестр не содержит:

- хронологию реализации;
- списки изменённых code files;
- полные verification results;
- пересказ plan или design;
- отдельные записи для index/state-only изменений.

## Периодический Аудит

Еженедельная процедура формирует кандидатов на очистку, но не изменяет и не
удаляет файлы автоматически.

Для каждой записи оцениваются:

- возраст с последнего содержательного обновления;
- уникальность знания;
- актуальность;
- дублирование design, plan, wiki или другой memory-записи;
- входящие ссылки из `file-map.md`, wiki и активных документов;
- наличие подходящей более актуальной замены.

Основной возрастной порог кандидата составляет 90 дней. Возраст не является
достаточным основанием для удаления: актуальные decisions, root causes и
patterns сохраняются без ограничения срока.

Раньше 90 дней кандидатами могут стать:

- явные дубли;
- промежуточные session summaries;
- записи о sync/ingest/lint;
- summaries, полностью повторяющие design, plan или wiki;
- записи без уникального знания и retrieval-сценария.

Отчёт предлагает одно действие для каждого кандидата:

- оставить;
- объединить с другой записью;
- заменить ссылкой на канонический источник;
- удалить.

Удаление или объединение выполняется только после подтверждения пользователя.
После подтверждения файл удаляется из рабочей ветки, а его история остаётся в
Git. Одновременно очищаются `file-map.md`, индексы и другие прямые ссылки.

`Superseded by` применяется только к полезным историческим записям, которые
важно оставить в активной базе. Он не используется вместо удаления шума.

## Разовая Ревизия

После внедрения новых правил выполняется разовый аудит текущих:

- 35 файлов в `docs/agent-memory/sessions/`;
- 19 записей в
  `Code_wiki/состояние_проекта/repository_change_ingest.md`;
- связанных строк в `docs/agent-memory/file-map.md`;
- дублирующих полей в `memory/project-state.md`.

Аудит сначала создаёт отчёт с классификацией `оставить`, `объединить`,
`заменить ссылкой` или `удалить`. До отдельного подтверждения пользователя
существующие файлы и записи не удаляются.

## Автоматические Проверки

### `check-memory-needed.py`

Проверка больше не требует memory-update для каждого design или plan. Она
срабатывает только для изменений самих правил памяти и knowledge pipeline,
когда без обновления памяти возникнет противоречие в operating knowledge.

Изменение обычного spec/plan не считается автоматическим доказательством
необходимости новой memory-записи.

### Memory Audit

Добавляется отдельная проверка либо расширяется `/lint-wiki`. Предпочтителен
отдельный read-only скрипт, чтобы wiki lint проверял структуру wiki, а memory
audit оценивал жизненный цикл agent memory.

Проверка:

- находит битые ссылки;
- выявляет вероятные дубли;
- помечает session-записи, повторяющие plans/specs/wiki;
- проверяет возрастной порог и бюджеты;
- проверяет рост `repository_change_ingest.md`;
- формирует детерминированный отчёт без удаления файлов.

Повторный запуск без изменений должен давать тот же отчёт.

## Бюджеты И Сигналы

Бюджеты являются предупреждениями для ревизии, а не автоматическими причинами
удаления:

- ориентир не более 20 активных файлов в `docs/agent-memory/sessions/`;
- отсутствие двух активных записей с одинаковым уникальным знанием;
- компактная memory-запись без пересказа исходного документа;
- предупреждение при росте `repository_change_ingest.md` выше заданного
  лимита строк или размера;
- отсутствие index/state-only записей в repository-change реестре.

Точные технические пороги размера реестра определяются в implementation plan
после анализа формата нового компактного реестра.

## Изменяемые Области

Реализация должна согласованно обновить:

- `AGENTS.md`;
- `docs/agent-memory/protocol.md`;
- `docs/agent-memory/README.md`;
- `docs/agent-memory/file-map.md`;
- `scripts/check-memory-needed.py` и его tests;
- `.agents/skills/source-command-ingest/SKILL.md`;
- `docs/knowledge-pipeline/README.md`;
- `Code_wiki/состояние_проекта/repository_change_ingest.md`;
- `Code_wiki/index.md`;
- при необходимости `/lint-wiki`, `/sync-vision` и связанные tests/docs.

Разовая очистка является отдельным подтверждаемым этапом после появления
read-only отчёта кандидатов.

## Проверка Реализации

Необходимо подтвердить:

- `repository-change` ничего не меняет без названной `Code_wiki` ноды и нового
  устойчивого знания;
- изменение ноды создаёт одну компактную реестровую запись;
- обычный design/plan не требует новой memory-записи;
- memory audit не изменяет файлы и идемпотентен;
- audit обнаруживает fixture с дублем, устаревшей ссылкой и шумной session
  summary;
- после подтверждённой очистки отсутствуют битые ссылки;
- `lint-wiki`, memory checks и релевантные tests проходят.

## Acceptance Criteria

- Память больше не используется как лог каждого изменения репозитория.
- Новая memory-запись требует уникального долговременного знания и
  retrieval-сценария.
- `sessions/` используется только как исключение.
- `/ingest repository-change` запускается только для создания или
  содержательного изменения ноды `Code_wiki`.
- `repository_change_ingest.md` является компактным реестром изменений нод.
- Еженедельный аудит использует возраст и полезность, но только формирует
  кандидатов.
- Удаление выполняется после подтверждения, а исторический доступ обеспечивает
  Git.
- Разовая ревизия накопленного шума не удаляет данные до согласования отчёта.
- Проверки предотвращают дубли, битые ссылки и повторное превращение памяти в
  хронологический журнал.
