## Фактические владельцы и внешние записи

Это описание текущего устройства, не проект будущих операций.

| Состояние | Где хранится | Кто ещё меняет / координирует |
| --- | --- | --- |
| Local draft, editBlockReason | `stores/edit_version/editVersionDraft.ts` | commands сбрасывает draft и editBlockReason; session сбрасывает draft; navigation пишет editBlockReason |
| NavigationContext, navigationError, logoutAttempt | `stores/editor_navigation/editorNavigation.ts` | commands назначает commandId и очищает navigation при completion, interruption, access loss и blocked submit |
| localPhase, saveError, submitted command metadata, result, comparison, Revert confirmation | `stores/edit_version/editVersionCommands.ts` | draft меняет phase/error/comparison/submitted metadata; session знает состав полей и сбрасывает их |
| Opened workspace IDs, open intent, read generations | `stores/editor_session/editorSession.ts` | session координирует открытие, очистку, readback и назначенные наряды |
| Подтверждённые map/ChangeSet/baseline данные | отдельные read stores | `composables/edit_version/useEditVersionEditor.ts` согласует чтения и строит вычисляемый snapshot |
| Sent command, outcome, access/protocol blocks, durable recovery | `stores/workspace/workspace_recovery/workspaceRecovery.ts` | editor commands предоставляет RecoveryHost; recoveryRecord в commands — вычисляемая проекция |
| Actor, sid, epoch | `stores/auth.ts` | auth вызывает suspension и reset редактора; транспорт зависит от auth — соседняя задача F2 |

Особенно важны обратные записи draft → commands: замена только двух внешних присваиваний localDraft не устраняет общий риск владения. `clearOpenedWorkspace` знает внутренний набор полей commands; `resetEditor` дополнительно вызывает чужие `$reset` и отменяет Revert watcher.

## Текущий Save-and-leave

1. `requestNavigation` определяет dirty/sent/stale и создаёт контекст с id, actorId, sessionEpoch, sourceKey и target.
2. `resolveNavigation` проверяет id/actor/epoch/sourceKey. Выбор Save переводит контекст в saving и вызывает commands.
3. `saveLocalDraft` проверяет доступность действия, готовность чтений и dirty, создаёт commandId и напрямую записывает его в navigation.
4. `submitGeometryCommand` фиксирует source, проверяет actor/epoch и рабочую версию после initializeActor, затем вызывает recovery.submit.
5. Recovery обеспечивает отправку и последующую обработку результата; его callbacks возвращаются через RecoveryHost в commands.
6. `completeRecovery` отбрасывает чужой actor/epoch. При success выбранного контекста очищает локальную попытку. Переход выполняется только при совпадении sourceKey/commandId/epoch навигации.
7. `interrupted` отменяет связанную навигацию; session loss очищает доступ, access loss закрывает соответствующий workspace. Blocked submit также очищает navigation.

Здесь распределена координация между navigation, commands и recovery callbacks. Подтверждено архитектурное нарушение; самостоятельный новый пользовательский дефект этим чтением не доказан.

## Уже определённые требования

- Local draft, подтверждённый current, отправленная команда и представление карты имеют разный смысл. Recovery-проекция не считается вторым владельцем команды.
- Save-and-leave связан с исходным контекстом, commandId и epoch. Success требует согласования с current; промежуточные unknown/rejection/readback/storage/protocol/access проблемы отменяют переход окончательно.
- Поздний success не должен возрождать старый переход или завершать новую сессию.
- Unknown — неизвестность клиента, не серверное состояние running. Повтор сохраняет commandId и payload; новый login не даёт согласия на новую mutation.
- Независимый наряд может оставаться доступным при pending-команде другого наряда.
- Cancel возвращает к последнему прочитанному сохранённому состоянию без записи. Revert — отдельная запись baseline с двумя стадиями согласия при наличии dirty; отмена второй стадии не восстанавливает удалённый draft.
- Refresh/readback не должен выдавать старую квитанцию за актуальную геометрию. Read generations и session epoch сохраняются.
- Полная перестройка редактора, offline draft, event bus, новые backend-контракты и изменение retry/storage политики не следуют из F1.

## Проверки, обнаруженные в коде

`stores/editor_navigation/editorNavigation.test.ts` проверяет stay/discard, устаревшее подтверждение, успешный Save-and-leave, окончательную отмену после unknown, storage/protocol error, GET failure и domain rejection; отдельно — замену сессии во время подготовки logout.

`stores/edit_version/editVersionDraft.test.ts` содержит проверки Cancel, двухстадийного Revert, блокировок действий во время подтверждения, сохранения выбранной вершины при отмене dirty, запрета повторной отправки неизменённого rejected candidate и конкурентных Save.

В recovery-тестах есть независимые контексты, смена actor при подготовке storage, suspension одного наряда и durable preparation logout. При проектировании потребуется сопоставить точные гарантии будущей границы с телами этих тестов и отдельно проверить поздние завершения при смене контекста. Наличие названия теста не доказывает полноту покрытия.

Тесты в рамках этого первичного чтения не запускались. Код приложения не изменялся.

## Открытый вопрос 1 — граница F1/F2

Порядок рефакторинга допускает начать с операций владельцев F1, но одновременно указывает, что полная развязка общей компоненты импортов требует F2. Заголовки этапов оставляют F2 отдельной задачей. Не определено, должен ли результат текущего обсуждения ограничиваться F1 с явно отмеченным остатком F2 либо включать совместное проектирование этих границ. Это влияет на объём дизайна и критерий завершения; технический способ пока не предлагается.

Ответ пользователя 2026-11-16: только F1; F2 остаётся отдельной задачей. Полная развязка auth/HTTP/workspace не входит в текущий дизайн. Оставшиеся связи F2 сами по себе не означают незавершённость F1.

## Дополнительная проверка путей очистки

Прочитаны тела `editVersionDraft.test.ts` и `editorNavigation.logout.test.ts`, а также контракт RecoveryHost. Проверки различают Cancel, отмену dirty с сохранением выбранной вершины, удаление dirty перед Revert, успешное сохранение и прекращение доступа. Эти операции имеют разные последствия; объединять их смысл на основании общего присваивания null нельзя.

Logout-проверки явно сохраняют workspace и pending identity при отказе logout; явный discard при этом не отменяется. Успешный logout блокирует sent intent до нового согласия. Старый ответ logout не очищает replacement workspace. Эти гарантии остаются входными ограничениями F1, хотя внутреннее устройство auth относится к F2.

Дополнительный production-потребитель — `components/workspace/WorkspaceComparisonPanel.vue`: компонент напрямую меняет `commands.comparisonPreview`. Это UI-состояние представления сравнения, не изменение canonical geometry. Его следует отличать по риску от сброса draft или смены navigation.

## Открытый вопрос 2 — полнота владения внутри редактора

Формальный критерий этапа называет отсутствие внешних изменений draft/navigation «в затронутом сценарии». Углублённый аудит дополнительно относит к F1 внешние сбросы commands из session; текущий draft также напрямую меняет phase/error/submitted metadata/comparison. Поэтому остаётся уточнить ожидаемый объём: только явно названные draft/navigation либо все взаимные записи состояния в группе draft/commands/navigation/session, включая управление сравнением из UI. Это вопрос объёма и критерия завершения, не выбор архитектурного решения.

Ответ пользователя 2026-11-16: в F1 устраняются все взаимные записи состояния редактора, включая commands и управление сравнением из UI. F2 остаётся отдельной задачей.

## Согласованный охват F1

- Внешние изменения draft, navigation, commands и состояния сессии редактора проходят через смысловые операции владельцев. В охват входят вложенные изменения и удаление элементов коллекций, а не только присваивания верхнего уровня.
- Сравнение включено: выбор source/candidate/current, скрытие preview и отказ от stale-попытки. Скрытие preview не удаляет материал сравнения и не меняет серверный snapshot.
- Очистка при завершении контекста включена. В текущем `resetEditor` есть внешние `$reset` commands/draft/navigation; общий технический сброс не должен служить обходом согласованного владения и необходимой очистки ресурсов.
- Save, Save-and-leave, completion/interruption recovery, Cancel, обе стадии Revert, переключение наряда и очистка при потере доступа рассматриваются совместно в части владения состоянием.
- Связывание auth с workspace и HTTP с auth остаётся F2. Сохранение существующих вызовов auth к публичной границе редактора не является нарушением объёма F1; перенос auth-координации в эту задачу не согласован.
- Recovery I/O, scheduler, retry, IndexedDB/schema/migration остаются вне рефакторинга F1 (F4). Существующий RecoveryHost является доступной границей для completion/interruption; сохранение её поведения обязательно.
- Read stores и map presentation сохраняют свои роли. F6 и смена алгоритма согласования чтений не входят в задачу.

## Результат дополнительного поиска

Проверены прямые обращения, `$patch`, `$reset`, вложенные изменения navigation и staleComparisons в production-компонентах и stores. В обнаруженных production-путях основная концентрация нарушений остаётся в четырёх модулях draft/commands/navigation/session и WorkspaceComparisonPanel. `workOrders` уже предоставляет собственные операции выбора, очистки и обновления статуса. Чистые функции workspaceDraft создают отдельные geometry values и не используют Vue/Pinia; сохраняется их независимая роль.

Отсутствие дополнительных совпадений текстового поиска не считается доказательством невозможности мутации через alias, storeToRefs или будущий код. Конкретный механизм защиты публичной границы и архитектурные проверки предстоит выбрать при проектировании.
