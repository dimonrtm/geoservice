# Этап 3 · B1. Правила первого редактирования линии

Исходный разбор для обсуждения границ задачи, 19 ноября 2026 года. Основание — статическое чтение реализации и тестов. Итог обсуждения отражён в [дизайне B1](2026-11-19-stage-3-b1-design.md).

## Что считается допустимым изменением

Команда передаёт итоговую геометрию линии. Индекс вершины определяется относительно неизменяемого исходного снимка. После канонизации допустимы сдвиг одной внутренней вершины и возврат к исходной геометрии. При повторном изменении той же линии до возврата должен сохраняться индекс сдвинутой вершины. Равенство с текущей геометрией означает no-op. Возврат к исходной геометрии из изменённого состояния является записью. Это принятые ограничения первого сценария GeoService. [Команда Save](../../Wiki/commands/update_edit_version_feature_geometry.md), [инварианты EditVersion](../../DDD_Wiki/invariants/edit_version_persisted_edit_invariants.md).

## Где сегодня принимается решение

| Место | Что проверяется и почему порядок важен |
| --- | --- |
| Подготовка кандидата | Репозиторий проверяет принадлежность контекста. Проверка типа объекта и операций created/deleted предшествует поиску отсутствующего исходного состояния. Затем проверяются ссылки и статус снимка, декодируется исходная геометрия, проверяются её тип и наличие внутренней вершины. После этого применяется сохранённая политика канонизации. |
| Проверка текущего состояния | После проверки обоих handles и их взаимной принадлежности повторяется проверка исходного состояния. Затем проверяются наличие области работ, декодирование текущей геометрии, структура линии, число и положение изменённых вершин, соответствие признака операции фактической геометрии. Несогласованность здесь означает повреждённый контекст. |
| Проверка команды | PostGIS проверяет исходную и текущую геометрию и область работ. Только после этого учитывается наличие другого изменённого объекта. Далее вызывается чистая функция validate_transition. Для no-op используются текущие байты, для возврата к исходной линии — исходные. Пространственная проверка кандидата различает недопустимую геометрию и выход за область работ, в таком порядке. |
| Чтение change set | Проекция проверяет согласованность версии, набора объектов, типов и операций. Геометрически неизменённые точки и короткие линии допустимы в снимке. Для изменённого объекта отдельно проверяются видимость, единственность объекта и единственность внутренней вершины. Ошибка здесь означает невозможность достоверно прочитать снимок. |

## Что должно пережить рефакторинг

- Для created/deleted без исходного объекта интеграционный тест ожидает FEATURE_NOT_EDITABLE. Преждевременная материализация всего контекста может заменить этот исход на WORK_ORDER_CONTEXT_INVALID.
- Пустая разница координат допустима для чистого снимка. Проекция проверяет требование ровно одной вершины после обработки равенства. Общее правило, которое всегда требует ровно одну вершину, сломает чтение чистой версии.
- Проверка принадлежности и срока действия handles, одноразовое потребление при записи и ограничения вложенных транзакций относятся к протоколу репозитория. Действующий доступ проверяется до replay. Изменение persistence-контракта use case выделено в B2.
- Архитектурный тест проверяет импорты доменного пакета. Семантика при одновременном нарушении нескольких условий проверяется отдельно на примерах с известным первым отказом.

## Уточнение объёма

Пользователь включил интерпретацию пространственного вердикта кандидата в обязательный объём B1. Приёмка проверяет этот выбор без БД. Вычисление пространственных фактов остаётся в PostGIS. Для сохранённых данных отрицательный вердикт означает повреждение контекста.
