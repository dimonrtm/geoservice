# F1 — владельцы состояния и координация редактора

Дата: 2026-11-16. Статус: дизайн принят пользователем («Принимаю»). Следующий шаг — план реализации; способ выполнения ещё не выбран.

Основание: [анализ](2026-11-16-stage-2-f1-analysis.md), F1 в [аудите](architecture-review.md) и [порядке этапов](refactoring-order.md).

## Цель и выбранный подход

Устранить все взаимные записи состояния редактора, включая commands и управление сравнением из UI. Сохранить отдельных владельцев, сделать допустимые операции явными и собрать межмодульные сценарии в одном пути координации. Поведение Save/Cancel/Revert/recovery/navigation сохраняется.

Пользователь выбрал подход 1: отдельные владельцы и явная координация. Альтернатива — объединить локальное состояние в одном workspace-store — сокращала бы взаимодействия, но требовала более широкой переделки потребителей и создавала риск чрезмерной ответственности store. Обёртки-setters без изменения взаимных зависимостей не удовлетворяют задаче.

По объёму это полноценное изменение архитектурной границы, а не механическая замена присваиваний. Ниже технические решения конкретизации предложены агентом; выбор первого подхода сам по себе не означает согласование каждой детали документа.

## Границы

Включены draft, commands, navigation, session и их потребители: UI, map interaction, сборка presentation, callbacks RecoveryHost, очистка при смене контекста/доступа. Внешними изменениями считаются также вложенные записи, delete, мутация полученной коллекции, `$patch` и чужой `$reset`.

F2 остаётся отдельным: HTTP → auth и auth → публичные операции редактора сохраняются. Не требуется убрать всю сильно связанную компоненту приложения. F4 (recovery I/O), F6 (согласование read tokens), backend, протоколы, storage schema, retry и миграции не изменяются. Не добавляются offline draft, автосохранение, автослияние, новые dialogs или пользовательские сценарии.

Read stores сохраняют подтверждённые данные; recovery сохраняет отправленное намерение; MapLibre остаётся представлением. Не переносить их состояние в координатор.

## Владельцы и допустимые операции

Названия операций ниже смысловые; окончательные TS-имена выбираются при планировании без изменения контрактов.

| Состояние | Владелец | Допустимые операции | Межмодульный координатор |
| --- | --- | --- | --- |
| Draft, source token/geometry, выбранная вершина, editBlockReason | draft | начать/изменить попытку; отменить; восстановить current с сохранением выбора; завершить соответствующую попытку; очистить при завершении контекста; показать/снять причину блокировки | editor workflow |
| Local phase, save error, submitted metadata, result | commands | начать отправку; принять результат соответствующей команды; зарегистрировать отказ; подготовить исправленную попытку; завершить локальную работу/контекст | editor workflow |
| Stale материалы по recovery key, preview mode | commands | принять stale material; открыть/скрыть preview; удалить выбранную попытку; очистить материалы actor при reset | editor workflow; UI вызывает операции preview |
| Revert confirmation и его watcher | commands | начать подтверждение; завершить discard-стадию; отменить/потребить актуальное подтверждение; освободить watcher | editor workflow |
| Navigation context, navigationError, logoutAttempt | navigation | запросить/отменить переход; связать Save; окончательно прервать ожидание; потребить разрешённый переход; начать/завершить logout attempt | editor workflow |
| Opened IDs, read generations, open intent, open errors | session | открыть/восстановить; резервировать/принять чтение; инвалидировать/закрыть контекст; сбросить с сохранением монотонности поколения | editor workflow |
| Map, ChangeSet, baseline | существующие read stores | существующие load/accept/reset через editor read facade | существующая координация чтений |
| Frozen command/outcome/blocks | recovery | существующие submit/retry/read/suspend и RecoveryHost | существующий recovery executor |

У каждой операции ограниченный смысл и вход. Не вводить публичные `setState`, произвольный patch и универсальный «reset всё» с десятками независимых флагов. Разные основания очистки не смешиваются: Cancel, dirty discard, success, закрытие workspace и прекращение actor session дают разные эффекты.

## Направление зависимостей и сборка

Выделяется обычная TS-фабрика editor workflow с явно переданными узкими контрактами draft/commands/navigation/session, чтений, recovery, доступа и выполнения перехода. Она не импортирует конкретные Pinia stores, Vue, HTTP, IndexedDB или MapLibre. Она координирует операции, но не хранит вторую копию реактивного состояния.

Pinia остаётся адаптером владения и реактивности. Владельцы не импортируют друг друга для изменения состояния и не получают конкретный координатор через обратный импорт. Межмодульные проверки, которые сейчас вызывают соседние stores из actions/getters, собираются на уровне workflow/реактивного адаптера. Чистые геометрические правила остаются в domain/workspace.

Код сборки получает конкретные stores одного Pinia, создаёт workflow и связывает RecoveryHost. На экземпляр Pinia — один runtime; запрещён общий singleton для всех экземпляров. Связанные getters используют живые данные/функции чтения, а не снимок значений на момент сборки.

Для сохранения существующей границы auth допускаются тонкие совместимые методы `resetEditor`, `suspendWorkspaceRecoveryForAccessLoss` и аналогичные входы. Они делегируют явно связанному контракту workflow, не импортируя его фабрику или соседние stores. Такие методы не являются операциями владельца и не должны вызываться координатором обратно: координатор получает отдельные локальные операции. Это исключает рекурсию и перенос прежнего цикла в новый файл.

Сборка выполняется после создания Pinia и до restore/start auth и взаимодействия UI. Изолированные интеграционные тесты используют ту же явную сборку, а тесты чистого workflow — подставленные порты. Отсутствие сборки является ошибкой программирования, не тихим пропуском команды. Конкретные имена файлов и форма хранения runtime оставлены исполнителю; новые DI-container/event bus не нужны.

В текущем приложении точка сборки — `main.ts` после установки Pinia в app и до mount; browser session sync/restore запускаются позднее в onMounted App. В тестах, вызывающих setAuth напрямую, сборка выполняется до этого вызова: setAuth уже может вызвать reset редактора. Конструирование owners и связывание runtime сами по себе не запускают HTTP, restore или recovery retry.

UI и map interaction вызывают workflow для межмодульных действий. Для локального preview допустим прямой вызов операции commands. Чтение реактивного состояния сохраняется, включая адаптер чистого presenter из F3.

## Идентичность и актуальность

Навигация сохраняет id, actorId, sessionEpoch, sourceKey, target и связанный commandId. Решение об исполнении перехода проверяет весь захваченный контекст; после отмены контекст не воссоздаётся из позднего completion.

Draft должен иметь проверяемую принадлежность исходному workspace и локальной попытке. Это может быть внутренний контекст/поколение владельца, без изменения persisted recovery schema. Одного совпадения featureId недостаточно. Операция завершения попытки проверяет эту принадлежность и не очищает новый draft поздним callback.

Commands принимает результат по key/commandId/actor/epoch; foreground phase/result применяется только к актуальному рабочему контексту. Завершение фонового recovery A не сбрасывает draft или phase B. Stale material сохраняется по своему key по прежним правилам.

После каждого await, способного пересечь смену доступа/контекста, сохраняются проверки actor/epoch, opened IDs и нужных request generations. Нельзя заменить их проверкой наличия user или единственным isLoading.

## Сценарии

### Save и Save-and-leave

1. Workflow проверяет те же условия допуска, что текущие actions: доступ, блокировки, готовность чтений, dirty, отсутствие pending и запрет повторной отправки неизменённого rejected candidate.
2. Синхронно резервирует отправку, чтобы два Save не создали две команды. Создаёт commandId и связывает именно этот Save с актуальным navigation id до запуска асинхронной работы.
3. Передаёт замороженную команду и source существующему recovery. Persist-before-PUT, repeats и cleanup не переносятся из recovery.
4. Если отправка не начата, завершает соответствующую попытку запуска и отменяет только связанное ожидание навигации. Старый blocked результат не очищает новое navigation.
5. Единственный completion-путь workflow принимает RecoveryCompletion. Success для актуального foreground после требуемого readback и cleanup завершает соответствующий draft и обновляет commands. Только затем может потребить и исполнить исходный переход.

Окончательное прекращение Save-and-leave после unknown/rejected/readback/storage/protocol/identity/access/session сохраняется. Даже успешный автоматический retry не возвращает переход. Success receipt без current не разрешает уход. RecoveryHost.complete вызывается recovery после необходимого readback и storage cleanup; rejected без обязательного GET сохраняет существующий порядок.

RecoveryHost.interrupted сейчас передаёт key и reason, без commandId/epoch. F1 не расширяет этот протокол автоматически: сохраняет актуальность callback, которую обеспечивает recovery runtime, а workflow отменяет ожидание соответствующего key. На границе тестируется, что остановленный старый run не доставляет interruption новой сессии. Если это условие не выполняется, дефект фиксируется отдельно для согласования, не маскируется сменой поведения.

### Cancel, Revert, сравнение

Cancel удаляет локальную попытку без HTTP. Отмена dirty с сохранением выбора пересоздаёт draft из current. Revert с dirty сначала удаляет draft после согласия, затем запрашивает baseline reset; отмена второй стадии не возвращает draft. UUID команды создаётся после окончательного согласия.

Confirmation watcher остаётся во Vue-адаптере с явным владельцем/dispose. Проверки актуальности actor/workspace/token/access и ограничения действий сохраняются. Workflow использует результат проверки, не создаёт скрытые watchers для отправки команд.

Preview source/candidate/current — read-only overlay. Операция выбора проверяет наличие соответствующего материала; недоступный source не подменяется candidate/current. Скрытие preview сохраняет stale material. Отказ от попытки удаляет только материал выбранного контекста и согласованно завершает локальное редактирование.

### Закрытие workspace и reset

Workflow задаёт порядок завершения контекста, владельцы очищают собственные поля. Read/open generations инвалидируются до принятия поздних результатов. Session не перечисляет поля commands/draft/navigation и не вызывает их технический `$reset`.

Закрытие выбранного workspace сбрасывает foreground UI и preview, но не удаляет durable sent intent и не стирает stale material независимых нарядов. Полный reset actor очищает локальные приватные материалы и подтверждения; судьбой durable recovery управляет существующий suspension. Параметры сохранения sessionStorage selection/opened workspace сохраняют прежнюю семантику.

Управляемый logout продолжает существующие prepare/logout проверки sid/epoch. Его отказ сохраняет workspace/pending и снимает временную блокировку; явно удалённый draft не восстанавливается. Подтверждённый старый logout не очищает новую сессию. Auth orchestration не переносится в F1.

### Жизненный цикл

Runtime освобождает собственные bindings/watchers при dispose Pinia/application runtime. Unmount одной панели не останавливает общий recovery. Reset workspace не создаёт новые host bindings и не дублирует watchers. Reset actor не должен уничтожать необходимые функции сборки; повторный login использует тот же корректно связанный runtime, сохраняя требование явного согласия на доступ.

## Защита границы

Технический выбор агента: сохранить Pinia и не требовать в F1 полной миграции всех stores на setup-store с runtime readonly proxy. Публичные контракты workflow разделяют чтение и смысловые операции; изменяемые внутренние типы не передаются потребителям этих контрактов.

Дополнительно вводится узкая автоматическая проверка production-границы: запрещённые взаимные runtime imports владельцев, внешние записи их полей/вложенных значений, чужие `$patch`/`$reset`, записи через storeToRefs и шаблонные v-model. Проверка должна учитывать TS и Vue script/template, aliases используемых stores; один regex не считается достаточным доказательством. Не обещается формальная защита от произвольного обхода TypeScript через any/reflection. Fixtures тестов могут явно устанавливать начальное состояние; это не разрешение production-путей.

Итоговый граф сравнивается по конкретным путям F1. Оставшийся цикл через auth/HTTP документируется как F2; уменьшение общей SCC само по себе не является критерием успеха.

## Проверки и приёмка

| Проверка | Что подтверждает |
| --- | --- |
| Изолированный workflow с управляемыми портами | порядок операций владельцев; явные результаты отказа старта; отсутствие Pinia/I/O в координации |
| Навигация | stay/discard, success + GET + cleanup, окончательная отмена после каждого вида interruption |
| Асинхронные границы | старые command/id/epoch, A→B и A→B→A, новая попытка того же feature, поздний blocked submit, actor/sid replacement |
| Draft/Revert | независимость current/candidate; Cancel; dirty discard; две стадии; устаревшее подтверждение; конкурентные Save |
| Сравнение | три режима, недоступный source, hide сохраняет материал, discard только выбранного key, реактивное обновление overlay |
| Session/reset | монотонность поколений; отсутствие чужих записей; сохранение независимого recovery; прежние storage options |
| Runtime | повторное использование одного Pinia, два независимых Pinia, отсутствие дублирующих host/watchers, dispose и remount панели |
| Интеграция | реальные owners + recovery с текущими API mocks; существующие auth/logout/recovery/editor tests сохраняются |
| UI/E2E | действующие M4 Save/recovery/navigation/Revert/сравнение; без изменения текста, фокуса, доступности и состава dialogs |

Запустить профильные tests, полный frontend Vitest, lint, build и явный app typecheck; необходимые E2E — по текущему runbook M4. Исторические 551 passed не считаются текущим результатом. Backend-прогоны не нужны без изменений backend-контрактов. Окружение/пропуски отражаются отдельно, не как успешная проверка.

Готовность: все production-потребители затронутых владельцев используют операции, локальные циклы F1 устранены, сценарии проходят проверки, документация владения исправлена. Одного прохождения старых тестов недостаточно без проверки новых границ.

## Что оставлено исполнителю

Имена/расположение новых локальных файлов, детализация узких TS-контрактов, группировка тестов и последовательность миграции выбираются в плане. Допустимы небольшие вспомогательные функции workflow; нельзя создавать второй путь Save completion, универсальный event bus или новую библиотеку state machine. Недоказанные поведенческие дефекты не исправляются скрыто под видом рефакторинга.

После согласования документа составляется отдельный план. Код приложения до этого не меняется. Git add/commit/push запрещены; документы и будущие изменения остаются unstaged. Durable memory не дублирует данный дизайн.
