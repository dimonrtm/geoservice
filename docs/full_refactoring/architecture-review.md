# Соответствие кода правилам AGENTS.md

Дата: 2026-11-14. Проверяется рабочее дерево, включая ранее добавленные пользователем через агента правила в `AGENTS.md`.

## Вывод

Соответствие частичное. Backend имеет независимое геометрическое ядро, но прикладные сервисы тесно связаны с ORM, PostgreSQL и HTTP. На frontend большой store уже разделён, однако границы владения и координации между новыми stores остаются проницаемыми. Переписывать приложение целиком не требуется: основной эффект дадут локальные изменения контрактов и переноса ответственности.

После углублённой проверки: граф frontend содержит одну сильно связанную компоненту из 17 файлов; 12 из 14 backend service-модулей импортируют infrastructure. В legacy polygon store воспроизведены два проявления гонки позднего ответа. Дополнительно обнаружены отсутствие runtime-проверки части API-ответов, неограниченное пересогласование токенов чтения и доступ legacy use cases, проверяемый только на HTTP-границе. Подробная квалификация, достижимость и доказательства: [углублённый анализ](deep-analysis.md). Число строк или импортов не является самостоятельной оценкой качества.

## Область и метод проверки

Просмотрены правила, карта памяти, `Code_wiki/архитектура/backend.md`, `frontend.md`, `frontend_save_recovery.md`, прежнее ревью `docs/sprint_2/architecture-realtime-review.md` и принятое решение CQ-01. Поиск импортов выполнен по backend use cases/domain/web API и frontend stores/domain. Подробно проверены WorkOrder, открытие и сохранение EditVersion, геометрическая валидация, realtime publisher/connection manager, редактор, навигация, auth/HTTP и recovery. Также просмотрены MapView и существующие архитектурные тесты.

Не выполнялись полный построчный аудит всех файлов, полноценный анализ транзитивного графа Python-импортов, нагрузочные проверки, браузерный E2E и интеграционные тесты PostgreSQL. Размер файла и расположение каталога сами по себе не считались нарушением. Выводы относятся к архитектуре, а не к подтверждённым сбоям эксплуатации.

## F1. Владение состоянием редактора нарушается через прямые записи

**Доказательства:**

- `apps/frontend/src/stores/editVersionCommands.ts:24–28` импортирует draft, navigation и session; `editorNavigation.ts:12` и `editVersionDraft.ts:11` импортируют commands обратно.
- `editVersionCommands.ts:367,408,418,644` присваивает `editorNavigation.navigation = null`; строка 474 изменяет `navigation.commandId`.
- `editVersionCommands.ts:597` и `editorSession.ts:319` присваивают `editVersionDraft.localDraft = null` извне владельца.
- `editorNavigation.ts`, действие `resolveNavigation`, вызывает сохранение через commands; commands затем меняет внутренний контекст навигации.

**Правила:** frontend §1 — явные контракты и координация; §3 — один владелец и разрешённые операции; §5 — явное взаимодействие stores. Нарушается инкапсуляция ответственности, а не запрет Pinia как такового.

**Последствие:** изменение условий сброса draft или завершения перехода требует поиска внешних присваиваний. Контракт владельца обходится, а циклы затрудняют независимое тестирование и понимание порядка действий. Ошибка поведения этим фактом не доказана.

**Минимальное исправление:** сначала определить явные операции владельца и причины переходов, затем вынести согласование Save → readback → navigation в одну функцию/координатор с переданными зависимостями. Обёртка `setState` над каждым полем не решит проблему. Не дробить редактор на независимые микромодули и не вводить event bus.

**Проверка:** dirty navigation, Save-and-leave, отказ/unknown, смена actor/epoch, позднее завершение старой команды, двухэтапный Revert. Внешние потребители больше не меняют navigation/draft напрямую.

## B1. Правила допустимости редактирования находятся в инфраструктуре

**Доказательства:** `apps/backend/utility_service/infrastructure/postgresql/repositories/edit_geometry_validation.py:57` (`check_baseline`) запрещает изменение неподдерживаемого типа/операции и линии без внутренней вершины; `:92` (`check_context`) проверяет одну внутреннюю вершину и соответствие `operation` изменению. `edit_version_repository.py:447,474` вызывает эти функции. В том же модуле `inspect_spatial` выполняет SQL, а проверки используют persistence rows и EWKB codec.

**Правила:** backend §2 и §4 — доменные правила принадлежат модели, инфраструктура отвечает за хранение и технические механизмы.

**Последствие:** правило редактирования нельзя использовать независимо от представления хранения; repository одновременно читает данные и решает, допустим ли бизнес-контекст. Часть проверок действительно является диагностикой повреждённых данных — её нельзя автоматически объявить доменной.

**Минимальное исправление:** отделить декодирование и проверку целостности persisted-снимка от чистого решения о допустимости редактирования. Передавать в чистую функцию только необходимые значения/геометрию. SQL/PostGIS и чтение EWKB оставить адаптеру. Сохранить порядок ошибок и недопущение редактирования повреждённого контекста. Углублённая проверка уточнила: `EditGeometryScope` и issued handles защищают принадлежность транзакции и одноразовость проверенного изменения; их нельзя удалять как «лишнюю абстракцию». Чистая policy вызывается внутри сохранённого persistence-протокола.

**Проверка:** таблица разрешённых и запрещённых случаев для чистой функции; существующие Save/rejection тесты; интеграционные проверки PostGIS и повреждённых persistence-данных. Не создавать новую иерархию агрегатов ради перемещения двух функций.

## B2. Прикладная политика связана с PostgreSQL и ORM

**Доказательства:** `apps/backend/utility_service/use_cases/services/edit_version_service.py:7–50,67` принимает конкретные repositories/AsyncSession, использует ORM-типы и persistence rows. `:415` ловит `IntegrityError`; `:560` извлекает SQLSTATE/имя constraint для решения о повторном открытии. `work_order_service.py:61` управляет транзакцией AsyncSession и напрямую меняет ORM status. Аналогичный переход в `edit_version_service.py:449` выполняется внутри открытия версии; сама ORM-модель WorkOrder описывает поля/ограничения хранения, а не операцию перехода.

**Правила:** backend §2, §3, §5; SOLID/DIP. Это известный переходный долг, а не регрессия CQ-01: принятое решение CQ-01 прямо исключало repository ports из своей задачи.

**Последствие:** сценарий знает технические признаки конкурентного конфликта, а правила переходов распределены по прикладным путям. Изменение адаптера затрагивает use case. Простая подмена класса repository ещё не устраняет зависимость его входов/выходов от ORM. Уточнение достижимости: `start_work_order` используется тестами, production-вызовов поиск не выявил; текущий HTTP-путь открытия версии использует `get_by_id_for_update`. Поэтому отсутствие блокировки в старом `start_work_order` не заявляется как подтверждённая гонка рабочего HTTP-сценария.

**Минимальное исправление:** сначала преобразовать конкретный unique violation в осмысленный результат адаптера, сохранив rollback/retry. Затем для одного сложного сценария определить узкие контракты транзакции и нужных операций, переносить данные через независимые структуры. Общий переход состояния выражать чистой операцией лишь там, где он действительно общий; не объединять разные политики видимости ошибок 403/404.

**Проверка:** конкурентное открытие создаёт одну версию; корректны rollback, lock, replay, terminal rejection commit и повторное чтение. Не вводить generic repository или Unit of Work для всех таблиц сразу.

## B3. Прикладной слой выбирает HTTP-статусы

**Доказательства:** `work_order_service.py:50–105` создаёт ошибки с 404/409/403. `auth_service.py:10,34,40` использует `fastapi.status`. `use_cases/domain/exceptions/auth_api_error.py:2` хранит `status_code`. `use_cases/schemas/edit_version/geometry_save_out.py:6–43` содержит HTTP status в результате/отказе и таблицу соответствия кодов; `edit_version_service.py:107` передаёт этот статус в исключение.

**Правила:** backend §3 и §4 — прикладные результаты/ошибки переводятся в HTTP на внешней границе.

**Последствие:** прикладной контракт связан с транспортом, тесты use case закрепляют HTTP-представление. Папка `domain/exceptions` не делает HTTP-ошибку доменной.

**Минимальное исправление:** для простых операций вернуть смысловые коды/типы ошибок; mapping статусов оставить web API. Не выполнять глобальную замену всех исключений. Для Save отдельная задача: persisted receipt/replay уже связан с представлением ответа, поэтому нужно сохранить точное воспроизведение существующего результата, включая старые записи. Само хранение квитанции не объявляется ошибкой.

**Проверка:** прежние статусы, тела и correlationId API; ошибки приложения проверяются независимо от HTTP; Save replay не переинтерпретирует историческую квитанцию.

## F2. Auth/HTTP и workspace образуют связанную цепочку

**Доказательства:** `apps/frontend/src/stores/auth.ts:7–13` импортирует `api/auth`; `api/auth.ts:1` импортирует `api/http`; `api/http.ts:2,25` импортирует и получает auth store. HTTP request interceptor вызывает `ensureSessionReady`, response interceptor — `handleUnauthorizedResponse`. Дополнительно `auth.ts:1–2,132,160,173,481` знает commands/session редактора и выполняет его suspension/reset. Stores редактора в свою очередь импортируют auth.

**Правила:** frontend §1, §2, §6 — межмодульная координация выше модулей, внешние механизмы связаны явным контрактом.

**Последствие:** импорт транспортного клиента подтягивает store и workspace; изменение восстановления сессии требует учитывать HTTP и состояние редактора. Цикл импортов подтверждён, но сбой инициализации или бесконечный цикл запросов не установлен: исключения auth endpoints уже предусмотрены.

**Минимальное исправление:** связывать auth/workspace на уровне приложения явными callback-операциями. HTTP получает узкий доступ к token/epoch/readiness и обработчику отказа через настройку адаптера. Не создавать глобальную шину событий, второй HTTP-клиент без необходимости или новый auth framework.

**Проверка:** initial restore, refresh, local 401, смена sessionId того же actor, поздние ответы старой сессии, logout с pending Save, отказ status/refresh. Сохранить исключение `authErrorHandling: "caller"` и правила access barrier.

## F3. Presentation-модуль из domain зависит от stores

**Доказательства:** `apps/frontend/src/domain/workspaceCommandPresentation.ts:1–14` импортирует пять stores/composables и получает их в `workspaceCommandState`. В том же файле `presentWorkspaceCommands` вычисляет отображаемое состояние. `domain/dialogFocus.ts` работает с DOM; это UI helper, не доменное правило.

**Правила:** frontend §2 и §5 — чистые вычисления отдельно от Vue/Pinia/DOM, реактивная сборка в presentation-слое.

**Последствие:** даже потребитель чистого преобразования импортирует модуль со store-зависимостями. Каталог `domain` не имеет однозначной границы, поэтому будущие проверки импортов дадут ложное ощущение чистоты.

**Минимальное исправление:** вынести сбор состояния в небольшой composable/presentation adapter; вычисляющей функции передавать явную структуру входа. DOM helper разместить рядом с UI-поведением при затрагивании соответствующего кода. Не создавать отдельный пакет на каждую функцию и не дублировать формы состояния.

**Проверка:** вычисление сообщений/доступности действий тестируется без Pinia и браузерной сессии; небольшой интеграционный тест проверяет сбор входных значений.

## F4. Recovery сам выбирает конкретные реализации ввода-вывода

**Доказательства:** `apps/frontend/src/stores/workspaceRecovery.ts:3–8,27,49` импортирует snapshot read/save API и создаёт storage внутри store; `:190,293` вызывает чтение/запись. При этом `RecoveryHost` уже является полезным явным контрактом, и текущая архитектура существенно лучше полного смешения recovery с редактором.

**Правила:** frontend §2 — сложные сценарии отдельно от внешних механизмов; SOLID/DIP. Использование Pinia само по себе нарушением не является.

**Последствие:** проверка последовательности persist → send → readback → cleanup связана с конкретными модулями I/O; модульные mocks заменяют явные зависимости. Сам store одновременно собирает инфраструктуру и координирует сценарий.

**Минимальное исправление:** выделить создаваемый один раз исполнитель recovery с несколькими зависимостями: storage, send, readback и необходимый механизм ожидания. Pinia оставить реактивным владельцем представления состояния; существующие scheduler и RecoveryHost переиспользовать. Делать после уточнения границ F1, не переписывать весь механизм.

**Проверка:** запись завершается до PUT; неизвестный результат не становится отказом; повтор сохраняет commandId; readback failure не отправляет PUT повторно; epoch/access проверки и ограничение конкурентности сохраняются.

## B4. WebSocket transport находится в прикладном слое

**Доказательства:** `apps/backend/utility_service/use_cases/services/realtime_connection_manager.py:10,42,83–104` использует FastAPI WebSocket/WebSocketException, accept и protocol close code. `feature_realtime_publisher.py:9–15` зависит от конкретного manager.

**Правила:** backend §3–§5 — транспорт является адаптером, прикладная операция не зависит от WebSocket.

**Последствие:** use_cases содержит управление сетевыми соединениями/очередями наряду с прикладными операциями; издатель событий привязан к конкретному способу доставки.

**Минимальное исправление:** разместить manager в транспортном адаптере; издателю дать узкий контракт публикации, сборку оставить composition root. Механическое перемещение manager без устранения обратного импорта publisher не решает зависимость. Не добавлять брокер, Outbox или гарантированную доставку: это отдельные продуктовые требования.

**Проверка:** bounded queue, slow client, timeout/close, потеря сессии и diagnostics остаются прежними; адаптер не меняет wire protocol.

## Что сохранять и не считать нарушением

- Геометрические функции и `GeometryPolicy` в `domain_services` уже изолированы; CQ-01 не надо выполнять повторно.
- Существующие backend guards проверяют отдельные запрещённые импорты. Они не доказывают полной Clean Architecture, но их нужно сохранить.
- В frontend уже есть pure-функции draft/геометрии, раздельные read stores, поколения запросов и session epoch. Они полезны независимо от структуры каталогов.
- Recovery хранит отправленное намерение отдельно от обычного draft; совместимое вычисляемое представление не является вторым владельцем данных.
- MapView собирает карту из специализированных composables. Сам факт большого экрана, нескольких режимов карты или прямого импорта map adapter не доказывает нарушение.
- Старое CQ-02 про workOrders на 1484 строки устарело: текущий store отвечает за список и выбор. Реальный остаток описан F1, а не повторением прежнего размера.
- Не обнаружено оснований требовать GoF-паттерны ради количества, внедрять FSD, микрофронтенды, новую state-machine библиотеку или заменять Vue/Pinia.
- Нельзя добросовестно утверждать соответствие всем LSP/ISP-контрактам без их отдельной проверки. Основные подтверждённые проблемы этого обзора относятся к ответственности, DIP и владению состоянием.

Первый проход ограничивался 51 frontend-тестом и текстовым поиском backend-импортов. Углублённый проход расширил проверку: полный Vitest — 58 файлов / 501 тест, все прошли; `npm.cmd run typecheck` прошёл. Отдельный диагностический скрипт воспроизвёл F5, которого проходящий набор тестов не выявил.

Рабочий Python найден в OSGeo4W (3.12.13); прежняя формулировка о полной недоступности Python уточнена. В нём нет pytest и SQLAlchemy, Docker daemon недоступен. Поэтому backend pytest/DB integration не запускались.
