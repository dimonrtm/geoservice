# Этап 1: F3, B3 и F7 — дизайн

Дата: 2026-11-14. Статус: дизайн принят пользователем 2026-11-14. Реализация не начата.

## Цель и основание

Устранить три конкретные зависимости: чистое вычисление UI от stores; прикладные ошибки списка/открытия от HTTP; принятие непроверенных List/Open ответов на frontend. Сохранить действующие сценарии редактора и серверные гарантии.

Основание: [анализ и ответы пользователя](2026-11-14-stage-1-analysis.md), [очередность](refactoring-order.md), [аудит](architecture-review.md), [углублённый аудит](deep-analysis.md). Архитектурные ограничения: AGENTS.md и Code_wiki/архитектура/{frontend,backend}.md. Доменное основание: Wiki/entities/work_order.md, Wiki/commands/open_edit_version.md, DDD_Wiki/aggregates/work_order.md, DDD_Wiki/state_machines/editor_save_recovery.md. Это технический дизайн на основе репозитория, не внешнее доменное исследование.

## Подходы и выбранная граница

Пользователь согласовал локальное отделение каждой из трёх границ. F3 получает явный вход и отдельную реактивную сборку; B3 — прикладную ошибку выбранных операций и HTTP mapping; F7 — проверенный результат разбора списка с ошибками полей и проверку контекста Open.

Более широкая декомпозиция stores/сервисов не выбрана: не требуется для этих гарантий и затрагивает следующие этапы F1/F2/B2. Глобальная замена WorkOrderApiError исключена из-за Save/replay и readback. Отбрасывание всего списка при одной ошибочной строке не соответствует прямому выбору пользователя.

## Согласованное поведение

- Этап включает F3, ошибки WorkOrderService и Open из B3, F7.
- Backend Save/replay, квитанции команд и их исторические ответы не изменяются.
- Все позиции полученного массива нарядов отображаются в прежнем порядке. Ошибки отмечаются на соответствующей карточке с названием конкретного поля.
- При корректном id наряд можно выбрать и открыть, даже если остальные поля повреждены. Сервер продолжает проверять доступ и возможность открытия.
- Без пригодного id строка видна с ошибкой, но не является целью выбора/открытия.
- Если в полученном списке отсутствует id выбранного наряда, сохраняется прежнее поведение: сброс выбора; закрытие его workspace; очистка локального черновика; приостановка recovery. Повреждённые строки не являются исключением.
- Для нарушения протокола нет отдельной кнопки повтора. Существующие повторы сетевых/HTTP-ошибок и общая кнопка обновления списка сохраняются.
- F3 не меняет тексты, приоритеты сообщений и доступность команд редактора. B3 сохраняет внешние HTTP-ответы, порядок проверок и правила видимости.

## F3: чистая presentation и сборка состояния

### Контракт и ответственность

В `apps/frontend/src/domain/workspaceCommandPresentation.ts` остаются presentWorkspaceCommands и явный тип WorkspaceCommandState. Модуль импортирует только чистые правила и независимые типы контрактов; не импортирует Vue, Pinia, stores и composables, даже для вывода типа входа.

Вход сохраняет используемые сейчас факты: activeWorkspace, localDraft, phase, recoveryRecord, commandResult, saveError, readbackError, storageError, didSaveChangeGeometry, rejectedCandidateGeometry, canRetryPendingCommand, canRetryCurrentRead, canDiscardRejectedAttempt, workspaceInteractionLocked, revertBaselineReady, draftBaselineReady. actorCanEdit остаётся явным аргументом. Типы workspace/draft/recovery/result переиспользуются; отдельные копии объектов не создаются. Неиспользуемый editBlockReason из входа исключается без изменения поведения.

Общий тип фазы объявляется в независимом контракте и используется store и presentation, чтобы не выводить внутренний контракт через ReturnType сборщика или тип store. Это только существующее объединение строк, не новая state machine.

Реактивную сборку выполняет небольшой `composables/useWorkspaceCommandPresentation.ts`: при setup получает существующие stores и useEditVersionEditor, возвращает computed presentation. actorCanEdit передаётся реактивным getter из компонента. Все чтения значений и вызовы readyFor находятся внутри computed; не делать один нерективный снимок при setup. Не создавать watchers, timers, новые stores или собственный editor lifecycle.

WorkspaceEditCommands подключает этот composable. Чистая функция остаётся доступной для независимого теста. DOM/focus, обработчики Save/Revert, dialogFocus и владельцы состояния не переносятся.

### Сохраняемые условия

Не менять последовательность проверок storage/block/dialog/readback/sending/unknown/stale/recovery/geometry. Готовность baseline вычисляется отдельно для сохранённого changedFeature и текущего draft. Правила quality disclaimer, success без readback, rejected candidate и no-op сохраняются буквально.

## B3: прикладные ошибки WorkOrderService и Open

### Новый внутренний контракт

Добавить отдельную прикладную ошибку WorkOrderOperationError с ограниченным набором смысловых code и русским message, без status_code и без импортов web_api. Место — существующий пакет `use_cases/domain/exceptions`; это прикладная ошибка, а не объявление нового доменного агрегата. Набор допустимых кодов фиксируется enum или Literal; не принимать произвольный HTTP-код в конструкторе.

Перевести на неё все ошибки WorkOrderService и только Open-путь EditVersionService: open_visible_work_order, get_actor, get_visible_work_order, require_active_editor, raise_context_invalid и обе транзакционные ветки открытия, которые их вызывают. Перед правкой повторно проверить call sites. Если обнаружится новый вызов helper из Save/readback, не менять его поведение незаметно: разделить только нужное место или пересмотреть локальную границу.

Существующий WorkOrderApiError остаётся для Save/replay/readback и остальных потребителей. Новая ошибка не наследуется от него: наследование сохранило бы транспортный контракт. Совместимость достигается обработчиками API, а не поддельным status_code в прикладном классе.

### HTTP mapping

В web_api добавить исчерпывающее соответствие и отдельный handler, использующий существующий structured_error_response:

| Code | HTTP |
| --- | --- |
| WORK_ORDER_ACTOR_NOT_FOUND | 404 |
| ROLE_NOT_ALLOWED | 403 |
| WORK_ORDER_NOT_FOUND | 404 |
| WORK_ORDER_NOT_ASSIGNED | 403 |
| WORK_ORDER_STATE_CONFLICT | 409 |
| WORK_ORDER_CONTEXT_INVALID | 422 |

Сообщения остаются прежними. Сохраняются correlationId в теле/заголовке и log_handled_api_error. Не добавлять fallback, превращающий неизвестный код в произвольный ожидаемый отказ: неизвестный код является дефектом, а полнота mapping проверяется тестом.

WorkOrderService по-прежнему различает чужой/отсутствующий наряд; Open скрывает оба через WORK_ORDER_NOT_FOUND. Не унифицировать эти проверки. Авторизация в HTTP и актуальная проверка actor в use case сохраняются.

### Транзакции и соседние сценарии

Open сохраняет row lock, создание EditVersion и перевод assigned → in_progress в одной транзакции, touch существующей версии, распознавание только прежнего unique violation и новую транзакцию восстановления. HTTP 201 при создании и 200 при повторном открытии неизменны. SQLSTATE, repositories, ORM, порты и схема БД не реорганизуются.

SaveGeometryResult/SaveGeometryRejection, сохранённые response_status/payload, commit terminal rejection перед исключением, access-before-replay и COMMAND_ID_REUSED остаются в существующем пути. Обновление presentation в F3 не является изменением протокола или алгоритма Save.

## F7: контракт списка с ошибками отдельных полей

### Представление результата

API получает unknown. Парсер списка возвращает один упорядоченный массив проверенных строк; store остаётся единственным владельцем этого массива. Не хранить параллельно независимо изменяемые validItems, rawItems и errorsById.

Технический выбор дизайна: отдельный тип WorkOrderListEntry вместо расширения серверного WorkOrderSummary ложными корректными значениями. Строка содержит локальный rowKey, id (string либо null), code/title/description/status в проверенном виде и массив issues `{field, message}`. Непригодные поля имеют null; корректный description:null отличается от ошибки наличием/отсутствием issue. Данные исходного JSON не сохраняются как типизированный WorkOrderSummary.

rowKey обозначает позицию внутри результата загрузки, а не доменную идентичность. Для строк без id он позволяет Vue отобразить ошибку; никогда не попадает в API, selectedWorkOrderId, sessionStorage или recovery. Отдельный UX для дублей id не вводится: штатный запрос не создаёт дубли.

`items` в workOrders хранит строки этого типа. selectedWorkOrder возвращает строку с пригодным id; выбор по-прежнему хранится как id. WorkspaceDetailsPanel принимает идентифицируемую строку, а не утверждает, что все её поля корректны. Контракт WorkspaceResponse и геометрические модели не изменяются.

### Проверки полей

Технические решения агента, следующие из текущего API:

| Поле | Проверка | Сообщение при нарушении |
| --- | --- | --- |
| id | UUID в принятой сервером форме | Некорректный идентификатор наряда |
| code | строка | Некорректный код наряда |
| title | строка | Некорректное название наряда |
| description | строка или null; поле присутствует | Некорректное описание наряда |
| status | assigned или in_progress | Некорректный статус наряда |

Не добавлять новых доменных запретов на пустые строки code/title: backend DTO их сейчас допускает. Не преобразовывать числа/объекты в строки, не trim/исправлять значения автоматически. Для UUID использовать существующий predicate; пригодные UUID нормализовать в нижний регистр на этой границе. UUID в production приходят из backend; в API-тестах использовать настоящие UUID, не ослаблять проверку ради wo-1. Изолированные тесты store с подменённым API могут сохранять технические fixture ids, если не проверяют парсер.

Собирать все ошибки строки в стабильном порядке полей. Корректные поля отображаются даже при других ошибках. Для не-object элемента сохранять позицию и показать «Некорректные данные наряда»; определить конкретные поля из такого элемента невозможно.

Если value не объект или workOrders не массив, это общая ошибка протокола загрузки, а не пустой список. Старые items сохраняются, выставляется loadError без retry action; прежняя ветка reconcileAssignments при ошибке загрузки сохраняется. Если массив существует, ошибки его отдельных элементов не устанавливают общую loadError.

### UI и открытие

Карточки исправных строк сохраняют прежний вид. В ошибочной строке отображаются пригодные значения и сообщения issues. Для отсутствующего title использовать «Название недоступно», code — «Код недоступен», status — «Статус недоступен»; непригодное description не выводить как текст, но показать его ошибку. Без id строка не является кнопкой навигации; с id сохраняет существующую навигацию через editorNavigation, включая защиту dirty draft.

Ошибки полей отображаются также в панели выбранного наряда и не занимают место operational error Open. При отсутствии operational error кнопка открытия остаётся доступной по существующим guards, если id пригоден. Для неизвестного статуса текст кнопки — «Открыть»; известные assigned/in_progress сохраняют «Начать»/«Продолжить». Наличие ошибочного title/status не считается недостатком прав.

После успешного Open/readback существующее updateWorkOrderStatus может обновить локальное известное состояние статуса. При этом issues последнего List-ответа не стираются: это сообщение о полученных данных списка. Только следующий List-ответ пересчитывает issues. Не заменять title/code из workspace произвольной второй копией; не скрывать ошибку списка из-за успеха другой операции.

Никакой автоповтор List/Open не вводится. На нарушении протокола нет отдельной кнопки retry. Общая кнопка обновления списка остаётся, как и согласованная очистка выбранного/открытого наряда, если его id отсутствует в новом массиве. Id с ошибочными описательными полями остаётся участником проверки назначения. Строка без пригодного id — нет.

## F7: Open и обработка ошибок протокола

В api/editVersions.ts только openEditVersion получает unknown и проверяет ответ до возврата вызывающему коду. saveFeatureGeometry не меняется.

Для Open необходимы object editVersion, корректный UUID editVersion.id, совпадение нормализованного workOrderId с запрошенным и status=open. DTO backend не меняется. На frontend возврат сузить до проверенной проекции `{editVersion: {id, workOrderId, status}}`, которую реально потребляет loadVersion. Не объявлять ownerId/revision/dates проверенными через cast всей исходной структуры; не добавлять исчерпывающий парсинг неиспользуемых metadata. Старые типы полной Open summary удалить только после проверки отсутствия потребителей. created не требуется для поведения клиента; HTTP 200/201 обрабатываются прежним успешным путём.

Для повреждённой оболочки List и Open ввести узкий тип ошибки контракта этих операций с operation и issues. Не изменять смысл существующего ProtocolError Save/recovery. parseApiError распознаёт новый тип отдельно от unknown; список и Open получают понятные сообщения о некорректном ответе сервера с названиями полей, action=null. Не показывать сырой JSON или объект вместо значения. Не выдавать ошибку протокола за 403/404 или доказательство невыполнения операции.

Ошибки строки List не бросаются: возвращаются в issues. Общая ошибка List и ошибка Open бросаются до присваивания результата в store. Open с нарушенным контрактом не обновляет локальный статус наряда, не резервирует чтение и не запускает GET workspace. Существующие проверки epoch/requestSeq/выбранного id выполняются и в catch; поздняя ошибка не появляется на новом контексте. Backend мог уже открыть версию — отменять или повторять эту операцию автоматически нельзя.

## Проверки и критерии приёмки

| Часть | Обязательная проверка |
| --- | --- |
| F3 pure | Существующие сценарии сообщений/действий на обычных входных объектах, без Pinia/sessionStorage; импорт не подтягивает stores |
| F3 adapter | Реактивная смена draft, baseline readiness, phase, auth permission и lock обновляет представление |
| B3 application | Коды и порядок отказов, отсутствие status_code у новой ошибки, прежние транзакционные сценарии Open |
| B3 transport | Все шесть кодов сохраняют статус/message/correlationId; чужой наряд скрыт; 201/200 неизменны |
| B3 regression | Старый handler Save/readback не изменён; replay/rejection/atomicity и конкурентное Open проходят профильные проверки |
| F7 parser | Каждое поле, несколько ошибок, не-object строка, непригодная оболочка, порядок/пустой список, безопасная проекция Open |
| F7 API/store | Проверка до побочных действий; ошибочные строки не скрывают список; id отсутствует → прежняя очистка; старый ответ не меняет новый контекст |
| F7 UI | Все позиции видны; конкретные поля; открытие с пригодным id и ошибками остальных полей; без id нет открытия; неизвестный статус не становится assigned; нет retry-кнопки |

Перед реализацией зафиксировать baseline соответствующих тестов. Frontend: профильные Vitest, затем полный `npm test`, `npm run typecheck`, lint затронутых файлов. Backend: architecture tests, work_order_service/edit_version_service, exception_handlers/work_orders API и профильные интеграционные Open/Save/replay/rejection проверки в принятом окружении с БД. Состав E2E уточнить по существующим сценариям списка/открытия/редактора, не дублировать unit-тесты механически. Ошибки окружения отделять от регрессий. Прогоны этого этапа ещё не выполнены.

## Порядок и ограничения реализации

Три части остаются отдельно проверяемыми: F3; B3; F7 с согласованной правкой parser/store/UI. Внутри F7 API и потребители меняются согласованно, без промежуточного признания повреждённого ответа корректным. Общий validation framework, новая библиотека, DI container, event bus, FSD, миграции БД и массовые перемещения не нужны.

Допустимые технические уточнения исполнителя: точные имена файлов типов/парсеров, размещение небольшого HTTP mapping, структура fixtures и выбор существующих E2E для регрессии. Нельзя менять согласованную семантику ошибок, очистки workspace и доступа ради упрощения тестов. Все материалы остаются в docs/full_refactoring. Git add/commit/push запрещены; изменения оставляются пользователю для проверки.
