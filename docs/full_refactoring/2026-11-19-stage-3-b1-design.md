# B1 · Доменная политика первого редактирования линии

19 ноября 2026 года. Дизайн принят пользователем. Основание — [исходный разбор](2026-11-19-stage-3-b1-analysis.md) и [границы этапа 3](refactoring-order.md). [План реализации](2026-11-19-stage-3-b1-plan.md).

## Цель и критерий успеха

Разработчик должен видеть в доменном коде, какое изменение геометрии допустимо и какое нарушение имеет приоритет. Тест политики воспроизводит это решение на обычных значениях Python. Save и проекция сохранённого набора изменений используют одно определение допустимой разницы координат. Наблюдаемые результаты API, совместимость с сохранёнными командами и гарантии транзакции входят в критерии приёмки.

## Рассмотренные подходы

1. Вызывать отдельные чистые проверки из существующих веток репозитория. Объём переноса меньше, но порядок решений по-прежнему задаёт адаптер.
2. Собрать порядок проверок геометрии Save в единой чистой политике и предоставлять ей данные по мере необходимости. Пользователь выбрал этот подход за возможность прочитать и проверить приоритет отказов в одном месте. Цена выбора — явные промежуточные результаты между получением данных, проверкой токена и окончательным решением.

## Контракт политики и адаптера

Политика в существующем пакете `domain_services.edit_geometry` принимает тип и операцию объекта, декодированные значения геометрии, политику канонизации версии, признак изменения другого объекта и результаты пространственной проверки. Данные поступают по фазам. Для диагностики хранения адаптер сообщает факт отсутствия или повреждения с сохранением конкретной причины. Проверка связей строк, чтение EWKB, получение пространственных фактов и выбор байтов для записи принадлежат адаптеру.

Вариант реализации, оставленный проектировщиком: представить промежуточное решение обычным значением, указывающим, какой факт нужен дальше. Адаптер получает запрошенный факт и передаёт его в политику. Первый отказ завершает эту ветвь. Имена функций, типы результатов и способ выражения фаз выбирает исполнитель. Обязательное свойство — порядок конкурирующих бизнес-отказов читается в политике и проверяется без исполнения репозитория. Доменные результаты описывают причину отказа или разрешённый переход. На существующей границе они преобразуются в прежние коды и сообщения. Политике недоступны сессия, SQL, HTTP-статус и handles.

## Порядок решений

| Фаза | Решение и его место в сценарии |
| --- | --- |
| Допустимость цели | Для объекта другого типа или операции `created/deleted` первым возвращается `FEATURE_NOT_EDITABLE`, в том числе при отсутствующем baseline. Для подходящей цели сначала проверяются наличие и связи снимка, затем декодирование и соответствие типа. Повреждение даёт `WORK_ORDER_CONTEXT_INVALID`. Для исправной линии без внутренней вершины возвращается `FEATURE_NOT_EDITABLE`. |
| Подготовка | Используется существующая `prepare_geometry` с политикой версии. Сохраняется различие между немедленной ошибкой подготовки и кодом отказа, отложенным в `PreparedGeometry`. Между подготовкой и валидацией use case проверяет `draft_version_token`, поэтому stale имеет приоритет над отложенным отказом и последующими проверками. |
| Сохранённый контекст | После проверки handles повторно соблюдается порядок проверок baseline. Далее проверяются наличие области работ, читаемость текущей геометрии, соответствие структуры, допустимая разница вершин и соответствие `operation`. Затем последовательно учитываются пространственные факты для исходной и текущей геометрии. Отрицательный результат любого из трёх условий (валидность геометрии, валидность области, покрытие) даёт `WORK_ORDER_CONTEXT_INVALID`. |
| Предложенный переход | После успешной проверки сохранённых данных другой изменённый объект даёт `MULTIPLE_FEATURE_CHANGE_NOT_ALLOWED`. Затем применяется существующее правило `validate_transition`, включая отложенный отказ и запрет смены индекса вершины до возврата к baseline. |
| Итоговая геометрия | Для no-op адаптер берёт текущие EWKB, для возврата — исходные, иначе кодирует каноническое значение. Пространственная проверка выполняется и для no-op. По полученным фактам политика сначала проверяет валидность геометрии (`GEOMETRY_INVALID`), затем покрытие областью работ (`GEOMETRY_OUTSIDE_AOI`). Успех позволяет адаптеру выдать handle проверенного изменения. |

## Чтение и повтор команды

Общий геометрический критерий сравнивает линии с одинаковой структурой относительно baseline. Результат различает совпадение, изменение одной внутренней вершины с её индексом и недопустимое изменение. Проекция разрешает неизменённые точки и короткие линии. Для непустого изменения она дополнительно проверяет видимость, операцию и единственность изменённого объекта. Ошибка чтения повреждённого снимка сохраняет собственную диагностику. Save использует тот же критерий для проверки текущего состояния и существующие правила канонизации кандидата. [Проекция](../../apps/backend/utility_service/use_cases/services/version_change_projection.py), [доменный инвариант](../../DDD_Wiki/invariants/edit_version_persisted_edit_invariants.md).

Проверка baseline имеет ещё одного потребителя — построение fingerprint. Он должен получать прежний результат ранней проверки, в том числе для корректных, но недоступных для редактирования точек и коротких линий, для которых возможен fingerprint с baseline. Сохранённый contextless fingerprint по-прежнему сравнивается без baseline. Сохраняются форматы, данные хеширования, проверка текущего доступа до replay, протокол резервирования и запись результата отказа. Порты Save, транзакционная граница и транспортные результаты относятся к другим этапам. [Идентичность команды](../../apps/backend/utility_service/use_cases/services/edit_version_save_identity.py), [сценарий Save](../../apps/backend/utility_service/use_cases/services/edit_version_service.py).

## Приёмка

- Чистые табличные тесты проводят политику через фазы до результата. Включить конкурирующие нарушения: недоступная цель и отсутствующий baseline, повреждённая сохранённая геометрия и другой изменённый объект, другой объект и отложенный отказ кандидата. Для кандидата проверить все четыре комбинации валидности и покрытия, включая приоритет `GEOMETRY_INVALID` при двух нарушениях. Для сохранённых данных проверить каждый отрицательный пространственный факт.
- На одних и тех же парах координат проверить совпадение, сдвиг внутренней вершины, изменение конца линии, нескольких вершин и числа вершин. В тестах потребителей отдельно проверить допустимый чистый снимок с точкой и короткой линией, повреждение на чтении, отказ Save, повторный сдвиг той же вершины, no-op и возврат.
- Сценарные тесты подтверждают место stale-проверки, прежние fingerprint и replay, фиксацию отказа до ответа, token и события при записи и no-op. Интеграционные тесты подтверждают факты PostGIS и диагностику повреждённого EWKB. Протокольные тесты охватывают чужой, просроченный и уже потреблённый handle и ограничения вложенных транзакций. Проверка архитектурных импортов обязательна.
- Готовность требует подтверждения через штатные пути Save и чтения. Перенос всех решений в новый класс при сохранении конкурирующих проверок в репозитории оставил бы причину исходной задачи нерешённой. Объём B1 ограничен геометрией первого редактирования.
