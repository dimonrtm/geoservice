# Этап 5 · План реализации F2

Для исполнения по шагам использовать `superpowers:executing-plans` при работе в одном чате или `superpowers:subagent-driven-development` при выбранном пользователем исполнении с подагентами.

**Цель.** Развязать HTTP, auth и редактор так, чтобы повторный вход, выход с отправленным Save и смена доступа в другой вкладке сохраняли своё поведение. [Принятый дизайн](2026-11-21-stage-5-f2-design.md).

**Архитектура.** Общий Axios-клиент вкладки получает доступ к сессии при запуске. Auth сообщает о переходах доступа в определённых точках, а существующая сборка редактора связывает эти вызовы с владельцами workspace. Сценарий редактора и интерфейс читают живые значения из того же auth store. Стек — Vue, Pinia, TypeScript, Axios, Vitest и существующий анализатор границ.

## Общие ограничения

- Одно приложение на вкладку. Восемь API-модулей продолжают импортировать существующий `http`. Установку HTTP-перехватчиков выполняет приложение, время жизни редактора по-прежнему задаёт его Pinia.
- Сохранить browser coordinator, monitor, общий маркер, очередь status и текущие исключения для auth endpoints. После потери доступа отправленная команда продолжает требовать явного согласия. Обычный refresh той же сессии сохраняет workspace.
- В охват входят `editorSession` и пять перечисленных в шаге 3 UI-потребителей, включая legacy-ветки общей карты. Backend, схема IndexedDB, правила Save/replay, WS-протокол и тексты диалогов сохраняют свои контракты.
- Команды и пути `src/…`, `scripts/…` ниже даны от `apps/frontend`. Ссылки на материалы проекта приведены относительно документа. Изменения остаются в рабочем дереве для ревью пользователем.

## Случаи для ревью

| Ситуация | Наблюдаемая гарантия | Шаг |
| --- | --- | --- |
| Тот же пользователь успел войти с другим `sid`, пока шёл запрос | Старый 401 не меняет новый auth и открытый наряд | 1, 4 |
| После первого refresh вкладка получила 401 вместо 503 либо сменилась только роль | Маркеры выбора очищаются или сохраняются по причине перехода. При смене роли закрывается workspace без полного сброса списка по ID | 2 |
| Пока login ждёт остановки recovery, началась другая auth-операция | После ожидания проверяются поколение и браузерный маркер. Поздний login не устанавливает свой токен | 2 |
| Временно исчезла панель или auth store прошёл через обычный reset | Привязки продолжают работать. Повторная инициализация приложения в тесте после освобождения даёт один обработчик на запрос | 1, 2 |
| Открыто подтверждение recovery или выполняется изменение на legacy-карте при смене сессии | Диалог закрывается, старое подтверждение теряет силу, поздний результат не применяется к новому слою | 3 |

## 2. Передать реакции workspace в auth

**Контракт.** В `src/auth/sessionAccessEffects.ts` определить четыре операции. В `src/stores/auth.ts` добавить `bindSessionAccessEffects(auth: ReturnType<typeof useAuthStore>, effects: SessionAccessEffects): () => void`. Использовать уже имеющийся приватный runtime auth store для хранения связи. Тесты auth получают явные зависимости, а `installEditorRuntime(pinia)` связывает реальные операции конкретного редактора до первого входа.

```ts
import type { AuthRole } from "@/api/auth";

type SessionIdentity = {
  readonly actorId: string | null;
  readonly role: AuthRole | null;
  readonly sessionId: string | null;
};

type SessionTransition = {
  previous: SessionIdentity;
  current: SessionIdentity;
  cause: "update" | "initial-restore" | "clear" | "initial-ended";
};

interface SessionAccessEffects {
  beforeAccessLoss(previousActorId?: string): void;
  afterEpochChange(): void;
  afterSessionTransition(transition: SessionTransition): void;
  prepareExplicitLogin(actorId: string): Promise<void>;
}
```

Для замены A → B ожидается остановка A при прежнем epoch, затем уведомление после инкремента, затем переход с установленным B.
