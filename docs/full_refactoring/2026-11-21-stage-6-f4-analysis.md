# Этап 6 · F4. Изоляция ввода-вывода при восстановлении Save и Revert

Разбор текущего состояния на 21 ноября 2026 года, ревизия `b5f815c`. В F4 требуется сделать порядок действий при восстановлении проверяемым с управляемыми зависимостями и сохранить реактивное представление в Pinia. Аудит указывает на выбор конкретных реализаций внутри сценария. В действующем коде это по-прежнему видно после F1 и F2, хотя путь к store изменился. [Критерий готовности F4](refactoring-order.md#этап-6-изолировать-recovery-io--f4), [исходное замечание F4](architecture-review.md#f4-recovery-сам-выбирает-конкретные-реализации-ввода-вывода), [текущий recovery store](../../apps/frontend/src/stores/workspace/workspace_recovery/workspaceRecovery.ts).

## Что уже определено

Неизвестный исход означает, что редактор потерял сведения о результате отправки. Изменение могло сохраниться. Повтор использует прежние `CommandId`, целевой объект, токен версии и геометрию. Ограничение на новые изменения действует для затронутой рабочей версии. Редактор может работать с независимым нарядом, пока сохранена возможность вернуться к первому. Успешная квитанция подтверждает прежнюю операцию. Чтобы показать текущее состояние, редактору нужен актуальный снимок. Это принятые правила модели GeoService. [Состояния редактора](../../DDD_Wiki/state_machines/editor_save_recovery.md), [сценарий прерванной работы](../../DDD_Wiki/use_cases/interrupted_edit_work_recovery.md), [политика восстановления](../../Wiki/policies/editor_recovery_policy.md).

Порядок этапов фиксирует существующие данные, задержки, конкурентность, алгоритм миграции, пользовательское согласие и контракт `RecoveryHost`. После F1 и F2 runtime связывает host и эффекты сессии с конкретным экземпляром Pinia. Host проверяет пользователя и назначение, выдаёт право применить результат чтения и сообщает редактору о прерывании или завершении. Эти связи уже существуют на момент F4. [Порядок этапов](refactoring-order.md), [сборка редактора](../../apps/frontend/src/editor/editorRuntime.ts), [привязка RecoveryHost](../../apps/frontend/src/editor/workflows/commandsWorkflow.ts), [приёмка F2](2026-11-21-stage-5-f2-verification.md).

## Путь одной команды в текущем коде

| Момент | Фактическое поведение и существенное различие |
| --- | --- |
| Перед первым PUT | `submit` резервирует ключ пользователя, наряда и версии, ожидает `storage.insert` и перепроверяет пользователя и поколение сессии. В адаптере promise разрешается по завершении транзакции IndexedDB. При ошибке записи PUT не начинается. [Отправка команды](../../apps/frontend/src/stores/workspace/workspace_recovery/workspaceRecovery.ts), [транзакция](../../apps/frontend/src/stores/workspace/workspace_recovery/workspaceRecoveryIndexedDb.ts). |
| Потерян ответ | Первая интерактивная отправка идёт сразу после записи, вне очереди фоновых запросов. При неизвестном исходе запускается серия из пяти попыток с задержками 0, 2, 5, 10 и 20 секунд. После восстановления или ручного повтора у серии пять попыток всего. Для ключа работает один цикл. Фоновые PUT и отдельные сетевые шаги чтения используют общий планировщик с двумя слотами. Ожидание свободный слот не занимает. [Цикл отправки](../../apps/frontend/src/stores/workspace/workspace_recovery/workspaceRecovery.ts), [задержки](../../apps/frontend/src/stores/workspace/workspaceRetry.ts), [планировщик](../../apps/frontend/src/stores/workspace/workspace_recovery/workspaceRecoveryScheduler.ts). |
| Получен определённый исход | После успеха сценарий записывает результат и признак обязательного чтения. При отказе из-за устаревшей версии также нужно чтение. При обычном предметном отказе можно сразу перейти к очистке. Ошибки идентичности, протокола и доступа имеют отдельные ветви. [Классификация ошибок](../../apps/frontend/src/stores/workspace/workspaceSaveErrors.ts), [переходы по результату](../../apps/frontend/src/stores/workspace/workspace_recovery/workspaceRecovery.ts). |
| Не удалось дочитать снимок | Известный исход сохраняется. Повтор чтения использует GET. Промежуточные данные карты и ChangeSet могут пережить неудачу чтения baseline только пока актуальны команда, поколение сессии и выданное право применить снимок. Когда чтение вытеснено более новым, recovery может один раз получить новое право и начать чтение снова. Согласование токенов внутри самого сборщика снимка выделено в F6. [Чтение снимка](../../apps/frontend/src/composables/edit_version/readEditVersionSnapshot.ts), [тест замены устаревшего чтения](../../apps/frontend/src/stores/workspace/workspace_recovery/workspaceRecovery.test.ts), [граница F6](refactoring-order.md). |
| Завершение | После принятия обязательного чтения или отказа, допускающего завершение без GET, сценарий удаляет запись с проверкой `commandId` и ревизии. Только после успешного удаления и повторной проверки сессии вызывается `host.complete`. Ошибка удаления оставляет известный исход и блокирует дальнейшие действия по ключу. [Завершение](../../apps/frontend/src/stores/workspace/workspace_recovery/workspaceRecovery.ts), [проверка сбоя очистки](../../apps/frontend/src/stores/work_order/workOrders.recovery.test.ts). |

## Где ещё используется то же хранилище

| Вход в сценарий | Зачем требуется доступ к данным браузера |
| --- | --- |
| `initializeActor` | Дожидается начатой приостановки и обновлений, запускает миграцию старой записи из sessionStorage, читает записи пользователя из IndexedDB. Для каждой учитывает текущий доступ и требование явного согласия. |
| `prepareActorLogout` | Дожидается незавершённых вставок и обновлений, запускает миграцию и сверяет отправленные намерения с долговременными записями. При недоказанной сохранности возвращает отказ в подготовке к выходу. |
| `suspendActor` | Останавливает активные попытки для пользователя или конкретного наряда. После миграции проверяет и ещё не загруженные записи пользователя, чтобы требование явного согласия сохранилось после следующего входа. |

Все три пути напрямую вызывают `migrateLegacyRecovery(actorId, storage)`. Даже при подмене IndexedDB эта функция читает реальный `sessionStorage`. При переносе старой записи она сверяет исходное значение перед удалением, а квитанция в IndexedDB защищает от повторного появления уже завершённой команды. Потеря доступа и обычное открытие вкладки имеют разное поведение. После потери доступа оператор отдельно подтверждает продолжение для прежней команды в актуальной сессии. [Точки вызова](../../apps/frontend/src/stores/workspace/workspace_recovery/workspaceRecovery.ts), [миграция](../../apps/frontend/src/stores/workspace/workspace_recovery/workspaceRecoveryMigration.ts), [контракт восстановления](../../Code_wiki/архитектура/frontend_save_recovery.md).

## Исходные проверки

21 ноября на указанной ревизии прошёл **61 тест в 8 файлах Vitest**. В выборку вошли контракт записи, recovery store, оба формата хранения, миграция, планировщик, интеграция с нарядами и компонент списка восстановления. Существующий тест store создаёт Pinia, устанавливает fake-indexeddb, очищает sessionStorage и подменяет модули отправки и чтения. Для ошибки вставки он перехватывает метод прототипа IndexedDB. Это конкретная цена нынешнего способа проверки сценария. Отдельные браузерные спецификации покрывают перезапуск после Save и Revert, обработку потери и возврата доступа и реальные транзакции IndexedDB. ## Согласованный объём проверки

21 ноября пользователь подтвердил, что управляемая проверка F4 охватывает и путь отправленной команды до очистки, и три сценария из таблицы выше. Без IndexedDB и sessionStorage в тесте должно быть возможно проверить, какие команды восстанавливаются при открытии вкладки, для каких команд потеря доступа требует нового согласия и как результат незавершённой записи влияет на разрешение выхода. Сам алгоритм миграции и его проверки сохраняют действующий контракт. [Исходные требования этапа](refactoring-order.md#этап-6-изолировать-recovery-io--f4).

Пользователь также подтвердил, что все четыре сценария должны проверяться без создания Pinia. Например, при незавершённой вставке команды тест должен уметь задержать запись, запустить подготовку к выходу, затем завершить запись ошибкой и проверить, что выход заблокирован и PUT не начался. Сегодня этот тест требует активной Pinia и подмены метода IndexedDB. В приложении редактор и список восстановления продолжают получать через Pinia записи, фазы и ошибки. [Проверка подготовки к выходу](../../apps/frontend/src/stores/workspace/workspace_recovery/workspaceRecovery.test.ts), [чтение состояния редактором](../../apps/frontend/src/editor/workflows/commandsWorkflow.ts), [список восстановления](../../apps/frontend/src/components/workspace/WorkspaceRecoveryList.vue).

Из двух рассмотренных подходов пользователь выбрал передачу состояния в TypeScript-исполнитель. Pinia предоставляет реактивный объект в приложении, тест передаёт обычный объект. Устройство границы, обязанности адаптеров и критерии приёмки описаны в [принятом дизайне F4](2026-11-21-stage-6-f4-design.md).

## Два пограничных случая, выявленных при проверке дизайна

| Ситуация | Что видно в текущем коде | Возможное последствие |
| --- | --- | --- |
| Возможное будущее переназначение наряда во время первоначальной записи Save. | Пользователь уточнил, что продуктовая операция переназначения ещё не реализована. В браузерном тесте исполнитель меняется прямой записью в тестовую БД. Действующий API позволяет редактору прочитать назначенные ему наряды. [Браузерный тест](../../infra/m4/s2-x01-recovery.spec.ts), [API нарядов](../../apps/backend/utility_service/web_api/api/work_orders.py). | Граница F4 охватывает реакцию на полученный отказ доступа и проверку согласия после его возврата. Случай одновременного переназначения и записи Save отложен до появления операции переназначения. |
| Загрузка записей прежнего пользователя завершается ошибкой после успешной загрузки для нового пользователя. | В `initializeActor` путь успешного чтения сверяет поколение и пользователя. Обработчик ошибки устанавливает общий `storageError` без этой сверки, а `submit` учитывает эту ошибку при допуске Save. [Загрузка и допуск команды](../../apps/frontend/src/stores/workspace/workspace_recovery/workspaceRecovery.ts). | В новой сессии может появиться сообщение о недоступности хранилища и заблокироваться Save, хотя собственная загрузка нового пользователя прошла успешно. |

Это выводы из ветвей текущего кода. В исходном прогоне есть тесты смены пользователя при вставке и ожидания вставки перед выходом. Прогон не воспроизводил эти две последовательности отдельно. [Профильные тесты](../../apps/frontend/src/stores/workspace/workspace_recovery/workspaceRecovery.test.ts).

Пользователь включил исправление поздней ошибки загрузки в F4. Публиковать ошибку хранения вправе только актуальная инициализация текущего пользователя. Для приёмки согласованного поведения в дизайне описаны раздельные проверки устаревшей и актуальной ошибки. [Критерии смены пользователя](2026-11-21-stage-6-f4-design.md#ошибка-загрузки-при-смене-пользователя).
