# Этап 5 · F2. Развязка auth и рабочего пространства

Исходное состояние на 21 ноября 2026 года, ревизия `1c7763a`. Цель этапа — дать транспорту возможность проверить сессию, а редактору вовремя отреагировать на потерю доступа, сохранив существующее поведение при открытии наряда, сохранении и выходе. Пользователь выбрал настройку существующего HTTP-клиента при запуске приложения. [Дизайн F2](2026-11-21-stage-5-f2-design.md), [критерии этапа 5](refactoring-order.md#этап-5-развязать-auth-и-workspace--f2), [исходный аудит F2](architecture-review.md#f2-authhttp-и-workspace-образуют-связанную-цепочку).

## Какие связи остались после F1

| Участок | Что происходит сейчас |

Параметры сохранения выбора наряда и открытой версии также известны auth. ## Что происходит на границе доступа

| Событие | Наблюдаемое поведение |
| --- | --- |
| Первое восстановление вкладки | Успешный refresh при пустом auth сохраняет в sessionStorage идентификаторы выбранного наряда и открытой версии. Экран сначала загружает актуальные назначения. Начальный 401 или маркер завершённой сессии очищает сохранённый выбор. При начальном 503 выбор сохраняется для повтора. |
| Обновление токена или новый вход того же пользователя | При прежних пользователе, роли и `sid` смена токена сохраняет workspace и `sessionEpoch`. Другой `sid` того же пользователя инвалидирует прежние операции и сбрасывает редактор и наряды. Явный login ожидает ограничения восстановления для пользователя из ответа, затем повторно проверяет поколение auth-операции и актуальный маркер. |
| Смена пользователя или роли | При существующем пользователе сначала начинается приостановка восстановления для его ID и закрывается прежний workspace. Затем увеличивается `sessionEpoch`, останавливается текущая работа recovery и меняются данные auth. При смене только роли и прежнем `sid` общий сброс списка по ID не вызывается. Смена назначения отдельного наряда обрабатывается редактором в своём контексте. |
| Защищённый HTTP-запрос | При установленном `sid` запрос ждёт `ensureSessionReady()`. После ожидания клиент повторно сверяет epoch. Смена сессии отменяет устаревший запрос, а отсутствие подтверждения возвращает `SessionNotConfirmedError`. Для Save эти причины дают разные результаты. Login, logout, refresh и status обходят эту проверку, что позволяет самому monitor запросить status. |
| Ответ HTTP с отказом | Обычный 401 и 403 с `ROLE_NOT_ALLOWED` или `USER_INACTIVE` передаются в auth вместе с epoch запроса. При устаревшем epoch текущая сессия сохраняется. Рабочий 401 действует локально. У четырёх auth-операций `authErrorHandling: "caller"`, и их ошибки обрабатывает вызывающая операция. Отказ в назначении наряда не входит в общий перечень 403, завершающих локальный доступ. |
| Управляемый выход с отправленным Save | Навигация проверяет сохранность команды и блокирует новые локальные действия на время выхода. При неподтверждённом выходе сохраняются workspace и отправленная команда. Если пользователь до этого явно отбросил черновик, выбор сохраняет силу. При неопределённой доставке logout проверяется статус исходного `sid`. Позднее подтверждение прежней сессии не закрывает новую. |
| Принудительное завершение и возврат доступа | Совпавший внешний `ended` закрывает редактор без ожидания записи межвкладочного маркера и без автосохранения черновика. Ранее отправленная команда сохраняет свой идентификатор и данные. Для её продолжения после потери доступа требуется подтверждение для текущих пользователя, команды и epoch. Обычное восстановление всё ещё действующей сессии может продолжить доступное восстановление автоматически. |

Порядок имеет последствия для пользователя. При потере доступа auth синхронно начинает остановку работы старого редактора и продолжает очистку, пока сохранение ограничения в IndexedDB завершается асинхронно. При явном login auth дожидается операции `suspendActor` до установки нового пользователя. Безусловное ожидание во всех ветках задержало бы закрытие старого экрана. Продолжение без ожидания при login позволило бы начать восстановление до завершения проверки сохранённых записей. [Переходы auth](../../apps/frontend/src/stores/auth.ts), [остановка редактора](../../apps/frontend/src/editor/workflows/commandsWorkflow.ts), [восстановление и подтверждение](../../apps/frontend/src/stores/workspace/workspace_recovery/workspaceRecovery.ts).

HTTP также различает три способа передачи bearer. При отсутствии `authToken` используется текущий токен, `null` удаляет заголовок, явная строка сохраняет указанный токен запроса. Это важно при проверке статуса прежней сессии после появления новой. При возобновлении вкладки защищённому действию нужна проверка статуса, начатая после возобновления. [HTTP](../../apps/frontend/src/api/http.ts), [координация вкладок](../../Code_wiki/архитектура/browser_auth_sessions.md), [интеграционная проверка monitor](../../apps/frontend/src/api/auth.monitor.integration.test.ts).

## Что задаёт доменная модель

Auth владеет идентичностью и ролью пользователя. Контекст нарядов владеет назначением, открытой рабочей версией и правом действовать в ней. Поэтому смена роли затрагивает доступ редактора ко всем его командам, а утрата назначения требует отдельной проверки соответствующего наряда. Сетевой сбой загрузки списка сам по себе не доказывает переназначение. [Auth Context](../../DDD_Wiki/bounded_contexts/auth.md), [Work Order Context](../../DDD_Wiki/bounded_contexts/work_order.md), [реализация сверки назначений](../../apps/frontend/src/stores/editor_session/editorSession.ts).

Политика восстановления различает локальный черновик и уже отправленную команду. Выход не определяет исход отправленной операции. Для её разбора сохраняются прежние `CommandId` и содержимое, доступ проверяется заново. Успешная квитанция и актуальная геометрия подтверждаются раздельно. Это принятые правила модели GeoService. Браузерный `sid`, поколения запросов и очередность работы Pinia описывают их техническое обеспечение. [Политика редактора](../../Wiki/policies/editor_recovery_policy.md), [состояния восстановления](../../DDD_Wiki/state_machines/editor_save_recovery.md), [сценарий прерванной работы](../../DDD_Wiki/use_cases/interrupted_edit_work_recovery.md), [технический контракт](../../Code_wiki/архитектура/frontend_save_recovery.md).

## Согласованный сценарий HTTP во вкладке

В рабочей вкладке стартует одно Vue-приложение с одним экземпляром Pinia. Восемь API-модулей импортируют один экземпляр `http`. Оба его перехватчика сейчас обращаются к Pinia, зафиксированной импортом в модуле транспорта. [Запуск приложения](../../apps/frontend/src/main.ts), [экземпляр Pinia](../../apps/frontend/src/pinia.ts), [HTTP-клиент](../../apps/frontend/src/api/http.ts).

После уточнения значения «экземпляр приложения» 21 ноября пользователь ограничил F2 существующим способом запуска GeoService — одно приложение на вкладку, в том числе при нескольких открытых вкладках. Проверка двух независимо запущенных редакторов на одной странице была предложена в ходе обсуждения и снята. Существующий тест F1 проверяет владение черновиком и навигацией двух экземпляров Pinia. [Граница F1](2026-11-16-stage-2-f1-design.md), [тест редактора](../../apps/frontend/src/editor/editorRuntime.test.ts).

Проверочный пример F2. Редактор открывает наряд, и вкладка отправляет запрос. Пока он в пути, тот же пользователь входит заново и получает другой `sid`. На прежний запрос приходит 401. Вкладка сверяет `sessionEpoch` запроса и сохраняет новую сессию и её workspace. Обычный 401 актуального запроса завершает локальный доступ. Подтверждённый logout исходного `sid` распространяется через браузерную координацию. Отдельные проверки покрывают каждый из этих случаев. [Обработка HTTP](../../apps/frontend/src/api/http.ts), [поздний 401](../../apps/frontend/src/api/auth.restore.integration.test.ts), [смена sid и координация вкладок](../../apps/frontend/src/stores/auth.multitab.test.ts).

У вкладок одного профиля и origin общие refresh-cookie, Web Lock и маркер входа. В каждой вкладке допускается один выполняющийся запрос status и один заменяемый ожидающий контекст. После возобновления вкладки защищённое действие ждёт свежую проверку. [Координация браузерной сессии](../../Code_wiki/архитектура/browser_auth_sessions.md), [очередь status](../../apps/frontend/src/api/auth.ts), [тесты status](../../apps/frontend/src/api/auth.test.ts).
