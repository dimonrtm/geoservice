# Порядок исправлений без оверинжиниринга

Дата: 2026-11-14. Основание — [аудит](architecture-review.md). Это предлагаемая очередность, не разрешение на реализацию и не детальный план миграции.

## Общая стратегия

Исправлять по одному поведению или границе. Не начинать с массового перемещения файлов. Сохранять API, транзакции, replay, порядок ошибок, session epoch, recovery и пользовательские подтверждения. Каждый этап должен быть отдельно проверяемым и допускающим откат без отката остальных этапов.

### Корректировка после углублённого анализа

1. Сначала закрыть небольшие пробелы границ: F7 (runtime parsing List/Open) и F3 (presentation без stores).
2. Для F6 определить ограниченный бюджет пересогласования токенов и явный результат исчерпания, затем проверить оба пути чтения. Не подменять несовпавшие снимки «последними доступными» данными. Число попыток/время — решение отдельной задачи, аудит не назначает произвольный норматив.
3. F1 и F2 планировать как соседние локальные шаги: они входят в одну компоненту импортов из 17 файлов. Сначала разорвать HTTP → конкретный auth store через узкий callback-контракт; затем вынести auth → workspace coordination и согласование Save/navigation. Допустимо начать с операций владельцев F1, но завершение всей развязки требует F2. В прежнем порядке F2 стоял слишком далеко от F1.
4. B1 выполнять с сохранением EditGeometryScope/handles; затем B2. Не переносить доступ и транзакционные guards из адаптера в чистую функцию и не переставлять access-before-replay.
5. F5 — подтверждённый дефект legacy store, но legacy-экран не входит в текущий App. Исправить до его повторного подключения; если работа над legacy не планируется, оставить отдельной задачей, не задерживая основной workspace. Не удалять legacy-код автоматически.
6. B5 относится к границе legacy use cases: согласовать при ближайшем изменении legacy feature API. Не превращать это замечание в утверждение о незащищённом HTTP endpoint.

Дальнейшие этапы описывают содержание задач; указанная корректировка приоритетнее первоначальной линейной последовательности. F4 и B4 остаются более поздними задачами.

## Этап 0. Зафиксировать исходные гарантии

- В рабочем окружении запустить backend architecture tests и профильные Save/Open/replay/rejection integration tests; на frontend — editor/recovery/auth тесты и соответствующие E2E.
- Перед каждой задачей проверить фактическое покрытие её риска. Добавлять недостающие поведенческие проверки, а не дублировать реализацию.
- Не делать обновление зависимостей, переименование каталогов и изменение поведения частью архитектурной задачи.

Готовность: есть известная исходная точка; ошибки окружения отделены от ошибок приложения. Углублённый аудит подтвердил полный Vitest (501 тест) и typecheck. Backend AST guards проверены отдельным скриптом; pytest/DB/E2E остаются необходимыми перед изменениями соответствующих путей.

## Этап 1. Небольшие изменения с ясной границей

**Frontend: F3.** Отделить сбор stores от `presentWorkspaceCommands`, передавать явный вход. Это небольшой пример желаемой границы без переписывания редактора.

**Backend: часть B3.** Для одной простой группы ошибок, например WorkOrder, отделить смысловой код от HTTP mapping. Начать вне Save/replay. Сохранить прежние HTTP-ответы и правила видимости ошибок.

Готовность: чистая presentation-функция тестируется без Pinia; выбранные прикладные ошибки не выбирают HTTP-коды, endpoint сохраняет контракт. Не обобщать решение на все подсистемы заранее.

## Этап 2. Исправить владельцев состояния редактора — F1

1. Составить короткую таблицу: состояние → владелец → допустимые операции → координатор.
2. Заменить внешние присваивания draft/navigation на смысловые операции с нужным контекстом, а не универсальные setters.
3. Выделить один путь координации Save-and-leave и recovery completion; зависимости передавать явно. Разорвать соответствующий цикл stores, а не просто перенести его в новый файл.
4. Сохранить раздельность server snapshot, local draft, pending command и map presentation.

Готовность: нет прямых внешних изменений draft/navigation в затронутом сценарии; переход после сохранения зависит от исходного контекста/commandId/epoch; отказ или unknown не вызывает позднюю навигацию. Весь редактор не обязан стать одной чистой state machine.

## Этап 3. Выделить чистые backend-правила — B1

Разделить materialization/проверку сохранённых данных и решение о допустимости редактирования. Передавать обычные значения и уже декодированную геометрию. Spatial SQL оставить в infrastructure. Сохранить порядок отказов и обработку повреждённого контекста. Сохранить scope.require/issue/consume, запрет использования чужого/stale handle и запрет неподходящих nested transactions. Readback projection и Save должны использовать согласованное правило одной внутренней вершины, но сохранять разные ошибки повреждения сохранённых данных и отклонения команды.

Готовность: выбранное правило проверяется без SQLAlchemy/PostGIS; адаптер получает факты и передаёт их правилу; интеграционные результаты остаются прежними. Не переносить геопространственные вычисления из PostGIS только ради «чистоты».

## Этап 4. Отделить persistence-контракт одного сценария — B2

Начать с открытия EditVersion: скрыть разбор unique violation в адаптере и сохранить семантику rollback/recovery. Далее отдельно оценить минимальные порты Save, transaction boundary и независимые структуры результата чтения.

Готовность: use case не проверяет SQLSTATE/constraint; конкурентное открытие сохраняет одну версию. Для Save дополнительно подтверждаются lock, commit терминального отказа, неизменная identity и replay. Порты появляются только для реально используемых операций.

HTTP-представление Save из B3 отделять следующим небольшим шагом с явным решением о совместимости persisted receipts. Не менять исторические квитанции и схему БД автоматически.

## Этап 5. Развязать auth и workspace — F2

После F1 связать модули в коде сборки приложения: передать HTTP необходимые функции доступа к сессии, а auth — прикладные callbacks для уведомления о смене доступа. Сохранить существующий coordinator/monitor и порядок suspension/reset.

Готовность: транспортный клиент не импортирует конкретный auth store; auth не импортирует детали редактора; тесты refresh, multitab, stale response, pending Save/logout и восстановления проходят. Не вводить event bus вместо нескольких явных функций.

## Этап 6. Изолировать recovery I/O — F4

Передать storage/send/readback в исполнитель существующего recovery-сценария. Не менять данные, delays, concurrency, storage migration, пользовательское согласие и RecoveryHost одновременно с выделением зависимостей.

Готовность: порядок persist/send/readback/cleanup проверяется управляемыми зависимостями; Pinia отображает состояние без необходимости собирать все реальные адаптеры в тесте. Если выделение не уменьшает сложность проверок или зависимостей, не расширять его дальше.

## Этап 7. Переместить транспорт realtime — B4

Выделить узкую операцию публикации и связать её с существующим WebSocket manager через composition root. Перенести manager в адаптер, не меняя протокол и алгоритмы очередей.

Готовность: прикладной издатель не зависит от FastAPI WebSocket manager; сохраняются диагностика, ограничения очередей и закрытие соединений. Не добавлять брокер и новые гарантии доставки.

## Что пока не делать

- Не переписывать frontend на FSD и не создавать семь обязательных слоёв.
- Не вводить интерфейс для каждого repository/store/component.
- Не переносить все backend enum/DTO в новый domain-пакет одним изменением.
- Не считать наличие ORM-моделей и Pydantic само по себе достаточным основанием для дублирования всех моделей.
- Не создавать новую общую библиотеку state machine, command bus или dependency injection container.
- Не переписывать MapLibre adapter целиком и не абстрагировать каждую операцию карты.
- Не повторять закрытую CQ-01 и старую декомпозицию workOrders.
- Не смешивать архитектурное исправление с новой функциональностью.

## Практический старт

Первые небольшие задачи — F7 и F3; затем ограничение пересогласования F6. Первая существенная задача frontend — согласованная развязка F1/F2 малыми шагами. Первая существенная задача backend — B1, затем узкая часть B2. F5 исправляется до использования legacy UI. Эти ветви можно планировать независимо, но одновременное изменение всех границ одного сценария затруднит проверку.

После каждого этапа проверять, что задача действительно уменьшила количество скрытых зависимостей и мест изменения одного правила. Если достигнута ясная граница и тестируемое поведение, останавливаться; полное соответствие абстрактной схеме каталогов не является целью.
