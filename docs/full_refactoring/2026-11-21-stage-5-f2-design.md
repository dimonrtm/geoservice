# Этап 5 · F2. Граница между сессией, HTTP и редактором

21 ноября 2026 года пользователь принял дизайн как основу плана реализации. Исходная ревизия — `1c7763a`. [План реализации](2026-11-21-stage-5-f2-plan.md), [разбор кода и решений](2026-11-21-stage-5-f2-analysis.md), [задача F2](refactoring-order.md#этап-5-развязать-auth-и-workspace--f2).

## Цель и охват

Когда меняется доступ, auth определяет, какая сессия действительна, а редактор отвечает за незавершённую работу. Например, поздний 401 от прежнего входа должен сохранить новый вход и открытый наряд. При подтверждённом выходе отправленный Save должен остаться доступным для разбора после явного согласия редактора. В обоих случаях поведение зависит от порядка действий. [Граница Auth](../../DDD_Wiki/bounded_contexts/auth.md), [контекст наряда](../../DDD_Wiki/bounded_contexts/work_order.md), [политика восстановления](../../Wiki/policies/editor_recovery_policy.md).

Пользователь включил в F2 транспорт, auth store, `editorSession` и пять потребителей интерфейса, в том числе всю общую `MapView`. Эксплуатационная модель — одно приложение на вкладку и обычная межвкладочная координация. Граница задачи охватывает связывание существующих операций. Backend, формат команд и ответов, схема IndexedDB, алгоритмы retry и readback, протокол WebSocket и пользовательские диалоги принадлежат действующим контрактам соседних задач. [Приёмка F1](2026-11-17-stage-2-f1-verification.md), [технические правила сессии](../../Code_wiki/архитектура/browser_auth_sessions.md).

## Выбранный подход

**Один существующий Axios-клиент на вкладку.** При запуске приложение передаёт клиенту функции чтения сессии и обработки отказа. Тогда прежние API-функции, в том числе вызовы из recovery и карты, продолжают использовать экспорт `http`. Восемь API-модулей сохраняют привычный способ вызова. Ценой служит явный порядок сборки перед первым запросом. [Транспорт](../../apps/frontend/src/api/http.ts), [запуск](../../apps/frontend/src/main.ts).

Рассматривались отдельный клиент на каждый независимо смонтированный редактор и передача владельца сессии с каждым запросом через общий транспорт. Первый вариант потребовал бы развести API-адаптеры редакторов, второй — провести контекст через все пути вызова, включая отложенный Save и запрос WebSocket ticket. Эти затраты относились к двум приложениям на одной странице. После уточнения пользователь снял этот сценарий и выбрал настройку общего клиента при старте.

## Сборка и владение

Точка сборки приложения после установки Pinia и до `app.mount` получает конкретный auth store, связывает редактор через существующий `installEditorRuntime`, передаёт auth операции реакции workspace и подключает обработчики HTTP. К началу `App.onMounted` готовы все три связи. Сама сборка не инициирует login, restore, status или replay. Существующее восстановление сессии запускает приложение, когда интерфейс смонтирован. [App](../../apps/frontend/src/App.vue), [сборка редактора](../../apps/frontend/src/editor/editorRuntime.ts).

| Владелец | Что предоставляет и за что отвечает |
| --- | --- |
| Auth | Владеет токеном, пользователем, ролью, `sid`, `sessionEpoch` и поколением auth-операции. Выбирает момент уведомления о переходе доступа. Типы этого контракта используют понятия сессии и причины перехода. |
| HTTP | Добавляет bearer, ожидает подтверждения сессии у защищённого запроса, помечает запрос epoch и передаёт подходящий отказ обработчику. Получает только нужные ему значения и функции. |
| Редактор и recovery | Через публичные операции F1 закрывают workspace, прерывают навигацию, приостанавливают восстановление и сбрасывают состояние владельцев. Recovery владеет долговременной записью команды. |
| Сборка | Связывает конкретные stores и клиент. Предоставляет `editorSession` и интерфейсу живые данные сессии. Здесь известны обе стороны связи и выполняется перевод причины перехода в действия редактора. |

Технический выбор для дизайна — регистрировать пару HTTP-перехватчиков при сборке и освобождать регистрацию при завершении приложения. Одна сборка устанавливает пару один раз. Повторный login, reset store или размонтирование панели не создают дополнительных обработчиков. Auth-эффекты принадлежат конкретному auth store и переживают его обычный `$reset`. Для редактора сохраняется уже проверенное F1 время жизни привязок на Pinia. Тест с двумя редакторами F1 продолжает проверять локальное состояние без установки двух HTTP-привязок. [Тесты runtime](../../apps/frontend/src/editor/editorRuntime.test.ts).

## HTTP и браузерная сессия

1. Клиент читает текущие `sid`, epoch, ID пользователя и токен через переданный контракт. Для обычного запроса при наличии `sid` запоминает epoch до `await ensureSessionReady()`. После ожидания сверяет epoch, затем считывает актуальный токен. Смена epoch отменяет запрос. Отрицательная проверка готовности при прежнем epoch возвращает `SessionNotConfirmedError`. Для Save эти причины различимы.
2. Login, logout, refresh и status сохраняют исключение из проверки готовности. Обычный запрос `/auth/me` подчиняется общим правилам. Сохраняются `sessionEpoch` и `sessionActorId` в конфигурации запроса, три режима `authToken` и прежняя обработка заголовка Authorization. При `undefined` берётся текущий токен, при `null` удаляется bearer, при явной строке используется переданное значение.
3. Обычный 401 и 403 с кодами `ROLE_NOT_ALLOWED` или `USER_INACTIVE` передаются в auth с epoch исходного запроса. Auth игнорирует отказ устаревшего epoch. Для `authErrorHandling: "caller"` решение принимает вызывающая операция. Ошибка возвращается исходному caller во всех случаях. `WORK_ORDER_NOT_ASSIGNED` относится к назначению наряда. Локальный рабочий 401 не публикует общий `ended`.
4. Координатор браузерной сессии, монитор и очередь status сохраняют действующий порядок работы с cookie, Web Lock и ревизией маркера. После возвращения на вкладку защищённое действие ждёт свежей проверки. При неопределённой доставке logout проверяется статус исходного `sid` с учётными данными этой сессии. Поздний ответ прежней операции не закрывает новую сессию. [HTTP и тесты](../../apps/frontend/src/api/http.test.ts), [restore через реальный клиент](../../apps/frontend/src/api/auth.restore.integration.test.ts), [монитор](../../apps/frontend/src/auth/browserSessionMonitor.ts).

## Переходы доступа и судьба workspace

У связи auth → workspace четыре назначения. Перед заменой доступа запускается остановка работы прежнего пользователя. Сразу после увеличения epoch вызывается `hideActor()`. После установки или очистки данных auth прикладная реакция решает, нужен ли сброс списка и редактора. При явном login отдельная ожидаемая операция ставит ограничение на восстановление для пользователя из ответа. Auth предоставляет факты перехода — прежний и новый пользователь и `sid`, изменение роли, первоначальное восстановление или подтверждённое окончание сессии. Параметры `preserveSelectedWorkOrder` и `preserveOpenedWorkspace`, типы editor store и порядок обращения к владельцам принадлежат стороне workspace. Это прямые вызовы в точках перехода. [Текущие ветви auth](../../apps/frontend/src/stores/auth.ts), [операции редактора](../../apps/frontend/src/editor/workflows/commandsWorkflow.ts).

| Переход | Требуемый результат и порядок |
| --- | --- |
| Обновление токена при тех же пользователе, роли и `sid` | Обновить токен. Workspace, черновик, открытая версия и epoch сохраняются. Изменение только email также сохраняет доступ. |
| Замена пользователя или `sid` у того же пользователя | Для прежнего actor инициировать suspension, прервать навигацию и принудительно закрыть workspace. Затем увеличить epoch, скрыть прежний recovery-контекст и обновить auth. После смены идентичности или замены `sid` того же actor сбросить сначала список нарядов, затем редактор. При активной синхронизации перезапустить monitor для нового `sid`. |
| Изменение только роли, включая `setUser` | Инициировать остановку для прежнего actor, закрыть workspace, изменить epoch и скрыть recovery-контекст до записи новой роли. Условие полного сброса списка связано со сменой ID или заменой `sid`. |
| Первоначальный restore | После успешного refresh с пустым состоянием auth сбросить состояние в памяти, сохранив в sessionStorage IDs выбора наряда и открытой версии. Экран загружает назначения до восстановления workspace. Начальный 401 или маркер `ended` запускает принудительную очистку даже при пустом пользователе. Начальный сетевой отказ или 503 сохраняет выбор для retry. |
| Очистка локальной сессии | Инвалидировать поколение restore и остановить monitor. При известном actor или принудительной очистке запустить остановку workspace. Увеличить epoch и скрыть recovery-контекст даже при пустом пользователе. Очистить auth и применить условия сброса списка и редактора. Runtime 401 действующей сессии и начальный 401 сохраняют разные сообщения и доступные действия. |
| Явный login | После публикации активного `sid` дождаться `suspendActor(result.user.id)`. После ожидания проверить поколение auth-операции и текущий маркер до установки новой сессии. Ограничение учитывает записи, ещё не загруженные из IndexedDB. Это другой момент ожидания, чем немедленное прекращение доступа при внешнем `ended`. |
| Выход из редактора | Навигация обрабатывает черновик, ожидает `prepareActorLogout` и проверяет `sid` и epoch. До подтверждения выхода сохраняется отправленная команда. Отказ оставляет редактор доступным, а ранее явный discard сохраняет силу. При внешнем `ended` закрыть приватный workspace сразу. Возврат доступа требует явного согласия для прежней отправленной команды. |

Смысл `clearLocalSession()` и `logout()` как существующих операций сохраняется для их потребителей, в том числе вызова из `RecoveryHost.interrupted`. Адресный отказ по назначению затрагивает соответствующий наряд. Исход уже отправленного Save, получение актуального снимка и очистка хранилища остаются в существующем recovery-сценарии. [Навигация](../../apps/frontend/src/editor/workflows/navigationWorkflow.ts), [восстановление Save](../../Code_wiki/архитектура/frontend_save_recovery.md).

## Что получают editorSession и интерфейс

Источник данных один — auth store. Сборка предоставляет реактивное чтение ID пользователя, статуса входа, роли или производного права редактировать и epoch. Читателю доступны значения и операции по его задаче. Например, карте достаточно статуса входа и epoch. Снимок этих значений в момент сборки нарушит проверки после повторного login. Токен требуется HTTP-клиенту, но отсутствует в представлении доступа для редактора.

| Потребитель | Поведение, которое должно сохраниться |
| --- | --- |
| `editorSession` | `reserveWorkspaceRead`, `applyWorkspaceRead`, `loadVersion`, `reconcileAssignments` читают сессию через привязку редактора. Проверки actor, epoch, ключа версии и поколения чтения сохраняют свои места, включая проверки после ожидания. |
| `EditorWorkOrdersView` | Загрузка назначений сверяет epoch и поколение списка перед восстановлением. Оба действия «Войти снова» на ошибке по-прежнему вызывают существующий выход. Управляемый выход из верхней панели проходит через сценарий навигации. |
| `WorkspaceEditCommands` | Доступность команд реактивно учитывает вход и роль editor. |
| `WorkspaceRecoveryList` | Видны записи текущего пользователя по доступным ему нарядам. Подтверждение связано с командой и epoch, диалог закрывается при смене сессии. |
| `useWorkspaceLineInteraction` | Смена пользователя или версии инвалидирует выбор линии. Доступ к правке учитывает роль и блокировку взаимодействия. |
| `MapView` целиком | Для подписки на слой используются текущие статус входа и epoch. После старого Save/Delete карта повторно проверяет epoch, поколение подписки и активный слой. Работают режимы workspace, пустой карты и legacy editing. |

Технический выбор — переиспользовать привязку зависимостей F1 для store и дать UI узкий реактивный доступ из сборки. Потребитель импортирует только контракт или функцию получения уже связанной зависимости. Такая функция сама не должна импортировать конкретный auth store или запускать сборку. Прямое использование auth в `App.vue` и `LoginScreen.vue` относится к управлению сессией и форме входа. [Привязка F1](../../apps/frontend/src/editor/editorRuntimeBinding.ts), [разбор пяти потребителей](2026-11-21-stage-5-f2-analysis.md#согласованный-охват-интерфейса).

## Приёмка реализации

| Проверка | Наблюдаемый критерий |
| --- | --- |
| Граф | `api/http` не зависит от конкретных Pinia и auth store. У auth отсутствуют импорты деталей work orders, editor session, commands и recovery, в том числе типы сброса. У `editorSession` и пяти согласованных UI-потребителей отсутствует прямой импорт auth store. Посредники не замыкают прежний цикл. Сравнить конкретные пути с [графом после F1](stage-2-import-graph.json). |
| Транспорт и bootstrap | На обычном пути запуска перехватчики связаны до первого restore и рабочего запроса. Тесты проверяют текущий токен, явный bearer, cookie-only запрос, исключения ready-проверки, два вида отмены, caller-owned ошибки, локальные 401/403 и устаревший epoch. Повторная инициализация и освобождение в тестовой среде не умножают вызовы обработчика. |
| Auth и workspace | Пройти переходы таблицы выше. Для изменения доступа проверить порядок побочных действий и actor, которому принадлежит suspension. Для явного login задержать завершение suspension и проверить актуальность операции после ожидания. Для начального 401 и 503 проверить реальные маркеры выбора и открытия. |
| Вкладки и команды | Пройти существующие проверки multitab, status после resume, Save в полёте при logout, отказ logout, внешний `ended`, явное разрешение восстановления и поздний старый 401 после повторного входа. Новый пользователь и новая сессия получают свой workspace. |
| Editor и карта | Проверить смену роли и пользователя при открытом редакторе, поздний GET, подтверждение recovery, смену выбора линии, отключение подписки и поздний результат legacy-редактирования. Использовать существующие тесты компонентов и сценариев. Недостающую проверку добавить только для конкретного непокрытого перехода или запрещённой связи. |

До реализации 158 тестов в 12 профильных файлах прошли. Этот срез задаёт исходное поведение. При проверке реализации к нему добавляются затронутые UI/карта, полный frontend Vitest, действующая проверка границ редактора, typecheck приложения и сборка. Реальный сценарий запуска, Save и восстановления можно сверить с уже имеющейся браузерной проверкой. [Исходный прогон](2026-11-21-stage-5-f2-analysis.md#исходные-проверки), [тест карты](../../apps/frontend/src/components/MapView.test.ts), [браузерные сценарии восстановления](../../infra/m4/s2-x01-recovery.spec.ts).

Имена и размещение новых функций, а также точная форма TypeScript-контрактов остаются исполнителю. Критериями выбора служат доступность только нужных операций, сохранение реактивности, отсутствие зависимости потребителей от кода сборки для получения сессии и проверяемый порядок переходов.
