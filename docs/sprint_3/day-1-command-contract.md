# День 1. Сохранение геометрии нескольких линий

**Контракт утверждён пользователем 27 ноября 2026 года для реализации в Sprint 3.** Редактор отправляет все подготовленные правки рабочей версии одним действием. Ответ подтверждает результат по линиям из команды. Полный состав сохранённых правок на момент чтения выдаёт `GET …/change-set`. Обсуждался и полный список в ответе на каждую запись. Его пришлось бы хранить для каждого повтора, а редактор всё равно перечитывает версию. [Текущие маршруты](../../apps/backend/utility_service/web_api/api/work_orders.py) · [Разбор ограничений реализации](day-1-analysis.md) · [План реализации](command-implementation-plan.md)

## Пример для ручной проверки

Открыть один штатный `WO-001` без сохранённых правок. На `L-003` сдвинуть среднюю вершину. На прямой `L-002` вставить первую внутреннюю вершину с видимым изгибом. Обе линии сохраняют исходные концы, включая общий `J-003`. Редактор выбирает положения вершин на карте. Для сравнения после отката используются фактически сохранённые координаты. UUID наряда, рабочей версии и токен брать из текущего сеанса. UUID обеих линий и их исходные координаты приведены в [разборе примера](day-1-analysis.md). ## Запись

Маршрут — `PUT /api/v1/work-orders/{workOrderId}/edit-versions/{editVersionId}/feature-geometries`. Один и тот же маршрут обслуживает одну или несколько линий. Тело JSON содержит `commandId` (UUID), `draftVersionToken` (непустая строка с прочитанной ревизией) и непустой массив `features`. Каждый элемент содержит уникальный в запросе `featureId` (UUID) и `geometry` (полный GeoJSON `LineString` в EPSG:4326, упорядоченные конечные числовые пары XY).

Шаблон тела для двух черновиков показан на JavaScript. Переменные `draftL003` и `draftL002` содержат полные геометрии после редактирования, `token` взят из согласованного чтения карты и состава изменений. При первой отправке клиент фиксирует идентификатор, токен и обе геометрии для возможного повтора.

```javascript
const save = {
  commandId: crypto.randomUUID(),
  draftVersionToken: token,
  features: [
    { featureId: "6c13a4d8-8d67-4fb3-a1f9-4ea5ab7f0213", geometry: draftL003 },
    { featureId: "6c13a4d8-8d67-4fb3-a1f9-4ea5ab7f0212", geometry: draftL002 }
  ]
}
```

Для отката редактор создаёт новую команду с актуальным токеном и одним элементом в `features`. В `geometry` передаётся точная исходная геометрия выбранной линии из `GET …/features/{featureId}/baseline`, поле `baselineGeometry`. Если откатывается вставка, эта геометрия содержит обе исходные точки. Линии, отсутствующие в команде, сохраняют текущее состояние. Третью подходящую линию можно сохранить позднее или сразу передать три подготовленные линии одной командой. Ограничения в две изменённые линии на рабочую версию нет.

Сервер проверяет доступ редактора к открытой рабочей версии, принадлежность и допустимость **каждой** линии. Применяется политика точности рабочей версии. Итоговые линии должны лежать в области наряда, сохранять порядок и исходные концы, иметь простую геометрию без вырожденных сегментов. Первая вставка допускает переход от двух вершин к трём, возврат к исходной форме восстанавливает оригинал из снимка с его точностью. Исходный снимок и учтённые соединения сохраняются во всех переходах. ## Ответ записи и отдельное чтение

Успешный PUT возвращает HTTP 200. Например, обе правки были сохранены в ревизии `"2"`, затем редактор откатил `L-003`. Пример ответа на **откат** использует штатные исходные координаты. Идентификатор команды и токены приведены для иллюстрации.

```json
{
  "commandId": "30bb272c-17b1-4a34-b5c2-7bf673fb3e1b",
  "commandState": "succeeded",
  "draftVersionToken": "3",
  "features": [
    {
      "featureId": "6c13a4d8-8d67-4fb3-a1f9-4ea5ab7f0213",
      "operation": "unchanged",
      "geometry": {"type": "LineString", "coordinates": [[65.520, 44.820], [65.525, 44.8205], [65.530, 44.820]]}
    }
  ],
  "hasPersistedChangeSet": true,
  "basicValidation": {
    "geometryStatus": "passed",
    "aoiStatus": "passed",
    "positionalAccuracyStatus": "POSITIONAL_ACCURACY_UNVERIFIED",
    "dirtyRelativeToBaseline": "passed"
  }
}
```

В ответе один элемент на каждую переданную линию с её фактически записанной или уже сохранённой канонической геометрией. `operation` показывает отличие этой линии от исходного снимка. Значения `hasPersistedChangeSet` и `basicValidation` относятся ко всей версии на момент завершения команды. После отката `L-003` они учитывают сохранившийся изгиб `L-002`. При пустом составе значения равны `false` и `null`. При непустом составе возвращается показанная выше сводка базовой проверки. [Действующие поля сводки](../../apps/backend/utility_service/use_cases/schemas/edit_version/geometry_contract.py)

`GET …/change-set` возвращает `draftVersionToken`, `hasPersistedChangeSet`, `basicValidation` и массив `changeSet`. При нуле правок массив пуст. При одной или нескольких в нём по одному элементу на каждую линию с сохранённым отличием. Так выглядит ответ после того же отката:

```json
{
  "draftVersionToken": "3",
  "hasPersistedChangeSet": true,
  "basicValidation": {
    "geometryStatus": "passed",
    "aoiStatus": "passed",
    "positionalAccuracyStatus": "POSITIONAL_ACCURACY_UNVERIFIED",
    "dirtyRelativeToBaseline": "passed"
  },
  "changeSet": [
    {
      "featureId": "6c13a4d8-8d67-4fb3-a1f9-4ea5ab7f0212",
      "operation": "updated",
      "vertexChange": "inserted",
      "vertexIndex": 1
    }
  ]
}
```

В `changeSet` значение `operation` равно `updated`. Поле `vertexChange` различает сдвиг существующей вершины (`moved`) и вставку (`inserted`). `vertexIndex` — индекс в текущей геометрии, с нуля. Для сдвига это также исходный индекс. Текущие геометрии и соединения читаются с карты (`GET` рабочей версии), оригинал выбранной линии — из её `baseline`. Массивы результатов записи и чтения упорядочены по UUID линии по возрастанию. Редактор сопоставляет линии по UUID и применяет карту и состав изменений только при совпадении их токенов. При расхождении повторяет чтение. [API рабочей версии](../../apps/backend/utility_service/web_api/api/work_orders.py)

## Ноль, одна и две правки в одном наряде

Токены в таблице иллюстрируют прогон с исходной ревизией `"1"`. Клиент использует токен сервера. На каждой строке GET перечисляет полный `changeSet`. После первого сохранения у `L-002` видна вставка, у `L-003` — сдвиг.

| Действие | Ответ PUT по переданным линиям | Последующее чтение версии |
| --- | --- | --- |
| Открыть чистый наряд | Записи нет | `"1"`, пустой массив, `false`, сводка `null` |
| Сохранить оба черновика командой A | `"2"`, обе итоговые геометрии, у обеих `updated`, флаг `true` | `"2"`, `L-002 inserted` и `L-003 moved` |
| Откатить `L-003` командой B | `"3"`, исходная `L-003 unchanged`, флаг `true` | `"3"`, только `L-002 inserted` с изгибом из ревизии `"2"` |
| Повторить A после B, включая перестановку линий в теле | Исходный ответ A с токеном `"2"` и обеими сохранёнными геометриями | `"3"`, только `L-002 inserted` |
| Откатить оставшуюся `L-002` командой C | `"4"`, исходная двухточечная `L-002 unchanged`, флаг `false`, сводка `null` | `"4"`, пустой массив |
| Повторить B после C | Исходный ответ B с токеном `"3"`, флагом `true` и одной `L-003 unchanged` | `"4"`, пустой массив |

Для обратного порядка отката автотест снова сохраняет обе линии из чистой версии. Затем возвращает `L-002` к двум исходным точкам. В GET остаётся одна `L-003 moved` с координатами из общего сохранения. Возврат последней линии очищает состав правок. Это проверки переходов одной рабочей версии. [Критерии А-02–А-05](acceptance-criteria.md)

## Атомарность, отказы и повтор

- Одно фактическое изменение версии, затрагивающее одну или несколько линий, прибавляет одну ревизию. В одной транзакции записываются геометрии, исход команды и событие этой ревизии со всеми фактически изменёнными линиями и их геометриями до и после. При возврате одной линии событие `change_set_cleared` допустимо только при полном опустошении состава изменений. Физическое хранение нескольких пар геометрий в событии выбирается при проектировании дня 3. [Текущая схема события](../../apps/backend/utility_service/infrastructure/postgresql/models/work_order/edit_version_change_event.py)
- Если после канонизации все переданные геометрии совпали с текущими, команда успешно возвращает их с прежним токеном, записывает свой исход и не создаёт событие. Если совпала только часть, ревизия увеличивается один раз, ответ перечисляет все переданные линии, а событие включает только фактические изменения.
- Пустой список, повтор одного UUID внутри списка или неверный формат геометрии дают `422 REQUEST_VALIDATION_ERROR` до регистрации команды. Недопустимая форма либо выход одной линии за область дают доменный отказ всей команды (`422 GEOMETRY_STRUCTURE_CHANGED`, `GEOMETRY_INVALID` или `GEOMETRY_OUTSIDE_AOI`). Сохранённый доменный отказ воспроизводится по прежнему идентификатору. Исправленная правка получает новый идентификатор. При техническом сбое внутри записи откатываются все записи этой попытки, включая изменения журнала. [Формат ошибок](../../apps/backend/utility_service/web_api/api/error_handling/work_order_edit_route.py) · [Проверки атомарности](../../apps/backend/tests/integration_tests/test_save_geometry_atomicity.py)
- Проверки текущего доступа, назначения редактора и открытого контекста действуют также при запросе записанного исхода. Правка недоступной линии отклоняет всю команду. При новой допустимой команде с устаревшим токеном ответ — `409 DRAFT_VERSION_STALE`. Редактор перечитывает карту и состав изменений. Ошибки сохраняют действующую оболочку `code`, `message`, `correlationId`. [Сценарий записи](../../apps/backend/utility_service/use_cases/services/edit_version_service.py)
- Один `commandId` обозначает одно намерение. Для распознавания повтора учитываются редактор, наряд, версия, исходный токен, идентификаторы линий и канонические геометрии по действующей политике точности. Перестановка **линий** допустима, порядок вершин каждой линии значим. Другой набор линий, геометрия или токен под занятым идентификатором даёт `409 COMMAND_ID_REUSED`. Точный повтор после проверки доступа возвращает сохранённый исход и его токен даже после последующих правок. Одновременная доставка той же команды также допускает только одно применение. [Правила идентичности команды](../../Wiki/value_objects/command_id.md)
- При потере ответа браузер сохраняет одну отправленную команду целиком в контексте редактора, наряда и версии. Для выяснения исхода используется повтор с прежним идентификатором и исходным токеном, затем независимое чтение актуального состояния. Вход другого пользователя изолирует черновики и отправленные команды. Вход, перезагрузка и восстановление связи сами по себе не дают согласия на новую запись. [Браузерные проверки восстановления](../../infra/m4/README.md)

## Совместимость с данными Sprint 2

Для автотеста А-07 в репозитории есть пример из прогона Sprint 2 на штатной `L-003` в `WO-001`. В `state.json` поле `originalRequest` содержит старую команду `ed787eca-76a7-41f1-a3e9-861b0a3eb995` с токеном `"1"`. В `saveResponse` записан исход с токеном `"2"` и полем `updatedFeature`. В `savedSnapshot` находятся сохранённая геометрия, исходный снимок, запись команды с отпечатком и событие. Эти поля дают конкретные значения для проверки совместимости. [Данные сохранения Sprint 2](../sprint_2/evidence/day-14/api-1d02f61f-38a5-47ec-a877-d7f18652c41c/state.json)

В изолированной БД тест начинает с состояния, созданного старым форматом до обновления. После обновления современный GET показывает одну `L-003 moved`. Команда Sprint 3 добавляет `L-002`, следующая возвращает `L-003` к исходной форме. GET показывает одну `L-002 inserted`. Старое тело и статус сравниваются с результатом повтора. [Критерий А-07](acceptance-criteria.md)

Старый `PUT …/features/{featureId}/geometry` при действующем доступе распознаёт повтор по прежним правилам отпечатка и исходному токену. Результат зависит от записи команды в журнале.

| Состояние старой команды | Ответ старого маршрута после обновления |
| --- | --- |
| Успех уже записан, поступил точный повтор | Сохранённые HTTP-статус и тело Sprint 2, включая прежний `updatedFeature`. |
| Записан отказ, поступил точный повтор | Сохранённые статус, код и сообщение отказа с `correlationId` текущего HTTP-запроса. Старый маршрут только читает этот исход, в том числе при прежнем `retry_on_access_change=true` и восстановленном доступе. Новая попытка сохранить правку возможна в формате Sprint 3 с новым идентификатором по явному действию редактора. |
| Впервые доставлена старая команда, идентификатор свободен | `422 LEGACY_COMMAND_NOT_ACCEPTED`. Идентификатор не резервируется. |
| Идентификатор занят другой командой или исходной командой другого формата | `409 COMMAND_ID_REUSED`. Формат входит в идентичность, в том числе когда на обоих маршрутах передана одна линия с той же геометрией. Правило действует в обе стороны. |

Старый маршрут сохраняет текущую геометрию, ревизию и историю событий. Если запись результата утрачена, но в истории есть событие с этим идентификатором, он занят и ответ — `409 COMMAND_ID_REUSED`. [Проверки прежнего повтора](../../apps/backend/utility_service/use_cases/tests/test_save_geometry_replay.py) · [Поля сохранённого исхода](../../apps/backend/utility_service/infrastructure/postgresql/models/work_order/edit_version_command.py)

Браузер читает прежнюю запись восстановления и отправляет исходную команду по старому адресу. При получении прежнего успешного ответа он перечитывает версию. Ответ `422 LEGACY_COMMAND_NOT_ACCEPTED` на старом маршруте завершает восстановление с известным отказом, даже если ранее ответ был потерян. Редактор может явно начать новое сохранение в формате Sprint 3. Автоматической пересылки старой команды в новый маршрут нет.
