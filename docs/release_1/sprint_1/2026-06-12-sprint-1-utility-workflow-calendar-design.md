# Спринт 1 Utility Workflow: План На 14 Календарных Дней

Дата: 2026-06-12
Статус: подтвержден пользователем

## Цель

Сформировать доменную основу нового Release 1 и реализовать первый рабочий участок сценария:

```text
Login -> Мои наряды -> Create/Open EditVersion -> Edit Workspace
```

К концу спринта `Editor` входит в систему, видит назначенный `WorkOrder`, создает или открывает связанную `EditVersion` и просматривает соответствующий участок utility network.

## Формат Спринта

- 14 календарных дней.
- Будние дни используются для основной разработки.
- Выходные являются облегченными днями для интеграции, документации, проверки и резерва.
- Ритм: 5 интенсивных дней, 2 облегченных дня, 5 интенсивных дней, 2 облегченных дня.
- План строится вертикально: работоспособный пользовательский сценарий расширяется от доменной основы к frontend workspace.

## Границы

### Входит

- роли `Editor` и `Reviewer`;
- separation of duties на уровне ролевой модели;
- demo users;
- базовые сущности utility network;
- воспроизводимый seed `synthetic_utility_feeder_01`;
- `WorkOrder`, назначение исполнителю и список назначенных задач;
- создание и повторное открытие `EditVersion`;
- workspace API;
- frontend `Мои наряды`;
- начальный `Edit Workspace` с AOI, сетью и состоянием version;
- интеграционная и демонстрационная проверка первого участка workflow.

### Не Входит

- изменение объектов или associations внутри `EditVersion`;
- validation;
- reconcile и conflict resolution;
- reviewer queue, approve/reject;
- post в `Default`;
- полный audit workflow;
- production-grade role administration.

`Reviewer` должен существовать как отдельная роль и demo user, но его пользовательский workflow реализуется в следующих спринтах.

## Подход

Выбран вертикальный подход. Backend и frontend развиваются вокруг одного пользовательского пути, а не отдельными длинными фазами. Это дает ранние контрольные точки и снижает риск обнаружить несовместимость API, seed и UI только в конце спринта.

## Контрольные Точки

- День 5: backend связывает пользователя, utility dataset и назначенный `WorkOrder`.
- День 9: создание и повторное открытие `EditVersion` работают устойчиво.
- День 12: доступен пользовательский вертикальный сценарий.
- День 14: сценарий воспроизводится после чистого demo seed.

## Ошибки И Защитное Поведение

- пользователь без роли `Editor` не получает editor workspace;
- `Editor` не видит чужой `WorkOrder`;
- нельзя создать `EditVersion` для чужого или недоступного work order;
- повторная команда открытия не создает дублирующую активную version;
- отсутствующий или некорректный seed выявляется интеграционной проверкой;
- API возвращает стабильные коды ошибок и достаточный workflow context для frontend.

## Проверка

Минимальный набор проверок спринта:

- role и assignment authorization tests;
- seed integrity test для базовой сети и work orders;
- создание `EditVersion`;
- идемпотентное открытие существующей version;
- workspace API contract test;
- frontend tests для списка work orders и перехода в workspace;
- один end-to-end smoke path на чистом seed;
- ручной demo в локальной Docker Compose среде.

## Критерий Завершения

Спринт завершен, если на воспроизводимых demo-данных:

1. `Editor` успешно входит в систему.
2. Видит только назначенный ему `WorkOrder`.
3. Создает новую или открывает существующую `EditVersion`.
4. Открывает workspace с корректными work order, AOI, version и utility network.
5. Повторное прохождение сценария после восстановления seed дает тот же результат.

Наличие моделей или отдельных endpoints без работающего пользовательского пути не считается завершением спринта.
