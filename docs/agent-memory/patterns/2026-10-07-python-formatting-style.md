## Summary

При написании и форматировании кода на любых языках проекта применять правила
ниже, если это допускают синтаксис и семантика языка, его линтеры и настроенный
в проекте форматтер. При конфликте приоритет имеют правила языка и его
инструментов; не отключать проверки и не менять их конфигурацию ради этого стиля.
Например, в JSON завершающие запятые запрещены и добавлять их нельзя.
Настройки Black, включая длину строки, относятся только к Python и не переносятся
автоматически на другие языки.

Ориентироваться на стиль коммита
`4bde517ce42125e60776f27cb6679851b93a6f75`: аргументы вызовов с несколькими
аргументами и параметры функций с несколькими параметрами располагать по одному
на строку, оставляя завершающую запятую перед закрывающей скобкой. Закрывающая
скобка — на отдельной строке. Словари и аналогичные объекты других языков,
в том числе вложенные, оформлять
многострочно, с отдельной строкой для каждого элемента и завершающей запятой.
Проверять также SQL в отдельных файлах и внутри строк на любом языке: длинные
запросы и списки колонок оформлять многострочно с ровными отступами.
Black содержимое SQL-строк не обрабатывает.

```python
await insert_running_command(
    connection,
    context,
    command_id,
)

async def save_change(
    session,
    command_id,
):
    ...

params = {
    "id": command_id,
    "context": {
        "edit_version_id": edit_version_id,
    },
}
```

Короткие вызовы с одним аргументом могут оставаться в одну строку. Не нужно
механически разносить каждую компактную tuple/list fixture: в эталонном коммите
такие элементы параметризации также встречаются в одну строку.

## Context

Пользователь явно выбрал этот коммит как образец и попросил сохранить правило
для будущей работы. Одного запуска Black недостаточно: без завершающих запятых
он допускает компактные вызовы, которые пользователь попросил раскрывать.
Запятая сохраняет выбранную многострочную форму при последующем Black.

`apps/backend/pyproject.toml` задаёт Black line-length 100 и target-version
py312, но не фиксирует это предпочтение по компоновке. Эта запись объясняет
дополнительное правило, которое нельзя вывести только из конфигурации formatter.
По явному уточнению пользователя применять это предпочтение к новому и
изменяемому коду на всех языках проекта с указанными выше ограничениями.
Не переформатировать несвязанные файлы без задачи.

## Verification

Для каждого затронутого языка использовать его проектные проверки форматирования
и линтеры. Проверять, что переносы строк, отступы и запятые не меняют семантику,
особенно в языках со значимыми отступами или переносами строк.

Образец проверяется через `git show` указанного коммита для файлов из
`Related files`. Проверки форматирования backend: `python -m black --check .`
и `python -m ruff check .` из `apps/backend`, затем `git diff --check` из корня.
Использовать доступное проектное Python/Docker-окружение.

При массовом изменении только форматирования сравнивать Python AST до и после,
чтобы подтвердить неизменность логики. При форматировании SQL допустимы только
пробелы и переносы вне quoted literals; SQL-токены, значения и параметры должны
сохраниться. Для этой части сравнивать SQL-токены и запускать соответствующие
DB tests. Не менять defaults, annotations или поведение под видом форматирования.
