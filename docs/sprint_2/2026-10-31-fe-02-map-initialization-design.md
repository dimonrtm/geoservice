# FE-02 — ошибка первоначального запуска карты

Дата: 2026-10-31. Статус: принят пользователем («Принимаю»).

Основания: [анализ и ответы FE02-Q01–Q07](2026-10-31-fe-02-map-initialization-analysis.md), [согласованный макет](fe-02/visual/content/map-startup-error-v1.html), [исходное ревью](frontend-review.md).

## Цель и размер изменения

Небольшое frontend-изменение: пользователь видит ошибку первоначального запуска карты и понимает, что страницу нужно обновить средствами браузера. Команды редактирования и восстановления не предлагаются до готовности карты. Backend, контракты API и доменная модель не меняются.

## Согласованное поведение

- В режимах `workspace`, `empty` и `editing` при ошибке первоначального запуска на месте карты показывается одно сообщение: **«Не удалось запустить карту»**, ниже **«Обновите страницу с помощью кнопки обновления в браузере.»**
- Расположение и текст соответствуют согласованному макету. Список нарядов в макете иллюстративный; переделывать его не требуется.
- У сообщения нет кнопок повторения или обновления. Автоматический retry и автоматическая перезагрузка отсутствуют.
- До готовности карты, включая ожидание запуска, команды скрыты. В workspace скрыта вся `WorkspaceEditCommands`, в том числе её действия восстановления неизвестного исхода и повторного чтения current. В legacy editing скрыта собственная панель редактирования.
- После готовности карты команды появляются с прежними ограничениями прав, draft и recovery. Готовность карты не разрешает запрещённые доменной логикой действия.
- Изменение видимости не сбрасывает localDraft, pending operation или recovery state, не отправляет Save/Revert и не создаёт новый CommandId.

## Подходы

**Выбран пользователем: локальное состояние в `MapView` с уведомлением родителя.** Компонент карты отвечает за первоначальную готовность и сообщение ошибки. `EditorWorkOrdersView` получает уведомление и управляет видимостью отдельной панели команд. Это сохраняет состояние renderer рядом с его экземпляром; цена — явная передача готовности между компонентами.

**Рассмотрен: общее состояние в Pinia.** Позволяет независимым компонентам читать readiness напрямую, но требует глобального состояния и правил его сброса. Для текущего числа потребителей преимущество не оправдывает усложнения. Простое снятие условия с badge не удовлетворяет требованию скрывать команды.

## Технические решения автора дизайна

Эти детали уточняют выбранный подход, а не приписываются ответам пользователя.

1. Использовать локальное состояние первоначального запуска `loading / ready / error`; DOM-контейнер карты сохраняется во время запуска и показа сообщения. Ошибка показывается отдельным элементом с `role="alert"`, а не через общий `labelText`. Сообщение читабельно на узком экране и при увеличении масштаба; само не перемещает фокус.
2. Отделить отказ `createMap()` от последующей загрузки legacy-слоёв/features. Ошибку запроса данных после успешного создания renderer нельзя автоматически объявлять ошибкой запуска карты. Для workspace готовность команд наступает после успешной первичной отрисовки workspace; её синхронная ошибка тоже не должна оставлять пустой экран без сообщения. В `empty` достаточно успешного `createMap`; в `editing` сохраняются существующие шаги подключения редактирования, без преждевременного показа команд до их завершения. Отсутствие слоёв — существующее штатное состояние, не ошибка запуска renderer.
3. Сообщать родителю готовность текущего экземпляра карты. Начальное значение у родителя — false. При замене/удалении экземпляра не наследовать прежнюю готовность; позднее завершение удалённого компонента не должно открывать панель команд. Повторный readback для того же уже готового экземпляра не требует искусственного перезапуска карты.
4. Скрывать посторонние legacy badge/status поверх сообщения ошибки. В успешном workspace прежний информационный badge остаётся скрытым. Не добавлять новую индикацию бесконечного ожидания в рамках FE-02.
5. Не превращать локальную готовность в доменный guard Pinia. Существующие ограничения Save/Revert/recovery сохраняются независимо от отображения панели. Список нарядов, детали workspace и панель сравнения не переделываются в рамках этой задачи.

## Границы и нежелательные результаты

Вне задачи: timeout или отмена ожидания `load` внутри `useMapInstance`, обработка всех MapLibre error events, отказ OSM tiles, потеря WebGL после успешного запуска, исправление watcher FE-03 и FE-04. Защита от позднего уведомления удалённого компонента нужна только для корректности добавляемого состояния готовности и не означает переработку lifecycle карты целиком.

Недопустимо скрыто очищать данные при ошибке, подменять неизвестный исход сохранения отказом, показывать команды по готовности старой карты или показывать одну ошибку одновременно в нескольких badge. Обновление страницы остаётся явным действием пользователя; новая гарантия сохранения обычного несохранённого draft не вводится.

## Приёмочные проверки

| Сценарий | Ожидаемый результат |
| --- | --- |
| Rejected `createMap` в каждом из трёх режимов | Один доступный alert с согласованным текстом; нет кнопки retry и команд редактирования |
| `createMap` ещё ожидается | Команды workspace и legacy editing скрыты |
| Успешная первоначальная подготовка | Команды появляются с прежними ограничениями; успешный workspace без legacy badge |
| Workspace с recovery state и ошибка карты | Вся панель команд скрыта; state не очищен и новые mutation-запросы не отправлены |
| Замена/удаление карты, затем поздний результат старого запуска | Старая готовность не открывает панель нового экземпляра |
| Ошибка legacy API после успешного создания renderer | Не выдаётся за отказ создания renderer; существующее сообщение загрузки данных сохраняет свой смысл |
| Первичная отрисовка workspace выбрасывает исключение | Видимое сообщение запуска; команды остаются скрыты |
| Браузерный отказ WebGL при первом запуске | Сообщение видно в области карты, команды отсутствуют; после ручного обновления при исправном WebGL карта и команды доступны |

Проверки реализации: component/view regression tests с управляемым Promise и состоянием Pinia, typecheck и релевантные существующие frontend-тесты. Браузерная проверка отдельно от mocks: отказ WebGL, нормальное обновление, узкий экран и масштаб 200%. Реальные браузерные проверки и screen reader не объявлять выполненными на основании DOM-assertions.

## Что остаётся плану реализации

Имена событий и переменных, точное разбиение тестов, CSS в рамках согласованного макета и способ воспроизводимого браузерного отказа. План должен сохранить указанные границы и проверить готовность отдельно для всех трёх режимов. Код до согласования дизайна не меняется. После согласования следующий этап — `superpowers:writing-plans`; Git staging, commit и push выполняет только пользователь.
