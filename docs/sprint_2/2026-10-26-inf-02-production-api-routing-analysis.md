## Подтверждённая цепочка отказа

1. [http.ts](../../apps/frontend/src/api/http.ts) создаёт Axios client с `baseURL: import.meta.env.VITE_API_BASE_URL ?? "http://localhost:8000"`. Значение относится к запросам браузера посетителя.
2. [Dockerfile](../../apps/frontend/Dockerfile) выполняет `npm run build`, копирует `dist` в nginx и запускает nginx. Явной передачи API URL через build ARG/ENV и собственного proxy configuration нет.
3. [Base Compose](../../infra/docker-compose.yml) публикует `frontend-prod` как `8080:80`, но не публикует порт `utility_service`. Frontend зависит от health API; это связь старта контейнеров, а не маршрут браузерных запросов.
4. Без входного `VITE_API_BASE_URL` frontend обращается к порту 8000 машины посетителя. Base Compose этот путь не обеспечивает. Даже при браузере на Docker host API-порт базовым Compose не опубликован.
5. [Demo override](../../infra/docker-compose.demo.yml) отдельно публикует API 8000 и задаёт URL для `frontend-dev`. Работа dev-режима не подтверждает исправность production bundle.

Следствие: доступная страница nginx и healthy API могут сосуществовать с неработающим login, списком нарядов и workspace. При заданном локальном build-time env результат может отличаться; это не доказательство работоспособности чистой сборки.

## Связанные технические контракты

### Авторизация

[auth.ts](../../apps/frontend/src/api/auth.ts) использует `/api/v1/auth/login`, `/api/v1/auth/session/refresh`, `/api/v1/auth/logout` с `withCredentials: true`; `/api/v1/auth/me` использует общий HTTP client. Общий interceptor добавляет Bearer token и обрабатывает auth failures.

[Backend auth](../../apps/backend/utility_service/web_api/api/auth.py) устанавливает и удаляет session cookie с `HttpOnly`, `Path=/api/v1/auth`, настраиваемыми Secure/SameSite. [Settings](../../apps/backend/utility_service/utils/settings.py) требует Secure в production; SameSite по умолчанию `lax`. [Принятое решение INF-01](2026-10-26-inf-01-production-cookie-design.md) уже закрепило Secure=true в base и false в demo. Оно явно исключило HTTPS termination, сертификаты, browser login/refresh, routing и новый CI gate из объёма INF-01. Исключение из INF-01 само по себе не задаёт объём INF-02.

[Backend main](../../apps/backend/utility_service/web_api/main.py) разрешает credentials в CORS, использует список origins из Settings и ограниченный список методов/заголовков. Base Compose по умолчанию задаёт HTTP localhost origins. `/health` возвращает константный ответ без проверки БД. Поэтому проверки `/` и `/health` недостаточны для доказательства полной авторизованной работы.

### WebSocket

[useLayerRealtime.ts](../../apps/frontend/src/composables/map/useLayerRealtime.ts) вычисляет WebSocket URL отдельно: использует `VITE_API_BASE_URL`, затем Axios baseURL; понимает абсолютные HTTP(S)/WS(S) адреса, иначе возвращает `ws://localhost:8000`. Значит, изменение одного HTTP baseURL не гарантирует согласованного WebSocket пути.

Ticket запрашивается через HTTP по `/api/v1/ws/layers/{id}/ticket`, соединение открывается по `/api/v1/ws/layers/{id}`. `LEGACY_GIS_API_ENABLED` по умолчанию false. Поддержка транспортного пути и включение legacy API — разные вопросы. Включение legacy не следует автоматически из рекомендации ревью поддержать WebSocket.

### Воспроизводимость сборки и проверки

Dockerfile делает `COPY . .` после установки dependencies; отсутствие frontend `.dockerignore` зафиксировано отдельной INF-03. Влияние локального env на сборку пересекается с доказательством INF-02, но объединение задач пока не согласовано. Значения локальных env не читались.

[CI](../../.github/workflows/ci.yml) содержит frontend build/test и backend production image build; существующие API smoke используют demo Compose и запросы из контейнера. Они не доказывают браузерный маршрут через production nginx. Изменение CI в INF-02 пока не согласовано; INF-04 остаётся отдельной находкой.

## Исходная очередь уточнений

1. Что означает production в результате INF-02: безопасный контейнерный baseline для дальнейшего развёртывания или уже самостоятельно запускаемый HTTPS-стенд с браузерной авторизацией?
2. После определения результата: какие ограничения есть на публичные адреса и место завершения HTTPS; должен ли образ переноситься между адресами без пересборки?
3. Нужна ли приёмка WebSocket при явно включённом legacy API или достаточно текущего workflow Sprint 2?
4. Насколько полно подтверждать пользовательский путь: login/refresh/logout, workspace, Save/readback/Revert; нужна ли автоматическая проверка в CI?
5. Входит ли минимальная защита чистоты frontend build в этот объём или INF-03 реализуется отдельно?

Это очередь уточнений, а не выбранная архитектура или дополнительные принятые требования. Вопросы будут задаваться по одному; последующие могут отпасть после ответов.

## Вопрос 1

Какой результат ожидается от INF-02: рабочий маршрут frontend → API в production-safe Compose с явно описанными внешними условиями HTTPS, либо самостоятельный HTTPS-стенд, на котором сразу проверяются браузерные login, восстановление сессии и работа редактора?

Ответ пользователя: **вариант 1**. INF-02 обеспечивает рабочий маршрут frontend → API в production-safe Compose; HTTPS остаётся внешним условием развёртывания. Самостоятельный HTTPS-стенд не входит в ожидаемый результат. Конкретная архитектура маршрутизации этим ответом не выбрана.

## Вопрос 2

Должен ли один и тот же собранный production frontend работать при смене публичного домена или порта без пересборки, либо допустима отдельная сборка для каждого адреса развёртывания?

Пользователь спросил о сравнительной сложности. После объяснения различий между общим адресом и отдельным доменом API уточнён вопрос: нужна ли поддержка разных публичных доменов frontend/API?

Ответ пользователя: **достаточно одного общего адреса сайта**. Поддержка разных публичных доменов не требуется. Прямого ответа об обязательной переносимости образа без пересборки пока нет; общий адрес допускает такую переносимость, но конкретный способ реализации ещё не выбран.

## Вопрос 3

Нужно ли в INF-02 обеспечить и проверить существующий WebSocket-маршрут при явно включённом legacy GIS API, либо ограничить задачу HTTP API текущего редактора Sprint 2?

Контекст: инфраструктурное ревью упоминает WebSocket, однако ТЗ Sprint 2 исключает realtime broadcast из объёма. Backend по умолчанию отключает legacy GIS API. Поддержка маршрута не означает включение legacy API по умолчанию или добавление realtime в Save/Revert.

Ответ пользователя: **также существующий WebSocket-маршрут**. В INF-02 входят HTTP API и обеспечение/проверка существующего WebSocket-маршрута. Это не расширяет текущий Save/Revert до realtime broadcast и не меняет отключение legacy GIS API по умолчанию; для проверки разрешённого соединения потребуется явно включённый legacy API в изолированном проверочном окружении.

## Вопрос 4

Достаточно ли для приёмки INF-02 воспроизводимой локальной проверки production-маршрутов HTTP и WebSocket, либо такую проверку нужно также включить в CI как обязательную проверку изменений?

Контекст: в INF-01 пользователь выбрал локальную проверку без нового CI gate. Этот выбор относился к INF-01 и автоматически на INF-02 не переносится. Существующий CI не подтверждает путь через production nginx.

Ответ пользователя: **достаточно воспроизводимой локальной проверки**. Новый обязательный CI gate не входит в INF-02. Глубина локальной проверки уточняется отдельно.

## Вопрос 5

Какова требуемая глубина локальной приёмки: авторизованный HTTP-путь через frontend (login, refresh/logout, чтение списка нарядов и workspace) и успешное WebSocket-соединение либо дополнительно полный цикл Save → readback → Revert через тот же публичный адрес?

Речь о проверке реального API в изолированном окружении. Способ проверки cookie и браузерного поведения при внешнем HTTPS будет явно описан в спецификации; успешный HTTP-клиент сам по себе не доказывает браузерные правила Secure/SameSite. Выбор глубины не возвращает самостоятельный HTTPS-стенд в объём задачи.

Ответ пользователя: **вариант 2**. Локальная приёмка включает вход, восстановление сессии, выход, чтение нарядов/workspace, успешное WebSocket-соединение и полный цикл Save → чтение сохранённого результата → Revert через общий публичный адрес. Новый CI gate и самостоятельный HTTPS-стенд по-прежнему вне объёма.

## Вопрос 6

Включить ли в INF-02 минимальную защиту production-сборки frontend от локальных `.env*`, `node_modules` и `dist`, либо оставить её целиком отдельной задаче INF-03 и проверять INF-02 на специально очищенном build context?

Основание вопроса: текущий Dockerfile копирует весь frontend context. Локальный `VITE_API_BASE_URL` может повлиять на собранный адрес API; поэтому воспроизводимость маршрута пересекается с INF-03. Это уточнение границ работ, а не принятие способа исправления. Содержимое локальных env-файлов не требуется.

Ответ пользователя: **оставляем отдельной задачей INF-03**. Защита build context от локальных env/dependencies/artifacts не входит в исправление INF-02. Проверка INF-02 выполняется на чистом build context; результат не должен трактоваться как устранение INF-03 или гарантия сборки из загрязнённого рабочего дерева.

## Вопрос 7

Достаточно ли размещения сайта в корне публичного адреса (`https://example.test/`) либо нужна поддержка вложенного пути (`https://example.test/geoservice/`)?

Основание: frontend API использует пути `/api/v1/...`; WebSocket URL также строится от корня, Vite config не задаёт отдельный base path. Общий публичный адрес сам по себе не определяет необходимость размещения под префиксом. Вопрос касается требуемого сценария развёртывания, а не выбора proxy implementation.

Ответ пользователя: **достаточно сайта в корне адреса**. Поддержка размещения frontend под `/geoservice/` не требуется. Перед ответом разъяснено: разделение запросов между будущими микросервисами не требует переноса самого сайта во вложенный путь. Разбиение backend на микросервисы не входит в задачу.

## Итог анализа

Семь последовательных уточнений определили границы задачи. Дальнейших вопросов к пользователю, блокирующих предложение решения, нет. Конкретные технические механизмы и численные параметры проверок — предмет предлагаемой спецификации, а не дополнительные доменные требования.

Рекомендуемый подход и локальная матрица приёмки приведены в [предложении решения](2026-10-26-inf-02-production-api-routing-design.md). Переносимость чистого production-образа между публичными адресами предложена как следствие использования текущего origin, а не как дословно подтверждённое отдельное требование пользователя.

Дополнительная проверка кода установила:

- WebSocket endpoint отправляет `connected` после успешного ticket authentication; это наблюдаемый критерий реального соединения, сильнее проверки одного HTTP 101.
- Ticket выдаётся с проверкой legacy feature flag; consume проверяет одноразовость, слой, TTL и актуальные права пользователя. Проверка маршрута должна сохранить эти условия.
- `infra/m4/compose.yml` использует dev targets и отдельный API port, поэтому существующая M4-приёмка не доказывает исправность production nginx.
- `full_path_workspace_smoke.py` принимает `GEOSERVICE_BASE_URL`; его сценарии могут быть источником проверок, но запросы должны идти через frontend origin. Один API smoke не проверяет адреса, вычисленные production JavaScript.

Технические факты дополнительно сверены с документацией Vite, nginx и MDN; ссылки и их вклад указаны в предложении. Runtime-проверки по-прежнему не выполнялись. Анализ не объявляет INF-02 исправленной.
