## Цель и принятые требования

Две вкладки одного браузера должны восстанавливать вход без гонки ротации общей cookie. Все вкладки используют один аккаунт, но сохраняют независимый рабочий контекст. Успешный выход отзывает все токены данного входа в браузере; другие браузеры и устройства, в том числе того же пользователя, продолжают работать.

Пользователь выбрал второй подход и отдельно потребовал: «после выхода все токены этого браузера должны сразу стать недействительными».

- При наличии действительного входа новая вкладка восстанавливается автоматически, иначе показывает login.
- После подтверждённого сервером выхода остальные работающие вкладки этого браузера автоматически показывают login не позднее 5 секунд. Приостановленная вкладка проверяет состояние до возобновления защищённых действий.
- Если запрос выхода не дошёл до сервера, текущий вход сохраняется; показывается «Не удалось выйти, попробуйте ещё раз». Автоматического отложенного выхода нет.
- При фактической потере нового refresh token после серверной ротации повторный login допустим. Это исключение не применяется к штатной гонке вкладок.
- Поддерживаются актуальные Chrome, Edge и Firefox на компьютерах и ноутбуках. Мобильные устройства вне объёма.
- Техническая блокировка WorkOrder не нужна. Требования её удержания и освобождения за 2 секунды отменены. Действующие stale/token/access/lifecycle guards сохраняются.

Под «браузером» в реализации понимается один профиль и раздел хранения сайта для одного origin. Другой профиль, приватный контекст или другой браузер имеет отдельную cookie и отдельный вход. Отпечаток устройства не собирается. Это техническая конкретизация автора дизайна, а не ранее сформулированная пользователем деталь.

## Подходы и выбор

| Подход | Что обеспечивает | Ограничения |
| --- | --- | --- |
| Координация вкладок без изменения backend | Упорядочивает refresh/login/logout, синхронизирует UI выхода | Уже выданный access JWT принимается сервером до exp; пользователь это ограничение отверг |
| Координация вкладок и отдельная серверная сессия браузера | Всё выше плюс отзыв access/refresh/ticket конкретного входа | Нужны изменения схемы, auth dependencies, миграция и интеграционные проверки |

Выбран второй подход. Одна логическая авторизация браузера не означает неизменный секрет навсегда: refresh token продолжает ротироваться, access JWT может обновляться, но все они принадлежат одной отзываемой сессии. Токены не объединяются по user id между устройствами.

## Объём и исключения

Работа затрагивает frontend auth, backend auth/persistence, WebSocket ticket admission и тесты. Это больше исходного исправления одной гонки, поэтому требуется полный дизайн и последующий план.

Не входят: блокировки WorkOrder, общий login для разных браузеров, глобальный logout пользователя, автоматический refresh на каждый рабочий 401, новый offline mode, автоматическое сохранение локальной правки, переработка очередей realtime из AR-02, распределённый брокер или изменение геометрических инвариантов.

Недопустимые результаты: отправка двух штатных refresh с одним старым cookie; принятие токена отозванной сессии при новой проверке; завершение входа другого браузера; воскресший вход после позднего ответа; потеря identity отправленного Save/Revert из-за смешения logout и результата команды.

## Модель серверной сессии

Технический выбор автора: добавить родительскую сущность `BrowserAuthSession`, сохранив существующие `AuthSession` rows как историю одноразовых refresh credentials.

| Данные | Назначение |
| --- | --- |
| `BrowserAuthSession.id` (`sid`) | Стабильный UUID одного входа конкретного браузера |
| `user_id` | Аккаунт владельца; не ключ общего выхода со всех устройств |
| `created_at`, `expires_at`, `revoked_at` | Срок действия и окончательный отзыв |
| `AuthSession.browser_session_id` | Связь каждого поколения refresh token с родительской сессией |
| `WebSocketTicket.browser_session_id` | Связь ticket с той же сессией |

Refresh secret хранится в БД только как hash и передаётся браузеру только HttpOnly cookie. `sid` не является credential и сам по себе не даёт доступа. Уникальность hash и single-use ротация сохраняются. Нужны FK и индексы по родительской сессии; repository не должен допускать несовпадение user id credential и родителя.

Access JWT содержит подписанный `sid` наряду с существующими `sub`, `role`, `iat`, `exp`. Login/refresh response дополнительно возвращает `session_id`, чтобы frontend не разбирал JWT ради идентичности сессии. Frontend хранит access JWT только в памяти; в localStorage не появляются access/refresh secrets.

При refresh родительский sid остаётся прежним, старый refresh credential отзывается, создаётся новый. Текущий скользящий срок refresh сохраняется: успешная ротация обновляет срок родителя и нового credential по существующему `auth_session_ttl_hours`. Срок access JWT не увеличивается сверх собственной настройки. Отозванный родитель никогда не активируется повторно.

## Login, refresh и logout на сервере

### Login

После успешной проверки пароля создать новую браузерную сессию, refresh credential и access JWT с новым sid. Если переданная cookie относится к известной прежней сессии этого браузера, прежняя сессия отзывается в той же транзакции. Это относится и к повторному входу того же пользователя. Ошибка пароля не отзывает прежний вход.

При отсутствии cookie сервер не угадывает устройство по IP, user agent или user id и не отзывает другие сессии пользователя. Потеря/очистка cookie не позволяет серверу восстановить связь с прежним браузером; такие оставшиеся сессии ограничены сроком действия. Это граница идентификации браузера, не глобальная уникальность аккаунта.

### Refresh

По hash найти credential и его sid; заблокировать строку родителя, затем повторно проверить активность родителя, credential, срок и пользователя. Только после этого выполнить условную single-use ротацию. Порядок блокировок един для refresh/logout/replacement-login: родитель, затем дочерние credentials.

Два прямых запроса с одним credential по-прежнему дают не более одного успеха. Штатный frontend предотвращает такую отправку координацией вкладок. Сохранение старого токена в качестве допустимого повторного refresh и grace period не вводятся.

### Logout

Logout адресует конкретный ожидаемый `session_id`, а не «текущий user id». Сервер проверяет принадлежность предъявленного credential этому sid; одного sid в body недостаточно. Допускается доказательство через подписанный access JWT этой сессии или известный refresh secret, включая уже ротированное поколение, поскольку повторное прекращение той же сессии безопасно. Политика допустимого срока такого доказательства ограничена сроком предъявленного JWT либо сроком родительской сессии для refresh history; детали проверяются тестами без разрешения refresh по старому secret.

Сервер под блокировкой родителя устанавливает `revoked_at` и завершает транзакцию. Все его дочерние credentials и tickets становятся непригодными через проверку родителя, без зависимости от массового UPDATE каждой строки. Повторный logout той же отозванной сессии идемпотентен при достаточном доказательстве принадлежности.

Logout не возвращает `Set-Cookie`, в том числе команду удаления: он отзывает серверную сессию, а недействительная HttpOnly cookie остаётся до следующего login или собственного expiry. Это сознательный технический выбор после builder check: поздний ответ logout не может стереть cookie более нового входа. Оставшийся secret не даёт ни refresh, ни доступа. При несовпадении нельзя молча перенаправлять logout на новый sid. После подтверждённого отзыва API возвращает идентификатор завершённой сессии.

### Read-only состояние конкретной сессии

Добавить `POST /api/v1/auth/session/status` с ожидаемым `session_id`. Он не ротирует и не устанавливает cookie, не продлевает сессию и не выдаёт credentials. Результат содержит только sid и состояние `active` / `ended`. `ended` означает отсутствующего/отозванного/истёкшего родителя либо невозможность доступа отключённого/удалённого владельца, а не истечение одного access JWT.

Доказательство принадлежности — JWT с корректной подписью и совпадающим sid/sub; только для этого узкого endpoint допускается истёкший exp. Остальные проверки формата/алгоритма обязательны, JWT без sid не подходит. Альтернатива — известный refresh secret, чей hash связан с запрашиваемым sid; более новый cookie другого sid не используется как доказательство старой сессии. `session_id` без такого доказательства недостаточен. Ответ не содержит пользователя, данных WorkOrder или нового access token. Разрешение проверить статус истёкшим JWT не разрешает им logout, refresh или бизнес-запросы.

Status читается из актуальной БД без положительного cache. Удаление уже истёкшей/отозванной родительской записи не превращает доказанную старую сессию в `active`. Ошибка связи/БД даёт неизвестность, а не `ended`. Этот endpoint используется при пропущенных уведомлениях и для reconciliation; `/auth/me` для доказательства server-side отзыва не используется.

## Момент отзыва и проверка access JWT

Линеаризация выхода — commit транзакции, отзывающей родителя. Любая новая проверка авторизации после этого commit должна отклонять все access JWT данного sid, даже если их exp ещё не наступил. Отзыв не зависит от доставки браузерных уведомлений.

Общая auth dependency проверяет подпись/срок JWT, обязательный sid, совпадение `sub` с владельцем родителя, активность родителя и текущего пользователя. Отсутствующий/неизвестный/отозванный sid даёт существующий `AUTH_REQUIRED`/401; отключение пользователя сохраняет `USER_INACTIVE`/403. Ошибка БД не превращается в разрешение доступа или ложный окончательный 401.

Не использовать положительный cache активности сессии, который допускает доступ после logout. Проверка читает актуальное состояние БД в короткой транзакции; не следует разделять долгоживущий snapshot с ранее начатой бизнес-операцией. Выделить auth read session либо явно закончить её транзакцию до use case, не создавая конфликт SQLAlchemy autobegin с существующими `session.begin()`.

Запрос, который прошёл проверку до commit logout, может завершиться после него. Уже отправленный Save/Revert не отменяется выходом, подтверждённая запись не откатывается. Это граница новых проверок, не обещание отменить уже допущенные операции. Тесты различают запрос до и после commit.

## WebSocket tickets и существующие соединения

При выдаче ticket сохранить sid проверенного access context. При consume ticket проверить родительскую сессию; одноразовое потребление и проверку выполнять в согласованном порядке транзакции. Ticket от завершённого входа не открывает новое соединение, даже если его собственный TTL ещё не истёк.

`WebSocketUserContext` получает sid. В текущем single-worker deployment после commit logout manager закрывает соединения этого sid; другой sid того же пользователя не затрагивается. Успешный отзыв не откатывается из-за ошибки закрытия сокета. Перед новыми прикладными отправками проверяется активность соответствующей сессии, чтобы ошибка доставки close не оставляла канал данных отозванного входа. Уже допущенная отправка может завершиться как операция до границы отзыва.

Новые подключения должны перепроверять сессию непосредственно перед admission, а не полагаться только на ранее потреблённый ticket. Отдельно проверить гонку logout между consume и connect. Не использовать legacy layer websocket как обязательный канал auth-уведомлений frontend: legacy GIS может быть выключен.

Гарантия немедленного server-side отказа новых подключений обеспечивается БД на любом worker. Активное закрытие уже открытых сокетов в этом изменении проверяется для существующего single-worker deployment; межпроцессный broadcast остаётся за пределами AR-01 и должен быть отмечен в runbook.

## Координация вкладок

Технический выбор автора: общий Web Lock для операций login/refresh/logout одного frontend origin; BroadcastChannel для уведомлений и запись не содержащего секретов состояния входа в localStorage для проверки пропущенных событий.

Все операции, меняющие auth cookie, проходят через один координатор. Lock удерживается от проверки актуальности намерения до завершения HTTP и фиксации результата координации. Ответ refresh не передаётся в соседние вкладки как общий access secret: каждая вкладка получает свой access JWT последовательным запросом с общей актуальной cookie; все JWT имеют один sid.

Перед отправкой после ожидания lock проверить, что операция всё ещё относится к актуальной авторизации. Если за время ожидания произошёл logout или replacement-login, старый refresh не отправляется. Локальный `restoreGeneration` FE-01 сохраняется для защиты продолжений; shared generation/sid нужны отдельно от `sessionEpoch` рабочих запросов.

Общее состояние содержит протокольную версию, ревизию перехода, sid и состояние входа; никакого password, token, геометрии или recovery payload. Изменения общей ревизии выполняются под тем же lock. BroadcastChannel — ускоритель доставки, durable marker — источник проверки актуальности, но не доказательство серверных прав. На неверном/неполном marker запрещено устанавливать пользователя без server auth.

При startup, `pageshow`, возврате видимости и перед защищённым действием проверяется общая ревизия. Каждая работающая авторизованная вкладка независимо проверяет `session/status` своего sid с интервалом не более 1 секунды, без параллельных status-запросов одной вкладки. Это сознательный дополнительный серверный read: он обнаруживает отзыв, даже если инициатор завершился между commit logout и записью общего marker. Ответ старого sid не применяется к новому входу. `ended` завершает локальный вход и распространяет подтверждённое состояние; `active` не устанавливает пользователя заново и не продлевает токен.

Status-запрос имеет отдельный timeout не более 1,5 секунды; после его завершения следующий начинается не позднее чем через 1 секунду. Отсутствие ответа не означает logout. Цель ≤5 секунд проверяется при работающем браузере и ответах status endpoint в пределах этого timeout; при произвольно медленной/недоступной сети нельзя гарантировать время получения серверного факта. Худший бюджет учитывает уже выполняющийся запрос, прочитавший `active` до commit logout: до 1,5 секунды на его окончание, до 1 секунды до следующего, до 1,5 секунды на новый ответ `ended`, до 1 секунды суммарного запаса на применение UI и задержки исполнения. Такой старый `active` не отменяет уже полученный marker `ended`. Тест включает именно эту гонку, а не только logout между двумя polling-запросами.

BroadcastChannel и marker дают быстрый локальный путь без ожидания polling. Замороженная вкладка не обязана исполнять JavaScript во время заморозки, но при возобновлении сначала сверяет marker и status, затем разрешает защищённые действия. Deadline подтверждается измерением в реальных браузерах, не только fake timers.

При login смена sid/actor сообщает соседним вкладкам о необходимости сбросить старый auth/workspace и восстановить новый общий вход. Refresh того же sid не сбрасывает чужой WorkOrder, local draft или recovery. Поздние события старого sid не очищают новый вход. Обычный 401 рабочего запроса не является доказательством отзыва всего sid: существующая локальная обработка сохраняется, но сообщение другим вкладкам о завершении общей сессии требует server status `ended` либо успешного logout. Истечение одного access JWT не завершает входы остальных вкладок.

Отмена ожидающего lock безопасна до отправки HTTP. Timeout запроса после отправки не доказывает, что сервер не изменил cookie/session. Не захватывать lock принудительно и не выполнять параллельный refresh «для надёжности». После неопределённого исхода восстановление допускает ошибку/retry либо повторный login согласно согласованному исключению, но не объявляет устаревшую сессию действующей.

После network timeout или завершения контекста нельзя гарантировать порядок поздних `Set-Cookie` от login/refresh только клиентским lock. Для восстановления известного входа frontend передаёт ожидаемый sid; сервер сверяет его с cookie и при несовпадении не ротирует credential и не выдаёт аккаунт другой сессии. Frontend также проверяет sid ответа до применения. Late refresh от отозванного sid не возвращает доступ, даже если браузер сохранил его cookie. Такая повреждённая/потерянная cookie может потребовать повторного login; сохранность cookie нового входа при произвольных поздних сетевых ответах не обещается. Это граница аварийной потери credential, не штатного параллельного restore и не повод принимать старый refresh token повторно.

Если общего marker ещё нет (первое открытие при существующей cookie), начальный refresh может определить sid. Если marker есть, его sid нельзя молча заменить результатом неизвестного старого ответа. Состояние `ended` не препятствует явному новому login и не передаёт сам credential; после него создаётся новая ревизия.

Существующий HTTP timeout 30 секунд сохраняется. Предложение автора: ожидание auth lock ограничить также 30 секундами, после чего показать повторяемую ошибку восстановления, сохранив уже действующий вход, если он был. Для logout после timeout ожидания/недоставленного запроса действуют сообщение и сохранение входа. Это ограничивает ожидание, но не снимает lock у работающей/замороженной вкладки.

### Недоступность browser API

Поддерживаемая конфигурация — HTTPS origin либо локальная разработка на localhost. Web Locks и общее хранилище проверяются явно. При отсутствии безопасной координации не выполнять некоординированный refresh и не показывать ложный успех; показать ошибку конфигурации/восстановления. Отсутствие BroadcastChannel допускает сверку общего marker через storage event и периодическую проверку. Самодельный mutex на одном read/write localStorage без атомарности не вводится.

Это выбранная автором граница fallback для актуальных поддерживаемых браузеров, а не поддержка произвольных старых браузеров или небезопасного HTTP deployment.

## Выход и сохранность рабочего контекста

В инициирующей вкладке сохраняются нынешние диалоги разрешения local dirty/sent/stale. Пользовательский выбор discard остаётся окончательным даже если последующий logout не удался; скрытый autosave не добавляется.

Подготовка recovery не должна преждевременно объявлять потерю доступа: сначала обеспечить сохранность отправленного намерения, затем отправить logout; окончательные hideActor, suspension по потере доступа и очистку auth выполнить по подтверждённому отзыву/доказанному 401. Нынешнее `prepareLogout -> suspendActor` необходимо разделить с учётом этой границы. При ошибке сохранения recovery существующий запрет управляемого выхода сохраняется.

Во время ожидающего logout повторные auth-действия координируются; в инициирующей вкладке новые изменения workspace временно недоступны, но данные не очищаются. При доказанно неотправленном/отклонённом до выполнения logout вход и рабочий контекст остаются, действие можно повторить.

Потеря HTTP-ответа после server commit не равна недоставленному запросу. Показать «Не удалось подтвердить выход» без обещания действующего доступа. Проверить целевой sid через `session/status`, не ротируя cookie. `ended` завершает UI-выход и уведомляет вкладки; `active` сохраняет вход и предложение повторить выход, но не доказывает, что прежний запрос никогда не завершится позднее. Периодическая status-проверка обнаружит поздний отзыв. При недоступности оставить неизвестность. Не отправлять отложенный logout автоматически после нового login и не отзывать новый sid. Истёкший access JWT не подменяет результат этой проверки обычным 401.

Соседние вкладки после подтверждённого выхода прекращают доступ без ожидания согласия на сохранение. Их local dirty не сохраняется автоматически; sent intent сохраняет прежнюю identity и правила recovery. Это следует из существующей политики принудительной потери доступа. Не обещать отмену уже отправленной команды или автоматическое продолжение после нового login.

## Миграция и совместимость

Предложение автора: одноразово завершить существующие legacy auth sessions при обновлении. Старые JWT без sid больше не принимаются; ранее выданные WebSocket tickets также недействительны. После обновления потребуется повторный login. Бизнес-данные, edit versions и история команд не изменяются.

Миграция добавляет родительские записи/связи для сохранения целостности существующей истории и помечает их недействительными; не переносит старый JWT в активную сессию по одному user id. Новые строки обязаны иметь sid. Конкретные имена migration/constraints и способ backfill оставлены исполнителю при соблюдении этого результата.

Frontend и backend выкатываются совместимо в одном обновлении; rolling-смешение старого backend, принимающего JWT без sid, с новым не поддерживается. Downgrade схемы не должен воскрешать старые credentials. Проверки миграции обязательны на чистой БД и на БД со старыми auth/ticket rows.

## Проверки и критерии приёмки

| Сценарий | Обязательный результат |
| --- | --- |
| Два/несколько startup restore с общей cookie | Все штатно восстанавливают аккаунт; server refresh не пересекаются по старому credential; WorkOrder state независим |
| Прямой конкурентный replay старого refresh | Не более одного успеха, серверная single-use защита сохранена |
| Разные browsers/profiles с одним user id | Разные sid; выход одного не отзывает другой |
| Logout, затем запрос с каждым ранее выданным JWT данного sid | Все новые проверки дают 401 сразу после commit, без ожидания exp |
| Logout, затем refresh текущего/старого credential и consume ticket | Доступ не выдаётся |
| Refresh в гонке с logout | После commit logout нет действующего потомка сессии; порядок определяется общей родительской блокировкой |
| Новый login после logout, затем поздний ответ/событие старого sid | Новый вход не очищается и старый не восстанавливается |
| Успешный logout в одной вкладке | Остальные работающие вкладки показывают login за ≤5 секунд; после reload старый вход не восстанавливается |
| Неотправленный logout / сервер недоступен | Нет преждевременной очистки входа и workspace; сообщение и ручной повтор |
| Logout выполнен, ответ потерян | UI не обещает сохранённый доступ; reconciliation устанавливает фактический результат без отзыва нового sid |
| Закрытие вкладки до отправки / во время refresh | Очередь не застревает навсегда; потерянный новый token допускает login, но не ослабление replay |
| Пропущенный broadcast, hidden/frozen/resume | Проверка marker предотвращает работу под старым sid; событие старой ревизии не влияет на новый вход |
| Инициатор закрыт после commit logout до публикации marker | Остальные работающие вкладки обнаруживают `ended` через status и выходят за ≤5 секунд в согласованных сетевых условиях |
| Access JWT истёк, но родитель активен | Status возвращает `active`, а бизнес-endpoint отклоняет этот JWT; ложного общего logout нет |
| Поздний logout после нового login | Нет `Set-Cookie` в logout, новый sid и его cookie не меняются |
| Поздний refresh повредил cookie после сетевой неопределённости | Sid guard не авторизует другую/отозванную сессию; допустим повторный login при потере credential |
| Один WorkOrder в нескольких вкладках | Нового запрета открытия нет; существующие stale/conflict правила работают |
| Миграция и старые credentials | Legacy JWT/tickets не дают доступа; бизнес-данные сохранены |

Проверки backend включают настоящие конкурентные транзакции PostgreSQL: unit mock `rotated_session=None` недостаточен. Проверки frontend включают настоящий store/interceptor/coordinator, управляемые задержки и ошибки. Браузерные проверки используют два page одного context с настоящим backend/cookie и независимые contexts для разных входов. Отдельные прогоны в Chrome, Edge и Firefox фиксируют версии; Chromium вместо Firefox не считается проверкой Firefox.

Регрессия: FE-01 late continuation, текущие auth/roles, Save/Revert recovery, DB migrations, frontend typecheck/lint/build, соответствующие backend suites. Команды и окончательное разбиение проверок определяются в плане. Результаты в этом документе не заявлены: реализация и прогоны ещё не выполнены.

## Решения автора, требующие проверки при одобрении

Пользователь выбрал подход и поведение; следующие детали предложены автором: родительская сессия с историей refresh credentials, Web Locks/BroadcastChannel/marker, sid в response, граница профиля/origin, 30 секунд ожидания lock, отсутствие небезопасного fallback, одноразовый повторный login после миграции, граница уже допущенных запросов и охват legacy tickets. После builder check добавлены: logout без изменения cookie, status endpoint с отдельным proof-контрактом, status polling каждой вкладки с паузой не более 1 секунды (timeout 1,5 секунды), sid guard и явная граница поздних cookie после сетевой неопределённости. Это не отдельные уже принятые ответы пользователя.

## Проверка полноты дизайна

Независимый builder check выявил три существенных пробела: поздний cookie-ответ, потерю уведомления при закрытии инициатора logout, смешение expiry access JWT и отзыва родителя. Они устранены разделами logout/status/координации. Повторная проверка подтвердила эти уточнения и указала на превышение пятисекундного бюджета при старом status-запросе; timeout уменьшен до 1,5 секунды и явно задан худший бюджет. Это проверка документа, не свидетельство работоспособности ещё не написанного кода.

Имена внутренних типов, форма модулей, конкретные SQL constraints и организация fixtures остаются исполнителю. Нельзя самостоятельно менять область выхода, убирать server-side отзыв, разрешать replay, возвращать блокировку WorkOrder или считать ошибку logout успешным выходом.

## Основания по browser API

- [Web Locks](https://developer.mozilla.org/en-US/docs/Web/API/Web_Locks_API): координация контекстов одного origin в secure context.
- [BroadcastChannel](https://developer.mozilla.org/en-US/docs/Web/API/Broadcast_Channel_API): обмен сообщениями в одной storage partition.
- [Chrome Page Lifecycle](https://developer.chrome.com/docs/web-platform/page-lifecycle-api): приостановка/выгрузка не позволяют обещать выполнение JavaScript в остановленной вкладке.

Эти источники обосновывают границы API, но не являются runtime-приёмкой проекта.
