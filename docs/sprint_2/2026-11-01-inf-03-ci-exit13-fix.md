# INF-03: CI exit 13 при проверке dev HTTP

Дата: 2026-11-01. Источник: предоставленный пользователем GitHub Actions log; последняя успешная строка dirty:prod-static, затем Process completed with exit code 13.

## Что установлено

Docker dev/prod build и проверка production-статики завершились. Следующий участок runner — запуск dev-контейнера и HTTP readiness / чтение преобразованного src/api/baseUrl.ts.

В Node exit 13 означает незавершённый top-level await при завершении event loop. AbortSignal.timeout использует unref-таймер, который намеренно не удерживает процесс. Поэтому он не является самостоятельной гарантией выполнения timeout/catch/finally в standalone CLI при отсутствии других активных handles.

Основания: [Node 20 exit codes](https://nodejs.org/docs/latest-v20.x/api/process.html#exit-codes), [исходник AbortSignal Node 20.20.2](https://github.com/nodejs/node/blob/v20.20.2/lib/internal/abort_controller.js#L106-L127).

Обычная проверка HTTP с реальным Vite в Linux Node 20.20.2 / Undici 6.24.1 до исправления прошла: точный сетевой триггер исходного GitHub сбоя не воспроизведён. Диагностика не доказывает конкретный дефект Undici. Отдельные контролируемые процессы воспроизводят слабое место runner: при ожидании headers/body с unref-операцией, а также никогда не завершающегося body без handles, прежний механизм завершается с exit 13 до cleanup. Это воспроизведение класса отказа, а не запись реального GitHub network trace.

## Исправление

HTTP-код вынесен в http-probe.mjs. readHttpResponse(url, timeout) создаёт обычный referenced setTimeout на всю операцию fetch и чтение тела. Deadline одновременно abort-ит запрос и отклоняет Promise.race, даже если транспорт не завершит promise после abort. finally очищает таймер при любом результате. Сроки 2 секунды для readiness и 10 секунд для модуля сохранены.

run.mjs использует helper в обоих HTTP-запросах и печатает начало dev-runtime фазы. Ошибки проходят через существующий catch/finally с записью summary и удалением собственных ресурсов. Workflow менять не потребовалось: существующий run.test.mjs уже запускается CI.

## Проверки

- RED: 3 standalone HTTP regression cases на старом механизме дали именно exit 13.
- GREEN: 11/11 tests на Linux Node 20 и Windows Node 24. Headers/body завершаются, зависший body даёт TimeoutError и выполняет finally. Deadline успешного запроса длиннее лимита дочернего процесса, поэтому забытый clearTimeout также вызвал бы ошибку теста.
- Реальный HTTP server: статус 503 и тело читаются, зависшее тело ограничивается TimeoutError.
- Изолированный Linux Node 20 + настоящий Vite: readiness и runtime API URL проходят; внешняя сеть не использовалась.
- Полный локальный Docker runner dev/prod/HTTP: [passed, cleanupErrors пуст](evidence/inf-03/ci-exit13-fix/summary.json).
- Независимое read-only ревью не обнаружило существенных замечаний.

Исходный GitHub workflow после исправления ещё не запускался. Изменения оставлены unstaged; агент не выполняет commit/push. Нужен повтор CI после внесения исправления пользователем. Если сбой повторится, новая фазовая строка и сохранённая диагностика помогут уточнить источник.

## Ограничение способа диагностики

Попытка запустить Linux runner с Docker socket и host network была отклонена автоматической проверкой доступа как слишком широкая. Она не выполнялась. Вместо неё использован контейнер с Node/Vite без внешней сети и read-only mount только проверочных скриптов, плюс обычный runner через разрешённый Docker CLI хоста. Высокопривилегированный контейнер для исправления не нужен.

Отдельная agent memory не создаётся: причина, ограничения и регрессия сохранены здесь и в тестах; существующий контракт Code_wiki не меняется.
