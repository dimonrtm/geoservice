# FE-04 — русский язык документа и настраиваемое название приложения

Дата: 2026-11-07. Статус: дизайн принят пользователем 2026-11-07. [План реализации](2026-11-07-fe-04-document-language-plan.md). [Реализация и проверки](2026-11-07-fe-04-document-language-report.md).

Основание: [анализ и ответы пользователя](2026-11-07-fe-04-document-language-analysis.md), [FE-04](frontend-review.md#fe-04--p3--русский-интерфейс-объявлен-англоязычным-документом).

## Цель и согласованное поведение

Небольшое изменение HTML, конфигурации сборки и одного упоминания в UI: русский интерфейс объявляется русскоязычным документом, а технический title `frontend` заменяется на название приложения.

- Корневой HTML имеет `lang="ru"` с момента получения документа, до выполнения JavaScript.
- Все вкладки и состояния приложения используют одно название, по умолчанию `GeoService`. Наряд, роль и текущее состояние в title не добавляются.
- Название настраивается при развёртывании. Для изменения production-названия допустима пересборка frontend и замена образа.
- Все упоминания названия внутри интерфейса используют то же значение. Сейчас это tooltip `Выйти из GeoService` в `App.vue`; после изменения — `Выйти из <настроенное название>`.
- Значение обрезается по краям. Отсутствующее, пустое и состоящее только из пробелов значение даёт `GeoService`.
- Название является обычным текстом, включая кириллицу, кавычки, `&`, `<` и `>`. Оно не интерпретируется как HTML. Язык документа не зависит от языка названия.

## Рассмотренные подходы

| Подход | Последствия | Выбор |
|---|---|---|
| Единая настройка при сборке | HTML и клиент получают одинаковое значение; изменение production-названия требует пересборки | Принят пользователем: соответствует допустимой пересборке и текущему статическому frontend |
| Настройка при запуске production-контейнера | Позволяет переиспользовать образ, но требует дополнительной обработки HTML или runtime-конфигурации | Не выбран: возможность менять имя без пересборки не требуется |

Отдельное присваивание title после запуска Vue не обеспечивает настроенное название в первоначальном HTML, поэтому не является самостоятельным подходом для этого дизайна.

## Устройство изменения

Следующие технические детали — инженерная конкретизация принятого подхода.

Ввести публичный параметр `VITE_APP_NAME`. В конфигурации Vite получить его с учётом mode и окружения и один раз вычислить нормализованное название. Из этого значения сформировать `<title>` через HTML-преобразование Vite и клиентскую строковую константу, доступную UI через небольшой модуль конфигурации приложения. Не вычислять default и trim независимо в HTML и Vue.

При вставке в HTML экранировать текст для содержимого `<title>`; клиентскую константу передавать как корректно сериализованный строковый литерал. Во Vue использовать обычную текстовую привязку, без `v-html`. Преобразование должно работать в dev и production. HTML содержит ровно один title; после сборки в нём не остаются шаблонные маркеры. Базовый исходный title — `GeoService`.

В production Compose явно передать параметр как build argument frontend; Dockerfile должен сделать его доступным во время `npm run build`. Простая runtime environment-переменная nginx не меняет готовую статику. В demo/dev передавать тот же параметр в окружение Vite. Локальные `.env` остаются исключёнными из Docker context; для локального запуска поддерживается обычная загрузка окружения Vite. Пример настройки добавить в `infra/.env.example`, правила пересборки и dev-перезапуска — в документацию задачи в `docs/sprint_2`.

Новых зависимостей не требуется. Конкретные имена внутренних модулей и вспомогательных функций определяются при планировании с соблюдением именования проекта. API `loadEnv` и `transformIndexHtml` описаны в [документации Vite по окружению](https://vite.dev/guide/env-and-mode) и [HTML-преобразованиям](https://vite.dev/guide/api-plugin#transformindexhtml); реализация должна соответствовать установленной в проекте версии Vite 7.

## Границы

Не входят: многоязычный интерфейс, переключатель языка, перевод сторонних controls и технических терминов, смена favicon, динамические названия по нарядам, полный аудит доступности, новые backend-настройки. Имена browser storage, IndexedDB, auth lock, пакетов и Docker-сервисов — технические идентификаторы, их изменение не требуется.

Доменные инварианты WorkOrder/EditVersion, авторизация, восстановление черновиков и поведение карты сохраняются. Переименование не должно сбрасывать сессии или локальные данные. Полное соответствие WCAG этим изменением не заявляется.

## Критерии приёмки и проверка

1. Без настройки исходный ответ dev-сервера и собранный HTML содержат `lang="ru"` и единственный title `GeoService` до запуска Vue.
2. С настройкой `  Сети Уфы  ` title и подсказка выхода содержат `Сети Уфы`; пустая и пробельная настройка дают default.
3. Название с кириллицей, кавычками, `&` и последовательностью `</title>` после разбора HTML остаётся точным текстом названия, не создаёт элементы и не исполняет код; UI показывает то же значение.
4. Вход, восстановление сессии, редактор и Reviewer сохраняют общее название; открытие другого наряда и выход не меняют его. Проверка всех состояний может опираться на существующие component tests; для браузерного smoke достаточно основного пути входа и выхода.
5. Проверка production Compose/Docker подтверждает передачу пользовательского названия до сборки. Одной проверки локального Vite недостаточно для доказательства настройки при развёртывании. Исходный HTML из собранного образа и UI согласованы.
6. Выполняются релевантные проверки frontend: форматирование изменённых файлов, lint, typecheck, тесты затронутого поведения и build. Проверки должны выявлять рассогласование HTML/UI и ошибку экранирования, а не дублировать реализацию.
7. Отдельный screen reader smoke проверяет озвучивание русского текста. В отчёте указываются средство, браузер и фактический результат; при невозможности выполнить проверку фиксируется ограничение. DOM-проверки не заменяют проверку реальной озвучки, и непроверенный результат не объявляется успешным.

Код и конфигурация меняются только на этапе реализации после согласования дизайна и подготовки плана. Изменения остаются unstaged; Git add/commit/push выполняет пользователь. Отдельная agent memory не требуется: требования и причины выбора сохранены здесь.
