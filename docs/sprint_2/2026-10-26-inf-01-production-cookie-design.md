# INF-01: безопасный старт API в базовом Compose

Дата: 2026-10-26.
Статус: принят пользователем 2026-10-26; реализован. Проверки и ограничения — в [отчёте](2026-10-26-inf-01-production-cookie-implementation-report.md).
Основание: [анализ и ответы пользователя](2026-10-26-inf-01-production-cookie-analysis.md).

## Цель и согласованные границы

Устранить отказ API при импорте Settings: базовый Compose задаёт `DEV_MODE=false`, но не передаёт обязательный `AUTH_SESSION_COOKIE_SECURE=true`. При валидных обязательных параметрах API должен запускаться и отвечать на `/health`, сохраняя production-валидацию.

Пользователь выбрал безопасный старт API как результат INF-01 и воспроизводимую локальную проверку как достаточную приёмку. HTTPS termination, сертификаты, браузерный login/refresh, frontend routing, CD и новый CI gate не входят в задачу. INF-02/03/04 остаются отдельными задачами.

## Подход и альтернативы

Выбран пользователем вариант А: явное `true` в base Compose и явное `false` в demo override. Это отражает уже действующую политику Settings и не требует нового параметра от оператора.

Рассмотренный вариант Б — required environment placeholder — не выбран: он добавляет обязательный вход с единственным допустимым production-значением и усложняет интерполяцию demo-конфигурации. Глобальный default Settings не меняется, валидатор не ослабляется.

## Изменения конфигурации

В `infra/docker-compose.yml`, внутри `services.utility_service.environment`, добавить:

```yaml
AUTH_SESSION_COOKIE_SECURE: "true"
```

В `infra/docker-compose.demo.yml`, в том же environment, добавить:

```yaml
AUTH_SESSION_COOKIE_SECURE: "false"
```

Значения — строки. Base продолжает задавать `DEV_MODE=false`, target `prod` и `start_api.sh`. Demo продолжает задавать `DEV_MODE=true`, target `dev` и demo startup. Наличие переменной Secure в shell не изменяет выбранную политику YAML; явное небезопасное переопределение в production отклоняется существующим валидатором.

`Settings`, auth endpoints, cookie name/Path/HttpOnly/SameSite/TTL, миграции и seed scripts не меняются. Производственный API не получает автоматических миграций или demo seeds. Изменять CORS и `.env.example` для новой обязательной переменной не требуется: новой обязательной переменной нет.

## Воспроизводимая локальная проверка

Предлагаемая реализация приёмки — PowerShell-скрипт и краткий runbook в `docs/sprint_2`. Они используют Docker Compose v2 и существующий Dockerfile. Host Python не требуется. Это выбор агента для текущего Windows-окружения, а не дополнительное требование пользователя.

Проверка должна использовать реальное описание сервиса из base Compose, свежую сборку target `prod` из текущих исходников и штатный `start_api.sh`. Одного импорта Settings или `docker compose config` недостаточно.

### Изоляция

- Для каждого запуска создать уникальное имя Compose project и уникальные имена проверочных контейнеров.
- Передать синтетические DB/JWT значения через отдельное временное окружение/файл. Исключить влияние локальных `.env` и случайных host overrides; после завершения восстановить изменённое окружение процесса.
- Запускать API через `docker compose run --no-deps` с явным уникальным `--name`, без переопределения production command и без `--service-ports`. Это исключает конфликт с фиксированным `container_name: utility_service` и не запускает PostGIS/frontend/migrate.
- Использовать синтетический DB URL, не указывающий на существующие базы. Проверяемый `/health` не обращается к БД, создание SQLAlchemy engine само по себе не требует соединения.
- Проверять HTTP изнутри контейнера; наружные порты не публиковать.
- В `finally` удалить только созданные этой проверкой контейнеры и сеть, сверив принадлежность уникальному project. Не выполнять общий `down -v`, не затрагивать рабочие volumes и существующие контейнеры.

Это запуск API-сервиса с базовой конфигурацией, а не приёмка всего стека `docker compose up`. Зависимости намеренно не запускаются: готовность БД, миграций и пользовательского входа вне объёма INF-01.

### Матрица приёмки

| Проверка | Ожидаемый результат |
| --- | --- |
| Разрешённая base-конфигурация при синтетических обязательных DB/JWT значениях | Итоговый environment: `DEV_MODE=false`, Secure=true; target `prod`, штатный API command |
| Реальный старт API из этой конфигурации | Процесс остаётся работающим; запрос `GET /health` внутри контейнера возвращает HTTP 200 и `{"ok": true}` в пределах ограниченного ожидания |
| Runtime Settings работающего контейнера | `dev_auth_enabled=False`, `auth_session_cookie_secure=True`; выводить только эти несекретные значения |
| Тот же production запуск с явным Secure=false | Ненулевое завершение и сообщение валидатора про обязательный Secure; отсутствие штатного старта HTTP |
| Объединённая base + demo конфигурация | `DEV_MODE=true`, Secure=false, target `dev`, demo startup сохранён |
| Settings с параметрами объединённого demo environment | Успешная валидация с Secure=false; demo seeds и рабочая БД для этой проверки не запускаются |
| Существующие settings/auth и Compose startup/security tests | Проходят; repo-dependent тесты запускаются с доступным checkout, чтобы не получить ложный успех через skips |

Для отрицательного запуска задать ограничение ожидания: зависание или неожиданный работающий API — провал проверки. При ошибке положительного запуска собрать ограниченный диагностический вывод без environment/secrets и вернуть ненулевой exit code. Полные resolved config и cookie/token values не сохранять.

Положительная проверка не должна передавать Secure через `run -e`: иначе она могла бы скрыть дефект base YAML. Runtime overrides допустимы только в явно обозначенном отрицательном сценарии.

Проверка demo здесь подтверждает конфигурацию и валидацию Settings. Она не заявляет повторную браузерную приёмку HTTP demo. Если проверки выявят изменения auth-поведения за пределами ожидаемой настройки Secure, результат требует отдельного разбора, а не молчаливого расширения задачи.

## Артефакты и критерий завершения

Изменяемые runtime-файлы — только два Compose YAML. Новые материалы локальной проверки и отчёт находятся в `docs/sprint_2`; индекс этой папки дополняется ссылками без перезаписи существующих изменений пользователя. Постоянные unit tests, дублирующие добавленные строки YAML, не нужны: regression evidence даёт выполнение реальной конфигурации и существующих тестов.

В отчёте сохранить команду запуска проверки, версии Docker/Compose, идентификатор проверенного образа, результаты матрицы и ограничения. Не хранить секреты и полный environment. Все новые текстовые файлы — UTF-8 с LF.

INF-01 завершена, когда выбранная политика внесена и локальная матрица пройдена. Успешный `/health` подтверждает старт API, но не готовность production-развёртывания, БД или браузерной сессии. Изменения остаются unstaged; Git staging, commit и push выполняет пользователь.
