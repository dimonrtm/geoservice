# День 14: спецификация итоговой приёмки Sprint 2

Дата: 2026-10-26. Статус: принята пользователем 2026-10-26.
Основания: [анализ и ответы пользователя](2026-10-26-day-14-acceptance-analysis.md), [ТЗ](2026-07-31-sprint-2-technical-requirements.md), [календарь](2026-07-31-sprint-2-calendar-plan.md).

## Цель и результат

Установить фактическую готовность Sprint 2 по AC-01–AC-10, Definition of Done и M5. Результат — `docs/sprint_2/2026-08-16-sprint-2-acceptance-report.md` с вердиктом «принят» либо «не принят», доказательствами и явным перечнем блокирующих отклонений. Фактические даты проверки указываются отдельно от календарной даты в имени отчёта.

Приёмка касается технического сохранения draft. Она не подтверждает positional accuracy, topology, review/post или производственную валидацию условной организации.

## Выбранный подход

Пользователь выбрал существующие проверки и отдельный ручной UI-demo. Используются текущие backend/frontend suites, изолированные DB tests, фазовый API smoke Дня 13 и существующий M4. Новый runner не создаётся.

Альтернатива — единый runner, объединяющий проверки и evidence. Он упростил бы повторный запуск, но потребовал бы нового кода и его проверки; для этой приёмки не выбран.

## Обязательная матрица

| Область | Проверка | Значение для приёмки |
| --- | --- | --- |
| Backend | Полные format/lint/tests | Включая settings, seed specification, fixture upgrade idempotency/rollback и startup order |
| PostgreSQL/PostGIS | Существующий изолированный DB suite | Atomicity, concurrency, registry/history, geometry guards, migration upgrade/downgrade/upgrade; skipped DB tests обычного pytest не заменяют этот suite |
| Frontend | format:check, lint, typecheck, tests, build | Полные существующие проверки приложения |
| Fresh setup и API | Существующий smoke Дня 13 на изначально пустой изолированной БД | Save → настоящий restart штатного backend → readback/replay/отказы/Revert; БД сохраняется между фазами |
| Recovery и доступность | Полный существующий M4 suite | Только существующее покрытие; browser zoom 200% явно непроверен и не блокирует M5 |
| Ручной UI-demo | Агент управляет браузером через пользовательский интерфейс | WO-001 → L-003 → drag внутренней вершины → Save → refresh → restart backend → readback → Revert |

Remote GitHub Actions для M5 не требуется. Предыдущие отчёты служат контекстом, а не заменой нового полного локального прогона. Проверки из DoD сопоставляются с конкретными результатами; один общий exit 0 не заменяет доказательства содержательных критериев.

## Порядок и изоляция

1. Зафиксировать HEAD, состояние рабочего дерева и применяемые команды. Существующее изменение `.obsidian/graph.json` не затрагивать.
2. Выполнить полные локальные suites. DB tests запускать только в предназначенном для них окружении, не на пользовательской demo БД.
3. Выполнить fresh API smoke по runbook Дня 13. Каждый полный прогон начинается на новой БД. Между Save и verify/retry/Revert перезапускается только backend; сохранить свидетельство смены запуска и готовности сервиса.
4. Выполнить существующий M4 и сохранить результаты отдельно от исторических артефактов. Учесть, что текущий runner пишет в прежние evidence-пути: новые результаты архивировать в каталог Дня 14, исторические свидетельства сохранить.
5. Выполнить отдельный ручной UI-demo на изолированном окружении с пустой исходной БД. Пользовательские mutations делать только через UI; SQL, API-вызовы или изменение browser storage не заменяют действия редактора. Restart backend выполняется инфраструктурной командой, а не через UI приложения.
6. Свести evidence, отклонения и вердикт в отчёт. При необходимости исправления основного сценария перепроверить затронутые критерии и выполнить финальный полный regression на итоговом коде.

Конкретный способ предоставления браузеру изолированного UI-окружения выбирается при подготовке исполнения по существующей инфраструктуре. Он не должен затрагивать пользовательский volume или конфликтовать с fixed names/ports. API smoke override без опубликованных портов сам по себе не предоставляет браузеру UI.

Очистка касается только ресурсов конкретных тестовых запусков. Global prune и удаление пользовательского demo volume не требуются. Недоступность инструмента или окружения отражается как непроверенный обязательный критерий, а не как успех.

## Доказательства

Новые артефакты сохраняются в `docs/sprint_2/evidence/day-14/` с разделением запусков. Сохраняются безопасные результаты suites, smoke JSON/restart manifest, результаты M4 и скриншоты с описанием шагов ручного demo. Credentials, токены, environment dumps и произвольные чувствительные логи не публикуются.

Для каждого критерия отчёт содержит источник требования, фактическую проверку, результат и ссылку на evidence. Число тестов указывается по новому прогону; прежние значения не копируются как ожидаемый результат.

API smoke доказывает неизменность геометрии baseline L-003, revision и отсутствие повторных событий через существующий read-only observer. Это независимая автоматическая проверка, а не часть ручных действий пользователя. Объём baseline proof не расширяется на остальные features или поля.

В ручном demo фиксируются выбор L-003 и внутреннего handle, сохранённое состояние, сохранность после refresh и restart, возврат к baseline после Revert и честное отображение POSITIONAL_ACCURACY_UNVERIFIED. Успешный автоматический M4 не подменяет ручной demo.

## Исправления и вердикт

- Исправляются только дефекты, блокирующие основной сценарий. Расширение функциональности, новая полировка и новые доменные возможности не входят в День 14.
- Если основной путь проходит, но существующий M4 выявляет дефект обязательного recovery или доступности, дефект записывается как блокирующий без исправления в День 14. Спринт не принимается.
- Ошибка иного обязательного check или невозможность выполнить его также не позволяют заявить полную приёмку. Проверка, завершившаяся ошибкой окружения, отличается в отчёте от подтверждённого дефекта приложения.
- «Принят» допустимо только при подтверждении всех обязательных критериев в согласованных границах. «Не принят» сопровождается точными отклонениями, ожидаемым и фактическим результатом, затронутыми критериями и evidence.
- Непроверенный настоящий zoom 200% и отсутствие remote CI перечисляются как согласованные ограничения, а не blockers.

## Документация, ingest и Git

Отчёт включает состав принятой версии, матрицу AC/DoD, suites, fresh setup, ручной demo, M4, blockers, неблокирующие ограничения и решение об ingest.

`/ingest repository-change` выполняется только если работа принесла новую устойчивую техническую информацию, ещё не отражённую в Code_wiki. Новые результаты тестов и завершение дня сами по себе этого не требуют. Agent memory не дублирует анализ, спецификацию, runbook или отчёт.

Артефакты пишутся по-русски с LF; paths и identifiers не переводятся. Изменения остаются unstaged. `git add`, `git commit`, `git push` запрещены.
