# AR-02. Независимая доставка и актуальное состояние карты

Дизайн принят пользователем 2 ноября 2026. [Анализ и основания](2026-11-02-ar-02-analysis.md).

## Граница и результат

Область работы — legacy GIS CRUD и открытая карта активного слоя при включённом `LEGACY_GIS_API_ENABLED`, в текущем однопроцессном развёртывании. Подписка доставляет изменения по возможности. При разрыве клиент восстанавливает актуальное состояние через HTTP. Журнал событий, межпроцессная доставка и команды WorkOrder/EditVersion выходят за границы задачи.

Автор зафиксированной записи получает успешный HTTP-ответ, быстрый подписчик получает событие, пока отправка медленному подписчику всё ещё заблокирована. Порог времени в миллисекундах пользователь не задавал. На карте более старая версия не замещает новую, а удалённый объект не появляется вновь из запоздалого события. После длительного разрыва открытая карта с действующим доступом сама возвращается к актуальным данным.

## Рассмотренные подходы

1. Перечитывать видимые данные по уведомлению. Проще обрабатывать удаление и перестановку событий, но при активном редактировании добавляются HTTP-запросы.
2. Применять снимки из событий непосредственно с проверкой версии. Пользователь выбрал этот подход. Он позволяет показывать изменение без обязательного чтения слоя на каждое событие, но требует согласовать версию, удаление, геометрию и ответы параллельных чтений в одном кеше.

## Доставка на сервере

После успешного выхода из транзакции publisher формирует прежний JSON события один раз. Менеджер ставит его без ожидания свободного места в отдельную FIFO-очередь каждого соединения слоя. На пути HTTP-ответа нет проверки сессий подписчиков, ожидания записи в сеть и закрытия сокетов. Ошибка доставки не меняет результат CRUD. Ошибочная или откатившаяся запись не создаёт уведомление.

Один исполнитель на соединение последовательно забирает кадры, проверяет активность sid перед каждой фактической отправкой и ждёт транспорт в пределах deadline. FIFO относится к порядку поступления в менеджер. При регистрации первым помещается `connected`, до доступности подписки для fanout. Маршрут больше не конкурирует за отправку этого кадра. Предложенные начальные настройки — максимум 32 ожидающих кадра и 5 секунд на одну отправку, с возможностью подставить меньшие значения в тестах. Это инженерные значения, а не согласованный SLA. Для каждого сокета также ограничить суммарный размер ожидающих кадров в байтах сериализованного сообщения. Конкретный бюджет выбрать при планировании. Пользователь согласовал исключение для одиночного кадра, который сам превышает этот бюджет. Даже при пустой очереди такой кадр не ставится на отправку. Подписка закрывается с кодом 1013, карта автоматически переподключается и получает актуальное состояние через HTTP. Размер кадра не меняет результат уже зафиксированного CRUD.

При переполнении или истечении deadline немедленно исключить соединение из рассылки, отбросить остаток и закрыть сокет с временным кодом 1013. Таймаут и очистка одного соединения не останавливают остальные. Закрытие, отмена исполнителя и освобождение ссылок идемпотентны при одновременных disconnect, logout и остановке приложения. Закрытие транспорта и ожидание завершения ограничены. На logout сохраняются действующие правила AR-01, включая 1008, исключение всех соединений sid и право ранее допущенной отправки завершиться. Сообщение в очереди ещё не допущено. Сбой проверки доступа не разрешает отправку.

## Версии и видимость объектов

Создание и обновление используют существующую `feature.version`. Для нового `feature_deleted` добавить `deletedVersion` из успешно выполненного условного DELETE (`request.version`). Это последняя живая версия. При равной версии удаление имеет приоритет. HTTP-ответ удаления сохраняет текущую форму. Старый клиент игнорирует добавленное поле. Новый клиент при удалении без версии инициирует восстановление из актуального снимка слоя с отсечением старой подписки.

Для каждого объекта слоя кеш принимает только более новую версию или удаление при равной версии. Дубликаты безвредны. Маркер удаления сохраняется и для отсутствующего в кеше объекта. Те же правила применяются к ответам локальных CRUD, всем страницам bbox и WebSocket-событиям. При обновлении геометрии пересчитать принадлежность к загруженным тайлам, удалить объект из прежних тайлов и добавить в новые по тем же пространственным условиям, что применяет bbox API. Если клиент не может достоверно определить пересечение, перечитать затронутые тайлы. Обновить видимый источник карты из результата слияния.

## Восстановление и ограничение памяти

Пока слой активен и доступ действителен, временные ошибки сети, перегрузки, HTTP 5xx и 429 при получении билета или загрузке данных допускают повтор с ограниченной сверху задержкой. Предложение — сохранить первые интервалы 0,5/1/2/5 секунд и далее повторять с паузой до 30 секунд и разбросом. После окончательного 401/403, отсутствующего слоя или закрытия 1008 остановить попытки. Смена слоя, logout и размонтирование отменяют прежние таймеры, подписку и применение поздних ответов. Каждый новый сокет получает свежий билет.

При восстановлении сначала зарегистрировать подписку, затем начать новое чтение видимых тайлов с первой страницы. Использовать отдельное поколение кеша. Старые сокеты, HTTP-запросы и фоновые страницы не могут обновить новый кеш или источник карты. События текущей подписки, пришедшие во время чтения, объединять со снимком по версиям, включая принадлежность к тайлам и удаления. Нельзя завершать синхронизацию по первому кадру или первой странице. Дождаться успешного завершения нужных страниц для актуальной видимой области. Временный сбой перечитывания должен приводить к повтору даже при открытом сокете. Учитывать существующие ограничения масштаба и bbox при следующем доступном чтении карты.

Ограничить накопление записей версий и удалений активной подписки. При достижении лимита начать новое поколение подписки и полное перечитывание видимой области. Запрещено просто вытеснить маркер во время жизни старой подписки. Порог, способ пространственной проверки и внутренние структуры оставлены реализации.

Смена поколения сама по себе защищает только от старых клиентских запросов. Публикация давно завершённой транзакции может впервые поступить уже в новую подписку. Если после смены поколения приходит снимок объекта, для которого ещё нет подтверждённой версии или маркера удаления, перед его первым показом свериться с существующим `GET /api/v1/layers/{layer_id}/features/{feature_id}`. Успешный ответ участвует в обычном сравнении версий, отсутствие объекта исключает его показ. При временной ошибке повторить проверку в действующем поколении. Обычные обновления уже известного объекта продолжают применяться непосредственно из события.

## Приёмочные сценарии

- Для быстрого подписчика с пустой очередью передать событие, которое само превышает байтовый бюджет. Проверить успешный HTTP-ответ записи, закрытие подписки с кодом 1013, автоматическое переподключение и отображение объекта через HTTP без ручной перезагрузки. Контрольный кадр ровно на границе бюджета при пустой очереди должен доставляться обычным путём.
- Для create/update/delete на реальном HTTP-маршруте с управляемой блокировкой одного транспорта получить ответ, проверить запись отдельным чтением и доставку быстрому подписчику до освобождения блокировки. Ошибки версий и откаты не публикуются.
- Проверить первый кадр, порядок очереди, переполнение, таймаут и очистку, отзыв sid при наличии ожидающих кадров и независимость других сессий. Сохранить проверки AR-01.
- На карте проверить версии 3 → 2, дубликат 3, удаление 3 → позднее обновление 3, перемещение через границу тайла и позднюю страницу bbox. Проверять отображаемую коллекцию и отсутствие обязательного перечитывания на обычное обновление.
- Переждать более четырёх попыток, восстановить сеть, получить свежий билет и актуальную карту без действий пользователя. За время разрыва создать, изменить и удалить объект. Проверить также временный отказ билета и сбой поздней страницы после восстановления сокета.
- При смене слоя или logout во время синхронизации старая доставка и старые ответы не меняют новый экран. Прохождение этих сценариев предстоит подтвердить при реализации.
