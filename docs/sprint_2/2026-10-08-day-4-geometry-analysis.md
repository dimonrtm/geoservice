## Уже зафиксированные правила

Источники: `2026-07-31-sprint-2-technical-requirements.md`, `2026-10-01-day-2-first-save-schema-design.md`, `Wiki/commands/update_edit_version_feature_geometry.md`, `Wiki/policies/edit_geometry_precision_policy.md`, `DDD_Wiki/invariants/edit_version_persisted_edit_invariants.md`.

1. Клиент передаёт полную resulting GeoJSON LineString; сервер возвращает canonical geometry.
2. Непустой diff относительно immutable baseline содержит ровно одну внутреннюю вершину. Индекс относится к baseline coordinate array.
3. Равенство baseline допустимо для Revert и baseline/no-op. Поэтому безусловное требование «ровно одно отличие» отклонило бы допустимый запрос.
4. No-op определяется сравнением с current snapshot. Отличие от baseline определяет `operation`, но само по себе не доказывает новое изменение current snapshot.
5. Канонизируется перемещённая вершина; endpoints и остальные вершины не перенормализуются. Full-line normalization и snapping к сети исключены.
6. Зафиксировано округление midpoint от нуля: при шаге `0.0000001` значения `+0.00000015` и `-0.00000015` дают соответственно `+0.0000002` и `-0.0000002`.
7. Save/Revert используют один HTTP contract. В request из ТЗ отсутствуют отдельные `operation`, `vertexIndex` и `structureHash`.
8. Domain rejection должен сохраняться с fingerprint. Ошибки request validation до use case не резервируют CommandId.
9. Повтор команды должен воспроизводиться после других Save; fingerprint не может случайно измениться только потому, что изменился current snapshot.
10. Spatial checks valid/simple/collapsed/AOI относятся к Дню 5; registry orchestration и mutation — к следующим дням. День 4 должен определить совместимые с ними правила, но календарь не требует реализации всего Save.

## Неоднозначности и их последствия

### 1. Входные отличия и отличия после canonicalization

Документы одновременно требуют не менять остальные координаты и проверять resulting diff после canonicalization. Не определено, можно ли принять несколько входных отличий, если часть исчезнет после округления.

Пример: endpoint сдвинут на `0.00000001` при grid `0.0000001`, а внутренняя вершина заметно перемещена. Endpoint мог бы вернуться на прежнее значение при округлении, но это потребует применить normalization к запрещённой для изменения координате. Аналогично две внутренние вершины могут отличаться во входе, а после округления отличаться будет одна.

Требуется уточнить семантику допустимого запроса до выбора порядка guard/canonicalization.

### 2. Последовательные Save на линии с несколькими внутренними вершинами

У demo L-003 одна внутренняя вершина; общий контракт eligible line допускает минимум три вершины, а не ровно три. Если current отличается от baseline в вершине A, следующий full resulting запрос может вернуть A к baseline и переместить B. Resulting diff остаётся единственным, но относительно current изменены две вершины.

Не установлено, разрешена ли такая смена редактируемой вершины одним Save, либо нужен отдельный Revert. Это влияет на structure guard, vertex identity и тесты; пример L-003 сам по себе вопрос не закрывает.

### 3. Baseline вне configured grid

В БД нет проверки grid для baseline. Существующий код копирует baseline без нормализации, а configuration допускает смену шага. Следовательно, факт наличия demo coordinates на default grid не доказывает это свойство для всех существующих линий.

Нужно определить точное восстановление baseline вне сетки и поведение unchanged запроса. Если канонизировать baseline при Revert, можно получить geometry, которая не равна immutable baseline. Это вступит в противоречие с смыслом Revert.

### 4. Числовая граница

Существующая схема использует `float`; новое требование — Decimal canonicalization. Не определено, что именно должно быть источником Decimal: исходное десятичное число JSON или числовое значение после существующего parsing. От этого зависит поведение значений около midpoint.

Нужно также определить равенство записей `1`, `1.0`, `1e0`, `-0` и `0`; допустимость string/bool координат; пределы длины/экспоненты числа; представление результата при передаче в PostGIS и обратно. Проверка unit-функции сама по себе не доказывает точность HTTP/storage round-trip.

### 5. Диапазон сетки и конфигурация во времени

Настройки явно допускают любой finite positive шаг, включая `1E+1000`. Не определены origin, рабочие ограничения вычисления и судьба команды после смены шага или версии алгоритма.

Одинаковый raw request при разных settings может дать разные canonical coordinates. Нужно уточнить, обещается ли воспроизводимость при неизменной конфигурации либо в течение всего lifecycle EditVersion независимо от deployment/configuration changes. Полей закреплённой geometry policy в исследованных моделях нет.

### 6. Fingerprint допустимой и отклонённой команды

Wiki перечисляет WorkOrder, EditVersion, feature, baseline identity, ожидаемый token, operation, vertex, structure hash и canonical geometry. Схема registry дополнительно хранит actor. Не определены точный набор полей, роль actor внутри fingerprint, формат сериализации, версия формата и алгоритм digest.

У структурно недопустимого запроса может не быть единственной изменённой вершины или допустимой canonical geometry. Однако такой domain rejection должен иметь fingerprint. Нужна однозначная идентичность и для отказов: исправленный intent не должен случайно совпасть с rejected запросом.

Нельзя выводить fingerprint из текущего before/after перехода без проверки replay-сценария: после первого Save current уже другой. Для Revert и no-op тот же риск касается вычисления operation и vertex index.

### 7. Граница request validation / domain rejection

ТЗ принимает только LineString, но среди domain ошибок перечисляет изменение parts, empty/collapsed/invalid geometry. Общая GeoJSON схема сейчас отсекает некоторые случаи до use case. Например, MultiLineString не пройдёт специализированный LineString request, а пустой coordinates не пройдёт существующий validator.

Нужно разделить случаи, для которых CommandId вообще не резервируется, и случаи durable rejection. От этого зависит область определения fingerprint и ожидаемые тесты structure guard.

## Ответы пользователя

### 1. Входное отличие endpoint, исчезающее после округления

Пользователь выбрал вариант 2: запрос допустим, если после округления endpoint совпадает с baseline. Само входное отличие endpoint до округления не является достаточным основанием для отказа.

Это уточняет первоначальное прочтение запрета изменения endpoints: требуется различать входное числовое отличие и изменение итоговой геометрии. Ответ не разрешает сохранять endpoint, отличающийся от baseline, и пока не определяет поведение baseline вне сетки.

### 2. Несколько входных отличий внутренних вершин

Пользователь выбрал вариант 1: запрос допустим, если после округления только одна внутренняя вершина отличается от baseline, даже когда во входе отличались несколько. Ограничение числа изменённых внутренних вершин проверяется по результату округления, а не по числу входных отличий.

Вместе с ответом 1 это исключает безусловный отказ только на основании нескольких входных координатных отличий. Эти ответы не разрешают менять число или порядок вершин, перенормализовывать baseline либо сохранять изменённые endpoints. Правила для baseline вне сетки ещё требуют уточнения.

### 3. Смена изменённой вершины между Save

Пользователь выбрал вариант 2: если current snapshot отличается от baseline в вершине A, одним Save нельзя вернуть A к baseline и переместить B. Сначала требуется отдельный Revert, затем новый Save для B.

Следствие: единственного итогового отличия от baseline недостаточно для разрешения mutation. Необходимо учитывать индекс уже изменённой вершины в current snapshot. Это правило проверки допустимости перехода не означает, что изменяемый current snapshot должен входить в fingerprint: replay исходной команды должен оставаться устойчивым после последующих изменений.

### 4. Точный Revert к baseline вне сетки

Пользователь выбрал вариант 1: Revert восстанавливает точный baseline без округления его координат, даже если они не лежат на configured grid. Само наличие baseline вне сетки не является основанием заранее запретить редактирование линии.

Следствие: правило canonicalization не должно превращать точный возврат baseline в новое отличие. Требуется отдельно уточнить отношение к входным отличиям нетронутых координат, когда baseline вне сетки: буквальное совпадение округлённого значения с такой baseline coordinate невозможно.

### 5. Endpoint и baseline вне сетки

Пользователь выбрал вариант 1: если входная координата endpoint и baseline coordinate округляются до одного значения, запрос допустим; в resulting geometry сохраняется точная baseline coordinate, а не округлённая.

Пример при шаге `0.0000001`: baseline X = `65.52000004`, request X = `65.52000003`; оба округляются до `65.5200000`, но resulting endpoint X остаётся `65.52000004`. Это уточняет ответ 1 для baseline вне сетки: сравниваются результаты округления входа и baseline, без изменения сохраняемого baseline endpoint.

### 6. Внутренняя вершина в том же узле округления, что baseline

Пользователь выбрал вариант 1: если request coordinate внутренней вершины и baseline coordinate округляются одинаково, resulting geometry сохраняет точную baseline coordinate. Такая вершина считается неизменённой относительно baseline, даже если исходные числа различались.

Если current snapshot ранее содержал перемещение этой вершины, такой результат означает возврат к baseline, а не no-op относительно current. Правило отдельного Revert перед сменой изменённой вершины из ответа 3 сохраняется.

Пример при шаге `0.0000001`: baseline X = `65.52500004`, request X = `65.52500003`; resulting X = `65.52500004`, а не `65.5250000`.

### 7. Replay после смены configured grid

Пользователь выбрал вариант 1: повтор исходного запроса с тем же `commandId` должен возвращать исходный результат даже после изменения configured grid и перезапуска backend.

Пример: исходный Save выполнен при шаге `0.0000001`, ответ потерян, backend перезапущен с шагом `0.000001`. Повтор прежней команды должен распознаться как replay; пересчёт по новой сетке не должен вызывать ложный `COMMAND_ID_REUSED` или новую mutation.

Это требование выходит за гарантию детерминизма при неизменных settings. Исследованная схема registry содержит fingerprint и terminal result, но не содержит отдельного поля исходной geometry policy. Способ обеспечения гарантии пока не выбран; возможное влияние на схему необходимо оценить после уточнения требований.

### 8. Сетка закрепляется за EditVersion

Пользователь выбрал вариант 1: новые Save внутри уже открытой EditVersion используют прежнюю сетку, закреплённую при открытии версии, до конца её жизни. Смена configured grid применяется к новым EditVersion, а не к новым командам существующей версии.

Вместе с ответом 7 это требует сохранения правил сетки между запросами и перезапусками backend. В исследованной модели EditVersion отдельных полей закреплённой сетки нет. Это существенная зависимость от схемы/открытия версии, которую предстоит включить в обсуждение границ реализации. Способ хранения и начальные значения для уже существующих версий ещё не определены. Ответ не устанавливает автоматически правила обновления версии алгоритма canonicalization.

### 9. Точное десятичное значение из JSON

Пользователь выбрал вариант 1: canonicalization должна учитывать точное десятичное число из входного JSON до любого преобразования в float.

При шаге `0.0000001` точное `0.00000015` округляется до `0.0000002`, а `0.000000149999999999999999999` — до `0.0000001`. Потеря этого различия при parsing недопустима. Преобразование в Decimal после существующей float-схемы само по себе не обеспечивает принятый контракт.

Это требование относится к входной границе будущего Save request; оно не означает, что пользователь уже согласовал замену всех общих GeoJSON schemas или способ хранения в PostGIS. Пределы допустимой длины и экспоненты чисел ещё не определены.

### 10. Начальная сетка существующих EditVersion

### Уточнение перед ответом о допустимом шаге: перевод в метры

Пользователь пока не выбрал вариант ограничения сетки; сначала запросил максимальную точность в метрах при выборе варианта 1.

В текущем `workspace_aggregate.sql` вызов `ST_AsGeoJSON` не задаёт `maxdecimaldigits`. По [документации используемой серии PostGIS 3.4](https://postgis.net/docs/manual-3.4/ST_AsGeoJSON.html) default — 9 знаков после запятой. Это ограничение текущего вывода: для десятичной сетки с нулевым origin шаг `1e-9` градуса является ориентиром самой мелкой сетки такого формата. Это не фундаментальный предел PostGIS и не доказательство готовности всего round-trip. Произвольный шаг с более длинным десятичным представлением требует отдельной проверки, даже если его величина больше `1e-9`.

Расчёт для широты demo L-003 `44.8205°` выполнен по радиусам кривизны эллипсоида WGS 84 с [параметрами NGA](https://earth-info.nga.mil/?action=wgs84&dir=wgs84): `a=6378137 m`, `1/f=298.257223563`. Один градус по широте здесь примерно `111128.27 m`, по долготе — `79092.63 m`.

| Шаг | По широте | По долготе |
| --- | --- | --- |
| Текущий default `1e-7°` | `0.01111 m` (11.1 мм) | `0.00791 m` (7.9 мм) |
| `1e-9°`, ориентир текущего формата вывода | `0.000111 m` (0.111 мм) | `0.0000791 m` (0.079 мм) |

Это разрешение координатной сетки, а не positional accuracy исходных данных. Выбор ограничения сетки сам по себе не фиксирует её минимальный шаг; гарантия выбранного диапазона требует проверки canonical serialization, storage/readback и точного сохранения baseline вне сетки. Последнее нельзя считать решённым только ограничением шага: текущий вывод с 9 знаками способен потерять дополнительные разряды baseline.

1. Входные координаты читаются как точные десятичные числа; midpoint округляются от нуля.

## Варианты решения: хранение правил и границы компонентов

Пользователь выбрал вариант A и подтвердил предложенное разделение ответственности ответом «Да». Детали следующих разделов ещё согласуются.

### Вариант A: неизменяемые поля policy непосредственно в EditVersion

Каждая версия хранит собственные `geometry_xy_resolution`, `geometry_rounding_mode` и `geometry_policy_version`. Они назначаются один раз; новая общая настройка не влияет на существующие версии. Версия policy задаёт интерпретацию чисел и правил canonicalization, чтобы будущая смена алгоритма не меняла молча смысл старой версии.

Преимущества: правила читаются вместе с root, не требуется отдельный справочник и join; snapshot policy явно принадлежит EditVersion. Цена: значения повторяются в строках, при расширении структуры policy может понадобиться новая migration.

Это рекомендуемый вариант для Sprint 2: в проекте одна система координат и один rounding mode, отдельный жизненный цикл policies пока не требуется.

### Вариант B: отдельный неизменяемый справочник geometry policies

EditVersion хранит ссылку на запись с шагом, rounding mode и версией правил. Новая конфигурация создаёт или выбирает другую запись, существующие версии сохраняют прежнюю ссылку.

Преимущества: общий каталог явно именованных policies, меньше повторяющихся значений. Цена: дополнительная таблица, FK, поиск/создание policy, правила её неизменности и удаления. Это больше оправдано при нескольких datasets или управляемом каталоге правил, которых текущий scope не требует.

### Общая граница вычислений для обоих вариантов

- Числовой разбор будущего Save request сохраняет Decimal до canonicalization; существующая общая float GeoJSON schema не служит промежуточным форматом этого пути.
- Детерминированное ядро получает request, immutable baseline и закреплённую policy; не обращается к БД, глобальным settings или current snapshot. Оно формирует нормализованное представление запроса для fingerprint и результат проверки относительно baseline. Представление structurally invalid requests будет описано отдельно.
- Проверка перехода получает current snapshot отдельно: смена изменённой вершины требует Revert. Fingerprint не зависит от того, как current изменился после исходной команды.
- В будущем Save сначала проверяет доступ и контекст, затем распознаёт replay. Проверки нового перехода по current snapshot выполняются для новой команды; они не должны заново отклонять уже завершённую команду.
- Repository и открытие версии отвечают за durable policy; PostGIS spatial validation и полная Save transaction остаются следующими этапами календаря.

Точные числовые границы, состав fingerprint, обработка отказов, migration/backfill и readback рассматриваются в следующих разделах проектирования после выбора подхода. Product changes не выполнялись.

## Проектирование: canonicalization и structure guard

Пользователь согласовал алгоритм canonicalization и structure guard ответом «Да». Реализация не начата.

### Числовое правило

Обозначим через `Q(x)` округление числа `x` к ближайшему кратному закреплённого шага `g`, с midpoint от нуля. Сетка имеет origin `0`. В математическом виде: `Q(x) = g * round_half_away_from_zero(x / g)`.

Реализация должна сохранять точность решения о midpoint и не зависеть от внешнего Decimal context. Простого округления количества десятичных знаков недостаточно: шаг `0.00000025` означает кратность шагу, а не только восемь знаков после запятой. Конкретная организация точной арифметики и пределы входа будут зафиксированы в спецификации; выражение выше является математическим правилом, а не инструкцией использовать деление с произвольной текущей Decimal precision.

Для каждой ординаты X/Y соответствующей вершины, при исходной ординате `b` из baseline и входной `r`:

`result = b`, если `Q(r) == Q(b)`; иначе `result = Q(r)`.

Это покоординатное правило: если у внутренней вершины изменился только X, совпадающий на сетке Y сохраняется точно из baseline. Округление baseline используется только для сравнения; immutable baseline не переписывается. Поэтому результирующая geometry намеренно может содержать baseline coordinates вне сетки. Точный baseline request является неподвижной точкой алгоритма.

### Последовательность проверок

1. Разобрать числа как точные Decimal. Проверки входного формата отсекают нечисловые/non-finite значения, неправильные XY-пары и пустой LineString до use case; детальный контракт request validation будет описан отдельно.
2. Установить соответствие структуры: eligible baseline — LineString минимум с тремя вершинами; request сохраняет тип и число вершин. При несовпадении структуры не выполнять сопоставление через усечённый zip или перестановку вершин. Ошибка domain structure для запросов, дошедших до этой границы, должна иметь воспроизводимую идентичность.
3. По каждому индексу построить candidate geometry с правилом `Q` и восстановления baseline. Порядок вершин не сортировать и направление линии не нормализовать.
4. Сравнить candidate с точным baseline: endpoints должны совпасть; допустимы ноль или одна отличающаяся внутренняя вершина. Изменение обеих ординат одной вершины считается одним изменением вершины.
5. Отдельно определить уже изменённую вершину current относительно точного baseline. При current diff в A и candidate diff в B, где A != B, отклонить переход: нужен отдельный Revert. Current с несколькими отличиями от baseline — повреждённый/неподдерживаемый контекст; не исправлять его автоматически.
6. Сравнить candidate с current для определения no-op. Candidate == baseline задаёт `operation=unchanged`; иначе `operation=updated`. Само вычисление fingerprint не зависит от current и этого сравнения.
7. Перед фактической mutation следующего этапа календаря выполнить spatial checks resulting geometry в PostGIS. Структурная допустимость не доказывает valid/simple/AOI.

Проверки шага 5 относятся к новой команде после распознавания replay, а не к повторной оценке уже выполненной команды.

### Таблица переходов

| Current относительно baseline | Candidate относительно baseline | Результат |
| --- | --- | --- |
| Нет отличий | Нет отличий | No-op |
| Нет отличий | Отличается A | Первое изменение A |
| Отличается A | Та же точная geometry, что current | No-op |
| Отличается A | Новая позиция A | Повторное изменение A |
| Отличается A | Нет отличий | Revert |
| Отличается A | Отличается B | Отказ, сначала отдельный Revert |

Независимо от таблицы, candidate с изменённым endpoint или двумя отличающимися внутренними вершинами отклоняется. Входные отличия, исчезающие при сравнении на сетке, сами по себе отказа не вызывают.

## Проектирование: command fingerprint

Пользователь согласовал контракт fingerprint ответом «Да». Детальная спецификация сериализации и контрольные примеры будут зафиксированы в итоговом design document до реализации.

### Назначение и состав

Fingerprint идентифицирует нормализованный intent в неизменяемом контексте. Предлагаемый внешний формат: `geom-v1:sha256:<64 lowercase hex digits>`. Версия формата фиксируется контрактом geometry policy v1; будущий несовместимый алгоритм не подменяет v1 для существующих EditVersion.

В хешируемое представление входят:

- версия формата fingerprint;
- `workOrderId`, `editVersionId`, `featureId`, `actorUserId`;
- baseline identity: `defaultStateId`, `baseNetworkRevision`;
- ожидаемый `draftVersionToken` как точная opaque string из запроса;
- постоянный тип команды `replace_feature_geometry`: Save и Revert используют одну операцию замены resulting geometry;
- закреплённые шаг, rounding mode, версия geometry policy и SRID `4326`;
- baseline structure hash, связывающий geometry type, SRID, размерность, число частей/вершин и точную упорядоченную последовательность baseline coordinates;
- представление resulting candidate geometry или специальное представление входа с несовместимой структурой;
- индекс внутренней вершины, если candidate отличается от baseline ровно в одной внутренней вершине; иначе `null`. Полная geometry остаётся в представлении и не теряется при `null`.

`commandId` — ключ registry и не входит в fingerprint. Не входят current geometry, current draft revision, время, correlationId, результат spatial validation, текст ошибки или verdict перехода. Поле `draftVersionToken` в fingerprint — именно ожидаемый token запроса, а не текущая revision из БД. `operation=updated|unchanged` в ответе не подменяет постоянный тип команды.

### Представление чисел и байтов

Внутри хешируемого документа координаты представлены каноническими десятичными строками: без лишних конечных нулей, без экспоненты, с единым нулём `0`. Поэтому `1`, `1.0`, `1e0` совпадают, а `-0` и `0` не различаются. Эта сериализация не должна зависеть от Decimal context или проходить через float. Строки являются внутренним форматом fingerprint; HTTP geometry по-прежнему использует JSON numbers.

UUID сериализуются единообразно. Ключи JSON сортируются, whitespace вне значений отсутствует, escaping имеет фиксированный режим, хешируются UTF-8 bytes. Порядок координатных массивов сохраняется: линия в обратном направлении не становится эквивалентной исходной. Числовые ограничения входа и длина канонической записи будут явно ограничены в разделе числового контракта.

### Структурно недопустимые запросы

Нужен fingerprint и для запроса, который дошёл до use case, но нарушает structure guard:

1. Если тип и количество координат позволяют сопоставить request с baseline, используется построенная candidate geometry — даже когда изменены endpoints или несколько внутренних вершин. Представление не зависит от последующего отказа.
2. Если структура не позволяет сопоставление, используется отдельный тег `unmatched_structure` и полное входное geometry с нормализованной десятичной записью чисел, без округления к сетке и без усечения массива. Такой вход не выдаётся за canonical resulting geometry. Числовые записи одного значения эквивалентны, но разные входные значения в этой ветке не объединяются по сетке.
3. Форматные ошибки, включая пустой LineString, не доходят до этого контракта и не резервируют CommandId.

Таким образом, исправление числа вершин меняет представление/fingerprint; endpoint violation не исчезает из идентичности команды. Для корректной структуры несколько raw requests, дающих одну candidate geometry, обозначают один canonical intent.

### Последствия для replay

- Тот же ID и fingerprint возвращают сохранённый terminal result.
- Тот же ID и другой fingerprint дают `COMMAND_ID_REUSED`.
- Новый ID при том же fingerprint является новой командой, которая проходит актуальные guards.
- Смена current snapshot или общих settings не меняет fingerprint прежнего request: baseline и geometry policy закреплены, expected token взят из запроса.
- Если команда перемещения B получила durable rejection из-за ранее изменённой A, последующий Revert A не превращает повтор прежнего ID для B в новую попытку. Он возвращает прежний отказ; новая попытка после Revert получает новый ID и актуальный token. Исключение повторной проверки доступа, уже принятое в спецификации Дня 2, сохраняется и реализуется будущей Save orchestration.

Обязательные проверки fingerprint: фиксированные ожидаемые digest для контрольных примеров; эквивалентные числовые записи; изменение каждого значимого поля; неизменность при смене current/global settings; endpoint/count/multiple-vertex rejection; baseline/no-op/Revert и отсутствие float conversion в числовом представлении.

## Проектирование: durable policy и обновление существующих версий

Пользователь согласовал хранение policy, однократное назначение и порядок обновления ответом «Да».

### Хранение

Добавить в `work_order.edit_versions` три NOT NULL поля:

- `geometry_xy_resolution`: точное NUMERIC без преобразования через float; допустимый диапазон задаётся числовым контрактом;
- `geometry_rounding_mode`: фиксированное значение `ROUND_HALF_AWAY_FROM_ZERO` для policy v1;
- `geometry_policy_version`: целая версия правил, первоначально `1`.

Policy v1 фиксирует origin `0`, SRID `4326`, XY, алгоритм baseline-aware canonicalization и формат fingerprint v1. Изменение любого из трёх полей после создания запрещается на уровне БД. SQLAlchemy metadata отражает столбцы и CHECK constraints; trigger неизменности, как и в Днях 2–3, создаётся Alembic.

Постоянный server default для шага не устанавливается: новые EditVersion должны явно получать policy от пути создания, а не случайно возвращаться к универсальному шагу независимо от runtime settings.

### Обновление

Новая migration добавляет поля, однократно заполняет policy всех существующих версий из конфигурации обновления, затем включает NOT NULL, CHECK и guard неизменности. DDL и backfill выполняются одной transaction. Geometry, draft revision, operation, registry и history при этом не меняются. Downgrade удаляет добавленную policy и guard; это потеря закреплённых правил, что будет явно отмечено в runbook.

В текущем Compose сервис migrate получает только DATABASE_URL. В рамках Дня 4 ему необходимо передать те же geometry settings, что API; общий валидатор policy не должен требовать JWT/security settings для запуска миграции. Историческая migration должна сохранять собственный стабильный контракт, а не зависеть от будущих изменений runtime validation. Точные способы устранения дублирования/фиксации validation будут описаны в плане.

Для текущего demo-развёртывания предлагается согласованное обновление с остановленным API: единая конфигурация для migration и нового приложения, migration, затем запуск API. Rolling upgrade с одновременно работающим старым writer не включается в scope. Это предотвращает создание версий старым кодом без обязательных policy fields во время обновления.

### Создание и повторное открытие

При создании новой EditVersion `EditVersionService` передаёт проверенную текущую policy в `WorkOrderRepository.create_open_edit_version`; root и policy записываются атомарно. Повторное открытие через `touch_edit_version` не переназначает policy. Чтение policy для canonicalization и fingerprint выполняется из EditVersion, а не из глобальных settings.

Restart/configuration change не запускает повторный backfill. Новая конфигурация влияет только на версии, созданные после изменения. Неизвестная geometry policy version не обрабатывается алгоритмом v1 как будто она известна; это несовместимость контекста, которую следует явно отклонить.

### Проверки

Migration/backfill на non-default grid; повторный запуск без переназначения; rollback при недопустимой конфигурации; новые версии до/после смены settings; reopen; неизменность policy прямым SQL; metadata parity; чтение через новую session после restart; отсутствие изменения baseline/current geometry, revisions и history.

## Проектирование: числовые границы и точный readback

Пользователь отклонил первоначальное предложение субмиллиметровой сетки и затем согласовал минимальный шаг `0.0000001°`. Раздел обновлён под это решение. Технические ограничения представления чисел и детали readback остаются проектными предложениями до рассмотрения итоговой спецификации.

### Поддерживаемая сетка

- Default остаётся `0.0000001°`.
- Минимальный шаг `0.0000001°`, примерно 8–11 мм на широте demo. Более мелкие шаги не поддерживаются.
- Для предлагаемого числового контракта значение шага содержит не больше 9 значащих десятичных позиций после запятой, без учёта лишних конечных нулей. Таким образом поддерживается и уже предусмотренный тестами `0.00000025°`: большее число знаков в записи шага не означает меньший шаг сетки. Это техническое ограничение представления, которое проверяется отдельно от минимальной величины шага.
- Верхняя граница — `360°`, полный оборот долготы. Более крупная сетка для ограниченных EPSG:4326 координат при origin 0 не даёт полезной операции перемещения; она отклоняется как configuration error, а не молча заменяется default.
- Origin `0`; policy v1 поддерживает только SRID 4326 и XY. Это не positional accuracy specification.
- Недопустимая настройка блокирует обновление/запуск, а не записывается в новые версии. Это намеренно сужает ранее принятый settings-only контракт «любой finite positive Decimal»: существующий тест принятия `1E+1000` должен быть заменён проверкой отказа и явными boundary cases. Изменение будет отражено в спецификации и приёмке.

Кратность и числовые границы проверяются точной арифметикой, не float. Более мелкая сетка требует отдельного расширения проверенного контракта; из изменения точности сериализации автоматически не следует её поддержка.

### Вход и расчёт

Транспортный parser будущего Save читает исходные JSON numbers в Decimal до float-схемы. Координаты-строки, bool, null, NaN/Infinity и неправильные XY-пары отклоняются как request validation; JSON scientific notation допустима. Дублирующиеся JSON keys отклоняются, чтобы запрос не имел нескольких трактовок.

Предлагаемые вычислительные пределы: до 64 символов в исходном числовом token координаты и абсолютное значение явно заданной десятичной экспоненты не больше 324. Это допускает согласованный пример непосредственно ниже midpoint и обычные shortest representations любых конечных binary64 координат в географическом диапазоне, но исключает неограниченные числовые вычисления. Это ограничение размера входного числа, а не поддержка перемещений с такой пространственной точностью. Значение проверяется в диапазоне X `[-180,180]`, Y `[-90,90]` до canonicalization. Если после canonicalization значение вышло за диапазон, domain результат — `GEOMETRY_INVALID`; clamp не применяется.

Canonicalization выполняется с контролируемой точностью и режимом округления, независимо от внешнего Decimal context. Потеря информации при промежуточном делении возле midpoint недопустима. Её отсутствие требуется доказать тестами точных midpoint и ближайших допустимых чисел с обеих сторон на шагах вроде `0.00000025` и `0.0000003`, которые не являются степенями десяти.

### Baseline и current из БД

Точное сохранение baseline означает сохранение значений координат, уже находящихся в PostGIS, а не восстановление неизвестного исходного десятичного литерала до их первого сохранения. Для вычислений baseline/current читаются через бинарное представление EWKB, без промежуточного `ST_AsGeoJSON(...,9)`.

В адаптере каждому конечному binary64 значению соответствует детерминированная кратчайшая десятичная запись, которая при обратном преобразовании воспроизводит то же binary64 значение. Эта запись используется как Decimal baseline для числового сравнения и fingerprint. Исходные значения baseline сохраняются для построения resulting geometry; восстановление точного baseline не выполняется из обрезанной девятизначной проекции.

На выходе координаты остаются JSON numbers. Преобразование рассчитанной canonical координаты в storage float допускается только на границе адаптера с проверкой обратимости принятого десятичного представления. Это не означает, что десятичные дроби становятся точно представимыми в binary64: гарантия — возврат к той же canonical decimal координате и воспроизведение baseline storage values.

### Изменения readback в границах Дня 4

Для геометрии features в workspace требуется убрать потерю точности из-за `ST_AsGeoJSON` с default 9 digits. Предлагаемый путь — передавать geometry через EWKB до backend-адаптера и формировать GeoJSON coordinates из сохранённых значений без десятичного обрезания. Уже установленные GeoAlchemy2/Shapely позволяют реализовать этот адаптер без новой зависимости. Geometry type, порядок координат и SRID проверяются; неподдерживаемая размерность не отбрасывается молча.

Это точечная корректировка числового readback; новые поля workspace `changeSet`, `basicValidation` и Save endpoint остаются последующим дням. Изменение необходимо для уже согласованной гарантии baseline вне сетки и входит в проектирование Дня 4 как её прямая зависимость.

### Проверяемая гарантия

- Для canonical grid coordinates: Decimal → storage → JSON → Decimal даёт то же canonical число.
- Для исходных baseline coordinates вне сетки: нетронутые ординаты и Revert сохраняют исходные storage values; сравнение в integration tests выполняется через координаты и EWKB.
- Проверяются отрицательные значения, ноль, координаты около границ диапазона, baseline длиннее 9 decimal places и около границы округления, non-default grid, новый HTTP/readback cycle и новая DB session.
- Сохранение baseline signed zero при копировании не должно вызывать искусственное событие; fingerprint нормализует числовой ноль согласно согласованному контракту.

Реальный PostGIS/HTTP round-trip ещё не проверялся. Числовые гарантии выше являются критериями будущей реализации, а не заявлением об уже прошедших тестах.
