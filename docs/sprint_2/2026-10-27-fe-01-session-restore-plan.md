## Цель и ограничения

Повторное восстановление сессии удерживает экран ожидания до результата или существующего HTTP timeout. Его устаревшее продолжение не меняет новую сессию и её рабочий контекст.

- В scope: «повтор восстановления → новый вход → поздний ответ восстановления», включая новый вход того же пользователя.
- Во время ожидания нет отмены, перехода к другому входу, повторной кнопки retry или выхода с экрана ошибки.
- Сохранить timeout 30 секунд, текущие тексты ошибок, правила initial/runtime, хранение access token в памяти и server-side guards.
- Общая координация login/logout/restore, межвкладочная AR-01, backend и cookie protocol не входят в изменение.
- Защита store не отменяет `Set-Cookie` уже полученного ответа. Штатный UI предотвращает исходную конкурентную отправку; согласованность cookie при произвольных принудительных auth-вызовах не заявляется.
- Выполнять последовательно, без делегирования. Сохранять чужие изменения; оставлять результат unstaged. Не выполнять `git add`, `git commit`, `git push`.
- Документы писать по-русски, текстовые файлы — UTF-8 с LF. Не обновлять память пересказом этого плана.

- [x] Установить признак только у `refreshSession`. Сохранить endpoint, `withCredentials`, body и возвращаемый тип.
- [x] При этом признаке response interceptor не вызывает `handleUnauthorizedResponse`, но возвращает исходный rejected promise. `restoreSession.catch` остаётся владельцем обработки отказа.
- [x] Для остальных запросов сохранить обработку 401, `403 ROLE_NOT_ALLOWED`, `403 USER_INACTIVE`, передачу request epoch и отсутствие вызова backend logout.
- [x] Обновить API-тест точной конфигурации refresh; подтвердить, что login/logout не получают исключение автоматически.
- [x] Покрыть interceptor матрицей: caller-managed 401/403 не очищает сессию; обычные 401/указанные 403 делегируются; 503 и прочие ошибки сохраняют исходный отказ без новой auth-очистки.

**Готовность шага:** refresh-ошибка достигает store без предварительных побочных эффектов, поведение остальных запросов сохранено.

## 3. Ограничить право старого restore изменять состояние

**Файл:** `apps/frontend/src/stores/auth.ts`.

- [x] Ввести идентичность попытки восстановления, принадлежащую экземпляру store, а не глобальную переменную модуля. Каждая попытка захватывает своё значение до `await`.
- [x] В начале `loginWithPassword`, до запроса login, инвалидировать прежний restore. Передать управление состоянием новому входу: старое ожидание больше не владеет `isRestoring`; не оставлять экран заблокированным, если новый login завершится ошибкой.
- [x] Успех restore применяет `setAuth` только пока попытка актуальна. Ошибка проверяет актуальность до `parseApiError`, `clearLocalSession` и установки сообщения. Устаревшие исходы завершаются без эффектов.
- [x] Защитить `finally`: завершившийся старый restore не меняет readiness новой сессии. Собственные изменения epoch в актуальных `setAuth`/`clearLocalSession` не должны мешать нормальному завершению этой же попытки.
- [x] Сохранить нынешнюю семантику `sessionEpoch` для обычных HTTP-запросов и recovery. Не заменять идентичность попытки сравнением user id и не увеличивать epoch на каждый refresh ради этого исправления.
- [x] Сохранить `preserveWorkOrderStateOnInitialUser`, initial 401 с принудительным reset, initial 503 с сохранением маркеров и runtime-представление ошибки.
- [x] Не добавлять очередь всех auth-команд, новую политику login/login или изменения logout. Не возобновлять инвалидированный restore после ошибки нового login.
- [x] Проверить и успешный, и неуспешный новый login: старый restore остаётся неактуальным, ожидание не зависает. Это проверка передачи управления в исходном сценарии, а не расширение до общей координации авторизации.

**Готовность шага:** deferred-матрица шага 1 проходит; актуальные success/error всегда завершают ожидание; новый вход того же actor защищён.
