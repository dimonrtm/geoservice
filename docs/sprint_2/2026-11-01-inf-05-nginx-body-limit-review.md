# INF-05 — P2: production proxy отклоняет крупный Save до backend

Дата: 2026-11-01. HEAD: `c85360f2c98548df9d24eabf9d857c860c801659`.
Статус: исходная находка, исправлена отдельной задачей 2026-11-01;
[отчёт реализации](2026-11-01-inf-05-save-size-implementation-report.md).
Остальной текст сохраняет обстоятельства исходного воспроизведения до исправления.
Добавлена вместо снятой INF-04; её номер не переиспользуется.

## Суть и причина

`apps/frontend/nginx.conf:15` направляет `/api/v1/` в API, но не задаёт
`client_max_body_size`. Production Dockerfile использует `nginx:1.27-alpine`
и копирует этот файл в `/etc/nginx/conf.d/default.conf`.
Действует стандартный предел тела запроса nginx `1m` (1 048 576 байт);
превышение возвращает 413. Основание —
[официальная документация nginx](https://nginx.org/en/docs/http/ngx_http_core_module.html#client_max_body_size)
и реальное воспроизведение ниже на nginx 1.27.5.

Frontend передаёт полную геометрию линии, даже при изменении одной вершины:
`apps/frontend/src/stores/workOrders.ts:959`,
`apps/frontend/src/api/workOrders.ts:42`. Backend parser
`apps/backend/utility_service/web_api/parsers/geometry_save_request.py:32`
не устанавливает аналогичного предела тела или количества вершин.
Поэтому крупная линия может быть корректна по формату API, но production proxy
блокирует саму передачу команды. Маленькая demo-линия не выявляет эту границу.

## Сценарий и последствия

Для редактируемой линии полное JSON-тело Save превышает 1 MiB. При отправке
через production nginx запрос получает `413 text/html` до вызова API/parser.
Команда не достигает доменных guards и persistence; повтор того же тела
не устраняет ограничение. Это ограничение доступности Save для крупных линий,
а не доказательство потери сохранённых данных или обхода авторизации.

P2 — оценка ревью: затронут production-путь основной команды, но маленький
demo dataset проходит. Частота таких линий в реальных данных не измерялась.

## Проверка принятых границ

- Дизайн INF-02, раздел «nginx: сохранение API-контракта», требует передачи
  тела, Content-Type и ответов API. Ограничение тела до 1 MiB в нём не закреплено.
- В runbook явно принят restart frontend при изменении IP backend; это
  поведение рассмотрено и исключено из новых находок.
- BE-01 снята пользователем: стоимость parser для 100 000 вершин приемлема
  в редком случае. INF-05 не возвращает претензию к времени parser и не
  предлагает автоматически вводить ограничение числа вершин.
- В Code_wiki есть legacy-требование 20MB для другого API-контракта.
  Оно не использовано как утверждённый размер лимита Save Sprint 2.
- `DDD_Wiki/invariants/edit_version_persisted_edit_invariants.md` описывает
  изменение одной внутренней вершины при сохранении остальных. Размер
  отправляемого полного LineString от этого не становится постоянным.

## Изолированное воспроизведение

Команда из корня репозитория:

```powershell
& docs/sprint_2/evidence/code-review/verify-nginx-body-limit.ps1
```

Runner создаёт уникальную внутреннюю Docker-сеть без опубликованных портов,
тестовый Python HTTP upstream с настоящим parser из текущего checkout
и nginx с текущим `apps/frontend/nginx.conf`, смонтированным read-only.
Client последовательно отправляет одинаковое тело напрямую и через nginx.
Данные синтетические: 60 000 различных последовательных XY на прямой,
без дубликатов; это не измерение production dataset.

| Случай | Размер | Прямо в HTTP adapter настоящего parser | Через текущий nginx |
| --- | ---: | --- | --- |
| 3 вершины | 191 байт | 200, JSON, 3 вершины | 200, JSON, 3 вершины |
| 60 000 вершин | 1 433 457 байт | 200, JSON, 60 000 вершин | 413, HTML nginx |

Итоговый запуск exit 0. Первый запуск probe завершился ошибкой импорта
`utility_service`; исправлен только путь импорта диагностического скрипта,
затем проверка повторена. В обоих запусках собственные контейнеры и сеть удалены.

Использованы имеющиеся локальные образы `geoservice-day14-check:latest`
и `geoservice-inf02-e06a7579-frontend-prod:latest`; свежая сборка production
приложения не выполнялась. Версия nginx — 1.27.5. Python-исходники parser
и nginx server config взяты из текущего checkout через read-only mounts.

## Ограничения доказательства и дальнейшего разбора

Upstream — диагностический HTTP adapter, не полный FastAPI endpoint. Его 200
означает принятие формата настоящим parser, а не успешный доменный Save.
Авторизация, принадлежность линии наряду, AOI, positional policy, существующая
геометрия, token и запись в БД не проверялись. На штатной L-003 ошибка не
воспроизводилась: она слишком мала. Доказан именно преждевременный отказ proxy
на большом теле, независимо от последующего доменного результата.

Точное допустимое ограничение размера, пользовательская реакция и критерии
исправления требуют отдельного разбора. Конфигурация и продуктовый код не менялись;
никакое решение о снятии лимита, выборе 20MB или расширении CI не принято.
Agent memory не дублирует отчёт: решение по INF-04 и новая находка сохранены
в Sprint 2, отдельный repository-change ingest не нужен.
