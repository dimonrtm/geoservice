## Причинная цепочка в текущем коде

### Поправка по результату реализации

Браузерный прогон выявил пропущенный при анализе guard:
`apps/frontend/src/domain/workspaceLineInteraction.ts`, функции
`lineSelectionBlockReason` и `vertexMoveBlockReason`, разрешают ровно три вершины.
Следовательно, текущий UI не отправляет Save большой линии из первоначального
probe. INF-05 воспроизводится на API/proxy-пути, но не является воспроизведённым
отказом штатного UI на такой линии. Полный browser acceptance на большой fixture
из дизайна невозможен без изменения этого guard и связанных проверок.
Пользователь уточнил приёмку: большую линию проверить настоящим API через nginx
с БД, браузерный Save/Revert — на обычной линии. UI не расширяется. Продуктовая
гарантия для доступных UI линий сохраняется; исправление дополнительно снимает
скрытый предел API/proxy для доменно допустимых больших линий.

| Участок | Наблюдаемое поведение | Следствие |
| --- | --- | --- |
| `apps/frontend/src/stores/workOrders.ts`, `saveLocalDraft` | Создаёт `commandId`, использует source token, копирует всю candidate geometry | Сдвиг одной вершины не означает маленький запрос |
| `apps/frontend/src/api/workOrders.ts`, `saveFeatureGeometry` | PUT полного запроса в `/api/v1/work-orders/.../edit-versions/.../features/.../geometry` | Размер включает геометрию и поля конверта |
| `apps/frontend/nginx.conf` | `/api/v1/` проксируется без явного ограничения размера | Действует стандартный лимит nginx |
| `apps/frontend/Dockerfile`, target `prod` | Копирует конфигурацию в `nginx:1.27-alpine` | Production-путь отличается от прямого обращения к API |
| `apps/backend/utility_service/web_api/api/work_orders.py` | После зависимостей endpoint читает `await request.body()` и вызывает parser | При отказе proxy тело не достигает endpoint |
| `apps/backend/utility_service/web_api/parsers/geometry_save_request.py` | Проверяет JSON, поля, числовые XY и диапазоны; нет верхнего предела числа вершин/байт | Форматно допустимое тело может быть больше лимита proxy |

Parser ограничивает длину числового токена 64 символами и показатель степени;
это не ограничение размера всей команды. Пустой token запрещён, верхняя длина
token в parser не установлена. Число вершин не определяет точный размер JSON:
влияют запись координат и сериализация. В прежнем BE-01 probe 100 000 вершин
занимали 800 132 байта, а INF-05 probe с 60 000 вершинами — 1 433 457 байт.
Поэтому прежнее принятие времени parser не подтверждает прохождение proxy.

## Что доказало существующее воспроизведение

Тело 191 байт проходит напрямую и через nginx. Тело 1 433 457 байт получает
200 от HTTP adapter настоящего parser и 413 HTML через nginx 1.27.5.
Конфигурация nginx и Python-исходники были смонтированы из checkout read-only;
использовались существующие образы, не свежая сборка всего приложения.

200 adapter не доказывает успешный Save: не проверены авторизация, baseline,
принадлежность feature версии, AOI, изменение ровно одной внутренней вершины,
token, журнал команды и транзакция БД. Доказан отказ транспортного слоя
раньше этих проверок. Частота проблемы и фактическая производительность
полного пути на больших линиях неизвестны.

## Последствие для восстановления — статический вывод

`parseApiError.ts` классифицирует Axios response с 413 HTML как `kind=http`.
`workspaceSaveErrors.ts` не распознаёт 413 отдельно: результат —
`blocked / protocol / SAVE_OUTCOME_UNCONFIRMED`.
`workspaceRecovery.ts`, функция `send`, сохраняет protocol block и прекращает
цикл отправки. Проверки `blocks.length` запрещают дальнейший запуск;
восстановление доступа удаляет только access block.

Таким образом, текущий путь не является бесконечным автоматическим повтором
413. Возникает сохранённый заблокированный recovery context. Одного устранения
лимита инфраструктуры недостаточно, чтобы утверждать автоматическое возобновление
уже заблокированного контекста. Это вывод чтения кода, не новый browser test.

Отдельно требуется различать первый отказ proxy и 413 при повторе после ранее
потерянного ответа. Во втором случае 413 текущей попытки сам по себе не доказывает,
что первоначальная операция не была сохранена. Автоматически считать прежний
intent отменённым или создавать новый `CommandId` из этого наблюдения нельзя.

## Принятые доменные ограничения

Save заменяет полную resulting geometry. Непустое изменение первого slice —
сдвиг одной внутренней вершины; остальные координаты и число вершин сохраняются.
Revert передаёт baseline через тот же командный контракт и подвержен тому же
транспортному ограничению. Retry сохраняет `CommandId` и payload; readback
отдельно подтверждает актуальное состояние. Authoritative `Default` не меняется.

В прочитанных контракте команды и инвариантах нет продуктового потолка размера
линии. Его отсутствие также не является доказанной гарантией обработки
неограниченного объёма. Legacy `Content-Length <= 20MB` в
`Code_wiki/архитектура/api_contract_first_release_requirements.md` относится
к другому контракту; перенос значения в Sprint 2 не согласован.

BE-01 снята пользователем: разбор 100 000 вершин за 0,578 секунды приемлем
для редкого случая. INF-05 не возобновляет претензию к parser performance.
INF-04 снята: существующие infra contract tests остаются локальными;
новый CI gate из этой задачи автоматически не следует.

## Инфраструктурная граница и пробелы проверки

Принятый INF-02 путь включает внешнее завершение HTTPS, затем frontend nginx,
затем внутренний API. Настройка внешнего TLS-компонента не входит в прежнюю
реализацию. Его ограничения размера не исследованы; локальный успех внутреннего
nginx не доказывает прохождение любого внешнего proxy.

HTTP client использует timeout 30 секунд. Размер, время передачи, время parser,
доменные проверки и доступность browser storage — разные ограничения;
существующее evidence не характеризует их на полном большом Save.
Нет основания считать их отдельными доказанными дефектами INF-05.

## Неуточнённые требования

До выбора решений нужно установить продуктовую гарантию размера,
границы обработки слишком большого запроса, судьбу уже заблокированных
контекстов и глубину приёмки полного Save/Revert. Эти вопросы обсуждаются
последовательно; список не является принятой программой расширения задачи.

### Вопрос 1 — ожидаемая гарантия

Должен ли редактор иметь возможность сохранять допустимую правку любой линии,
которую система уже загрузила и разрешила редактировать, независимо от размера
полного запроса Save?

Ответ пользователя: «Да».

Принята продуктовая гарантия: размер полного запроса сам по себе не должен
препятствовать сохранению допустимой правки любой линии, которую система уже
загрузила и разрешила редактировать. Конкретный способ обеспечения гарантии
не выбран; ответ не означает принятия настройки nginx или изменения формата команды.

### Вопрос 2 — уже заблокированные намерения

Входит ли в INF-05 восстановление уже сохранённых в браузере попыток Save/Revert,
которые получили 413 и оказались в protocol block, с сохранением прежнего намерения
и без повторного ручного редактирования линии?

Ответ пользователя: «Нет в текущем состоянии проекта таких линий нет.
А после исправления они не будут появлятся».

Восстановление ранее заблокированных попыток исключено из INF-05. По сообщению
пользователя, сейчас таких линий нет. Ожидаемый результат исправления — отсутствие
новых отказов по размеру для линий, доступных для редактирования; это требование,
а не уже доказанное свойство реализации. Миграция сохранённых protocol blocks
не требуется. Общая recovery policy продолжает действовать для иных отказов.

### Вопрос 3 — внешняя инфраструктура

Сохраняется ли принятая в INF-02 граница: реализация и проверка охватывают
frontend nginx из репозитория и backend, а совместимость внешнего HTTPS proxy
с размером Save фиксируется как требование развёртывания без настройки этого
внешнего компонента в INF-05?

Ответ пользователя: «Да сохраняем».

Принята прежняя граница INF-02: реализация и проверка охватывают компоненты
репозитория; совместимость внешнего HTTPS proxy с размером Save фиксируется
в инструкции развёртывания. Настройка внешнего компонента не входит в INF-05.
Локальная проверка не будет выдаваться за проверку внешней инфраструктуры.

### Вопрос 4 — критерий приёмки

Должна ли приёмка INF-05 подтверждать полный пользовательский цикл на большой
синтетической линии: Save через production nginx, чтение сохранённой геометрии
после перезагрузки страницы и Revert?

Пользователь запросил объяснение способа приёмки. Описан отдельный локальный
production-стенд с временной БД, синтетической доменно допустимой линией,
запросом больше 1 MiB, browser Save, readback после reload и Revert с повторным
reload; evidence сохраняется в Sprint 2, ресурсы стенда удаляются.

Уточнение пользователя: «Только не тащи ее в ci. Оставь локальной проверкой».
Приёмка остаётся локальной; добавление CI job и изменения workflow исключены.
Большая fixture не меняет рабочий demo dataset и не вводит нагрузочный норматив.
Один большой пример проверяет прежний порог, а не доказывает неограниченную
масштабируемость. Проверка конфигурации дополняет этот пример.

## Готовность к обсуждению решений

Существенные требования уточнены: допустимый Save уже редактируемой линии
не должен отклоняться из-за размера; восстановление прежних protocol blocks
не входит в задачу; внешняя инфраструктура покрывается инструкцией; приёмка
полного пути локальная, без CI.

Пользователь выбрал вариант 2: отключить ограничение размера только для маршрута
сохранения геометрии. Вариант отключения для всего `/api/v1/` не выбран.
Пользователь принял [дизайн](2026-11-01-inf-05-save-size-design.md) сообщением
«Принимаю». Подготовлен [план реализации](2026-11-01-inf-05-save-size-plan.md).
Реализация и локальная приёмка завершены: [отчёт](2026-11-01-inf-05-save-size-implementation-report.md).

Отдельная agent memory не создаётся: материал сохранён здесь, уникального
долговременного знания вне этого документа пока нет.
