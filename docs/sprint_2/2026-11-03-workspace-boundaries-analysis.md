# Границы Workspace в редакторе

Анализ исходной реализации на 03.11.2026, Git `21a5a74`. Пути к удалённым при реализации файлам относятся к этой ревизии. [Итог реализации](2026-11-04-workspace-boundaries-report.md). Исходное требование пользователя относит Workspace к интерфейсу редактора и исключает его из доменных агрегатов.

## Где расходятся модель и реализация

| Участник сценария | За что отвечает сейчас | Основание |
| --- | --- | --- |
| WorkOrder | Назначение редактора, область работ и атомарное открытие версии. На наряд допускается одна открытая версия. | [Агрегат WorkOrder](../../DDD_Wiki/aggregates/work_order.md) |
| EditVersion | Рабочие копии объектов и связей, сохранение геометрии, версия черновика. Токен меняется при изменении содержимого всей версии. | [Агрегат EditVersion](../../DDD_Wiki/aggregates/edit_version.md) |
| Utility Network | Поставляет исходное состояние сети. Запрос экрана читает базовые объекты из схемы utility_network, а редактируемые копии и связи из work_order. Поэтому принадлежность объекта зависит в том числе от того, какую его версию читают. | [Карта контекстов](../../DDD_Wiki/context_map/geoservice_context_map.md), SQL (`apps/backend/utility_service/infrastructure/postgresql/sql/workspace_aggregate.sql`) |

У него нет собственной идентичности или операции сохранения. | [Workspace Loaded](../../Wiki/system_events/workspace_loaded.md), строки результата (`apps/backend/utility_service/infrastructure/postgresql/repository_rows/workspace.py`) |

## Что сегодня связано одним чтением

1. Клиент передаёт идентификаторы наряда и версии. Сервис отдельно проверяет активность и роль редактора. Затем проверяет назначение по наряду и состояния наряда и версии. Чужая версия скрыта ответом 404. WorkspaceService (`apps/backend/utility_service/use_cases/services/workspace_service.py`)
2. Репозиторий одним SQL-запросом получает данные для карты и для проверки черновика. Для карты отбираются объекты, пересекающие AOI, и связи с двумя видимыми концами. Для проверки изменений сравниваются все объекты версии с исходными, включая скрытые фильтром карты. Эти выборки имеют разный смысл. SQL (`apps/backend/utility_service/infrastructure/postgresql/sql/workspace_aggregate.sql`), проекция черновика (`apps/backend/utility_service/use_cases/services/workspace_draft_projection.py`)
3. Публичный GET возвращает вложенный ответ с нарядом, AOI, версией, геометрией, связями и состоянием черновика. Согласованность геометрии и токена при одновременном сохранении была явным требованием дня 8. Повтор команды может вернуть исторический результат, поэтому восстановление опирается на чтение актуального состояния. [Спецификация дня 8](2026-10-12-day-8-api-readback-design.md), [проверки конкурентного доступа](../../apps/backend/tests/integration_tests/test_workspace_save_concurrency.py)
4. На клиенте общий тип ответа используют хранилище нарядов, построение слоёв карты и логика локальных правок. Одно и то же имя встречается и у компонентов экрана, и на границе HTTP. [Контракт](../../apps/frontend/src/contracts/work-orders.ts), [хранилище](../../apps/frontend/src/stores/workOrders.ts), [слои карты](../../apps/frontend/src/map/workspace-layers.ts), [локальные изменения](../../apps/frontend/src/domain/workspaceDraft.ts)

## Уточнение пользователя от 03.11.2026

Данные наряда и его рабочей версии должны читаться из схемы `work_order`. Baseline должен получаться отдельно из контекста Utility Network. Сегодня это разделение нарушают и чтение экрана, и запрос контекста сохранения геометрии. SQL чтения (`apps/backend/utility_service/infrastructure/postgresql/sql/workspace_aggregate.sql`), [SQL сохранения](../../apps/backend/utility_service/infrastructure/postgresql/sql/edit_geometry_context.sql)

Пользователь уточнил общее правило: один репозиторий обращается к данным своего ограниченного контекста. Оно распространяется и на Save. Для серверной проверки рабочая версия и исходная линия читаются через репозитории соответствующих контекстов. Существующий запрос DefaultState использует только таблицы схемы `utility_network`. [Выборка исходного состояния](../../apps/backend/utility_service/infrastructure/postgresql/sql/default_state_aggregate.sql)

Пользователь подтвердил, что фронтенд получает baseline отдельным HTTP-запросом. Сейчас сервер сравнивает текущую и исходную геометрию, проверяет согласованность изменений по всей версии и возвращает в `changeSet.baselineGeometry` исходную геометрию изменённой линии. Проекция черновика (`apps/backend/utility_service/use_cases/services/workspace_draft_projection.py`)

После получения наряда и текущей геометрии клиент показывает карту в режиме просмотра, даже если baseline ещё загружается или запрос завершился ошибкой. Успешная загрузка baseline для открытой версии обязательна для редактирования. Сегодня клиент дожидается единого ответа до показа карты. [Открытие наряда](../../apps/frontend/src/stores/workOrders.ts)

Для текущего этапа клиент запрашивает baseline только одной редактируемой фичи. Внутренний запрос DefaultState сегодня читает все объекты и связи исходного состояния наряда. [Выборка DefaultState](../../apps/backend/utility_service/infrastructure/postgresql/sql/default_state_aggregate.sql)

В чистой версии целевая линия определяется выбором редактора. Если есть сохранённое изменение, допустимая линия уже известна по `changeSet.featureId`. [Правила выбора линии](../../apps/frontend/src/domain/workspaceLineInteraction.ts)

Пользователь подтвердил отдельное чтение ChangeSet для EditVersion. По этому ответу клиент узнаёт, есть ли сохранённая правка, какая фича и какая вершина изменены. Исходная геометрия приходит только по запросу baseline для одной фичи. Пока правок нет, ChangeSet пуст, хотя baseline выбранной для первой правки фичи уже существует. При раздельном чтении текущей карты и ChangeSet нужно учитывать сохранение из другой сессии между запросами. Нынешний контракт ChangeSet (`apps/backend/utility_service/use_cases/schemas/workspace/change_set_out.py`), [требования к актуальному состоянию](2026-10-12-day-8-api-readback-design.md)
## Уточнение о составе readback

Первый запрос readback возвращает WorkOrder вместе с EditVersion, текущей геометрией объектов и связями. Этого достаточно, чтобы показать карту в режиме просмотра. Затем клиент отдельно получает ChangeSet версии и baseline редактируемой фичи. Редактирование допускается после загрузки baseline этой фичи.

Если ChangeSet содержит изменённую фичу, клиент автоматически запрашивает её baseline по `featureId`, сразу после получения ChangeSet. Выбирать линию на карте для этого не требуется.

Пользователь разрешил удалить прежний `GET .../workspace` при переходе клиента на раздельное чтение. Поддержка старого HTTP-контракта не требуется.

Ответ с картой и ответ с ChangeSet, включая пустой, содержат `draftVersionToken` своей выборки. При несовпадении экран автоматически перечитывает данные и токены. Редактирование доступно после получения согласованной пары и baseline выбранной линии. Ответ от предыдущего чтения или другого открытого наряда не должен включать редактирование.

## Как сервис получает ChangeSet

Сервис читает текущую геометрию через репозиторий контекста `work_order`, а исходную геометрию закреплённого за версией снимка — через репозиторий контекста `utility_network`. При чтении ChangeSet сервис сравнивает координаты по порядку и определяет индекс изменённой вершины. Отдельное хранение индекса не требуется.

Если baseline недоступен, запрос ChangeSet завершается ошибкой. Клиент отличает ошибку от успешно прочитанного пустого ChangeSet. Уже загруженная карта остаётся в режиме просмотра, редактирование и откат недоступны.

Для открытой версии экран делает до пяти запросов ChangeSet за один цикл загрузки. Первый запрос выполняется сразу. После неудачи перед следующими попытками клиент ждёт последовательно 2, 5, 10 и 20 секунд. После пятой неудачи автоматические повторы прекращаются, карта остаётся в режиме просмотра. При первом успешном ответе повторы прекращаются, клиент сверяет полученный токен с токеном карты по общему правилу readback. [Существующие интервалы повторов в редакторе](../../apps/frontend/src/stores/workspaceRetry.ts)

После пятой неудачи экран показывает кнопку «Повторить». Нажатие запускает новый цикл загрузки ChangeSet для той же открытой версии без закрытия карты.

Для отдельного запроса baseline выбранной линии действует тот же лимит и те же интервалы. После исчерпания попыток «Повторить» перезапускает только загрузку baseline. Успешно полученный ChangeSet сохраняется.

## Граница модулей фронтенда

Пользователь потребовал выделить самостоятельные модули и на фронтенде. Сейчас один API-модуль обслуживает список нарядов, открытие версии, чтение Workspace и Save. Хранилище нарядов управляет также чтением карты, локальной правкой, откатом, навигацией и подключением recovery. Несколько компонентов обращаются к нему напрямую. При этом хранение незавершённых команд и их восстановление уже частично выделены. [API](../../apps/frontend/src/api/workOrders.ts), [хранилище нарядов](../../apps/frontend/src/stores/workOrders.ts), [восстановление](../../apps/frontend/src/stores/workspaceRecovery.ts)

Пользователь подтвердил расширенную границу. В `stores/workOrders.ts` остаётся только работа с нарядами. Кроме трёх модулей чтения, выделяются локальное редактирование, команды сохранения и отката, навигация. Перенос затрагивает также потребителей вне экрана нарядов: корневой компонент использует хранилище для навигации, а обработчики сессии — для очистки состояния и приостановки recovery. [Корневой компонент](../../apps/frontend/src/App.vue), [обработка сессии](../../apps/frontend/src/stores/auth.ts)
