# INF-05: крупный Save через production nginx

Дата: 2026-11-01. Статус: принят пользователем сообщением «Принимаю».
Основание: [анализ и ответы пользователя](2026-11-01-inf-05-save-size-analysis.md).

## Назначение и объём

Допустимая правка линии, уже загруженной и разрешённой для редактирования,
не должна отклоняться из-за размера полного запроса Save. Сейчас стандартный
лимит nginx 1 MiB отклоняет такой запрос до backend. Save и Revert используют
один маршрут и передают полную геометрию.

Это небольшое изменение конфигурации с локальной сквозной приёмкой.
Ограничение размера снимается только на пути сохранения геометрии; остальные
API сохраняют прежнее поведение. Формат команды, доменные guards, авторизация,
идемпотентность и recovery не меняются. Восстановление прежних protocol blocks
исключено пользователем: таких случаев сейчас нет. CI и workflow не меняются.

## Рассмотренные подходы

| Подход | Последствия | Решение |
| --- | --- | --- |
| Отключить предел для `/api/v1/` целиком | Минимальная настройка, но расширяет изменение на все API | Не выбран |
| Отключить предел только для пути Save/Revert геометрии | Соответствует INF-05; требует отдельного location с сохранением правил proxy | Выбран пользователем ответом «2» |
| Повысить конечный предел | Лишь переносит отказ на больший запрос; не обеспечивает принятую гарантию | Не соответствует требованиям |

## Изменение nginx

В `apps/frontend/nginx.conf` добавить отдельный регистрозависимый regex location
для канонического пути, которым пользуется frontend:

```text
^/api/v1/work-orders/[^/]+/edit-versions/[^/]+/features/[^/]+/geometry$
```

Для него задать `client_max_body_size 0`. Полный путь ограничен началом и концом:
соседние endpoints и дополнительные суффиксы не получают исключение. Проверка
UUID и допустимого HTTP method остаётся в backend. Настройка применяется к пути,
а не только к PUT; иных операций backend на этом endpoint она не создаёт.

Сохранить `proxy_pass http://utility_service:8000` без URI-части и переписывания
пути. Явно повторить действующие proxy-настройки общего API location: HTTP/1.1,
Host и Upgrade/Connection, read timeout, отключение cache, upstream retry и
перехвата ошибок, безопасные access/error logs. Новый location не наследует
настройки соседнего location. Общий `/api/v1/` и раздача статики сохраняются.

Выбор regex и явного повторения небольшого блока настроек — техническое решение
автора дизайна. Оно не требует нового шаблонизатора, include-файла или изменения
Dockerfile. При реализации проверить приоритет location и фактическую конфигурацию
nginx. При последующих правках proxy оба блока должны оставаться согласованными.

Основание семантики директив:
[client_max_body_size и location](https://nginx.org/en/docs/http/ngx_http_core_module.html#client_max_body_size),
[proxy_pass](https://nginx.org/en/docs/http/ngx_http_proxy_module.html#proxy_pass).
Нулевое значение снимает проверку размера тела; regex location использует
proxy_pass без URI-части. Никакой новой клиентской или серверной квоты не вводится.

## Локальная приёмка

Уточнение пользователя при реализации: UI Дня 10 поддерживает ровно три вершины.
Большая линия проверяется настоящим API через nginx с БД; браузерный цикл
выполняется отдельно на штатной линии. Это заменяет первоначально согласованную
большую browser fixture. UI не расширяется.

Проверки запускаются вручную. Использовать подход из INF-02: отдельный Compose
project, временная БД, уникальные ресурсы, loopback port frontend, внутренний API,
настоящие production targets. Собирать текущий checkout, включая незакоммиченные
изменения, с действующим `.dockerignore`. Рабочие контейнеры и данные не менять.

1. Проверить `nginx -t` и доставку большого тела на точный geometry path;
   контроль с прежней конфигурацией должен показывать 413. Это проверка proxy,
   не подмена доказательства доменного Save.
2. Убедиться, что большое тело на соседнем API path по-прежнему получает 413,
   а маленький запрос проходит к upstream. Проверить отсутствие совпадения
   исключения с дополнительным суффиксом geometry path.
3. Создать только в тестовой БД доменно допустимую большую baseline-линию,
   наряд и доступ редактора. Линия простая, внутри AOI, с разными соседними XY;
   сдвиг одной внутренней вершины остаётся допустимым после канонизации.
4. Через настоящий API выполнить login, открыть EditVersion, прочитать workspace,
   изменить одну внутреннюю вершину и отправить Save через frontend nginx.
   Зафиксировать UTF-8 JSON-тело больше 1 048 576 байт и успешный ответ API.
5. Отдельным GET подтвердить сохранённую геометрию из backend, новый token,
   `hasPersistedChangeSet=true` и неизменность baseline. Проверить, что остальные
   вершины не изменены.
6. Выполнить Revert через тот же API-путь. Отдельным GET подтвердить
   равенство baseline и `hasPersistedChangeSet=false`. Проверить размер Revert:
   его тело тоже должно превышать прежний порог.
7. На свежей отдельной тестовой БД выполнить настоящий browser цикл из production
   bundle на штатной линии: login → drag → Save → reload → Revert → reload.
   Подтвердить изменённую вершину, tokens, change set, неизменность baseline
   и отсутствие блокировки recovery.
8. Проверить, что geometry endpoint без авторизации остаётся защищён backend,
   а ошибочные запросы не превращаются в HTML/200. Сохранить компактное evidence
   и удалить только ресурсы собственного стенда, включая временную БД.

Runner, инструкция и отчёт размещаются в `docs/sprint_2`; evidence — в
`docs/sprint_2/evidence/inf-05/`. Размер fixture выбирается по фактической
сериализации с запасом над прежним порогом, а не по одному числу вершин.
Приёмка не подключается ни к CI, ни к автоматически запускаемым существующим suites.

## Развёртывание и пределы утверждений

Инструкция требует совместимого поведения внешнего HTTPS proxy для того же
geometry path: его лимит не должен снова запрещать сохранение редактируемой
линии. Настройка и проверка внешнего компонента остаются вне INF-05.
Сохраняется принятое в INF-02 требование перезапуска frontend при смене IP backend.

После изменения потребуется пересборка и пересоздание production frontend,
поскольку конфигурация копируется в образ. Локальная приёмка использует новый образ.

Гарантия относится к отсутствию отказа по размеру тела. Она не обещает бесконечную
память, диск или время обработки: прежние таймауты и buffering не изменяются.
Проверка одной большой линии подтверждает API/DB сценарий выше старого порога;
отсутствие конечного лимита в выбранном location подтверждается отдельно
конфигурацией. Результаты не выдаются за нагрузочное испытание или проверку
любого внешнего proxy.
