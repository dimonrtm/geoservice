# BE-02: корректная очистка properties в legacy PATCH

Дата: 2026-11-01. Статус: принят пользователем («Принимаю»); реализован и проверен. Результаты: [verification.md](evidence/be-02/verification.md).

## Цель и основание

Устранить два сценария BE-02 из `backend-review.md`: очистка properties должна сохраняться и возвращать `{}` как при `geometry=null`, так и при одновременной передаче новой geometry. HTTP-ответ и содержимое `feature_updated` должны описывать результат этой записи.

Причина и источники разобраны в `2026-11-01-be-02-analysis.md`. Пустой словарь корректно передаётся repository, но сервис использует truthiness при сборке ответа. Это приводит либо к подстановке старых свойств, либо к исключению внутри транзакции.

## Согласованные требования

- Пользователь сохранил обязательность `geometry` и `properties` в JSON. Пропуск любого из этих полей остаётся ошибкой валидации.
- `properties={}` полностью очищает свойства; непустой объект полностью заменяет их; `properties=null` сохраняет прежние свойства при переданной geometry.
- `geometry=null` сохраняет прежнюю геометрию при переданных properties; оба поля `null` остаются недопустимыми.
- Пользователь выбрал локальное исправление сервиса без изменения repository-контракта.

## Подходы

1. **Выбран:** явно различать `None` и `{}` при сборке ответа. Минимальная область изменений, сохраняются SQL и существующий путь публикации.
2. **Рассмотрен:** возвращать полное состояние из `UPDATE ... RETURNING`. Это связывает DTO непосредственно с записанной строкой, но расширяет repository-контракт, SQL-проекцию, работу с геометрией и тестовые подмены. Для установленной причины BE-02 такой объём не требуется.

## Изменение

В `apps/backend/utility_service/use_cases/services/feature_service.py`, методе `update_feature`, выбирать `request.properties`, если это значение не `None`; иначе использовать properties ранее загруженного объекта. Существующая проверка невозможности собрать полное состояние сохраняется.

Условие чтения текущего объекта остаётся прежним: он нужен, когда geometry или properties равны `None`. При переданных geometry и `{}` результат собирается из запроса без дополнительного чтения. Сборка `FeatureOut` остаётся внутри транзакции. После успешного выхода из неё тот же объект используется для публикации и ответа.

## Границы

Не меняются HTTP/schema-контракт, SQL repository, optimistic version check, форматы ошибок, повышение legacy version при успешном UPDATE, правила доступа и значение legacy-флага по умолчанию. No-op продолжает обрабатываться по существующим правилам legacy.

Не добавляются изменение атрибутов Utility EditVersion, гарантированная доставка realtime, исправления BE-03/AR-02/AR-03, миграции или изменения frontend. Исправление содержимого события не означает гарантии его доставки: существующее поведение при ошибке publisher сохраняется.

## Критерии приёмки

| Сценарий | Ожидаемый результат |
|---|---|
| Исходные properties непустые; PATCH с `geometry=null, properties={}` | Успех, properties пустые, geometry прежняя, version увеличена на один |
| PATCH с новой допустимой geometry и `properties={}` | Успех, оба значения записаны, version увеличена на один; ошибочного 422 нет |
| Исходные properties уже `{}`; повторная очистка | Успех по существующим legacy-правилам, version увеличена на один |
| Новая geometry и `properties=null` | Прежние properties сохранены, включая случай прежнего `{}` |
| Непустые properties, в том числе ключи со значениями `false`, `0`, `null` | Словарь сохраняется полностью, значения не интерпретируются как отсутствие изменения |
| Успешная очистка | Properties и version в ответе и payload события совпадают с результатом записи |
| Конфликт version при очистке | Существующий отказ без записи и без публикации |
| Оба поля `null` или обязательное поле пропущено | Существующий отказ валидации до мутации |

## Проверка

Предлагаемые автором уровни проверки:

1. Регрессионные unit-проверки настоящего FeatureService с repository/publisher doubles: обе ветви очистки должны обнаруживать исходный дефект; проверить переданный repository словарь, результат и аргумент publisher. Дополнить проверки сохранения properties при `null` и отсутствия публикации при отказе. DummySession не считать доказательством commit/rollback.
2. Проверки request schema/HTTP-границы для обязательности полей и формы ответа. HTTP-проверка с подменённым сервисом не заменяет регрессионную проверку настоящего сервиса.
3. В disposable PostGIS-БД выполнить оба успешных сценария через настоящий сервис и repository; после завершения транзакции прочитать состояние из отдельной session. Сопоставить properties, geometry и version с ответом и перехваченным аргументом публикации. Проверить отсутствие изменений при stale version. Для проверки реального rollback вызвать контролируемое исключение после UPDATE, но до выхода из транзакции, и убедиться отдельным чтением, что исходное состояние сохранилось и публикации не было. Это тестовый сценарий, без новых production hooks.

Сквозная проверка доставки через WebSocket не обязательна для этой локальной причины: достаточно проверить содержимое переданного publisher объекта и существующую сериализацию события. Общая demo-БД не используется.

Точные имена тестов, использование существующих fixtures и способ тестового внедрения ошибки остаются исполнителю. Нельзя объявлять подтверждённый commit/rollback только по mock-проверкам.
