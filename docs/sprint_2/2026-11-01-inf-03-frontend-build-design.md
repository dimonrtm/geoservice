# INF-03: изоляция frontend Docker build

Дата: 2026-11-01. Статус: дизайн принят пользователем («Принимаю»). Подготовлен [план реализации](2026-11-01-inf-03-frontend-build-plan.md); исполнение завершено, см. [отчёт](2026-11-01-inf-03-frontend-build-implementation-report.md).
Основание: [анализ и ответы пользователя](2026-11-01-inf-03-frontend-build-analysis.md).

## Цель и согласованные границы

Обычная Docker-сборка из apps/frontend должна работать независимо от локальных node_modules, env-файлов, старого dist и служебных артефактов разработчика. Это относится к dev и prod. Актуальные исходники, включая незакоммиченные изменения, остаются входом сборки.

Пользователь согласовал:

- Docker dev/prod не подхватывают локальные frontend env-файлы.
- Локальный npm run dev продолжает их использовать.
- Dev-контейнер получает настройки явно при запуске; существующий VITE_API_BASE_URL в demo Compose сохраняется.
- Production использует существующий same-origin маршрут через nginx; отдельный публичный API endpoint сейчас не нужен.
- CI постоянно проверяет реальную Docker-сборку с искусственным загрязнением и завершается ошибкой при регрессии.
- Побайтовая идентичность образов при сборках в разные дни не требуется.

Это небольшая инфраструктурная задача: правила context, проверочный runner, CI job и документация. Изменения доменной модели и пользовательского интерфейса не требуются.

## Рассмотренные подходы

| Подход | Преимущество | Цена |
| --- | --- | --- |
| Список исключений в apps/frontend/.dockerignore | Минимальные изменения, новые исходники доступны без отдельного разрешения | Новые категории локальных артефактов требуют дополнения правил |
| Запрет всего context с разрешением необходимых входов | Новые посторонние файлы исключаются автоматически | Новые необходимые пути нужно добавлять в разрешения |

Пользователь выбрал первый подход ответом «1». Причина рекомендации агента: он соответствует конкретному дефекту, сохраняет текущую структуру сборки и дополняется проверкой поведения в CI.

## Правила сборки

Добавить apps/frontend/.dockerignore: исключить node_modules, dist/dist-ssr, coverage, кэши Vite, TypeScript build info, логи, метаданные Git, настройки IDE и типичный мусор ОС. Исключения каталогов зависимостей и env применяются также во вложенных путях. Файлы .env и семейство .env.* исключаются целиком, включая mode-specific варианты и .env.example. Последнее — выбор агента: шаблон не требуется сборке и остаётся доступен на компьютере.

Исходники src, ресурсы public, index.html, package.json, package-lock.json, конфигурация TypeScript/Vite и nginx.conf остаются доступны. Не исключать все dotfiles или все конфигурационные файлы общим правилом. Не добавлять Dockerfile-specific ignore, который мог бы перекрыть общий файл.

Dockerfile сохраняет существующую последовательность установки зависимостей и COPY, targets и базовые образы. Зависимости устанавливаются внутри Linux-сборки из текущего lock-файла. Изменять package manager и добавлять зависимости для проверок не требуется.

Не добавлять production build args или механизм runtime-подстановки env в nginx. Resolver API и его существующая возможность override вне стандартного Docker-пути не меняются. Изоляция context устраняет случайный источник override; отсутствие текущего сценария внешнего API не трактуется как требование удалить поддержку из кода.

## Постоянная проверка

Выбор агента: runner на Node.js со стандартной библиотекой, размещённый в docs/sprint_2/inf-03/, чтобы один сценарий запускался локально на Windows и в Linux CI. Он вызывает Docker через массив аргументов без сборки shell-команд из строк. Версии инструментов и итоговые результаты записываются без env-значений и секретов.

Runner создаёт принадлежащий ему временный context из актуальных исходников frontend. Подготовка не читает и не копирует реальные пользовательские env и node_modules: вместо них добавляет искусственные данные. Сам .dockerignore копируется из рабочего дерева. Подготовка fixtures явно отделяется от проверки: после добавления загрязнений context не очищается.

Искусственные загрязнения:

- маркер в node_modules и во вложенном node_modules;
- .env, .env.local, .env.production, .env.production.local и вложенный env-маркер;
- уникальный безвредный URL на домене .invalid в VITE_API_BASE_URL;
- старый файл dist и маркеры в представительных каталогах кэшей/служебных файлов.

Сначала проверить наличие fixtures во временном context: иначе тест мог бы пройти без проверяемого условия. Затем собрать текущий Dockerfile с target dev и проверить /app после общего COPY: искусственные env, старый dist и маркеры отсутствуют, а реальные установленные зависимости и нужные исходники присутствуют. Не требовать отсутствия самого node_modules: Linux npm ci должен его создать. Эта проверка покрывает общий base, наследуемый dev и build.

Из того же загрязнённого context собрать target prod. Проверить наличие index.html и собранных assets, отсутствие старого dist-файла и искусственного API URL в итоговой статике. Дополнительно проверить dev-контейнер с явно переданным VITE_API_BASE_URL: Vite запускается, отвечает по HTTP и использует явно переданное значение. Для этого не нужен реальный backend.

Проверка общего слоя необходима: Vite может очистить dist, а unused env могут не попасть в bundle. Чистый итоговый сайт сам по себе не доказывает чистоту сборочного слоя. Проверка не претендует на полный аудит cache exports или сетевого трафика BuildKit; запрет входов задаёт .dockerignore, а runner проверяет его эффект на широком COPY и итоговом продукте.

В CI добавить отдельный frontend Docker job на ubuntu-latest, с Node и Docker Buildx. Существующие npm jobs сохраняются. Ошибка сборки, проверки или отсутствие Docker завершают job ненулевым кодом, без успешного skip. Образы не публикуются. При необходимости сохранять краткое evidence и диагностический лог с ограниченным сроком хранения. Требование обязательного status check для merge зависит от настроек GitHub branch protection и не меняется одним workflow; изменение этих настроек не входит в задачу.

Runner удаляет только собственные временные файлы, контейнеры и теги образов, включая обработку ошибок; не выполняет общий Docker prune и не затрагивает существующий Compose-стенд, volumes и локальные env. Диагностика не должна выводить environment существующих пользовательских контейнеров.

## Приёмка и проверка чувствительности

| Проверка | Ожидаемый результат |
| --- | --- |
| Загрязнённый context, target dev | Сборка успешна; fixtures отсутствуют в /app; установленные зависимости присутствуют |
| Загрязнённый context, target prod | Сборка успешна; статика существует; посторонний URL и старый файл отсутствуют |
| Dev runtime env | Vite отвечает и учитывает явно заданный API URL |
| Контрольная регрессия в отдельной временной копии без ignore | Проверка обнаруживает загрязнение; исходное рабочее дерево не меняется |
| Обычная сборка из текущего Windows workspace после исправления | Dev/prod собираются с реальными локальными зависимостями на хосте; env-значения не выводятся |
| Существующие frontend проверки | format/lint/typecheck/tests/build проходят |

Контрольную регрессию выполнить при реализации, чтобы подтвердить чувствительность runner; второй заведомо неисправный build на каждом CI-запуске не обязателен. При локальной приёмке также собрать чистый временный context и сопоставить результаты проверок с загрязнённым: успех сборки, наличие статики, отсутствие примесей. Не сравнивать image digest как критерий идентичности.

Полный повтор Save/readback/Revert browser smoke не является новым постоянным требованием INF-03: клиентская логика, nginx routes и backend не меняются. Если реализация потребует их изменения, пересмотреть границы до продолжения.

## Не входит в задачу

Удаление пользовательских файлов, фиксация base images по digest, миграция package manager, обновление зависимостей, новый способ размещения frontend/API, изменение cookie/CORS и доменных guards, устранение INF-04, публикация образов и изменение настроек GitHub repository.
