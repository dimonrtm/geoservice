# S2-X01 — независимое восстановление команд редактора

Дата: 2026-10-23. Статус: письменная спецификация принята пользователем сообщением «Принимаю». Реализация и приёмка завершены: [отчёт](2026-10-23-s2-x01-recovery-implementation-report.md). День и дата выполнения не назначаются; календарь Sprint 2 не изменяется.

## 1. Назначение и основания

Редактор должен безопасно выяснять исход прежнего Save/Revert после потери ответа, продолжать независимую работу в других нарядах и возвращаться к восстановлению после закрытия браузера. Старое подтверждение не заменяет актуальную геометрию; управляемая навигация явно разрешает судьбу локальной правки.

## 2. Объём и неизменяемые границы

S2-06/readback, S2-07/Save API, S2-08/editing UI и S2-09/retry-recovery предоставляют базовую реализацию. Дорабатывается только недостающее поведение; уже выполненные требования подтверждаются регрессией.

Включено:

- Несколько независимых recovery contexts; unknown A не запрещает Save B/C. Продуктового лимита количества контекстов нет.
- Сохранность отправленных намерений после refresh, повторного входа и обычного закрытия/открытия браузера в том же профиле/origin при сохранности storage.
- Автовосстановление доступных контекстов; отдельное подтверждение каждого наряда после обнаруженной потери доступа.
- Сравнение source/candidate/current после stale; ручное создание новой правки, без переноса candidate.
- Управляемые переходы между нарядами и добровольный logout, правдивые сообщения, ручной маршрут разбора дефекта.

Сохраняются synchronous backend Save, атомарность terminal result, access/lifecycle/token guards, HTTP error shape, idempotency, одна линия/внутренняя вершина, immutable baseline и история. Новые серверные endpoint, aggregate, блокировка, persisted `OutcomePending`, async jobs/polling не вводятся. Save/Revert не подтверждают позиционную точность/топологию.

Вне scope: offline editing, гарантированное восстановление обычного неотправленного draft, перенос между устройствами, восстановление уничтоженного storage, работа одного наряда в нескольких окнах, history UI, автоматическое удаление по сроку, встроенный сервис обращений, baseline repair. Профиль браузера доверенный; изоляция аккаунтов требуется через UI/API, не от чтения локального хранилища владельцем профиля. Стандартное предупреждение браузера при refresh/закрытии не добавляется.

Недопустимые результаты: новый CommandId вместо неизвестной команды; подмена current квитанцией; автоматический reapply; скрытое удаление local draft при управляемом переходе; чужие материалы в новой сессии; сообщение об успехе по догадке.

## 3. Рассмотренные подходы

| Подход | Компромисс | Решение |
| --- | --- | --- |
| A: все контексты и выполнение внутри `workOrders.ts` | Меньше перестановок, но смешение auth/navigation/retry в большом модуле | Не выбран |
| B: один work orders store и выделенные модули выполнения/хранения | Первоначальная рекомендация агента; меньше изменений владения | Не выбран |
| C: отдельный recovery store — единственный владелец отправленных намерений | Чёткая самостоятельная ответственность; шире изменения связей и тестов | Выбран пользователем |

Мотив пользователя сверх выбора C не предполагать. Техническое преимущество выбранного решения — независимый жизненный цикл отправленных команд. Параллельные копии pending/current в двух stores запрещены.

## 4. Владение данными

### 4.1. Recovery store

Новый `useWorkspaceRecoveryStore` владеет отправленными намерениями по ключу `(actorId, workOrderId, editVersionId)`. Одновременно допускается одна незавершённая команда этой версии. `CommandId` остаётся идентичностью конкретной команды, не ключом наряда.

Владеет frozen command, установленным исходом, необходимостью readback, блокировками/подтверждением доступа и runtime generations/controllers/timers. Выполняет PUT и обязательный GET независимо от выбранного workspace. Хранение реализовано отдельным storage-модулем.

### 4.2. Work orders store

`useWorkOrdersStore` владеет выбором наряда, workspace snapshots, local draft, Revert confirmation и управляемой навигацией. Материалы завершённого stale-сравнения хранятся в памяти по контексту, чтобы переживать переключение нарядов; после refresh могут исчезнуть.

Существующие изменяемые `recoveryRecord`, execution phase, retry/readback state переносятся в recovery store. Панель получает их через selectors для выбранного контекста. В work orders допустимо только presentation-сообщение о завершении; оно не определяет retry, identity или право новой записи.

### 4.3. Связь stores

Work orders вызывает recovery actions и подключает явный обработчик результатов. Recovery store не импортирует work orders store. Новое намерение проверяется владельцем workspace, затем recovery store запрещает повторный запуск той же версии, сохраняет контекст и отправляет PUT.

Ответ GET передаётся владельцу workspace с actor/context/request generation. Устаревший ответ не заменяет более свежий GET. Readback A не меняет selection, draft или focus B. Карта использует snapshot выбранного контекста; geometry квитанции не становится current. У каждого контекста отдельное поколение исполнения; смена actor инвалидирует все старые callbacks.

Техническое уточнение агента: обработчик принятия snapshot возвращает явный результат применения. Recovery не очищается лишь по факту получения HTTP 200, если снимок отвергнут из-за потери контекста/доступа. Порядок выдачи поколений всех workspace GET, включая обычное открытие и recovery, должен быть единым для конкретного контекста; локальные счётчики разных модулей не сравниваются между собой произвольно.

## 5. Долговременный контекст

### 5.1. IndexedDB

Используется IndexedDB: отдельная запись на контекст, versioned schema, индекс actor. Асинхронные транзакции используются для изменения отдельных записей с проверкой identity. Свойства API: [MDN — Using IndexedDB](https://developer.mozilla.org/en-US/docs/Web/API/IndexedDB_API/Using_IndexedDB).

Запись содержит:

- schema version, actor/target, неизменные `CommandId`, исходный token и geometry;
- source geometry и vertex index новых команд для сравнения после stale;
- установленный outcome: unknown, success/result либо terminal rejection;
- необходимость readback, отдельно блокировки и требование подтверждения после доступа;
- редакцию записи для проверки обновлений/удаления.

Access block не стирает известный success/rejection. В storage не попадают токены, обычные неотправленные drafts, текущая рабочая копия workspace, runtime timers или отложенная навигация. Source всей локальной попытки отличается от baseline всей работы. Для Revert source — current, относительно которого подтверждён возврат, candidate — baseline.

PUT разрешён только после завершения транзакции записи. Обновление/удаление проверяет context, CommandId и редакцию: старый callback не снимает новую блокировку и не меняет другую команду. Смена actor во время записи не разрешает последующую отправку.

После установленного результата, необходимого readback и передачи состояния в память запись удаляется. Ошибка удаления сохраняет блокировку новых mutations этой версии. Удаление recovery record не затрагивает backend history/registry. Неизвестные команды не удаляются по таймеру.

### 5.2. Миграция v1 из sessionStorage

При инициализации исходного actor проверяется его существующая v1-запись. Валидная запись переносится без изменения identity/payload/известного исхода; blocked остаётся blocked. Сначала транзакционно записываются новый record и отметка импорта, затем удаляется старый record. Отметка удерживается до подтверждённого удаления старой записи. Повторный запуск между шагами не импортирует завершённую команду заново.

При уже существующей совпадающей identity более позднее состояние не откатывается к v1. Несовместимые записи не затираются и не объединяются по предположению; сохраняются для разбора, mutations затронутого контекста блокируются.

У v1 нет source geometry. Она отмечается отсутствующей; baseline/current не подставляются вместо неё. Replay/readback доступны; после stale показываются candidate/current и отсутствие source. Полное сравнение гарантируется для новых записей. Уже потерянную v1 после закрытия прежней вкладки восстановить невозможно.

### 5.3. Ошибки хранения

| Ситуация | Поведение |
| --- | --- |
| Не записана новая команда | PUT не отправляется; local draft остаётся |
| Ошибка записи после отправки | Исход не объявляется отменённым; сохраняется прежняя identity, выполнение блокируется |
| Ошибка удаления завершённого record | Новые mutations этого контекста запрещены |
| Повреждённый record с определимым контекстом | Запись не удаляется; блокируется этот контекст |
| Область повреждения не определима безопасно | Новые mutations исходного actor блокируются до разбора |
| Storage недоступен целиком | Новые отправки запрещены; разрешённый просмотр доступен |

Logout не удаляет незавершённые записи. Гарантия сохранности относится к обычному режиму того же профиля/origin; приватный режим, очистка/вытеснение browser storage и аварийная потеря данных не покрыты. Отсутствие записи после разрушения storage не служит доказательством отказа прежней операции.

## 6. Выполнение, очередь и доступ

### 6.1. Очередь

После установления actor и загрузки его записей доступные незаблокированные контексты восстанавливаются автоматически. Максимум два одновременно выполняемых recovery HTTP-запроса на вкладку. Retry-wait не занимает слот, справедливая очередь не позволяет A задерживать B/C на всю серию. Прямой новый пользовательский Save независимого наряда допускается при guards/write-before-send; лимит фоновой очереди не запрещает редактирование.

Один контекст — одна серия и один запрос одновременно. Первоначальная отправка допускает пять дополнительных попыток; восстановление и ручная серия — пять попыток с задержками 0/2/5/10/20 секунд. После исчерпания остаётся unknown и ручной retry; бесконечного polling нет. Переключение наряда не начинает серию заново. Обработчик очереди учитывает смену actor/блокировку непосредственно перед отправкой.

### 6.2. Переходы

| Состояние | Допустимое продолжение |
| --- | --- |
| Unknown, автоматическая серия | Прежние PUT с неизменной identity/payload |
| Unknown, серия исчерпана | Ручная новая серия прежней команды |
| Success и незавершённый GET | Только GET |
| Stale и незавершённый GET | Только GET; candidate удерживается |
| Stale и успешный GET | Материал сравнения в памяти, явный отказ и ручная новая правка |
| Иной доказанный domain rejection | Без автоматического PUT; исправление candidate/отказ согласно действующим guards |
| Access block | Отдельное подтверждение после возврата доступа; затем действие по известному outcome |
| Protocol/identity/storage block | Остановка и объяснение; согласие после доступа не снимает этот block |

Неизвестный исход блокирует новые Save/Revert только соответствующей версии. Доказанный отказ не маскируется под unknown. Отмена клиентского ожидания не отменяет отправленный PUT.

### 6.3. Доступ

Потеря назначения/доступа одного наряда останавливает его, независимые продолжаются. Потеря сессии, смена actor или добровольный logout останавливает все исполнения прежнего actor, инвалидирует callbacks, скрывает его материалы. Известный outcome сохраняется отдельно от необходимости подтверждения.

Исходный actor после возвращения подтверждает каждый наряд отдельно. Согласие связывается с actor/target/CommandId и текущей сессией; новая потеря доступа его инвалидирует. Unknown повторяет прежний PUT, known outcome требует только оставшегося GET. Серверные guards не обходятся, закрытый lifecycle не переоткрывается ради восстановления.

При обычном открытии браузера с успешно восстановленной сессией и без сохранённой блокировки доступа используется автоматический запуск. Приложение не обещает обнаружить отзыв прав, случившийся вне наблюдения: фактический отказ API останавливает выполнение. Известная блокировка не снимается успешным refresh сессии.

Техническое уточнение агента: остановка при logout охватывает все незавершённые записи actor, включая фоновые; известный отказ доступа нельзя хранить только в памяти. Добровольный выход с обещанием сохранности завершается после записи необходимых признаков остановки. Принудительное прекращение доступа не удерживается при отказе storage; UI сообщает ограничение, доступ закрывается.

## 7. Интерфейс, навигация и сравнение

### 7.1. Восстановления

На существующем экране редактора — компактный список «Незавершённые действия» текущего actor: наряд, состояние, доступное действие. Рядом с нарядом — индикатор. В выбранном workspace подробности находятся в существующей панели команд.

Действия: «Повторить запрос», «Повторить загрузку», «Продолжить выяснение результата» с отдельным подтверждением конкретного наряда после доступа. Фоновое завершение не открывает модальное окно, не меняет карту/focus. Материалы недоступного workspace скрыты. Если guards не позволяют узнать исход, остаются честное состояние и ручной разбор, без обходного API.

### 7.2. Управляемые переходы

Dirty local draft: «Сохранить и перейти», «Отказаться от правки и перейти», «Продолжить редактирование». Цель перехода фиксируется. Повторные нажатия не создают дубли. Успех Save и readback автоматически завершает переход только при действующем запросе в той же сессии.

Unknown, readback error, domain rejection, потеря доступа, смена actor или отмена пользователем инвалидируют отложенный переход. Поздний recovery не выполняет старую навигацию/logout. Новое подтверждение перехода — отдельное намерение навигации, не новый CommandId неизвестного Save.

Для уже отправленной команды точное пояснение: **«Выход не отменяет отправленную команду»**. Выбор «Перейти»/«Выйти» либо «Остаться». Переход в B сохраняет recovery A активным; logout останавливает и сохраняет контекст. Если нельзя безопасно сохранить требуемое состояние, управляемый переход с обещанием сохранности не выполняется. Принудительное прекращение доступа не блокируется диалогом.

После stale/readback переход в другой наряд сохраняет сравнение в памяти. Добровольный logout требует явного согласия на потерю материалов сравнения, включая материалы других нарядов. Refresh/закрытие вкладки не сопровождается browser warning.

### 7.3. Stale-сравнение

Панель «Сравнить попытку»: «До моей правки», «Моя отклонённая попытка», «Сейчас на сервере». Таблица XY изменённой вершины и переключаемый просмотр линий на карте. Preview подписан и read-only; current остаётся независимым, редактирование preview недоступно. Baseline обозначается отдельно для Revert.

Кнопка **«Отказаться от попытки»**, текст рядом: **«Попытка будет удалена. Затем можно заново изменить актуальную линию»**. Действие очищает материал; новое изменение готовится вручную на current с новым CommandId. Закрытие панели не удаляет материал. Legacy source может отсутствовать и так обозначается.

Материал сохраняется между нарядами в памяти, но после завершённого stale readback может исчезнуть при refresh. До завершения обязательного GET применяется долговременная сохранность отправленного контекста. При возврате к наряду current читается штатно; прежний snapshot сравнения не объявляется автоматически свежим.

### 7.4. Revert и сообщения

Сохраняются два отдельных решения Revert: окончательно отказаться от local draft либо продолжить работу, затем подтвердить baseline reset. Отмена второго диалога не восстанавливает draft. Confirmation context включает actor/workspace/feature/token; изменение его инвалидирует согласие. Unknown Revert повторяет прежнюю команду без нового согласия на baseline reset; после stale новый Revert требует нового согласия и ID.

Квитанция относится к своей операции, current — к последнему GET. Исторический Revert не доказывает равенства нынешней линии baseline. Доказанный no-op показывается отдельно; при недостатке данных после восстановления допустимо «Прежняя операция выполнена». Сохранение не означает завершения наряда.

Позиционная точность и топология не объявляются проверенными. Geometry/AOI guards не подменяют их. История после Revert сохраняется.

### 7.5. Разбор дефектов и доступность

Candidate error предлагает исправление/отказ. Дефект или недоступность основания — объяснение и ручной маршрут вне приложения с workOrder/editVersion/feature/command IDs, error code и correlationId при наличии. Общий контекстный код не является доказательством конкретного дефекта. Токены/секреты исключены. Реальный сотрудник не выдумывается; используется принятый процесс условной организации.

Переиспользуются focus trap, безопасный начальный фокус, Escape без mutation, возврат фокуса. Фоновые объявления объединяются, выбранный контекст имеет понятный статус. Применяются ранее принятые viewport/keyboard проверки; новые обещания smartphone scope или полного WCAG соответствия отсутствуют.

## 8. Проверка и закрытие

### 8.1. Матрица обязательных сценариев

| ID | Сценарий | Доказательство |
| --- | --- | --- |
| X01-01 | Save/Revert → commit → потеря ответа → retry | Прежние ID/payload, одна mutation, отдельный GET |
| X01-02 | Закрытие/открытие браузера | Настоящий restart браузера с тем же тестовым профилем, IndexedDB без ручного заполнения |
| X01-03 | Unknown A → Save B → unknown B → Save C | Независимость контекстов, current C не подменяется ответами A/B |
| X01-04 | Save A → Save B → поздний replay A в одной версии | Result A исторический, current B; revision/events не меняются на replay |
| X01-05 | Потеря доступа → другой actor → исходный actor | Чужие данные/PUT отсутствуют; отдельное подтверждение каждого наряда |
| X01-06 | Потеря доступа только A | B/C продолжают работу; старый callback A не снимает block |
| X01-07 | Stale → сравнение → B → A | Source/candidate удержаны в памяти, current не подменён; новый edit только вручную |
| X01-08 | Refresh до/после stale readback | До GET контекст удержан; после GET потеря сравнения допустима |
| X01-09 | Dirty → Revert → отмена второго диалога | Draft уже удалён, PUT отсутствует; подтверждённый Revert сохраняет историю |
| X01-10 | Save-and-leave success/unknown/GET error/rejection | Переход только при непрерывном успехе, иначе отменён; late success не вызывает logout |
| X01-11 | Миграция v1 с прерыванием | Нет новой identity/дубликатов/отката outcome; legacy source честно отсутствует |
| X01-12 | Storage write/delete/corruption failures | Нет PUT до записи, нет новой mutation при небезопасном состоянии |
| X01-13 | No-op и качество | No-op доказан или сообщение нейтрально; точность/топология не объявлены проверенными |
| X01-14 | Нулевой сегмент после canonicalization | Атомарный отказ, geometry/revision/change event не изменены; rejection registry допустим |
| X01-15 | Планировщик и поздние запросы | Не больше двух recovery HTTP одновременно, single flight, слоты свободны в retry-wait |
| X01-16 | UI, map preview и direct actions | Фокус/клавиатура, отсутствие подмены current; guards нельзя обойти прямым action |

Storage/store tests используют управляемые promises и fake timers, проверяют порядок/количество HTTP и неизменность payload. Эмуляция storage не заменяет браузерный тест IndexedDB. Component/map tests исполняют реальные действия, а не только проверяют disabled.

### 8.2. Сквозная среда

Расширяется существующий `infra/m4` в изолированном окружении и отдельном browser profile. Пользовательские demo backend/БД/профиль не затрагиваются. Настоящий success скрывается после commit; browser restart не заменяется reload или вручную собранным storage snapshot. Приёмка Save и Revert выполняется отдельно.

Счётчики revision/command registry/change events сравниваются до команды, после первого commit и после replay. Baseline проверяется отдельно. Evidence не содержит auth secrets; screenshots подтверждают UI, а не отсутствие duplicate mutation. Существующие M4 restart API + refresh scenarios сохраняются как регрессия.

### 8.3. Проверки реализации и отчёт

Применяются frontend targeted/full tests, `npm.cmd run typecheck`, `lint`, `build`, `format:check`; backend DB/API regression через `infra/db-tests.cmd`; M4 через существующий package runner; ручные диалоги, map comparison, keyboard/focus и принятые viewport. Команды исполняются при реализации, результаты не заявлены этим документом.

Итоговый отчёт S2-X01 сохраняется в `docs/sprint_2/` с фактическими evidence по трём шагам карточки и матрице выше. LF/`git diff --check` проверяются. Задача закрывается только после выполнения обязательных сценариев; документы прошлых дней не подменяют новые прогоны.

Production dependency не добавляется без обоснованной необходимости; предпочтительны имеющиеся средства.
