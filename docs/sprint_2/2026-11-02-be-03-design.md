# BE-03 · Освобождение соединения PostgreSQL при подписке на слой

Дизайн принят пользователем 02.11.2026. [План реализации](2026-11-02-be-03-plan.md)

## Цель и границы

При включённом legacy realtime редактор может держать подписку на слой открытой. После завершения начальных проверок подписка должна вернуть соединение PostgreSQL в пул процесса, чтобы им могли воспользоваться следующие клиенты, Auth и Utility Save. Объём изменения — backend-маршрут подписки и его тесты. Параметры пула, HTTP-выдача ticket, протокол WebSocket, порядок рассылки и диагностика публикации находятся за границей BE-03. [Исходный анализ](2026-11-02-be-03-analysis.md)

## Выбранный подход

Пользователь выбрал отдельную зависимость FastAPI для начальной проверки подписки. Второй рассмотренный вариант помещал короткий блок работы с БД непосредственно в обработчик. Он обеспечивал тот же момент освобождения, но возлагал создание сервисов на маршрут. Отдельная зависимость даёт обработчику только готовый контекст пользователя.

1. Зависимость получает сокет, идентификатор слоя и фабрику сессий. Внутри собственного блока `async with` она создаёт сервисы ticket и слоя на одной локальной сессии, используя существующие функции сборки.
2. Сначала выполняется существующая проверка ticket. Его успешное погашение фиксируется отдельной транзакцией до чтения пользователя. Последующий отказ по пользователю или слою сохраняет одноразовость погашенного ticket. После проверки пользователя зависимость проверяет существование слоя.
3. Зависимость завершает контекст сессии и возвращает `WebSocketUserContext` обычным `return`. При исключении контекст также завершается. Обработчик подписки больше не получает сервисы, зависящие от `get_session`. ORM-объект слоя используется только внутри проверки.
4. Обработчик вызывает `connection_manager.connect()` уже после возврата соединения в пул. Менеджер заново проверяет браузерную сессию перед допуском подключения и перед каждой отправкой, включая `connected`. Далее маршрут ожидает сообщения до отключения. Действующие правила отказа, коды и причины закрытия сокета сохраняются. ## Проверки

**Постоянная регрессия.** Тест маршрута исполняет выбранную зависимость с наблюдаемой тестовой фабрикой сессий. К моменту входа в `connect` контекст начальной DB-сессии уже завершён. Это более ранняя граница, чем первая отправка и первый `receive`. При отказе после обращения к БД контекст также завершается, а менеджер не регистрирует сокет. При адаптации подмен сохранить существующие проверки успешной подписки, отказов и отзыва браузерной сессии. [Тесты маршрута](../../apps/backend/utility_service/web_api/tests/test_ws_layers.py) · [Тесты отзыва](../../apps/backend/tests/integration_tests/test_browser_auth_websocket_revocation.py)

**Разовая приёмка.** На изолированной тестовой PostgreSQL с PostGIS запустить один процесс backend с включённым legacy и штатным пулом 5 + 5. Один процесс нужен, чтобы распределение клиентов между пулами не скрыло дефект.

1. Подготовить слой, редактора и рабочий контекст для допустимого Utility Save. Зафиксировать исходное число выданных соединений пула и состояние транзакций backend. Диагностическое соединение учитывать отдельно.
2. Для каждого сокета получить собственный ticket. Открыть не менее 11 подписок к этому процессу, дожидаясь `connected` от каждой. Удерживать все сокеты открытыми до окончания проверок.
3. В паузе после последнего handshake подтвердить возврат числа выданных соединений к исходному значению и отсутствие оставленных подписками транзакций в состоянии `idle in transaction`. Общее число физических подключений само по себе не показывает, заняты ли они.
4. Выполнить аутентифицированный запрос Auth с обращением к БД и успешный Utility Save с изменением геометрии. Повторным чтением workspace подтвердить сохранённую геометрию. Убедиться, что подписки оставались открытыми. Численный предел времени ответа не входит в приёмку.
5. Закрыть сокеты. В `docs/sprint_2` сохранить результат с числом активных подписок, наблюдениями пула и транзакций, исходами Auth, Save и повторного чтения. Не включать токены и ticket.

Конкретная подстановка фабрики в тестах и способ снятия показаний пула остаются деталями реализации. Прохождение приёмки подтверждается отдельным прогоном после исправления.
