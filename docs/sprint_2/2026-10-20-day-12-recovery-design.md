# День 12 — восстановление после сбоев и перезапуска

Дата: 2026-10-20. Статус: спецификация принята пользователем после исключения выбора инструмента M4; продуктовая часть реализована 2026-10-21, M4 открыта.

Основание: [анализ и 16 ответов пользователя](2026-10-20-day-12-recovery-analysis.md), принятие рекомендуемого подхода сообщением «Принимаю», [ТЗ Sprint 2](2026-07-31-sprint-2-technical-requirements.md). Календарная дата Дня 12 остаётся 14 августа.

## 1. Цель и границы

Редактор может безопасно завершить восстановление Save/Revert после потери ответа, перечитать current после сбоя GET, отказаться от отклонённой stale-попытки и выполнить явно подтверждённый возврат к baseline. Сохранённое изменение переживает backend restart и refresh; повтор прежней команды не дублирует mutation.

Дорабатываются существующие `useWorkOrdersStore` и панель команд. Save и Revert используют общий механизм отправки, записи recovery context, классификации ошибок, повторов и readback. Единственным владельцем рабочего состояния остаётся store.

В scope входят:

- ручная серия повторов неизвестного исхода;
- одиночное ручное чтение после ошибки readback;
- явный выход из stale без переноса прежнего candidate;
- Revert по baseline из readback, подтверждения и снятие выбора;
- автоматические recovery tests и сквозная автоматическая/ручная приёмка M4.

В S2-X01 остаются явное продолжение после обнаруженной потери доступа и повторного входа, работа с другим нарядом при незавершённом восстановлении, расширенное сравнение/перенос локальной попытки и новые сценарии управляемой навигации.

Не добавляются server pending-state, polling результата, новый aggregate, серверная блокировка на время диалога, offline editing, межвкладочная координация, history UI, очистка registry/history, изменение baseline или расширение одной линии/внутренней вершины. Проверка M4 касается restart backend, а не crash recovery PostgreSQL или уничтожения browser storage.

## 2. Роли данных и инварианты

| Данные | Роль |
| --- | --- |
| Workspace current | Последнее успешно прочитанное серверное состояние |
| Immutable baseline | Исходная геометрия из `changeSet.baselineGeometry` |
| Local draft | Неотправленная пользовательская попытка относительно прочитанного current |
| Frozen pending command | Отправленное намерение: actor, target, `CommandId`, исходный token и geometry |
| Command result | Квитанция конкретного исполнения; может быть исторической |
| Confirmation context | Временный контекст согласия на Revert; не серверная операция |

Новые намерения получают новый `CommandId`; любой retry сохраняет прежние ID, target, actor, token и geometry. Новый readback не обновляет token в pending command.

Карта, current token и наличие persisted change set обновляются только через workspace GET. Ни candidate, ни старый replay не перезаписывают current. Успешный Revert не стирает историю и не подтверждает positional accuracy/topology.

Подтверждённый отказ не повторяется как unknown. Новый Revert после stale требует нового согласия и нового ID. Если при чтении current уже равен baseline, сбрасывать нечего: новая команда не создаётся.

## 3. Управление восстановлением

### Неизвестный исход

После исчерпания автоматической серии показывается действие **«Повторить запрос»**. Оно явно повторяет ранее отправленное действие, а не сохраняет новую правку.

Ручной запуск выполняет пять попыток с задержками перед попытками `[0, 2000, 5000, 10000, 20000]` мс. Это тот же режим, что recovery после refresh. Первоначальная отправка Save/Revert сохраняет режим Дня 9: первая отправка плюс до пяти дополнительных попыток.

Серия прекращается при success, доказанном domain rejection, stale, access/protocol/identity block, смене контекста или невозможности безопасно продолжить из-за storage. После повторного исчерпания остаются unknown и прежний record; ручное действие снова доступно. Общий lifetime retry budget не вводится.

Перед началом серии store синхронно закрывает возможность повторного запуска. Click, Enter/Space и прямой вызов action не могут создать параллельную серию. Пока серия активна, новые Save/Revert, Cancel и переключение наряда недоступны. Правило одинаково для Save и Revert; повторного подтверждения отправленного Revert нет.

### Известный результат и ошибка GET

Действие **«Повторить загрузку»** выполняет ровно один GET и не вызывает PUT. Оно применимо после известного success и после stale, если обязательный readback не завершён.

Пока GET выполняется, повторный запуск заблокирован. При ошибке сообщение сохраняет известный исход: «операция выполнена, актуальные данные не загружены» либо «изменение отклонено, актуальные данные не загружены». Новый GET не требует новой команды или подтверждения Revert.

Cleanup recovery выполняется после необходимого успешного чтения и успешного удаления storage record. Ошибка cleanup не даёт права новой записи. При такой ошибке сохраняются действующие storage guards; универсальной кнопки очистки или обхода блокировки нет.

### Stale после успешного GET

Интерфейс предоставляет действие **«Отказаться от отклонённой попытки»**. Оно очищает candidate и состояние отказа без HTTP mutation. Затем пользователь выбирает актуальную линию и начинает новую правку. Source/token новой попытки берутся из current.

Сравнение и перенос прежнего candidate не вводятся. До успешного readback действие недоступно. Если отклонён Revert, после разрешения прежней попытки можно заново выбрать «Сбросить» без обязательного начала геометрического редактирования.

После завершённого stale readback сохраняется граница Дня 9: refresh может удалить отклонённую локальную попытку и ожидание явного отказа. Это исключение не распространяется на unknown или незавершённый readback.

## 4. Revert

«Сбросить» доступно при `hasPersistedChangeSet=true`, допустимых actor/workspace и отсутствии recovery/storage/access/protocol блокировки. Target определяется сохранённым change set, а не произвольным выбранным объектом.

### Разрешение local dirty

Если есть несохранённая правка, сначала предлагаются:

- **«Продолжить редактирование»** — local draft остаётся, Revert не выполняется.
- **«Отказаться от локальной правки»** — local draft окончательно отменяется без HTTP, затем открывается отдельное подтверждение возврата.

Первый диалог явно сообщает, что отказ окончателен. Отмена второго диалога не восстанавливает локальный candidate. Вариант скрытого или предварительного Save не добавляется.

Если local dirty нет, первый диалог не нужен.

### Подтверждение возврата

Второй диалог сообщает, что линия вернётся к исходной геометрии, сохранённое отличие исчезнет, а история останется. Подтверждение не означает проверки точности или топологии.

Согласие связывается с actor, workOrder/editVersion, target feature и token показанного current. Пока открыт диалог, нельзя параллельно изменить локальную геометрию или запустить другую команду. Смена actor/workspace/token или потеря доступа закрывает/инвалидирует подтверждение; старый callback не отправляет запрос.

На подтверждение store повторно проверяет разрешения и актуальность confirmation context. Затем создаёт новый UUID и frozen command:

- target — `changeSet.featureId`;
- geometry — копия `changeSet.baselineGeometry`;
- token — прочитанный `draftVersionToken`;
- actor — текущий разрешённый редактор.

Recovery record сохраняется до первого PUT. Если запись не удалась, PUT не выполняется и сообщение не утверждает неизвестный результат уже отправленного действия.

Изменение на сервере после показанного snapshot обнаруживается через штатный stale. Автоматический новый Revert со свежим token запрещён.

### Завершение

После success выполняется GET. До его завершения новые правки заблокированы. После успешного readback/cleanup выбор снимается и маркер скрывается.

Обычно результат Revert — baseline, `operation=unchanged`, `hasPersistedChangeSet=false`, `changeSet=null`, `basicValidation=null`. Если replay исторический и после него уже была новая запись, карта показывает более свежий current из GET; интерфейс не утверждает, что текущая линия всё ещё равна baseline.

При unknown действует обычная серия повторов той же команды. При ошибке GET повторяется только чтение. При stale — чтение, разрешение прежней попытки и новое подтверждение при наличии актуального change set.

## 5. Матрица доступности

| Состояние | Повторить запрос | Повторить загрузку | Отказаться от stale-попытки | Новое редактирование / Save / Revert |
| --- | --- | --- | --- | --- |
| Unknown, серия завершена | Да | Нет | Нет | Нет |
| Sending / retry-wait | Нет | Нет | Нет | Нет |
| Known result, GET выполняется | Нет | Нет | Нет | Нет |
| Known result, GET завершился ошибкой | Нет | Да | Нет | Нет |
| Stale, GET успешно завершён | Нет | Нет | Да | После явного разрешения попытки |
| Recovery завершён | Нет | Нет | Нет | По обычным guards и dirty/change set |
| Access / protocol / identity / storage block | Нет | Нет | Нет | Нет |

Кнопки не являются единственной защитой: действия store проверяют те же условия. Существующий запрет переключения наряда при unknown сохраняется. Доступ после обнаруженной потери доступа не возобновляет запись автоматически.

## 6. Ответственность компонентов

| Область | Изменение |
| --- | --- |
| `stores/workOrders.ts` | Ручная серия, защита одиночного GET, явное разрешение stale, создание Revert через общий pipeline |
| `stores/workspaceRetry.ts` | Существующие интервалы и отмена; отдельный таймер панели не нужен |
| `stores/workspaceRecoveryStorage.ts` | Существующий контракт сохранения identity и terminal result |
| `domain/workspaceCommandPresentation.ts` | Доступность recovery actions и правдивые сообщения |
| `components/WorkspaceEditCommands.vue` | Действия, два отдельных решения Revert, управление фокусом |
| `composables/map/useWorkspaceLineInteraction.ts` | Согласованность marker/selection и запрет взаимодействия во время подтверждения/восстановления |
| API client и backend | Существующие PUT и GET; новые endpoint/schema не требуются |

Диалог может иметь локальное presentation state, но полномочия и связывание согласия с контекстом проверяются в store. Отдельный recovery store/controller и общая архитектурная переработка не вводятся.

Не расширять persisted command ради подписи операции без необходимости. После refresh при недостаточном знании о пользовательском названии действия используется нейтральное сообщение о результате операции. `operation=unchanged` нельзя использовать как признак «это был Revert» или «это был no-op».

Существующие request generations и проверки identity сохраняются. Отмена таймера или уничтожение компонента прекращают клиентскую работу, но не означают отмену серверной mutation.

## 7. Сообщения, фокус и карта

Различаются неизвестный исход, подтверждённое исполнение с недоступным current, stale, ошибки доступа/storage/protocol. Не выводить сырые коды как основной текст и не показывать «сохранено» для отклонённой команды.

Статусы передаются одной live region; автоматические обновления не перехватывают фокус. В диалогах удерживается Tab/Shift+Tab, Escape закрывает текущий диалог без отправки Revert; фокус возвращается на инициатор либо заголовок панели. Начальный фокус — на безопасном действии продолжения/отмены.

После окончательного отказа от local draft Escape во втором диалоге не восстанавливает его. Эта последовательность проверяется отдельно.

Сохраняется пояснение о непроверенной позиционной точности. Карта не подменяется candidate/replay во время загрузки; недоступность редактирования объясняется текстом. Responsive-проверка использует размеры Дня 11; нельзя объявлять новый scope смартфонов или соответствие всего приложения WCAG.

## 8. Автоматическая проверка и M4

Матрица D12-01–D12-20 из анализа является частью этой спецификации. Store/component tests исполняют реальные actions, используют управляемые HTTP promises и fake timers. Проверяются количество/порядок запросов и неизменность payload, а не только `disabled`.

Для M4 нужны два сценария: content-changing Save и content-changing Revert. В каждом:

1. Отправить действие через UI в действующей сессии.
2. Дождаться реального серверного success после commit, скрыть ответ от страницы.
3. Не дать последующим автоматическим повторам разрешить unknown до перезапуска.
4. Перезапустить backend-процесс, сохранив БД; дождаться готовности API.
5. Обновить ту же вкладку с её `sessionStorage`.
6. Разрешить восстановление прежней команды и отдельный GET.
7. Проверить identity, актуальные данные, revision и отсутствие дополнительного change event.

Счётчики сравниваются с состоянием после первого commit, а не только с исходным состоянием до отправки. На первую content-changing команду допустимы ровно одно увеличение revision и одно соответствующее событие; replay не добавляет ничего. Baseline проверяется независимо.

Дополнение от 2026-10-21: пользователь отдельно принял [Playwright Test и потерю ответа после commit](2026-10-21-day-12-m4-tool-options.md). Тесты находятся в отдельном пакете `infra/m4`; `route.fetch()` получает настоящий success, а `route.abort()` скрывает его от страницы после проверки commit. Повторы блокируются до restart и новой навигации. Существующий pytest DB runner остаётся регрессионной проверкой и не заменяет объединённый сценарий.

Проверка выполняется в отдельном тестовом окружении, без вмешательства в пользовательский рабочий backend и его данные. Внутри измеряемого сценария нельзя пересоздавать БД, сбрасывать seed или вручную формировать recovery record. Требование проверки не предполагает добавления production debug endpoint.

Evidence содержит исходные ID и payload команды, факт нового запуска backend, порядок PUT/GET, значения revision/change set и количество событий до/после replay. Auth tokens и секреты не сохраняются. Скриншоты помогают проверить UI, но не доказывают отсутствие duplicate mutation.

Ручной happy path из ТЗ сохраняется отдельно. Он подтверждает пользовательскую работоспособность, а автоматический сценарий контролируемой потери ответа — наиболее рискованную границу.
