## Что происходит сейчас

1. `EditorWorkOrdersView` показывает `MapView` в режиме `workspace`, когда store содержит `activeWorkspace`; иначе использует `empty`. Панели команд и сравнения располагаются отдельно от карты.
2. `useMapInstance.createMap()` создаёт `Map`, добавляет navigation control, публикует объект в `map.value`, вызывает `resize` после `nextTick` и ждёт событие `load`.
3. После разрешения Promise `MapView` вызывает `renderWorkspace()`, затем устанавливает `mapReady=true`. Только после этого появляется `WorkspaceLineInteraction`.
4. Исключение внутри общего `onMounted` перехватывается и записывает «Не удалось инициализировать карту» в `labelText`.
5. `labelText` отображается только внутри `.badge` с условием `props.mode !== 'workspace'`. В основном рабочем режиме ошибка не видна. Отдельного alert и повторного запуска создания карты нет.

Это подтверждение по пути исполнения и шаблону, а не результат запуска WebGL в браузере. Первичный дефект не требует отказа API: workspace может быть успешно загружен, а конструктор карты — завершиться исключением.

## Связанные случаи, которые нельзя молча объединить

| Случай | Установлено кодом | Предел вывода |
| --- | --- | --- |
| Исключение `new Map` | Попадает в общий catch, сообщение скрыто в workspace | Конкретный браузерный отказ WebGL ещё не воспроизведён |
| Ошибка первичного `renderWorkspace` | Тот же catch и тот же скрытый текст | Текст не различает создание карты и отрисовку workspace |
| `load` не наступил | Ожидание не имеет timeout, reject или cancel | Нельзя утверждать, что любой tile error блокирует `load` |
| Обновление props до `load` | Watcher вызывает `renderWorkspace` при наличии map, без проверки `mapReady` | Это отдельная FE-03; включение в текущую задачу требует уточнения |
| Unmount до `load` | `destroyMap` удаляет map, но явной отмены Promise и защиты continuation нет | Требуется отдельная проверка позднего callback, а не заявление о гарантированной гонке |
| Ошибка после успешного запуска | Отдельного состояния ошибки карты и обработки потери WebGL-контекста в просмотренном коде нет | Включение runtime-сбоев расширяет исходный сценарий FE-02 |
| Отказ OSM raster tiles | Подложка зависит от внешнего URL; стиль задаётся локальным объектом | Недоступность подложки не доказывает недоступность объектов workspace |

Общий catch в legacy-режиме охватывает также загрузку слоёв и features. Называть каждую такую ошибку сбоем WebGL некорректно. Основной App использует workspace; legacy `MapPageView` использует `editing`.

## Связь с доменной моделью

`Workspace Loaded` означает чтение WorkOrder, EditVersion, AOI и объектов через API, а не готовность браузерной карты. Поэтому успешное получение данных и невозможность их отобразить — разные факты.

`EditVersion` защищает baseline, current, token, command identity и атомарность Save. Сбой renderer сам по себе не доказывает отказ сохранения, не откатывает persisted change set и не разрешает новую команду вместо команды с неизвестным исходом. Это вывод из действующих инвариантов, а не новое решение условной организации.

Recovery policy требует сохранять идентичность неизвестной операции, не подменять current поздним replay и отдельно решать судьбу локальной правки. Любое будущее действие восстановления карты должно быть сверено с этими ограничениями. Перезагрузка страницы потенциально затрагивает обычный несохранённый draft, сохранность которого после аварийного закрытия не гарантирована политикой.

В aggregate-документе осталась историческая формулировка о read-only slice. Для фактического текущего состояния использован код и материалы Sprint 2; эта формулировка не отменяет реализованные команды правки.

## Панель команд и состояние данных

`WorkspaceEditCommands` получает состояние из workOrders store и auth; `MapView` не сообщает ей readiness/error. При отсутствии localDraft панель предлагает выбрать линию на карте независимо от успешности создания карты. При наличии draft доступность действий определяется существующими правилами команд, а не доступностью renderer.

Это важно для уточнения поведения: показать ошибку карты и изменить доступность Save/Cancel/Revert — разные требования. Не следует автоматически считать все команды опасными или безопасными при недоступном изображении.

## Существующие проверки и пробелы

`MapView.test.ts` проверяет успешное создание empty/editing/workspace, загрузку workspace-слоёв, fit и отсутствие legacy badge в успешном workspace. В просмотренных тестах нет rejected `createMap`, повторной попытки и сценария ожидания `load` с unmount. Отдельный тестовый файл `useMapInstance` поиском в `src` не обнаружен.

Кандидаты для будущего согласования приёмки: видимость ошибки в workspace, доступность сообщения с клавиатуры и assistive technology, успешная и неуспешная повторная попытка, сохранность draft/recovery, поздний результат после unmount, актуальность workspace после ожидания, различение отказа renderer и подложки. Это перечень рисков для обсуждения, не утверждённый план реализации.

В этом этапе тесты и браузерные проверки не запускались, код и конфигурация не менялись. Проверка уже существующих happy-path тестов не докажет видимость отсутствующего error UI.

### FE02-Q05 — команды при неготовой карте

Ответ пользователя 2026-10-31: «Команды редактирования нужны когда есть готовая карта которую можно редактировать. Если крта не инициализирована то их не надо показывать».

Команды редактирования должны быть скрыты до готовности карты, включая ожидание первоначального запуска и его ошибку. После готовности остаются действующие ограничения прав и состояния редактирования; готовность карты сама по себе не разрешает Save/Revert. Для workspace это затрагивает отдельную панель `WorkspaceEditCommands`, для legacy editing — команды внутри `MapView`.

### FE02-Q06 — восстановление при неготовой карте

Ответ пользователя 2026-10-31 на вопрос о действиях восстановления: «тоже скрывать до обновления страницы».

До готовности карты скрыта вся панель `WorkspaceEditCommands`, включая действия восстановления неизвестного исхода и повторного чтения current. После обновления страницы панель может появиться только при успешной готовности карты, согласно FE02-Q05. Скрытие панели не сбрасывает draft, command identity или recovery state и не разрешает неизвестный исход операции. Существующие ограничения восстановления сохраняются.

## Сводка согласованного поведения

- До готовности карты команды редактирования и восстановления скрыты; после готовности сохраняются действующие ограничения команд.

## Подходы для выбора

1. **Локальное состояние карты и уведомление родителя (рекомендуется).** `MapView` владеет состоянием первоначального запуска и сообщением, скрывает собственные legacy-команды и сообщает готовность `EditorWorkOrdersView`. Родитель показывает всю панель `WorkspaceEditCommands` только при готовой карте. Состояние относится к текущему экземпляру карты; для нового экземпляра readiness начинается заново. Изменений доменного store для этого не требуется. Цена — явная передача состояния между двумя компонентами и проверки переходов mount/unmount.
2. **Общее состояние готовности в Pinia.** Карта обновляет общий UI store, а панели читают его напрямую. Это пригодится при нескольких независимых потребителях состояния карты, но добавляет для текущей задачи глобальное состояние и обязательный сброс при замене/удалении карты. Смешивать его с состоянием исхода Save нельзя.

Пользователь выбрал первый подход ответом «Да». Простое отображение существующего badge не удовлетворяет согласованному требованию скрывать команды до готовности карты.

Отдельная agent memory не создаётся: факты и основания сохранены здесь, дублирование не добавляет долговечного знания.
