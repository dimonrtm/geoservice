## Подтверждённые зависимости

Пути ниже относительно корня репозитория.

| Узел | Текущее поведение и зависимость | Значение для CQ-01 |
| --- | --- | --- |
| `apps/backend/utility_service/domain_services/feature_registry.py` | Импортирует шесть ORM Feature-моделей, ORM `Layer` и `UnknownStorageTableError` из `use_cases` | В одном production-модуле есть обе запрещаемые зависимости |
| `apps/backend/utility_service/domain_services/bbox.py` | `Bbox` — dataclass; `parse_bbox` выбрасывает прикладной `BusinessValidationException` | Числовая проверка связана с внешним слоем через тип ошибки |
| `apps/backend/utility_service/infrastructure/postgresql/repositories/layer_repository.py` | Единственный найденный внешний Python-потребитель registry; использует `get_layer_feature_model` в пяти методах | Затронуты bbox read, create, update, delete и get feature |
| `apps/backend/utility_service/web_api/api/layers.py` | Вызывает `parse_bbox` непосредственно перед `FeatureService.get_features_from_bbox` | Ошибка парсинга сейчас доходит сразу до HTTP handler, минуя сервис |
| `apps/backend/utility_service/web_api/api/exception_handlers.py` | Для обоих исключений возвращает 422 и `{"error": str(e)}` | Тип ошибки влияет на внешний контракт; необработанное исключение даст другой ответ |
| `apps/backend/utility_service/use_cases/services/feature_service.py` | Также использует `BusinessValidationException` для ошибок геометрии | Это не ошибка, принадлежащая только bbox; изменение общего класса имеет более широкое влияние |

По просмотру импортов production-кода `domain_services` нарушения сосредоточены в двух исходных модулях. `edit_geometry` импортирует стандартную библиотеку и собственные доменные модули. В тестах `domain_services/tests/test_bbox.py` также импортируется `BusinessValidationException` из `use_cases`.

### Registry

`FEATURE_MODELS_BY_TABLE` сопоставляет шесть имён таблиц (`feature_points`, `feature_polygons`, `feature_lines`, `feature_multipoints`, `feature_multipolygons`, `feature_multilines`) конкретным ORM-классам. `get_layer_feature_model` читает `layer.storage_table`; неизвестное имя вызывает `UnknownStorageTableError` с сообщением «Для данного слоя не найдена подходящая модель».

`ALL_FEATURE_MODELS` повторяет набор классов. По поиску Python-кода репозитория внешних потребителей этой коллекции не найдено. Внешних потребителей `resolve_feature_model` также не найдено; его вызывает обёртка в том же модуле. Это наблюдение о репозитории, не доказательство отсутствия внешних скриптов.

Registry не вычисляет доменный тип инженерного объекта и не управляет `NetworkFeature` из utility workflow: он выбирает SQLAlchemy-модель по физическому имени таблицы legacy слоя.

### Bbox и контракт ошибок

`parse_bbox` разделяет строку по запятым и требует четыре числа, затем последовательно проверяет долготу в [-180, 180], широту в [-90, 90], строгое возрастание широты и долготы. Возвращается `Bbox(min_lon, min_lat, max_lon, max_lat)`. Прямое создание `Bbox` этих проверок не выполняет.

У текущего контракта пять текстов ошибок: неверный состав чисел, диапазон долготы, диапазон широты, порядок широты, порядок долготы. Сохранение поведения включает порядок проверок и формат ответа, а не только успешный результат. Сейчас пересечение антимеридиана и нулевая ширина/высота не принимаются. Расширение допустимой геометрии в требованиях CQ-01 отсутствует.

Универсальный HTTP handler для `Exception` возвращает 500 `INTERNAL_ERROR`. Поэтому изменение класса исключения без учёта его обработки способно изменить API, даже если арифметика bbox останется прежней. В проекте отдельно проверяется, что произвольный `ValueError` остаётся 500.

## Сопоставление с Wiki и DDD_Wiki

- `DDD_Wiki/subdomains/generic_map_editing.md`: Layer/Feature CRUD, bbox, optimistic version и realtime — generic/supporting capability; она не должна переопределять authoritative workflow.
- `DDD_Wiki/bounded_contexts/utility_network.md`: контекст инженерной сети владеет features, associations и revision; это не тождественно физическому registry legacy-таблиц.
- `Wiki/entities/network_feature.md`: identity и ограничения first persisted change set относятся к объекту инженерной сети и работе с baseline.
- `Wiki/value_objects/aoi.md`: AOI — серверная граница данных работы; видимость через пересечение и допустимость изменения через полное покрытие различаются. Bbox фильтра legacy API не заменяет AOI.
- `DDD_Wiki/aggregates/edit_version.md`: Save сохраняет границу агрегата, атомарность, DraftVersionToken, CommandId и правила событий. CQ-01 сам по себе не требует их изменения.

Эти материалы объясняют доменную границу, но не задают точные Python-пути классов исключений или правила совместимости внутренних импортов.

`Code_wiki/архитектура/backend.md` описывает существующую архитектуру `web_api -> use_cases -> infrastructure`, запрет прямого импорта infrastructure в web_api и отсутствие обратных импортов web_api. Там `domain_services` назван набором доменных helper-функций; полной изоляции всех application services от ORM не обещано. Поэтому требование CQ-01 нельзя автоматически распространить на весь backend.

## Существующая проверка и пробелы доказательств

`apps/backend/tests/test_architecture_boundaries.py` проверяет три направления: web_api не импортирует infrastructure, use_cases не импортирует web_api, infrastructure не импортирует web_api. Проверки независимости domain_services нет. Анализатор собирает AST-импорты, не разрешает относительные пути до полного имени и не анализирует динамический импорт; это ограничение существующего механизма.

`domain_services/tests/test_bbox.py` содержит один успешный сценарий и пять ошибочных входов. Они фиксируют тип исключения и сообщения, но не все пограничные случаи парсинга.

`web_api/tests/test_exception_handlers.py` фиксирует 422 и legacy JSON для `BusinessValidationException`, а также 500 для неожиданного `ValueError`. Это проверка handler, не сквозная проверка ошибки реального bbox endpoint.

`web_api/tests/test_layers_api.py` использует подставной сервис, поэтому сам по себе не доказывает сохранность SQL mapping. Отдельных прямых тестов registry по поиску его имён в Python-коде не найдено. Наличие косвенного покрытия не равнозначно проверке всех шести моделей и неизвестной таблицы.

В этом исследовании выполнены чтение кода и документов, поиск импортов и потребителей. Тесты и runtime-сценарии не запускались; старые результаты из sprint reports не выдаются за проверку текущего HEAD.

## Уточнение совместимости

Первый вопрос: нужно ли сохранять совместимость внутренних Python-импортов и типов исключений для потребителей вне репозитория, или обязательный контракт ограничен HTTP-поведением и потребителями текущего checkout?

Причина: исходное ревью требует сохранить API, но не определяет судьбу старого пути registry и прикладного исключения bbox.

Ответ пользователя 2026-11-10: «нет» — внешних потребителей нет. Сохранять старые внутренние Python-пути ради внешней совместимости не требуется. HTTP-контракт и поведение текущего приложения сохраняются по исходным требованиям.

На этом этапе не осталось выявленных пробелов в требованиях, мешающих сравнению подходов. Размещение ошибок и способ их преобразования — предмет выбора дизайна, а не отсутствующее доменное правило. Граница задачи остаётся CQ-01, без расширения на CQ-03 и без изменения геометрических инвариантов.

## Артефакты и память

Дополнительная проверка: наследников `BusinessValidationException` в Python-коде репозитория нет. Класс выбрасывается напрямую в 11 production-точках: шесть проверок bbox, две проверки соответствия типа геометрии слою и три проверки данных/сборки ответа в `FeatureService`. Таким образом, общий класс смешивает доменные и технические причины; само его расположение не определяет смысл каждой причины. Пользователь после этого уточнения выбрал вариант 1 («Тогда пока 1 вариант»).

Код, конфигурация, тесты и реестр закрытия CQ-01 не изменялись. Отдельная agent memory не нужна: результаты анализа и ответ пользователя сохранены в этом документе, дублировать их в памяти оснований нет.
