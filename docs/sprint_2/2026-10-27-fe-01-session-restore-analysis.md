# FE-01: анализ конкурентного восстановления сессии

Дата: 2026-10-27. Статус: анализ завершён; пользователь принял предложенное техническое решение и критерии приёмки. Реализация не выполнялась.

## Принятие решения

2026-10-27 пользователь ответил «Принимаю» на предложение по итогам анализа. Приняты экран ожидания при retry, проверка актуальности восстановления перед success/catch/finally и обработка ошибки refresh в store без предварительной очистки сессии HTTP interceptor. Согласованы проверки поздних success/401/503/timeout, нового входа того же пользователя и сохранности рабочего контекста новой сессии.

Граница остаётся узкой: «повтор восстановления → новый вход → поздний ответ восстановления». Общая переработка конкурентных auth-действий и межвкладочная AR-01 не входят в решение. Ограничение защиты cookie, описанное ниже, сохраняется. Принятие решения не обозначает выполненную реализацию или успешные проверки.

## Подтверждённая последовательность дефекта

1. `App.vue:33` при старте вызывает `restoreSession`, если приложение ещё не готово и восстановление не выполняется.
2. `auth.ts:155` начинает восстановление: очищает `sessionError`, выставляет `isRestoring=true`, но не меняет `isReady`.
3. После первого 503/timeout `catch` очищает локальную сессию и устанавливает сообщение с повтором; `finally` выставляет `isReady=true`, `isRestoring=false`.
4. «Повторить» в `App.vue:39` вновь вызывает тот же action. На время ожидания получается `isReady=true`, `isRestoring=true`, `sessionError=null`, `user=null`.
5. В шаблоне `App.vue:53` загрузочный экран зависит только от `!isReady`. Ошибки и авторизованного пользователя нет, поэтому показывается `LoginScreen`.
6. В `LoginScreen.vue` отправка формы вызывает `loginWithPassword`. Его результат после дополнительного `await suspendActor` безусловно применяется через `setAuth`.
7. Старое восстановление затем безусловно применяет свой результат: успех вызывает `setAuth` прежнего пользователя; ошибка вызывает `clearLocalSession`; `finally` меняет readiness независимо от более новых действий.

Следовательно, дефект имеет две отдельные наблюдаемые части: доступность входа во время retry и применение устаревшего результата внутри store. Проверка только видимости формы не доказывает корректность продолжений async actions.

## Матрица текущего поведения

| События по порядку | Текущий результат по коду |
| --- | --- |
| Retry ещё ожидается | Форма входа доступна при пустом пользователе |
| Retry → успешный login B → поздний успех restore A | B заменяется на A, вызываются последствия смены actor |
| Retry → успешный login B → поздний 503/timeout | B очищается, появляется ошибка восстановления |
| Retry → успешный login B → поздний 401 | Даже если interceptor отверг старый epoch, `catch` restore очищает B; для initial режима ошибка скрывается |
| Restore → локальный logout → поздний успех restore | Store способен снова установить пользователя; нет проверки актуальности восстановления |
| Два вызова restore без завершения первого | Два HTTP-запроса; нет проверки занятости внутри action |
| Завершение одного restore при другом ожидающем действии | Старый `finally` способен снять `isRestoring` и включить `isReady` |

Последние три строки — смежные сценарии, установленные трассировкой методов, а не подтверждённые отдельными пользовательскими прогонами. Их включение в приёмку ещё требует определения границ задачи.

## Почему существующая защита не закрывает дефект

`api/http.ts` записывает `sessionEpoch` и actor при отправке запроса. На 401 и отдельных 403 вызывает `handleUnauthorizedResponse`. Проверка epoch находится только в этом обработчике; затем interceptor всё равно возвращает rejected promise. Поэтому `restoreSession.catch` получает ошибку и обрабатывает её повторно без проверки актуальности.

У текущей ошибки также есть особенность: interceptor может сам вызвать `clearLocalSession` и увеличить epoch до выполнения `catch`. При дальнейшей проработке нельзя смешивать изменение сессии чужим новым действием и обработку отказа собственного запроса.

`setAuth` увеличивает epoch только при изменении id или role. Замена токена для того же пользователя с той же ролью epoch не меняет. `setUser` использует аналогичную границу; `clearLocalSession` увеличивает epoch всегда. Таким образом, нынешний epoch не является номером каждой попытки входа или восстановления.

`loginWithPassword` имеет два асинхронных участка: запрос login и ожидание `workspaceRecovery.suspendActor`. `logout` очищает состояние синхронно, затем ожидает HTTP и безусловно меняет readiness в `finally`. Эти места важны для определения полного порядка auth-действий; они не объявлены отдельными исправленными дефектами.

## Последствия для доменной работы

`setAuth` при смене actor/role приостанавливает recovery прежнего actor и вызывает `hideActor`; при смене id сбрасывает work orders. `clearLocalSession` также скрывает actor и сбрасывает рабочее состояние. Поэтому старый ответ способен прервать уже начатую работу новой сессии и поменять выбранный рабочий контекст.

При этом из FE-01 не следует обход серверного assignment, изменение чужой геометрии или отмена уже отправленного Save. Такие утверждения требуют иных доказательств. Сохранённое намерение recovery и текущая аутентификация имеют разные жизненные циклы.

Успешное первоначальное восстановление сохраняет маркеры открытого workspace и выбранного наряда через `preserveWorkOrderStateOnInitialUser`. Initial 401 принудительно сбрасывает их; initial 503 сохраняет их при отсутствии пользователя. Это уже закреплено тестами и важно для последующего анализа регрессий.

## HTTP и cookie

`api/auth.ts` выполняет login, refresh и logout с `withCredentials`; общий timeout клиента — 30 секунд. Backend login и refresh устанавливают HttpOnly cookie, logout удаляет её. `AuthSessionService.refresh_session` атомарно ротирует refresh token; проигравший повтор получает отказ.

Следовательно, применение JSON-ответа в Pinia и изменение cookie HTTP-ответом — разные эффекты. Из проверки store нельзя вывести корректность cookie после уже отправленных конкурентных запросов. Браузерная проверка этого сценария пока не выполнялась. Межвкладочный сценарий остаётся отдельно описанным AR-01.

## Что подтверждают существующие тесты

- `stores/auth.test.ts`: обычный login/restore/logout; initial 401 и 503; сохранение маркеров workspace; смена пользователя; локальная очистка и завершение logout при ошибке backend.
- `stores/auth.epoch.test.ts`: поздний unauthorized от старого epoch не очищает новую сессию; смена роли инвалидирует epoch. Само продолжение `restoreSession` не проверяется.
- `App.test.ts`: начальный экран при `isReady=false`; кнопка retry вызывает подменённый `restoreSession`; dismiss ошибки показывает login. Реальное промежуточное состояние retry не проверяется.

В этом проходе тесты не запускались: это анализ требований, изменения реализации отсутствуют. Наличие теста в исходниках не обозначается как новый успешный результат проверки.

## Вопросы для последовательного уточнения

### Вопрос 1 — поведение во время повторного восстановления

После «Повторить», пока refresh ожидает ответ, должен ли пользователь только дождаться результата/таймаута, или ему нужна возможность явно прекратить ожидание и перейти к входу под другой учётной записью?

Требования задают retry после ошибки и запрет чужих recovery-материалов, но не описывают пользовательское прерывание самого ожидания auth. Это продуктовый выбор; механизм реализации до ответа не предлагается.

Ответ пользователя 2026-10-27: только дождаться результата или таймаута. Возможность прервать ожидание и перейти к другому входу не требуется. Это требование к поведению интерфейса, а не выбор механизма реализации.

### Вопрос 2 — границы исправления в одной вкладке

Включает ли FE-01 согласованное поведение всех пересекающихся login/restore/logout в одной вкладке, в том числе повторных вызовов и нового входа того же пользователя, или только исходный сценарий retry восстановления → login → поздний ответ восстановления?

Основание: исходная находка описывает конкретный пользовательский сценарий, но рекомендация ревью говорит о конкурентных auth-действиях в целом. У `loginWithPassword` и `logout` тоже есть асинхронные продолжения без проверки актуальности. Межвкладочная координация уже выделена в AR-01 и этим вопросом не затрагивается.

Ответ пользователя 2026-10-27: ограничиться исходным сценарием «повтор восстановления → новый вход → поздний ответ восстановления». Общая переработка конкурентных login/restore/logout и AR-01 не входят в задачу.

Оба продуктовых пробела закрыты. Остальные вопросы относятся к технической реализации и проверкам, а не требуют новых решений пользователя. Предложение ниже принято пользователем 2026-10-27; код ещё не изменён.

## Итоговый контракт FE-01

1. Пока повторное восстановление ожидает ответ, интерфейс показывает ожидание. Форма входа, повторная отправка retry и выход с экрана ошибки в это время недоступны. Отмена ожидания не добавляется.
2. Ожидание заканчивается ответом или существующим timeout HTTP-клиента. Новый срок ожидания и автоматические повторы не вводятся.
3. После актуального успеха открывается соответствующий роли интерфейс. После актуальной ошибки сохраняются существующие правила `presentSessionError`: initial 401 ведёт к входу без сообщения, retryable ошибка возвращает возможность повтора.
4. Если новая сессия уже установлена, результат старого восстановления не меняет её token, user, role, `sessionError`, `isReady`, `isRestoring` и не вызывает сброс workspace или остановку recovery новой сессии. Это относится к success, 401, 503 и timeout.
5. «Новая сессия» не требует другого user id: повторный вход того же пользователя также не должен откатываться старым ответом.

Пункт 4 — защитный контракт store. После исправления UI исходная последовательность перестаёт быть доступным штатным пользовательским маршрутом, но это не основание оставлять безусловное применение устаревшего результата.

## Предлагаемое решение в согласованных границах

### Экран ожидания

Условие верхней ветки `App.vue` должно учитывать `auth.isRestoring` наряду с `!auth.isReady`. Тем самым одинаковый экран ожидания охватывает первую попытку и retry. Значение `isReady` не требуется переопределять как индикатор каждого сетевого запроса. Существующие действия после завершения ожидания сохраняются.

### Актуальность продолжения восстановления

Ввести явную идентичность попытки восстановления и проверять её актуальность перед любыми эффектами success/catch/finally. Новый password login должен инвалидировать прежнюю попытку восстановления; это локальная связь двух действий, не общий планировщик auth-команд.

Защиту нужно установить до первого `await` нового login, чтобы старый restore не вмешался также во время запроса login или последующего `suspendActor`. При передаче управления новому входу состояние ожидания старого restore должно перестать принадлежать ему: его последующий `finally` не управляет экраном новой операции. Обычный `LoginScreen` уже содержит собственный индикатор отправки.

Не использовать только сравнение user id или нынешнего `sessionEpoch`: они не описывают каждую попытку входа того же actor. При проектировании кода сохранить существующую роль `sessionEpoch` для workspace/recovery и старых HTTP-ошибок; не увеличивать его на каждый refresh без анализа последствий для потребителей.

Обработка актуального результата и завершение его состояния должны быть согласованы: собственный `setAuth` или `clearLocalSession` меняет epoch, но не должен превращать нормальное завершение этой же попытки в «чужой» ответ и оставлять экран в ожидании.

### Единственный владелец ошибки refresh

Для refresh предлагается явно передать обработку auth-ошибки вызывающему store action, исключив предварительную очистку этим же ответом в общем HTTP interceptor. Предпочтительна явная метка запроса в типизированной конфигурации HTTP. Устаревший refresh тогда отклоняется до любых побочных эффектов, а актуальный отказ полностью проходит существующую ветку `restoreSession.catch`.

Это узкое исключение только для refresh. Обработка 401/403 обычных рабочих запросов сохраняется. Нельзя глобально отключить interceptor или подавить сам rejected promise: обе меры изменили бы поведение других сценариев.

### Предел защиты cookie

Номер попытки защищает состояние приложения, но не отменяет `Set-Cookie` уже пришедшего HTTP-ответа. В штатном UI FE-01 предотвращает отправку конкурентного login во время ожидающего refresh, поэтому исходная гонка не создаётся через этот экран. Проверка искусственно установленной новой сессии доказывает защиту store, а не порядок cookie.

Гарантия согласованности cookie при произвольных принудительно пересекающихся auth-запросах потребовала бы отдельного контракта управления этими запросами. Она не заявляется результатом узкого FE-01. Серверная single-use ротация не ослабляется; AR-01 не закрывается.

### Что не входит в предложение

Общая сериализация login/logout/restore, login/login и logout/login; новая межвкладочная координация; автоматический refresh при любом 401; изменение backend-контракта, timeout или правил восстановления отправленного Save; общий рефакторинг auth store. Смежные строки исходной матрицы сохраняются как наблюдения, не как обязательства этого исправления.

## Проверяемые критерии приёмки

| Проверка | Ожидаемый результат |
| --- | --- |
| Первая попытка дала 503 → пользователь нажал retry → refresh удерживается deferred promise | Видно ожидание; нет формы входа, кнопки retry и выхода с экрана ошибки |
| Актуальный retry успешен | Корректный пользователь и роль, ожидание завершено |
| Актуальный retry дал 503 или timeout | Возвращается сообщение с повтором, ожидание завершено |
| Актуальный initial retry дал 401 | Вход без сообщения о runtime-потере сессии; прежние маркеры workspace сброшены |
| Отложенный restore → новый успешный login → старый success | Новая сессия и состояние workspace/recovery неизменны |
| Та же последовательность со старым 401/503/timeout | Нет очистки новой сессии, нового сообщения и изменения readiness |
| Та же последовательность при новом login того же actor | Старый token не заменяет новый; результат не зависит от смены user id |
| 401 refresh через реальный interceptor | Нет предварительной очистки перед проверкой актуальности store; актуальная ошибка по-прежнему обрабатывается |
| Старый restore завершается, пока новый login ожидает `suspendActor` | Старый результат не устанавливает actor и не управляет состоянием нового входа |
| Актуальное первоначальное восстановление и обычный рабочий 401 | Сохраняются существующие правила маркеров workspace, скрытия actor и recovery |

Для UI нужен тест с реальным `restoreSession` и отложенным mock API, а не только spy вызова кнопки. Для store нужны управляемые deferred ответы и наблюдение за эффектами в `workOrders`/`workspaceRecovery`. Для interceptor нужна отдельная интеграция клиентского HTTP-слоя с store: mock всего `api/auth` её не покрывает.

При последующей реализации: целевые Vitest-проверки App/auth/http, затем frontend suite и typecheck; браузерный проход retry с задержкой refresh подтверждает фактическую недоступность login и возвращение из ожидания. Полный backend прогон не является доказательством устранения этой клиентской гонки. Сейчас проверки перечислены как критерии будущей реализации, а не выполненные результаты.

## Оценка вариантов

| Вариант | Оценка |
| --- | --- |
| Только учесть `isRestoring` в App | Закрывает видимый вход во время retry, оставляет устаревшие эффекты store |
| Только проверить epoch в success | Не закрывает catch/finally, предварительный interceptor и новый вход того же actor |
| Только отменить запрос | Не доказывает отсутствие уже выполненной ротации или уже доставленного ответа |
| Экран ожидания + актуальность restore + единая обработка его ошибки | Предлагаемый вариант: покрывает исходную находку с сохранением узкой границы |
