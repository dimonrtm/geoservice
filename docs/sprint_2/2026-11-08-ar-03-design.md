# AR-03: диагностика ошибок публикации и отправки

Дата: 2026-11-08. Статус: принят пользователем в чате. [План реализации](2026-11-08-ar-03-plan.md).

Отдельная проверка достаточности дизайна для планирования выполнена: существенных вопросов не выявлено. Это проверка документа, не подтверждение реализации или прохождения тестов.

Основания: [анализ](2026-11-08-ar-03-analysis.md), [исходное замечание](architecture-realtime-review.md), [действующий контракт AR-02](2026-11-02-ar-02-design.md).

## Цель и согласованные границы

При сбое legacy realtime по серверным логам можно установить конкретное изменение объекта, подключение получателя и наблюдаемую причину неуспешной отправки. При аварийном прекращении подписки можно найти каждое отброшенное изменение её очереди. Запись в БД остаётся успешной независимо от ошибки публикации после commit.

Граница диагностики — серверная отправка в сокет. Подтверждение получения браузером и применение события frontend не добавляются. Отсутствие подписчиков и штатное закрытие вкладки получателем не требуют записей о недоставке. Причина аварийного разрыва описывается в пределах доступных серверу фактов.

Это техническая диагностика поддерживающего Generic Map Editing, не история Save/Revert, не доменный post и не operational registry команд. Сохраняются single-worker, best-effort, версии событий, восстановление карты через HTTP и ограничения AR-02. В задачу не входят outbox, retry публикации, метрики, dashboard, новая система хранения логов, автоматическая очистка архивов и изменения frontend.

## Рассмотренные подходы

1. Отдельная запись на каждую пару «изменение — подключение». Удобно искать одно изменение или все потери подключения; массовая авария создаёт больше строк. Пользователь выбрал этот подход.
2. Одна запись о сбое подключения со списком изменений. Строк меньше, но они крупнее, сложнее поиск, при обрезке записи теряется часть списка. Не выбран.

Далее описаны инженерные решения агента в рамках выбранного подхода. Они становятся принятыми после согласования документа.

## Контекст изменения и подключения

Для каждой попытки публикации после commit заранее создать неизменяемый диагностический контекст: eventId, eventType, layerId, featureId и featureVersion. Для удаления featureVersion означает последнюю живую версию из deletedVersion. EventId совпадает с идентификатором в исходящем JSON и создаётся до преобразования FeatureOut в JSON. Ошибка сериализации поэтому не лишает запись идентификатора изменения. Контекст доступен защитной обёртке FeatureService, а не только внутренностям publisher.

Для каждой принятой подписки создать случайный connectionId, не связанный с JWT, ticket, sid, email или адресом памяти объекта. Переподключение получает новый идентификатор. Его достаточно для различения двух соединений одного пользователя. Передача connectionId браузеру, идентификация пользователя и привязка к HTTP correlationId не требуются принятым результатом и не добавляются в этой задаче.

Элемент очереди хранит сериализованный кадр, размер и отдельный диагностический контекст. Извлечение идентификаторов повторным разбором JSON при сбое не требуется. Subscription также хранит текущий кадр до окончательного исхода отправки: извлечённый из очереди кадр не должен исчезнуть из учёта при ожидании проверки сессии или транспорта. Байтовый лимит сохраняет смысл AR-02 — ожидающие кадры; текущий кадр учитывается отдельно.

## Формат и смысл записей

Использовать стандартный logging с отдельным именем `utility_service.realtime`, JSON-сообщениями и уровнем WARNING для диагностируемых сбоев. Сохранить существующую конфигурацию HTTP-логирования. Проверить выход записей в stderr/stdout реально используемого backend-запуска, а не только перехват через caplog.

Запись `realtime_delivery_failed` содержит UTC timestamp, eventId, eventType, layerId, featureId, featureVersion, connectionId, reason, stage и outcome. Поля служат для поиска по изменению и подключению без содержимого Feature. Дополнительные поля по ситуации: closeCode, exceptionType, timeoutSeconds, frameBytes, pendingFrames, pendingBytes и соответствующий лимит. Размеры и количества снимаются до очистки.

Outcome различает достоверный отказ до передачи (`not_sent`) и незавершённую либо ошибочную попытку отправки (`send_unconfirmed`). Таймаут или исключение транспорта не доказывают, что байты не дошли до клиента. Успешно завершённый send_text не регистрируется как потеря, даже если закрытие подписки обнаружено почти одновременно.

В сообщения не попадают геометрия, properties, тело кадра, заголовки, query string, ticket, токены, sid, email и произвольный текст close reason. Для исключения сохраняются имя класса и безопасные места стека: имя файла без абсолютного каталога, функция и номер строки. Не сохраняются str(exception), repr(exception), локальные переменные и строки исходного кода: они могут содержать данные сообщения или секреты. Причина задаётся кодом приложения, а не необработанным текстом исключения. Ограничить диагностический стек последними 10 кадрами.

## Классификация причин

| Наблюдаемый исход | Причина / действие |
| --- | --- |
| Ошибка подготовки или сериализации события | `publication_failed`; stage различает подготовку и сериализацию |
| Один кадр больше байтового лимита | `frame_too_large` |
| Полная очередь по количеству | `queue_frames_exceeded` |
| Суммарный байтовый бюджет превышен | `queue_bytes_exceeded` |
| Истёк deadline send_text | `send_timeout` |
| Ошибка send_text без подтверждённого штатного закрытия | `send_error`, с безопасным типом исключения |
| Аварийный disconnect в receive | `abnormal_disconnect`, с фактически наблюдаемым кодом |
| Disconnect без достаточной классификации | `disconnect_unknown`; не утверждать, что причина — сеть |
| Исключение проверки активности сессии | `session_check_failed`; сохранение fail-closed и существующего закрытия с 1008 |
| Неожиданный сбой writer | `writer_failed` |

Если одновременно превышены несколько лимитов, порядок классификации: размер одиночного кадра, количество, суммарные байты. Нормальное False при проверке сессии отличается от исключения: недействительная сессия, logout и управляемая остановка приложения — штатные завершения, не ошибки доставки. Это инженерное применение согласованной границы «ошибка против нормального поведения».

Маршрут WebSocket передаёт менеджеру наблюдаемый код disconnect и тип завершения вместо безусловного disconnect без причины. Для распознанного закрытия 1000/1001 не создавать записи о потерях. Пустой close frame, представленный транспортом как 1005, считать штатным завершением без указанного статуса; это важно для существующих вызовов frontend `close()` без параметров. Аварийное завершение 1006 не объявлять штатным. Остальные коды и отсутствие сведений классифицировать по наблюдаемому исходу, не выдумывая причину сети. Точное соответствие кодов сообщения ASGI и исключения проверить на установленном transport stack при реализации.

Если раньше получена явная ошибка отправки, а штатный close обнаружен позднее, зафиксированный факт ошибки не переписывается. Задача не гарантирует распознавание намерения пользователя по одному транспортному исключению. Если штатное завершение уже известно, его последующая отмена writer не создаёт ложную ошибку.

## Публикация до распределения по очередям

Для публикации использовать снимок активных подписок слоя, снятый до формирования/сериализации кадра. До окончания постановки в очереди не добавлять сетевых await. Именно этот снимок определяет целевые подключения текущей попытки; новые подписчики не получают ретроспективную ошибку.

При общем сбое до fanout сформировать по одной записи `realtime_delivery_failed` с `publication_failed` для каждого целевого подключения. Если сбой возник до получения снимка либо publisher не смог предоставить контекст получателей, защитная обёртка FeatureService пишет одну запись `realtime_publication_failed` с известным контекстом изменения, без выдуманного connectionId. Такой fallback явно означает отсутствие сведений о получателях, а не их отсутствие.

Пустой снимок — обычный no-op без записей о недоставке. Отсутствие optional publisher также сохраняет нынешнее штатное поведение. Сбой подготовки при заведомо пустом снимке не следует провоцировать ненужной сериализацией.

Один слой отвечает за диагностику каждой обработанной ошибки: manager не пробрасывает уже учтённую ошибку для повторного логирования FeatureService. При непредвиденном частичном fanout нельзя объявлять неотправленными кадры, уже поставленные в очереди; учитывать только оставшихся получателей. Успешно поставленные кадры завершаются по обычным правилам writer.

## Аварийное завершение подписки

Очистка соединения остаётся идемпотентной. Первый обработчик атомарно исключает подписку из fanout и закрепляет причину завершения. При диагностируемом сбое регистрируются:

- кадр, из-за которого сработал отказ при постановке, даже если он не попал в очередь;
- текущий кадр, если серверная отправка не завершилась успешно;
- каждый оставшийся кадр очереди.

Каждая пара eventId/connectionId получает не более одной записи о своём исходе. Ожидающий кадр получает outcome=not_sent, начатая и не подтверждённая отправка — send_unconfirmed. Stage различает enqueue, session_check, send и queue_discard; отброшенные вследствие сбоя кадры наследуют причину завершения подписки, а не вымышленное собственное исключение отправки. Успешно отправленные кадры исключаются из текущего контекста до следующего await.

Повторные retire, receive-finally, timeout, callback фоновой задачи и отмена writer не дублируют записи. Не вводить бесконечный глобальный набор обработанных eventId: дедупликация опирается на состояние живой подписки и кадра и освобождается вместе с ними. При session_check_failed сохранить текущий охват закрытия соединений sid; каждой затронутой подписке передать техническую причину, не подменяя её обычным logout.

Кадр connected не является изменением объекта: сбой его отправки фиксируется как `realtime_connection_failed` с connectionId, layerId и reason, без выдуманных featureId и eventId. Если за ним уже накопились изменения, они учитываются отдельно по общим правилам.

Ошибка закрытия транспорта после retire — отдельное `realtime_cleanup_failed` с connectionId и безопасной причиной; она не повторяет список изменений и не заменяет первоначальную причину. Неожиданные исключения фоновых задач учитываются владельцем операции; callback не должен вторично сообщать уже обработанную ошибку. Штатная отмена задач не логируется как сбой.

## Производительность и ограничения

Сохранить отдельные ограниченные FIFO, deadlines, коды закрытия AR-01/AR-02 и отсутствие ожидания транспорта подписчиков на пути HTTP CRUD. Диагностика выполняет ограниченную работу по имеющимся кадрам и подключениям, без новых обращений к БД и сети, без неограниченной очереди фоновых логов и без rate limit, который скрывал бы отдельные изменения. Массовая авария создаёт пропорциональное число записей — осознанная цена выбранного подхода. Абсолютно нулевая задержка логирования не обещается.

Ошибка диагностического обработчика не должна подменять успешный результат commit или мешать очистке подписки. Невозможность записать сам лог не исправляется рекурсивным логированием. Падение процесса, отказ системы вывода логов, потеря контейнерных логов и события после уже удалённой подписки не получают гарантии аудита. Отсутствие записи не является доказательством доставки.

## Проверка результата

1. Для create/update/delete вызвать ошибку publisher после реального commit: HTTP остаётся успешным, отдельное чтение подтверждает результат, лог содержит правильный контекст изменения. Проверить раннюю ошибку подготовки и сериализации, общий снимок двух подписчиков и fallback без сведений о получателях.
2. На управляемых сокетах проверить send_error, deadline, каждый вид переполнения и крупный одиночный кадр. Быстрый подписчик получает событие, пока медленный заблокирован; успешная доставка не попадает в ошибки.
3. Заполнить очередь несколькими различными изменениями, удержать текущий кадр и вызвать аварию. Проверить точное множество пар eventId/connectionId, включая непоставленный кадр при overflow; для уже завершённой отправки записей нет.
4. Проверить гонки receive-disconnect, writer-error, timeout и shutdown: не более одной записи на пару, отсутствие утечки задач и повторной очистки. Проверить, что not_sent и send_unconfirmed отражают реальную стадию.
5. Для штатного закрытия, пустого close frame, отсутствия подписчиков, False проверки сессии, logout и штатной остановки нет записей о потерях. Для аварийного или неизвестного disconnect — правильная классификация без недоказанного объяснения.
6. Исключение проверки сессии отличается от обычного отказа доступа, сохраняет запрет отправки и диагностирует затронутые очереди. Отдельно проверить connected, отказ cleanup и неожиданное завершение writer.
7. Подставить контрольные секреты в payload, исключения и close reason. Убедиться, что они отсутствуют во всём выводе новых диагностических записей, включая стек. Проверить сериализуемость и достаточность безопасных полей.
8. Проверить видимость WARNING в выводе настоящего backend-процесса и поиск записи по eventId и connectionId. Сохранить регрессии AR-01/AR-02 и существующие тесты HTTP-контрактов. Браузерная проверка применения событий не требуется, поскольку frontend не меняется.

## Граница реализации

Основные участки: FeatureService, FeatureRealtimePublisher, WebSocketConnectionManager, ws_layers, небольшая общая утилита безопасного logging и соответствующие unit/integration tests. Размещение общих типов и утилиты, конкретные имена методов и организация тестовых fixtures оставлены плану; use_cases не должны импортировать web_api ради логирования.

Дизайн не разрешает изменение product-кода до согласования. После согласования составить план в docs/sprint_2. Git add/commit/push не выполнять. Отдельная agent memory не нужна: требования, основания и решения сохранены в этих артефактах.
