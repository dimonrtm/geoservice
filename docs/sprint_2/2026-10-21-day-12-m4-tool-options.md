# День 12: варианты инструмента M4 и потери ответа

Дата: 2026-10-21. Статус: пользователь принял первый вариант сообщением «Принимаю»: Playwright Test, отдельное Docker Compose окружение, потеря настоящего ответа после commit через `route.fetch()` и `route.abort()`.

Основание: раздел 8 [спецификации](2026-10-20-day-12-recovery-design.md). Требуются два объединённых сценария: content-changing Save и content-changing Revert, потеря ответа после commit, restart backend с сохранением БД, refresh той же вкладки, replay и отдельный GET. Существующие Vitest/Vue Test Utils и pytest остаются средствами своих уровней проверки.

## Варианты

| Вариант | Потеря ответа | Преимущества | Цена и ограничения |
| --- | --- | --- | --- |
| Playwright Test + отдельное Docker Compose окружение + проверки БД | `route.fetch()` выполняет исходный запрос; после настоящего success и проверки commit вызывается `route.abort()` вместо передачи ответа странице | Один TypeScript-сценарий управляет браузером и сетевым барьером; удобен повторный локальный и CI-прогон | Новая тестовая зависимость и браузерный runtime; моделирует отказ доставки на границе браузера, а не физический разрыв сети |
| mitmproxy/mitmdump + браузерный runner + отдельное окружение | Reverse proxy получает ответ backend и прекращает его передачу через response hook при выключенном streaming | Сбой отделён от браузерного инструмента; подходит для дальнейших проверок сетевых отказов разных клиентов | Дополнительный процесс, маршрутизация API через proxy и управляющий addon; автоматизация браузера всё равно нужна |
| Собственный небольшой тестовый reverse proxy + управление браузером | Proxy буферизует настоящий ответ и закрывает клиентское соединение после проверки commit | Можно использовать имеющийся Node/Python runtime; полный контроль над барьером | Нужно разработать и проверить сам proxy; ручной браузерный прогон хуже воспроизводится и не заменяет автоматический сценарий принятой спецификации |

Рекомендация: первый вариант для двух сценариев M4. Он объединяет управление UI и отказом в одном тесте без отдельного proxy. Добавление ограничивается тестовой инфраструктурой. Внешний proxy предпочтительнее, если появляется самостоятельная цель проверять транспортные сбои разных клиентов.

## Предлагаемый механизм первого варианта

1. Создать изолированное окружение с настоящими frontend, API и БД. Запускать команды через UI, используя действующую сессию. Подготовить содержательно меняющие геометрию Save и Revert.
2. Установить перехват на уровне browser context. Для первого PUT сохранить identity и payload, выполнить `route.fetch({ maxRetries: 0, maxRedirects: 0 })` без изменения команды. Получить настоящий success и проверить зафиксированный результат отдельным соединением с БД.
3. Не передавать ответ странице: вызвать `route.abort('failed')`. Последующие PUT этой команды временно отклонять до отправки на backend, чтобы автоматические повторы не разрешили unknown раньше времени.
4. Перезапустить только backend, проверить факт нового запуска и готовность API. БД и seed внутри измеряемой последовательности не пересоздавать.
5. Выполнить reload той же вкладки. Перехватчик и его состояние остаются вне страницы. Держать барьер до запроса восстановления из новой загрузки страницы, затем разрешить его без изменения identity и payload. Не открывать барьер заранее: старый автоматический повтор иначе может успеть получить success перед refresh.
6. Проверить replay с прежними actor, target, CommandId, token и geometry, затем отдельный GET и отображение актуальных данных. Recovery record возникает естественно в приложении; тест не записывает его вручную.
7. Сравнить revision и события до первой команды, после первого commit и после replay: первая содержательная mutation добавляет ровно одну revision и одно соответствующее событие, replay — ноль. Независимо проверить baseline и результат Revert.

Артефакт прогона должен содержать ID команды, payload, порядок запросов, подтверждение restart, revision и количество событий. Не сохранять auth headers и секреты, в том числе в автоматически собираемых сетевых трассах.

Простое включение Offline, случайная остановка backend или `route.abort()` до отправки первого PUT не доказывают нужный случай: неизвестно, произошёл ли commit. Подмена success фиктивным ответом также не подходит. Требуется управляемая потеря именно настоящего ответа после реального commit.

## Основание выбора API

- [Playwright Route](https://playwright.dev/docs/api/class-route#route-fetch): `route.fetch()` выполняет запрос и получает результат, не передавая его странице; `maxRetries: 0` отключает внутренние повторы инструмента. `route.abort()` завершает перехваченный запрос ошибкой.
- [mitmproxy events](https://docs.mitmproxy.org/stable/api/events.html): response hook позволяет обработать полученный ответ. Для предлагаемого барьера streaming должен быть выключен.
- [mitmproxy Flow.kill](https://docs.mitmproxy.org/stable/api/mitmproxy/flow.html#Flow.kill): прекращает пересылку текущего запроса/ответа. Это требует проверки выбранного hook и режима буферизации при реализации, а не произвольного обрыва потока в любой момент.

Выбор инструмента принят; успешное выполнение M4 подтверждается отдельно результатами двух объединённых сценариев.
