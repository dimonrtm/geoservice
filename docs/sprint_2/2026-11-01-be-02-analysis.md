## Текущий путь запроса

1. `apps/backend/utility_service/web_api/api/layers.py`: `PATCH /api/v1/layers/{layer_id}/features/{feature_id}`, результат обёрнут в `feature`.
2. `web_api/api/auth.py`: `require_legacy_gis_editor` ограничивает доступ legacy-флагом и ролью.
3. `use_cases/schemas/feature/patch_feature_request.py`: `version >= 1`; `geometry` и `properties` nullable, но объявлены без defaults; оба поля обязательны. Оба `null` отклоняются; неизвестные поля запрещены.
4. `use_cases/services/feature_service.py`, `update_feature`: транзакция охватывает чтение, UPDATE и сборку ответа. Старый объект читается, если хотя бы одно поле равно `None`.
5. `infrastructure/postgresql/repositories/layer_repository.py`: UPDATE проверяет id и ожидаемую version; словарь properties целиком заменяет прежний JSONB, а `None` сохраняет прежние свойства при обновлении geometry. Успех увеличивает version на один; RETURNING содержит только id/version.
6. Сервис собирает полный `FeatureOut` из запроса и ранее прочитанного объекта. Для properties использует `or`, смешивая `{}` и отсутствие изменения.
7. После выхода из транзакции этот же объект передаётся publisher и возвращается вызывающему коду. `feature_realtime_publisher.py` сериализует его в `feature_updated`. Ошибка публикации подавляется сервисом; гарантированной доставки этот механизм не обещает.

Пути в пунктах 2–7 указаны относительно `apps/backend/utility_service/`.

## Причина и последствия

При `geometry=null, properties={}` старый объект загружен. Repository получает пустой словарь, но `request.properties or current_feature.properties` выбирает прежний словарь. После успешного commit ответ и подготовленное событие описывают старые свойства с новой version. Повторное чтение БД должно показать `{}`: это следствие SQL, ещё не проверенное в этой сессии интеграционно.

При новой geometry и `properties={}` старый объект не читается. То же выражение даёт `None`; сервис выбрасывает `BusinessValidationException` внутри транзакции. Обработчик переводит исключение в HTTP 422. Реальная транзакция должна откатить UPDATE; исторический DummySession rollback не моделирует и его не доказывает. Публикация расположена после транзакции и при таком исключении не вызывается.

Если старые properties уже равны `{}`, первый сценарий визуально маскирует дефект: fallback возвращает тот же пустой словарь. При одновременной передаче geometry ошибка сохраняется независимо от прежних свойств.

Непустой словарь с falsy-значениями, например `{"enabled": false}`, сам по себе истинен: проблема именно в пустом словаре, не в значениях его ключей.

## Матрица текущего поведения

Предполагаются существующий объект, разрешённый доступ, подходящий тип геометрии и актуальная version.

| geometry | properties | Поведение |
|---|---|---|
| `null` | `{}` | Запись очистки, но ответ/event берут старые properties |
| Новая | `{}` | Исключение при сборке ответа внутри транзакции |
| Новая | `null` | Геометрия меняется, прежние properties сохраняются |
| `null` | Непустой объект | Полная замена properties, прежняя geometry сохраняется |
| Новая | Непустой объект | Оба значения заменяются |
| `null` | `null` | Запрос отклоняет schema validator |
| Поле пропущено | Любое / поле пропущено | Нет обязательного поля; запрос не соответствует текущей схеме |

В legacy repository нет проверки содержательного no-op: успешный UPDATE повышает version даже при совпадающих значениях. Правило Utility о no-op без нового token сюда автоматически не переносится.

## Что уже определено материалами

- `{}` рассматривается в BE-02 как допустимая полная очистка, а не merge или отсутствие изменения.
- Исправный ответ и содержимое публикуемого события должны описывать записанное значение.
- `properties=None` при переданной geometry сохраняет свойства.
- Utility Save использует другой путь; разрешение изменения attributes в EditVersion из этой задачи не следует.
- Проверки реальных commit/rollback допустимы только в disposable test-БД.
- Соседние BE-03 и AR-02/03 не становятся частью BE-02 автоматически.

## Уточнение 1 — граница HTTP-контракта

В BE-02 приведены запросы с явно заданными обоими полями. Не определено, требуется ли в рамках этой задачи также разрешить пропуск неизменяемого поля, который текущая схема запрещает. Это отдельный выбор объёма: влияет на совместимость схемы, документацию и матрицу проверок.

Вопрос пользователю: должно ли исправление сохранить обязательность обоих полей `geometry` и `properties`, или также разрешить не передавать поле, которое не меняется?

Ответ пользователя от 2026-11-01: «Сохраняем». Обязательность обоих полей сохраняется; пропуск поля не становится допустимым. Неизменяемое значение передаётся как `null`.

После этого уточнения существенных открытых вопросов о требуемом поведении BE-02 не осталось. Очистка должна работать отдельно и вместе с geometry; ответ и содержимое события соответствуют записи; сохраняются version check, существующие ошибки, обязательность полей и граница legacy. Изменение правил no-op, доставка realtime, Utility attributes и соседние замечания не входят в исправление.

## Подходы для обсуждения

Пользователь выбрал подход 1: локальное исправление сборки ответа в сервисе. Согласование проведено 2026-11-01. Дизайн: `docs/sprint_2/2026-11-01-be-02-design.md`.

1. Локальное исправление сборки `FeatureOut` в сервисе: различать `None` и `{}` явно, сохранив контракт repository. Минимальная область изменений; нужно проверить обе ветви очистки, сохранение properties при `null`, отсутствие события при отказе и соответствие результата записи в disposable БД. Это рекомендация автора для ограниченной задачи BE-02.
2. Сборка ответа из полного результата `UPDATE ... RETURNING`: repository возвращает также properties и geometry. Источник ответа непосредственно связан с записанной строкой, но меняются repository-контракт, SQL-проекция и тестовые подмены; требуется проверить сериализацию геометрии из PostGIS. Для BE-02 это более широкая перестройка, чем требует установленная причина.

Отдельный SELECT после commit не рассматривается как равнозначный источник результата собственной операции: он может увидеть последующее конкурентное изменение. Безусловная загрузка старого объекта не устраняет смешение `{}` и `None`.
