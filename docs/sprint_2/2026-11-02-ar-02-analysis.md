# AR-02. Влияние медленного подписчика слоя на запись Feature

## Область дефекта

Дефект относится к legacy GIS при включённом `LEGACY_GIS_API_ENABLED`. В модели [Generic Map Editing](../../DDD_Wiki/subdomains/generic_map_editing.md) подписка служит обновлению карты. У [EditVersion](../../Wiki/entities/edit_version.md) собственные идентичность и жизненный цикл. В рассмотренном пути публикации участвует CRUD объектов слоя. Переносить выводы на команду Save рабочей версии оснований нет.

## Где возникает ожидание

1. В [FeatureService](../../apps/backend/utility_service/use_cases/services/feature_service.py) создание, изменение и удаление завершают блок транзакции до вызова соответствующего метода публикации. Все три операции ждут его завершения. Если HTTP-клиент теряет ответ в этом интервале, запись уже зафиксирована.
2. [FeatureRealtimePublisher](../../apps/backend/utility_service/use_cases/services/feature_realtime_publisher.py) формирует событие слоя. Создание и изменение несут снимок Feature, удаление несёт идентификатор. Событие получает случайный eventId и время с точностью до секунды. Эти поля не задают порядок фиксации конкурентных транзакций.
3. [Менеджер соединений](../../apps/backend/utility_service/use_cases/services/realtime_connection_manager.py) обходит снимок подписчиков слоя. Для каждого по очереди он ждёт проверки активности сессии, затем отправки JSON. [Проверка активности](../../apps/backend/utility_service/use_cases/deps.py) открывает отдельную сессию БД. Поэтому быстрый подписчик может ждать как чужого транспорта, так и чужой проверки доступа. Таймаут закрытия сокетов при отзыве сессии не ограничивает отправку данных.
4. Внутри одного вызова рассылки следующий сокет ждёт предыдущего. Разные запросы могут начать отдельные рассылки одновременно. Последовательный цикл сам по себе не гарантирует единого порядка публикации конкурентных изменений. Начальный кадр `connected` отправляется [маршрутом подписки](../../apps/backend/utility_service/web_api/api/ws_layers.py) после регистрации сокета.

## Границы подтверждения

[Первичное ревью](architecture-realtime-review.md) и [результат пробы](evidence/code-review/verification.md) подтверждают блокировку второй отправки на имитациях сокетов в версии от 26 октября. [Исходная проба](evidence/code-review/realtime_probe.py) не совместима с нынешними конструкторами менеджера и контекста пользователя. Последовательное ожидание подтверждено чтением актуального кода. Время реального HTTP-ответа и сетевой порог возникновения задержки в этом анализе не измерялись.

## Поведение клиента и ограничения

[Клиент подписки](../../apps/frontend/src/composables/map/useLayerRealtime.ts) различает терминальное закрытие с кодом 1008 и разрыв с возможностью переподключения. После восстановления подписки [MapView](../../apps/frontend/src/components/MapView.vue) запрашивает принудительную перезагрузку данных активного слоя. Это механизм восстановления текущего состояния. В протоколе рассмотренного пути нет курсора для запроса пропущенной последовательности событий.

Действующая проверка сессии применяется перед каждой отправкой, включая начальный кадр. После успешной проверки уже допущенная отправка может завершиться. Перегрузка соединения и отзыв прав имеют разные последствия для повторного подключения.

## Согласованное требование к восстановлению

Пользователь подтвердил, что после восстановления связи карта должна отражать актуальное состояние слоя. Если за время разрыва объект создали, изменили и удалили, после синхронизации он должен отсутствовать. Воспроизведение трёх промежуточных событий для этого сценария не требуется.

Пользователь также подтвердил, что при длительном временном разрыве открытая карта должна сама восстановить подписку на активный слой и показать актуальные данные, даже когда связь вернулась после нынешних четырёх попыток. Условие предполагает действующий доступ к слою.

Сейчас восстановление может остановиться ещё раньше. Любая ошибка запроса одноразового билета в `openSocket` переводит клиент в состояние ошибки авторизации. Временная недоступность HTTP при получении билета тем самым прерывает восстановление. Кроме того, получение кадра `connected` и успешное перечитывание данных слоя — разные наблюдаемые результаты. Проверка восстановления должна подтвердить оба.

## Согласованный критерий независимости

Проверка удерживает отправку медленному подписчику заблокированной. До её освобождения автор записи должен получить успешный HTTP-ответ, а быстрый подписчик того же слоя должен получить событие этой записи. Относительный порядок HTTP-ответа и доставки быстрому подписчику не задан. Пользователь выбрал этот наблюдаемый критерий без отдельного численного предела задержки.

## Актуальность карты при конкурентных изменениях

Пользователь подтвердил, что карта, уже получившая версию 3 объекта, должна сохранить её при запоздалом поступлении версии 2. Восстанавливать строгий порядок фиксации транзакций для подписчика не требуется. То же требование актуальности распространяется на удаление — устаревшее обновление не должно возвращать удалённый объект на карту. В текущем контракте событие удаления содержит идентификатор объекта без номера версии.

## Исключение для крупного события

Пользователь подтвердил, что если один снимок превышает весь байтовый бюджет очереди, допустимо закрыть даже быструю подписку с пустой очередью и автоматически восстановить актуальные данные через HTTP. Для событий, помещающихся в пустую очередь, сохраняется критерий независимой доставки быстрому подписчику.
