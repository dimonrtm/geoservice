Корневой и frontend `.gitignore` не являются правилами Docker context. Backend имеет собственный `.dockerignore`, но его область действия не распространяется на frontend.

## Причинная цепочка

1. Docker устанавливает зависимости в Linux `/app/node_modules`.
2. Следующий широкий `COPY` допускает наложение локального дерева на установленное. Результат зависит от состояния host; наличие Windows workspace не доказывает происхождение каждого файла локального `node_modules`.
3. Env-файлы становятся доступны в build stage. Vite загружает общие и соответствующие mode-файлы, а используемые клиентские env-переменные подставляет при сборке.
4. `VITE_API_BASE_URL` участвует в вычислении адреса HTTP и WebSocket. Случайная настройка может направить запросы в другой endpoint и нарушить вход, workspace и Save/readback.
5. Финальная nginx-stage не копирует всё содержимое `/app`. Поэтому нельзя утверждать, что любой env-файл или все host dependencies автоматически доступны посетителю сайта. Отдельные значения могут попасть в bundle; исходные env могут остаться в промежуточных слоях/кэше.

Не все переменные shell хоста автоматически становятся переменными Docker build. Также Compose `environment` для dev-контейнера и env внутри Vite production build — разные механизмы. Изменение runtime env готового nginx-контейнера не пересобирает JavaScript.

## Внешние технические основания

- [Docker: Build context](https://docs.docker.com/build/concepts/context/): контекст определяет доступные сборщику файлы; `.dockerignore` фильтрует их, правила привязаны к контексту; Dockerfile-specific ignore имеет приоритет.
- [Vite: Env Variables and Modes](https://vite.dev/guide/env-and-mode): `.env.local` загружается и при production build, mode-specific значения имеют приоритет над общими, существующий environment — над env-файлами; клиентские значения встраиваются при сборке.

Это внешние технические факты; выводы о GeoService получены сопоставлением с текущим кодом. Доменных решений условной организации в этом анализе не принималось.

## Неопределённости для последовательного уточнения

Первый вопрос: каково требуемое поведение production Docker-образа относительно явно настроенного внешнего API endpoint после закрытия INF-03? Same-origin уже является принятой основной схемой, но код сохраняет override, а review упоминает явную передачу разрешённых настроек без определения списка и назначения.

Ответ пользователя: «Пока нет такого сценария» — production frontend не имеет текущей потребности обращаться к API по отдельному публичному адресу. Существующая схема same-origin соответствует известной потребности. Это не является самостоятельным согласованием удаления override из кода или запрета будущих сценариев.

Границы защиты dev target, постоянная автоматическая проверка и смысл воспроизводимости уточнены ниже прямыми ответами пользователя.

Согласованное пользователем поведение dev/prod: Docker-сборки обоих targets не подхватывают локальные frontend `.env`-файлы. Запуск `npm run dev` непосредственно на компьютере продолжает использовать их. Настройки dev-контейнера передаются явно при запуске; существующий API URL из demo Compose сохраняет своё назначение. Основание — рекомендация агента и прямой ответ пользователя «Да». Способ реализации выбран ниже.

Согласовано включение постоянной автоматической проверки изоляции frontend Docker build в CI. Основание — ответ пользователя «Да добавляем» после описания проверки: временная копия frontend с искусственным маркером в `node_modules`, старым файлом в `dist` и `.env.local` с посторонним API URL; обычная Docker-сборка без очистки этой копии; проверка отсутствия загрязнений в сборочном слое и итоговой статике. Реальные пользовательские env и секреты не используются. При регрессии CI завершается ошибкой. Конкретный механизм и состав проверок предстоит определить в дизайне; наличие `.dockerignore` само по себе недостаточно. Прежнее исключение нового CI gate для INF-02 не применяется к согласованному объёму INF-03.

Согласованная граница воспроизводимости: «достаточно независимости от локальных файлов разработчика». Побайтовая идентичность образов между сборками в разные дни не требуется. Фиксация base images по digest и расширенная работа над воспроизводимостью не следуют из этой задачи. Здесь локальные файлы означают зависимости, env, результаты сборки и служебные артефакты; актуальные исходники приложения, включая незакоммиченные изменения, остаются входом сборки.

Пользователь выбрал подход 1: список исключений в apps/frontend/.dockerignore с CI-проверкой реальной сборки. Альтернатива — запрет context по умолчанию с разрешением нужных входов. Подготовлен [дизайн](2026-11-01-inf-03-frontend-build-design.md), который принят пользователем. Реализация завершена; фактические результаты приведены в отчёте.

## Ограничения доказательств и дальнейшего обсуждения

Статический механизм загрязнения установлен, но размер context, конкретное содержимое слоёв и сравнение результатов чистой/загрязнённой сборки не измерялись. Не проверялись секреты в пользовательских файлах. Будущая проверка должна различать отсутствие файлов в context, отсутствие их в build stage и отсутствие нежелательных значений в bundle: это разные утверждения. Очистка временной копии до сборки не может служить единственным доказательством устранения INF-03.

Артефакт будет дополнен ответами и выводами. Отдельная agent memory не нужна: источники и объяснение сохраняются здесь, дублировать их в памяти нет оснований.
