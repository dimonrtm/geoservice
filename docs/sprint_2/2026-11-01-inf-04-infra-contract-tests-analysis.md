## Подтверждённая причинная цепочка

1. `.github/workflows/ci.yml`, job `backend_test`, собирает target `dev`
   с context `./apps/backend` и запускает `pytest` внутри образа без mount checkout.
2. `apps/backend/Dockerfile` делает `COPY . /app`: образ содержит backend,
   но не соседние `infra` и `.github`.
3. `apps/backend/pyproject.toml` включает `tests` в discovery. Тесты не потеряны
   из-за неправильного `testpaths`: они доступны, но применяют skip markers.
4. Два модуля ищут корень по наличию `infra/docker-compose.yml`, третий —
   по `.github/workflows/ci.yml`. Поиск начинается от реального пути файла теста.
5. При отсутствии найденного корня применяются `pytest.mark.skipif`.
   Workflow не содержит отдельной проверки выполнения этих контрактов без skips.

Следствие: зелёный `backend_test` не доказывает выполнение этих проверок.
Наличие checkout на host runner само по себе недостаточно: pytest читает
файлы из backend-only контейнера. Простого изменения working directory тоже
недостаточно для поиска, основанного на `Path(__file__).resolve()`.

## Точный состав существующих проверок

| Модуль в `apps/backend/tests` | Всего | Ожидаемый skip в backend-only образе | Что проверяет |
| --- | ---: | ---: | --- |
| `test_compose_security_contract.py` | 8 | 8 | Required production env, dev/prod startup и target, demo env, geometry settings API/migrator, отсутствие auto override, disposable DB Compose |
| `test_compose_startup_contract.py` | 4 | 2 | Два backend startup-скрипта; безопасность `dev-up.cmd` и принадлежность DB launcher отдельному проекту |
| `test_ci_db_test_isolation_contract.py` | 2 | 2 | Запуск DB tests отдельно, сравнение demo fingerprint, cleanup |
| Итого | 14 | 12 | Статические контракты содержимого файлов |

Числа получены чтением функций и markers, а не новым прогоном pytest.
Два теста startup-скриптов не требуют repo root и не имеют infra skip marker.
Модуль проверки CI отсутствует в перечне файлов исходной находки, но имеет
ту же причину пропуска и защищает связанную инфраструктуру тестирования.

Проверки читают строки файлов; они не запускают `.cmd`, не поднимают
production API, не проверяют браузерный маршрут и не выполняют миграции.
Например, проверка cleanup ищет `if: always()` в остатке workflow после
заголовка шага, а не разбирает структуру YAML. Это ограничение существующей
силы проверки; исправление её запуска само по себе его не устраняет.

## Существующие CI-проверки и границы

- `smoke_test` проверяет отказ Compose без обязательных env, валидность base/demo
  config, затем поднимает demo API. Это частичное пересечение, не выполнение
  найденных Python contract tests.
- DB suite запускается отдельным `geoservice-db-tests` через
  `infra/docker-compose.test.yml`, только для `tests/integration_tests`.
  Он не компенсирует пропущенные три модуля.
- Отдельный `frontend_docker_isolation` добавлен в INF-03: это другой gate,
  с Node runner и проверкой build context; infra Python tests он не запускает.
- В backend есть намеренные пропуски DB tests при отсутствии `RUN_DB_TESTS=1`
  (`tests/integration_tests/network_db_support.py`). Нельзя считать все skips
  всего backend одинаковым дефектом.
- Общий `apps/backend/conftest.py` импортирует Alembic и DB isolation helper,
  а тот — SQLAlchemy. Хотя сами три модуля используют Path/pytest, обычный
  запуск наследует эти зависимости. При `RUN_DB_TESTS=1` конфигурация запуска
  также выполняет Alembic; infra tests сами в этом не нуждаются.

## Связь с доменной моделью

`DDD_Wiki/bounded_contexts/work_order.md` закрепляет владение WorkOrder,
DefaultState, EditVersion и command-side edits. Проверки launcher и изоляции
БД косвенно защищают эти данные от нежелательного удаления/пересоздания
при тестировании и dev startup; они не заменяют доменные integration tests.

`DDD_Wiki/invariants/edit_version_persisted_edit_invariants.md` и
`Wiki/policies/edit_geometry_precision_policy.md` требуют детерминированной
канонизации перед сравнением и сохранением геометрии. Три geometry-related
проверки Compose защищают передачу настроек API/migrator и demo defaults.
Это проверка wiring, а не доказательство выполнения математических инвариантов.

`DDD_Wiki/model_health.md` содержит stale-оговорки об очереди реализации.
Поэтому актуальность технического CI определяется кодом и документами Sprint 2,
а не историческими planned/status полями wiki. Прочитанный resolved конфликт
`Wiki/conflicts/2026-10-11-save-outcome-observer-vs-operation.md` не задаёт
новых требований к запуску infra tests и не расширяет INF-04 до recovery.

Новых решений условной организации или внешних доменных фактов в этом анализе нет.

## Уточнение истории: допустимость локального запуска и skips

Пользователь попросил проверить, не были ли эти тесты намеренно оставлены
локальными. Дополнительная проверка планов и Git выявила важное основание,
которое не было учтено в первоначальной оценке:

- `docs/superpowers/plans/2026-08-03-sprint-2-day-1-coordinate-grid-demo-fixture.md:262`
  прямо говорит: «Expected: tests/lint PASS; Compose tests могут быть SKIPPED
  только без repository `infra/`; изменения unstaged.»
- Commit `d01acb2` от 2026-07-01 (`~ fix ci 1`) вводит поиск корня и skip
  для security-contract модуля при отсутствии infra в backend-only image.
- Commit `02a53c4` от 2026-08-04 (`~ fix ci`) вводит аналогичные skips
  для двух repo-dependent startup tests.
- `test_ci_db_test_isolation_contract.py` создан в `0b96e6a` от 2026-08-04
  уже с разрешённым skip при отсутствии workflow в backend-only image.

Таким образом, пропуски были предусмотрены явно, а не возникли незаметно.
В просмотренных документах и истории этих файлов не найдено отдельного правила
«эти тесты только локальные, запускать в CI запрещено/не нужно». Разрешение
skip в окружении без infra не равнозначно обязанности создать отдельный CI gate.
Первоначальный дизайн Compose описывает статические тесты и CI config guards,
но не задаёт явного требования выполнять все эти Python tests в CI.

Уточнённая оценка: отсутствие CI-покрытия подтверждено, но нарушение ранее
согласованного требования обязательного CI-запуска не доказано. Классификация
INF-04 как дефекта P2 — оценка ревью, которую следует рассматривать с учётом
принятой ранее допустимости skips. До решения о желаемой политике не считать
добавление CI-запуска автоматически обязательным исправлением.

Предыдущий вопрос о расширении покрытия INF-01/INF-02 преждевременен:
сначала требуется определить, нужно ли менять существующую политику запуска.
