# CQ-01 — независимость domain_services

Дата: 2026-11-10.
Статус: дизайн принят пользователем 2026-11-10 («Принимаю»), реализован и проверен. [План реализации](2026-11-10-cq-01-plan.md), [результаты](2026-11-10-cq-01-verification.md).
Основание: [анализ](2026-11-10-cq-01-analysis.md), [исходное замечание CQ-01](architecture-realtime-review.md#cq-01--p3-доменный-слой-зависит-от-инфраструктуры-и-use-cases).

Независимая проверка полноты дизайна выполнена 2026-11-10: существенных вопросов, мешающих планированию, рецензент не обнаружил. Это проверка документа, не проверка реализации.

## Цель и размер работы

Локальный архитектурный рефакторинг backend с проверкой зависимостей и сохранения legacy API. Устранить импорт infrastructure/use_cases из production-кода `domain_services`, чтобы геометрические функции можно было использовать независимо от ORM и прикладных исключений.

Это ограниченное изменение двух модулей и их потребителей, а не перестройка архитектуры приложения. Пользователь подтвердил отсутствие внешних потребителей внутренних Python-импортов; совместимость старых путей не нужна.

## Рассмотренные подходы

1. **Выбран пользователем:** отдельная ошибка bbox, HTTP-преобразование в адаптере; общий `BusinessValidationException` остаётся в use_cases. ORM registry перемещается в infrastructure. Преимущество — точная ответственность ошибки и ограниченное влияние на приложение. Цена — отдельный тип исключения и его обработчик.
2. Перенос общего `BusinessValidationException` в доменный слой, также с переносом registry. Сохраняет общий тип для разных проверок, но переносит в домен исключение, которое сейчас обозначает и нарушение бизнес-правил, и проблемы данных/сборки ответа. Не выбран.

## Доменная и техническая границы

Сохраняются геометрические ограничения, HTTP-статусы и тела ответов. CQ-01 не меняет generic map editing в authoritative utility workflow: bbox не становится AOI, физический registry не становится моделью `NetworkFeature`. Сохраняются правила `EditVersion`, Save/Revert, транзакций, токенов и событий.

Вне задачи: CQ-02/CQ-03, изменение схем БД и SQL, DTO и frontend, введение repository ports, реорганизация всех исключений, исправление семантики legacy 422, расширение форматов bbox и поддержка антимеридиана. Не требуется очищать infrastructure от всех зависимостей use_cases: это не критерий CQ-01.

Неприемлемые результаты: сохранение обратного импорта через compatibility shim в domain_services, превращение неожиданного `ValueError` в 422, изменение порядка проверок bbox, потеря сопоставления одного из шести типов Feature.

## Устройство изменения

Следующие конкретные имена и размещения предложены агентом в рамках выбранного пользователем варианта и приняты в составе этого дизайна.

### Ошибка bbox

В `apps/backend/utility_service/domain_services/bbox.py` объявить `InvalidBboxError(ValueError)`. Класс не содержит HTTP-статуса, API-кода, ORM-типов или зависимости от `BusinessValidationException`.

Все шесть `raise BusinessValidationException` в `parse_bbox` заменить на `InvalidBboxError`. Сохранить тексты, порядок проверок и `raise ... from e` при ошибке преобразования числа. `Bbox`, сигнатура парсера и успешный результат остаются прежними. Не добавлять валидацию в конструктор dataclass.

`BusinessValidationException` и пять мест его выбрасывания в `FeatureService` остаются прежними. Эта задача не устраняет смешение причин в общем прикладном исключении.

### HTTP-преобразование

В `apps/backend/utility_service/web_api/api/exception_handlers.py` добавить обработчик именно `InvalidBboxError`, возвращающий `422` и `{"error": str(error)}`. Существующий handler `BusinessValidationException` сохраняется. Общий handler `ValueError` не вводится.

`layers.py` продолжает вызывать `parse_bbox` до вызова сервиса: новая application-прослойка для парсинга не нужна. Преобразование доменной ошибки в HTTP остаётся в web_api, а не внутри парсера. Correlation middleware и существующее поведение заголовков сохраняются.

### ORM registry

Переместить `apps/backend/utility_service/domain_services/feature_registry.py` в `apps/backend/utility_service/infrastructure/postgresql/feature_registry.py`. Сохранить mapping, `ALL_FEATURE_MODELS`, `resolve_feature_model`, `get_layer_feature_model`, типы и поведение неизвестной таблицы. Удалить старый модуль без re-export.

Обновить импорт в `LayerRepository`. Пять методов repository продолжают получать те же ORM-классы; запросы и границы транзакций не меняются.

`UnknownStorageTableError` остаётся по существующему пути `use_cases/domain/exceptions/unknown_storage_table_error.py`; registry в infrastructure продолжает его использовать, существующий HTTP-handler продолжает возвращать 422 с прежним текстом. Это осознанное ограничение задачи: ошибка выбора физической таблицы не переносится в domain_services ради формальной чистоты. Поскольку импортов infrastructure из web_api по-прежнему нет, существующая архитектурная граница сохраняется.

## Защита границы

В `apps/backend/tests/test_architecture_boundaries.py` добавить проверку production-модулей domain_services с исключением каталогов tests. Запретить зависимости на `utility_service.infrastructure`, `utility_service.use_cases` и `utility_service.web_api`, а также прямые импорты `sqlalchemy`, `geoalchemy2`, `fastapi` и `starlette`, которые обошли бы смысл границы.

Проверка должна различать полный префикс модуля (равенство либо начало с `prefix + '.'`) и случайное совпадение имени. Учитывать обычные `import`, `from ... import ...`, импорты через родительский пакет и относительные импорты. Проверять импорты под `TYPE_CHECKING` тоже. Для вариантов синтаксиса использовать небольшие тестовые примеры анализатора. Существующие три правила не ослаблять и не менять их область проверки тестовых файлов.

Это статическая защита прямых импортов, не доказательство всей транзитивной независимости и не анализ произвольного `importlib`. Для текущего production-кода отдельно проверить отсутствие скрытого пути через общие модули; универсальный анализатор графа зависимостей не входит в задачу.

## Приёмка и проверки

| Проверка | Что должна доказать |
| --- | --- |
| Архитектурный тест | В production domain_services нет запрещённых зависимостей; типичные формы импорта не обходят проверку |
| Domain bbox tests | Тот же результат и сообщения, новый независимый тип; четыре координаты, нечисловой ввод, диапазоны, строгий порядок и граничные значения |
| Registry tests в infrastructure | Все шесть имён таблиц дают ожидаемые ORM-классы; wrapper читает storage_table; неизвестная таблица сохраняет тип и сообщение ошибки |
| HTTP tests | Ошибка реального bbox endpoint при пройденном access guard даёт прежние 422/body и не вызывает feature service; успешный bbox передаёт прежние значения |
| Exception handler tests | Новый тип и прежний BusinessValidationException дают ожидаемый ответ; UnknownStorageTableError сохраняет 422; произвольный ValueError остаётся 500 |
| Существующие regression suites | Feature CRUD, API, geometry domain tests и архитектурные правила продолжают проходить |

Для bbox зафиксировать поведение `nan`/`inf`, равных границ и допустимых крайних координат без изменения алгоритма. Отсутствующий query parameter остаётся ответственностью FastAPI; новый handler его не переопределяет.

Целевые проверки затем дополнить общим backend-набором в доступном окружении. DB-dependent skips явно отразить в отчёте; не выдавать их за пройденную интеграцию. Поскольку SQL, модели и миграции не меняются, новый DB smoke-стенд для CQ-01 не является обязательным. Если реализация потребует изменений за этой границей, сначала пересмотреть дизайн и соответствующие проверки.

Проверить Ruff/Black для затронутого кода, LF для изменённых/новых текстовых файлов и отсутствие старых production-импортов registry. Не выполнять git add, commit или push.
