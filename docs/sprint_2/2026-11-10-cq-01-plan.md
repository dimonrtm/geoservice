# CQ-01 — план реализации

> **Для исполнителя:** использовать `superpowers:executing-plans` при самостоятельном выполнении либо `superpowers:subagent-driven-development`, если пользователь выберет выполнение подагентами. Выполнять задачи по порядку, отмечая шаги чекбоксами. Правила репозитория запрещают git add/commit/push независимо от требований навыков.

**Цель:** сделать production-код domain_services независимым от инфраструктуры и use cases, сохранив поведение legacy GIS API.

**Архитектура:** `InvalidBboxError(ValueError)` принадлежит модулю bbox, преобразование в прежний 422 выполняется HTTP-handler. ORM registry принадлежит PostgreSQL infrastructure. AST-проверка защищает границу domain_services.

**Стек:** существующие Python, FastAPI, SQLAlchemy, pytest, Ruff, Black. Новые зависимости не нужны.

**Спецификация:** [принятый дизайн](2026-11-10-cq-01-design.md), [анализ](2026-11-10-cq-01-analysis.md).

## Общие ограничения

- Сохранить HTTP-статусы, сообщения, JSON и correlation headers; не перехватывать произвольный ValueError как 422.
- Сохранить алгоритм bbox, сигнатуры и mutable dataclass Bbox без дополнительной проверки конструктора.
- Сохранить mapping всех шести таблиц, ALL_FEATURE_MODELS и UnknownStorageTableError по текущему пути.
- Не менять SQL, транзакции, модели/миграции, FeatureService, frontend, CQ-02/CQ-03 и правила EditVersion.
- Старый domain_services/feature_registry.py удалить без compatibility shim; внешних потребителей нет.
- Документы писать по-русски, текстовые файлы — UTF-8/LF. Изменения оставлять unstaged.

## Особое внимание при проверке

1. Несколько ошибок bbox одновременно: порядок прежних сообщений сохраняется — задача 1.
2. `nan`, `inf`, равные границы и крайние координаты: текущая область допустимых значений сохраняется — задача 1.
3. Неожиданный ValueError и отсутствующий bbox query parameter: сохраняется различие 500 и FastAPI validation 422 — задача 1.
4. Неизвестная storage_table после перемещения: прежний тип и текст, HTTP 422 — задачи 1–2.
5. Импорты через родительский пакет, относительные импорты и TYPE_CHECKING: архитектурный запрет не обходится; похожие имена не запрещаются ошибочно — задача 3.

## Окружение и запуск

Команды `python -m ...` ниже выполняются из `apps/backend` в окружении с зависимостями проекта. При подготовке плана на Windows обнаружен только WindowsApps alias `python.exe`, наличие рабочего локального Python не подтверждено. Не устанавливать зависимости глобально.

Исполнитель сначала проверяет доступный backend Python либо существующий backend Docker image. Для контейнерного unit-прогона использовать read-only mount текущего `apps/backend` в `/app`, `--workdir /app`, `--network none`, `PYTHONDONTWRITEBYTECODE=1`, без RUN_DB_TESTS. Image выбирать из фактически доступных, не подставлять вымышленный tag. Пример запуска после определения `$cq01BackendImage`:

```powershell
$cq01BackendRoot = (Resolve-Path apps/backend).Path
docker run --rm --network none --mount "type=bind,source=$cq01BackendRoot,target=/app,readonly" --workdir /app -e PYTHONDONTWRITEBYTECODE=1 --entrypoint python $cq01BackendImage -m pytest -p no:cacheprovider
```

При отсутствии подходящего окружения явно сообщить блокер проверки. Ошибка окружения не считается ожидаемым падением нового теста. Новый DB smoke-стенд по этому дизайну не требуется.
