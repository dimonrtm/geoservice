# День 10 — анализ взаимодействия с линией на карте

Дата анализа: 2026-10-17. Плановая дата дня: 12 августа 2026 года.
Статус: требования уточнены, дизайн принят пользователем 2026-10-17. Реализация выполнена после отдельного разрешения пользователя; [отчёт и проверки](2026-10-17-day-10-map-interaction-implementation-report.md).

## Цель и порядок работы

Editor выбирает eligible line в workspace и визуально перемещает внутреннюю вершину. Проверочный объект — `L-003`, индекс `1`. Drag изменяет только local draft; новая frontend dependency запрещена. Требуются component tests и ручная проверка.

По запросу пользователя вопросы задаются по одному, в отдельных сообщениях. Решения предлагаются после устранения существенных неопределённостей. Это ограниченное расширение существующего workspace; артефакты сохраняются здесь по прямому указанию пользователя.

## Доменная граница

Источники: `Wiki/commands/update_edit_version_feature_geometry.md`, `DDD_Wiki/invariants/edit_version_persisted_edit_invariants.md`, `Wiki/policies/network_edit_semantics_policy.md`.

- Цель — существующая baseline line в открытой EditVersion назначенного Editor.
- Одна feature и одна внутренняя вершина относительно immutable baseline; endpoints и количество вершин не меняются.
- Геометрический жест не изменяет associations, соседние устройства или authoritative Default.
- Валидность, простота линии и покрытие AOI относятся к требованиям сохраняемого результата. Из этого само по себе не следует правило ограничения движения указателя во время drag.
- Technical Save не доказывает positional accuracy или topology. Новые предметные правила не расширяют scope Дня 10 автоматически.
- Окончательная eligibility, canonicalization и spatial validation принадлежат backend согласно принятому дизайну Дня 9. Клиент не воспроизводит серверное округление.

Это анализ принятых правил проекта и фактического кода, а не новое доменное исследование или производственная валидация. Проверка технических API и предложение дизайна приведены ниже отдельно от принятых требований.

## Дополнительная проверка eligibility

`apps/backend/utility_service/infrastructure/postgresql/repositories/edit_geometry_validation.py`, `check_baseline`, подтверждает: `feature_type=line`, operation не `created/deleted`, согласованный baseline типа `LineString` минимум с тремя вершинами. Ограничения «ровно три вершины» в этом guard нет. `check_context` проверяет структуру относительно baseline и согласованность operation с diff.

Следовательно, demo `L-003` с одной внутренней вершиной — частный случай допустимой серверной линии. Требования UI не определяют выбор вершины при четырёх и более координатах. Это вопрос продуктового охвата Дня 10, а не необходимость пересмотреть доменный инвариант.

**D10-Q02, принято пользователем 2026-10-17:** пока взаимодействие ограничивается линиями с единственной внутренней вершиной, то есть XY `LineString` с ровно тремя координатами. Это ограничение UI Дня 10; серверная допустимость линий с большим числом вершин не меняется. Выбор между несколькими внутренними вершинами в текущую задачу не входит.

## Проверки и ограничения анализа

**D10-Q03, принято пользователем 2026-10-17:** интерфейс должен препятствовать недопустимому перемещению уже во время drag, включая выход за AOI и совмещение внутренней вершины с endpoint. Откладывать эти ограничения до Save нельзя. Текущий `updateLocalVertex` проверяет только формат и диапазон XY; требование выходит за рамки существующей проверки локального ввода. Серверная validation остаётся обязательной.

**D10-Q04, принято пользователем 2026-10-17:** при недопустимой позиции указателя вершина остаётся в последней допустимой позиции и ждёт возвращения указателя в допустимую область. После возвращения снова следует за указателем. Скольжение вдоль границы не требуется. Недопустимая позиция не должна попадать в local draft; окончание drag за пределами допустимой области сохраняет последнюю допустимую позицию. Последние два положения — следствия запрета недопустимого перемещения, а не отдельная команда сохранения на backend.

**D10-Q05, принято пользователем 2026-10-17:** при блокировке перемещения необходимо показывать понятную причину. Место и способ отображения ещё не определены; серверные ошибки Save не заменяют обратную связь во время drag.

**D10-Q06, принято пользователем 2026-10-17:** если линия выбрана, но локальная геометрия не изменена, клик по пустому месту карты снимает выбор и скрывает маркер. Ответ получен на вопрос о чистом local draft; автоматически распространять его на dirty draft нельзя.

**D10-Q07, принято пользователем 2026-10-17:** клик по пустому месту после локального перемещения вершины запрашивает подтверждение отмены правки. Подтверждение отменяет только local draft, возвращает отображение к current, снимает выбор и скрывает маркер; отказ сохраняет правку и выбор. Эти переходы следуют из назначения подтверждения и D10-Q06. Позднее уточнение добавляет в День 10 отмену через диалог снятия выбора; отдельные Save/Cancel/Revert controls по-прежнему относятся к Дню 11. Неизвестная отправленная команда не считается обычной локальной правкой и не удаляется этим действием.

**D10-Q08, принято пользователем 2026-10-17:** при клике по другой доступной линии с несохранённой правкой также запрашивается подтверждение отмены; после подтверждения старая локальная правка отменяется и выбирается новая линия. Отказ сохраняет прежнюю правку и выбор. Это явная отмена перед новым выбором, а не обход запрета store на молчаливую замену dirty draft. Доступность новой линии определяется с учётом сохранённого changeSet: отмена local draft не снимает ограничения persisted feature/vertex.

**D10-Q09, принято пользователем 2026-10-17:** клик по недоступному объекту показывает причину недоступности. Ответ дан на выбор между сохранением текущего выбора с объяснением и обработкой как пустого места; принимается первый вариант: текущий выбор и local draft сохраняются, подтверждение отмены не открывается.

**D10-Q10, принято пользователем 2026-10-17:** если в месте клика несколько доступных линий, пользователю предлагается список для явного выбора нужной. Автоматический выбор ближайшей линии не используется. Для dirty draft подтверждение отмены относится к выбранной пользователем новой цели; открытие списка само по себе не означает отмену правки.

Продуктовый код не менялся. Тесты и ручной drag не запускались: текущая работа — анализ требований. Отчёт Дня 9 сообщает о прежних успешных проверках, но не является проверкой текущего интерактивного UI. Новая agent memory не создаётся: результаты сохраняются в этом документе без дублирования. Git staging/commit/push не выполняются.

## Технические выводы после уточнений

### Eligibility и идентичность

`workspace_service.py:feature_properties` публикует `featureType`, `operation`, `assetCode`. Поэтому клиенту не требуется угадывать тип объекта по одному лишь GeoJSON или разрешать редактирование по строке `L-003`. Для Дня 10 пригодны существующие линии с `operation=unchanged|updated`, конечной XY LineString ровно из трёх координат, доступным контекстом и совместимостью с changeSet. Двухвершинная и четырёхвершинная линии имеют разные причины недоступности, хотя обе не получают handle.

`project_workspace_draft` проверяет согласованность current/baseline, feature types и operations. Baseline не передаётся отдельно для каждой чистой feature: клиент опирается на согласованный workspace и не синтезирует baseline. Окончательный серверный guard сохраняется.

Сохранённый changeSet ограничивает выбор той же feature/vertex. Даже подтверждённая отмена local draft не позволяет выбирать другую persisted цель. При recovery/reading-current/stale/blocked недостаточно оставить визуально активный marker: локальные действия обязаны уважать существующие ограничения store.

### Пространственные ограничения

Серверный `edit_geometry_spatial.sql` проверяет `ST_IsSimple`, отсутствие нулевых сегментов и `ST_Covers(aoi, line)`. Проверка только moving point или extent AOI недостаточна. Для вогнутого Polygon, отверстия и MultiPolygon допустимость зависит от обоих сегментов. Касание границы разрешено; пересечение внутренности отверстия запрещено.

Для трёх координат необходимо различать нормальную прямую линию и наложение двух сегментов при развороте назад. Запрет одной лишь коллинеарности ошибочно исключил бы допустимую прямую. Совпадение moving vertex с endpoint создаёт нулевой сегмент и блокируется.

Клиентская проверка проверяет локальную XY-геометрию, но не обещает идентичность PostGIS во всех численных пограничных случаях. Сервер канонизирует координату по policy EditVersion, которая не входит в текущий workspace contract. Клиент не должен незаметно копировать default grid и объявлять будущий Save гарантированным: почти совпадающие координаты могут совпасть после серверного округления. Серверная проверка после канонизации остаётся обязательной. Расширение API ради policy в День 10 не согласовано.

### MapLibre и жизненный цикл

Проверена установленная версия `5.15.0`, включая `node_modules/maplibre-gl/src/ui/marker.ts`. `_onMove` вычисляет новую координату из положения указателя и исходного смещения захвата, вызывает `setLngLat`, затем событие `drag`. Публичный `setLngLat(lastAccepted)` в обработчике позволяет вернуть marker без завершения drag; следующая попытка снова вычисляется из указателя. Это основание технического варианта, не результат реального drag-теста. Кратковременное отображение запрещённой позиции и восстановление после возврата указателя требуют browser-проверки.

Hit testing может вернуть части/дубли features: геометрия результата клика не является исходником для сохранения. Нужны уникальные feature IDs и исходные координаты из workspace/localDraft. Слои AOI и базовая карта не являются выбираемыми объектами сети.

Текущий `renderWorkspace` не знает о candidate, поэтому визуальное перемещение требует отдельной проекции отображаемой геометрии. Нельзя изменять current, чтобы заставить карту перерисоваться. Перемещение не должно повторно запускать fitBounds или создавать новый Marker на каждом событии.

Нужно проверить teardown слушателей/marker, потерю доступа во время drag и устаревшие результаты диалога при смене workspace. После drag не должен срабатывать клик по пустому месту с немедленным подтверждением отмены. Собственные кнопки списка/диалога не должны передавать клик карте.

### Актуальность wiki

`DDD_Wiki/aggregates/edit_version.md` ещё описывает реализованный workspace как read-only, хотя backend Save и frontend state уже существуют. Для реализации актуальны код и материалы дней 8–9; доменные инварианты из wiki сохраняют силу. Старые формулировки возврата current в stale response не заменяют принятый строгий error body и последующий GET. Wiki в рамках этой задачи не переписывается.

## Принятый дизайн

Пользователь принял предложенное разделение ответственности 2026-10-17. Ответ «Принимаю» относится к дизайну после уточнений D10-Q01–Q10. Текущий запрос охватывает анализ и согласование задачи; реализация и её проверки ещё не выполнялись.

Принято расширить существующий workspace небольшим модулем взаимодействия карты, чистыми проверками eligibility/геометрии и Vue controls выбора/подтверждения. Pinia остаётся единственным владельцем localDraft. MapLibre владеет только marker и слушателями; UI хранит временные списки кандидатов, сообщение и цель подтверждения.

Возможные границы реализации:

| Вариант | Последствия |
| --- | --- |
| Выделить взаимодействие и чистые проверки, подключить к существующему MapView/store | Рекомендуется: изолированные проверки геометрии, управляемый lifecycle, без второго draft store |
| Добавить всё непосредственно в MapView.vue | Меньше новых файлов, но смешивает legacy Polygon flow, геометрию, диалоги и workspace lifecycle; сложнее проверять |
| Создать отдельный WorkspaceMapView | Чёткая граница utility map, но перенос существующего render/fit lifecycle и больше регрессионной работы для текущего объёма |

Предлагаемое поведение:

1. Клик запрашивает только workspace feature layers с небольшим экранным допуском. Уникальные hits сопоставляются с актуальным workspace. При нескольких доступных линиях открывается список с assetCode и идентификатором для различения; выбор строки запускает обычное действие выбора. Открытие/закрытие списка само по себе не меняет draft. Если доступны и недоступные объекты одновременно, выбор предлагается среди доступных; если доступны только недоступные, показываются причины без снятия выбора.
2. Для выбранной линии показываются выделение и один Marker на индексе `1`. Map projection подставляет candidate выбранной feature в копию отображаемого набора; workspace/current не меняется.
3. Каждое событие drag формирует candidate и проверяет оба сегмента относительно Polygon/MultiPolygon, включая отверстия и границы. Допустимая позиция передаётся store, недопустимая не записывается, marker возвращается к последней принятой позиции. Сообщение объясняет причину; при новом допустимом движении сообщение об ограничении очищается. После завершения drag за границей остаются последняя допустимая позиция и объяснение.
4. Клик в пустоту при чистом draft снимает выбор. Для dirty draft и перехода на другую eligible line открывается подтверждение; отказ ничего не меняет, согласие вызывает существующий local Cancel и затем новое действие. Перед подтверждённым переходом повторно проверяются workspace, доступность и актуальность цели.
5. Список и диалог имеют обычные доступные кнопки, управление фокусом и закрытие без потери правки. Полноценное перемещение вершины с клавиатуры остаётся Дню 11 вместе с общей keyboard/accessibility задачей. Причины показываются рядом с картой, а не в developer console.
6. Пространственные проверки реализуются без новой зависимости и без сетевого запроса на каждый drag. Проверка полного покрытия сегмента требует обработки пересечений с кольцами и интервалов между пересечениями; один midpoint всего сегмента недостаточен. Для численно неоднозначного случая безопаснее отклонить локальное движение с причиной, чем молча пропустить наружу. Детали численной устойчивости должны быть закреплены тестами; новый предметный positional tolerance не вводится.

Предполагаемые области изменения: `MapView.vue`, `EditorWorkOrdersView.vue`, `workspace-layers.ts`, новый composable взаимодействия, чистые geometry/eligibility helpers, небольшие controls списка/подтверждения и соответствующие tests. Store actions переиспользуются; любые необходимые изменения guards должны оставаться совместимыми с recovery. Backend, contracts Save и dependency manifest изменять не требуется в предложенном варианте.

## Матрица будущей проверки

| Область | Обязательные случаи |
| --- | --- |
| Выбор | Трёхвершинная existing line; Point, две/четыре вершины, MultiLineString, created/deleted; persisted changeSet другой feature; отсутствие доступа |
| Неоднозначность | Две реальные линии дают список; дубли одной feature не дают ложный список; отмена списка не меняет draft |
| Проекция | Candidate меняет только отображение выбранной линии; current/token/baseline/associations неизменны; endpoints неподвижны |
| Drag | Несколько допустимых событий меняют local draft до dragend; недопустимое событие не попадает в store; возврат указателя возобновляет движение; отпускание снаружи сохраняет последнюю допустимую позицию |
| Геометрия | AOI boundary допустима; outside, hole, вогнутый выход сегмента и разрыв MultiPolygon запрещены; нулевой сегмент и наложение запрещены; прямая линия без наложения допустима |
| Обратная связь | Причина недоступности/блокировки понятна; сообщение не создаёт новый диалог на каждое событие; допустимое движение очищает прежнее ограничение |
| Отмена | Чистое снятие выбора; dirty confirm accept/reject; подтверждённый переход на другую линию; repeated selection сохраняет draft; Cancel не вызывает HTTP |
| Lifecycle | Unmount/reset/access loss убирают marker/listeners; поздний callback не меняет новый workspace; завершение drag не запускает случайный deselect |
| Регрессия | Legacy editing/empty modes, один fit при открытии workspace, API/store recovery tests |

Component tests должны проверять связку событий карты, UI и состояния, а не только вызов mock-функции `setData`. Геометрические helpers требуют самостоятельных unit cases с Polygon holes и MultiPolygon. Моки MapLibre не доказывают реальную работу указателя: ручной сценарий включает `WO-001 → L-003 → drag → выход в недопустимую область → возвращение → завершение → отмена через подтверждение`. Проверки наложенных линий допустимо выполнять на явно синтетическом fixture, не меняя demo seeds.

После реализации: targeted Vitest, полный frontend suite, app typecheck, lint, build и ручной drag. Пока эти проверки не выполнены, M3 не объявляется пройденной.

## Проверенные внешние технические источники

- [MapLibre Marker API](https://maplibre.org/maplibre-gl-js/docs/API/classes/Marker/) — публичные drag events, `getLngLat`, `setLngLat`, lifecycle. Онлайн-документация может описывать более новую версию; механизм сверялся с установленным `5.15.0`, новые API автоматически не заимствуются.
- [MapLibre Map API](https://maplibre.org/maplibre-gl-js/docs/API/classes/Map/) — `queryRenderedFeatures` и возможные дубли/разбиение геометрии.
- [PostGIS ST_Covers](https://postgis.net/docs/ST_Covers.html) — полное покрытие геометрии с допустимой boundary, основание проверки сегментов, а не только вершины.
- [PostGIS ST_IsSimple](https://postgis.net/docs/ST_IsSimple.html) — простота геометрии, отдельная от одного лишь непустого типа.

Эти четыре документа подтверждают техническую семантику; они не представлены как новое исследование практики условной организации. Пользовательские решения D10-Q01–Q10 имеют собственное происхождение — ответы в текущем обсуждении.
