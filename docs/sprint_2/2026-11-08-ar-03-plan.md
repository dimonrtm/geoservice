# AR-03: план реализации диагностики realtime

> Для агента-исполнителя: применять superpowers:executing-plans при самостоятельном исполнении или superpowers:subagent-driven-development при выбранном пользователем исполнении через субагентов. Выполнять задачи последовательно; завершение отмечать чекбоксами. Git add/commit/push запрещены правилами репозитория.

**Цель:** по серверным логам находить конкретное изменение, подключение и причину сбоя отправки, включая отброшенную очередь, без изменения результата сохранения.

**Архитектура:** отдельный безопасный JSON-лог на пару eventId/connectionId; диагностический контекст сопровождает публикацию, очередь и текущий кадр. Менеджер владеет завершением подписки и исключает дубли; FeatureService сохраняет защитную границу после commit.

**Стек:** существующие Python/FastAPI, asyncio, logging, pytest, PostGIS и Docker Compose. Новые зависимости не нужны.

**Дизайн:** [2026-11-08-ar-03-design.md](2026-11-08-ar-03-design.md), принят пользователем. Статус плана: выполнен; результаты и границы проверки — в [отчёте](evidence/ar-03/verification.md).

## Общие ограничения

- Только legacy Layer/Feature realtime. Не менять frontend, HTTP-ответы, формат feature-событий, Save/Revert и бизнес-инварианты.
- Сохранить best-effort, single-worker, FIFO, max_pending_frames=32, max_pending_bytes=1024*1024, send_timeout_seconds=5.0, close_timeout_seconds=1.0 и коды закрытия AR-01/AR-02.
- Нет логов потерь при отсутствии подписчиков, обычном False проверки сессии, logout, управляемом shutdown и распознанном штатном закрытии. Нет логов успешных отправок.
- Различать not_sent и send_unconfirmed. Не считать отсутствие записи доказательством доставки. Не добавлять клиентские подтверждения, outbox, метрики и хранилище логов.
- Не выводить payload, токены, ticket, sid, email, query string, произвольный текст исключений и close reason. Стек: не более 10 последних кадров, только basename файла, функция и номер строки.
- Общие типы и logging не зависят от web_api. Не заменять существующее HTTP-логирование.
- Русский язык документов, UTF-8/LF, понятные имена по месту использования. Не создавать worktree для написания плана; при реализации оценить пригодность текущего checkout.

## Особое внимание при проверке

1. Штатный close без статуса не превращается в сетевую аварию: задача 4, тест пустого close frame на установленном transport stack.
2. Успешный send одновременно с retire не становится потерей: задача 3, тест управляемого порядка завершения.
3. Частично выполненный fanout не создаёт ложных потерь у уже принятых получателей: задача 2, fault injection между постановками.
4. Отказ logging handler не меняет исход commit и не останавливает cleanup: задачи 1, 3 и 5.
5. Ошибка проверки sid закрывает несколько подписок, но не теряет их очереди из диагностики: задача 3, две подписки одной сессии и независимая третья.

## Самопроверка плана и передача

План сверён с дизайном: формат/безопасность — задача 1; ранние ошибки и контекст — 2; queue/current/races/session/cleanup — 3; normal/abnormal disconnect — 4; commit и реальная видимость логов — 5. Все пять особых случаев имеют проверку в соответствующей задаче. Вспомогательные типы и методы перечислены вместе с потребителями; новый logging не импортирует web_api. Тесты при написании плана не запускались.

Реализация выполнена самостоятельно в текущем чате с итоговым независимым ревью. Отдельное обновление agent memory не требуется: план и дизайн сохраняют знания. Repository-change ingest оценивать после реализации только при появлении новой долговременной технической информации, не по факту завершения задачи.
