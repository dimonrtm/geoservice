## Действующие требования после уточнений

Этот раздел имеет приоритет над отменёнными ответами в истории вопросов ниже.

После отмены технической блокировки WorkOrder пользователь подтвердил итоговую формулировку этих границ ответом «Да». Это подтверждение требований, а не выбор технического подхода или разрешение реализации.

- Все вкладки одного браузера используют один аккаунт. Ранее согласованные разные аккаунты во вкладках и восстановление отдельного аккаунта каждой вкладки отменены последним прямым ответом пользователя.
- Один аккаунт может одновременно работать на нескольких устройствах и в разных браузерах. Вход привязан к конкретному устройству и браузеру; новый вход не завершает предыдущие входы.
- Работа вкладок с разными WorkOrder независима; это не независимость авторизации. По последнему ответу пользователя технический запрет повторного открытия WorkOrder не нужен. Требования ошибки второй вкладки, освобождения за 2 секунды и удержания при приостановке отменены. AR-01 не вводит владение нарядом или межвкладочную блокировку.
- Организационное правило учебного режима «редактировать один наряд в одном окне» не преобразуется в запрет открытия. Действующие серверные guards, stale rejection и разбор исходов уже отправленных команд сохраняются.
- Поддерживаемая среда: актуальные Chrome, Edge и Firefox на компьютерах и ноутбуках. Мобильные устройства исключены из текущего объёма. Конкретные версии необходимо фиксировать при проверках; операционные системы этим ответом не ограничены.
- При потере нового токена после уже выполненной сервером ротации допустим повторный вход. Штатная гонка восстановления двух вкладок по-прежнему должна проходить без повторного входа.
- После успешного выхода все ранее выданные токены данного входа браузера должны немедленно перестать давать доступ при новых серверных проверках. Пользователь выбрал второй подход: координация вкладок и отзываемая серверная сессия браузера. Первый подход с действующими до exp access JWT отвергнут.
- При наличии действительного токена выполняется автоматический вход; иначе показывается форма входа. Правило выбора между аккаунтами A и B в одном браузере больше не требуется.
- Раннее требование «один токен на пользователя» необходимо читать с последним уточнением: вход привязан к устройству и браузеру. Оно не задаёт один общий секрет для всех устройств, формат access/refresh token или отмену ротации.
- Последнее прямое уточнение отменяет глобальный выход: выход относится к текущему браузеру на текущем устройстве и не завершает входы в других браузерах/на других устройствах. Все вкладки текущего браузера используют общий аккаунт; прежнее требование выхода всех его вкладок сохраняется.
- Для остальных вкладок текущего браузера ранее согласованы автоматический переход на экран входа и предел 5 секунд после подтверждённого сервером выхода. Этот предел больше не относится к другим устройствам/браузерам.
- Прежние требования предупреждать о неподтверждённом выходе на других устройствах и автоматически завершать глобальный выход после восстановления связи отменены вместе с глобальным выходом. Если запрос выхода не дошёл до сервера, текущий вход сохраняется, пользователю показывается «Не удалось выйти, попробуйте ещё раз». Автоматический отложенный выход этим решением не вводится. Потеря ответа после фактического серверного выхода — отдельный случай, который нельзя приравнять к доказанно недоставленному запросу.

Одновременная работа на нескольких устройствах разрешена. Ответы о технической блокировке WorkOrder в истории вопросов ниже отменены последним уточнением после вопроса 24. Они не входят в действующий объём задачи.

## Запрос и исходное требование

Разобрать AR-01 из [архитектурного ревью](architecture-realtime-review.md), учитывая текущий код, Sprint 2 и Wiki/DDD_Wiki. Вопросы задаются по одному; предложения решения следуют после уточнения существенных требований. Артефакты находятся в `docs/sprint_2`; продуктовый код не изменяется.

Критерий исходного ревью: две вкладки восстанавливают тот же аккаунт без ручного login; использованный refresh token не становится пригодным для произвольного replay. Ревью также упоминает закрытие вкладки во время refresh и fallback механизма координации. Это исходные пожелания ревью, а не уже выбранный дизайн.

## Как работает текущая реализация

| Участок | Наблюдаемое поведение |
| --- | --- |
| `apps/frontend/src/App.vue` | При mount вызывает `restoreSession`, если локальный store ещё не готов и не восстанавливается; retry вызывает тот же action. Ожидание показывается при `!isReady || isRestoring`. |
| `apps/frontend/src/stores/auth.ts` | Каждая попытка получает локальный `restoreGeneration`; актуальный success устанавливает token/user, актуальная ошибка очищает локальную сессию. Initial 401 вызывает `forceWorkOrdersReset`. |
| `apps/frontend/src/api/auth.ts` | Refresh отправляется с cookie через `withCredentials`; `authErrorHandling: "caller"` передаёт обработку ошибки в store. Login и logout тоже используют cookie. |
| `apps/frontend/src/api/http.ts` | Timeout HTTP — 30 секунд. Access token берётся из памяти локального store. Для refresh interceptor не выполняет предварительную auth-очистку. |
| `apps/backend/utility_service/web_api/api/auth.py` | Login и успешный refresh устанавливают HttpOnly cookie с Path `/api/v1/auth`. Logout отзывает переданный token и удаляет cookie. Refresh сначала ожидает сервис, затем устанавливает cookie. |
| `apps/backend/utility_service/use_cases/services/auth_session_service.py` | В одной транзакции проверяет активную сессию и пользователя, отзывает прежний token и создаёт новый. При неуспехе ротации возвращает `AUTH_REQUIRED`/401. |
| `apps/backend/utility_service/infrastructure/postgresql/repositories/auth_session_repository.py` | Ротация — условный UPDATE по hash, `revoked_at IS NULL` и сроку действия с RETURNING. |

Поиск вызовов `refreshSession`/`restoreSession` показывает startup/retry путь. Автоматический refresh на каждый рабочий 401 текущим HTTP interceptor не выполняется. Поиск `BroadcastChannel`/`navigator.locks` в `apps/frontend/src` не выявил такой координации.

## Причинная последовательность

1. У вкладок A и B независимая память приложения, но общий refresh cookie C0.
2. Обе отправляют refresh с C0 до получения первого нового cookie.
3. A успешно отзывает C0 и создаёт C1 в транзакции.
4. B не находит активную C0 либо проигрывает условный UPDATE; получает 401.
5. Успешный ответ A устанавливает C1 и access token в A. Ошибка B не содержит вызова `clear_session_cookie` в показанном refresh endpoint.
6. В B `restoreSession.catch` считает initial 401 завершением сессии, очищает локальную авторизацию и вызывает принудительный reset work orders. Затем UI переходит к входу.

Поэтому формулировка «завершает одну сессию» требует точности: проигравшая вкладка теряет авторизованный UI; новая серверная сессия победителя не отзывается этим отказом. При полученной C1 следующие запросы браузера уже могут использовать новый cookie, но это само по себе не повторяет неудавшийся restore B.

Локальный `restoreGeneration` из FE-01 защищает применение продолжения внутри конкретного store. Он не упорядочивает запросы разных вкладок и не управляет применением HTTP Set-Cookie браузером.

## Что подтверждено, а что ещё нет

- Причина отказа прослежена по текущим исходникам от App до SQL UPDATE и обратно до очистки store.
- `test_refresh_session_rejects_replay_when_rotation_loses_race` в `apps/backend/utility_service/use_cases/tests/test_auth_session_service.py` подставляет `rotated_session = None` и проверяет отказ без выпуска новой сессии. Это unit-проверка ветки, а не запуск двух конкурентных транзакций.
- Исходное ревью сообщает об успешном прогоне этого теста. В этом исследовании тесты пока не запускались; исторические результаты не объявляются новым прогоном.
- Настоящий двухвкладочный браузерный сценарий с серверной ротацией в этом исследовании пока не выполнялся. FE-01 smoke с mock API его не заменяет.
- Сценарий закрытия вкладки нужно разделить на ожидание отправки, выполняющийся запрос и момент после серверного commit до получения нового cookie. Это разные состояния; одинаковый исход для них пока не определён.
- Если сервер успел отозвать C0, а новый cookie не получен браузером, один только факт завершения/закрытия клиентского запроса не доказывает возможность следующего успешного восстановления. Фактическая доставка cookie при закрытии вкладки ещё не проверена.

Значимые ограничения:

1. FE-01 согласован как узкое исправление retry → новый login → поздний restore. Общая координация login/logout/restore и AR-01 явно оставлены отдельно; нельзя объявить их принятыми требованиями FE-01.
2. Ошибка авторизации влияет не только на экран входа: auth store скрывает actor, приостанавливает recovery и сбрасывает work orders по действующим правилам.
3. Состояние отправленного Save/Revert и состояние наблюдателя различаются. Потеря авторизации не доказывает отказ серверной команды и не разрешает автоматически создавать новый CommandId.
4. Другая учётная запись не получает локальные recovery-материалы автоматически. Восстановление доступа не разрешает обход актуальных access/lifecycle/token guards.
5. Политика условной организации допускает редактирование одного наряда в одном окне; это организационное правило, а не реализованная межоконная блокировка и не запрет нескольких вкладок приложения.
6. Обычная неотправленная правка не получает новую гарантию восстановления после аварийного закрытия браузера только из-за исправления auth.

Wiki/DDD_Wiki задают ограничения работы и восстановления намерения, но найденные материалы не задают отдельного полного протокола межвкладочной авторизации. Техническое исправление не требует отдельного исследования с квотой внешних источников.

## Неопределённости для последовательного обсуждения

Первый вопрос касается границы продукта: охватывает ли задача только одновременное восстановление одного аккаунта или также согласованность входа, выхода и смены аккаунта между вкладками. От ответа зависит перечень обязательных сценариев, а не только выбор реализации.

После определения границы необходимо проверить, что требования однозначно описывают поддерживаемые браузеры и размещение приложения, завершение ожидания при недоступности соседней вкладки, допустимый исход потери ответа после ротации и сохранение изоляции рабочих контекстов. Это темы дальнейшего уточнения, не принятые решения и не пакет вопросов пользователю.

### Вопрос 1 — граница AR-01

Какого поведения вы ожидаете от остальных вкладок, если во время их восстановления пользователь в одной вкладке выходит из системы или входит под другим аккаунтом?

Ответ пользователя: «Вкладки не должны зависеть друг от друга если они не работают с одним и тем же WorkOrder».

Зафиксированное требование: вкладки с разными WorkOrder не должны зависеть друг от друга. Ответ не устанавливает конкретное поведение вкладок с одним WorkOrder и сам по себе не определяет, должны ли разные вкладки одновременно поддерживать разные аккаунты. Эти детали нельзя подменять предположением о едином аккаунте браузера.

Техническое следствие для уточнения: текущий cookie восстановления общий, хотя access token и состояние приложения находятся в памяти каждой вкладки. Новый login устанавливает общий cookie; уже открытая другая вкладка сохраняет свой access token, но при следующем восстановлении использует общий cookie. Следовательно, независимость рабочего контекста и независимость аккаунта — разные требования.

### Вопрос 2 — независимость аккаунтов

Должны ли две вкладки с разными WorkOrder позволять одновременно работать под разными аккаунтами и сохранять каждая свой аккаунт после перезагрузки страницы?

Ответ пользователя: «Да».

Принято: две вкладки с разными WorkOrder могут одновременно работать под разными аккаунтами; перезагрузка каждой должна восстанавливать её собственный аккаунт. Это продуктовая гарантия, а не выбор способа хранения credentials. Текущая общая cookie как единственный источник аккаунта при restore этой гарантии не обеспечивает. Поэтому исходная рекомендация ревью о сериализации refresh сама по себе недостаточна для уточнённой задачи.

### Вопрос 3 — выход при одном аккаунте в разных вкладках

Если один и тот же пользователь открыл разные WorkOrder в двух вкладках, должен ли выход из аккаунта в одной вкладке оставлять вторую авторизованной, в том числе после её перезагрузки?

Первоначальный ответ пользователя: «Да». Отменён последующим прямым уточнением: «А нет если пользователь вышел то он вышел во всем приложении».

Действующее требование: выход не ограничивается вкладкой, в которой он выполнен; пользователь выходит во всём приложении. Прежнее решение о независимом logout для одного аккаунта больше не действует. Независимость вкладок с разными WorkOrder не означает независимость выхода. При ранее принятой возможности разных аккаунтов во вкладках требуется уточнить, распространяется ли выход на другие аккаунты. Область действия по устройствам пока также не определена.

### Вопрос 4 — вход в новой вкладке

Когда пользователь открывает GeoService в новой вкладке, должна ли она сразу входить под аккаунтом уже открытой вкладки или сначала показывать форму входа?

После уточнения области и задержки глобального выхода вопрос возвращён к обсуждению применительно к новой вкладке с вручную введённым адресом, без дублирования существующей вкладки.

Ответ пользователя: «Если у пользователя есть токен он должен войти по этому токену иначе показывать форму входа».

Принято: при наличии действительного токена новая вкладка входит автоматически, иначе показывает форму входа. Ответ не выбирает технический вид токена, способ его хранения или передачи. При ранее принятой возможности одновременных аккаунтов A и B остаётся неясным, как новая вкладка без собственной истории определяет свой аккаунт. Нельзя молча считать её токеном последний общий cookie: это ещё не согласованное правило выбора.

### Вопрос 5 — область выхода при разных аккаунтах

Если в одной вкладке открыт аккаунт A, а в другой — аккаунт B, выход из A должен завершить только все входы A или также выйти из B?

Ответ пользователя: «Только A».

Принято: выход из A завершает входы A во всех вкладках приложения, но не затрагивает B. Правило связано с аккаунтом, а не с совпадением WorkOrder. Независимость разных аккаунтов и восстановление собственного аккаунта вкладки после reload сохраняются. Область действия между браузерами и устройствами ещё не определена.

### Вопрос 6 — выход на других устройствах

Выход из аккаунта A должен завершать его сессии только в текущем браузере или также в других браузерах и на других устройствах?

Ответ пользователя: «также в других браузерах и на других устройствах».

Принято: выход глобален для аккаунта A, включая другие браузеры и устройства; другие аккаунты не затрагиваются. Это расширение исходной задачи о конкурентном restore до требований к жизненному циклу авторизации. Нельзя считать его выполненным только локальной очисткой UI или отзывом одного refresh token.

Проверка текущих исходников: `revoke_session` отзывает один hash; `get_current_user` проверяет JWT и существование/активность пользователя, но не отзыв его auth session. Access JWT содержит `sub`, `role`, `iat`, `exp`; logout не делает уже выданный JWT недействительным. В `utils/settings.py` срок access token по умолчанию — 30 минут (фактическая конфигурация среды может отличаться). Текущий код не обеспечивает принятую гарантию глобального выхода.

### Вопрос 7 — отображение глобального выхода

После выхода на одном устройстве остальные открытые вкладки этого аккаунта должны сами перейти на экран входа без действий пользователя или достаточно показать вход при следующем обращении к серверу?

Ответ пользователя: «сами перейти на экран входа без действий пользователя».

Принято: открытые вкладки аккаунта должны автоматически перейти на экран входа после глобального выхода, включая другие браузеры и устройства. Ожидание очередного пользовательского действия не удовлетворяет требованию. Другие аккаунты остаются авторизованными. Способ доставки уведомления не выбран.

Это требование о реакции UI не означает разрешение серверу принимать новые запросы с отозванной авторизацией до обновления экрана. Поведение уже выполняющихся запросов и недоступных по сети клиентов требует отдельного анализа. Принятые доменные ограничения сохраняются: принудительная потеря доступа не откладывается ради локальной правки; выход не доказывает отмену или неуспех уже отправленного Save/Revert.

### Вопрос 8 — задержка автоматического выхода

Какую максимальную задержку после подтверждённого сервером выхода вы считаете допустимой для автоматического перехода остальных вкладок на экран входа, если устройства подключены к сети и браузеры не приостановлены?

Ответ пользователя: «Не более 5 секунд».

Принято: не позднее 5 секунд после подтверждённого сервером выхода остальные открытые вкладки этого аккаунта автоматически переходят на экран входа при доступной сети и неприостановленном браузере. Другие аккаунты не затрагиваются. Этот срок относится к UI и не является разрешённым периодом серверного доступа после отзыва авторизации.

Отсчёт от подтверждённого сервером выхода отделяет распространение выхода от ситуации, когда исходный запрос ещё не дошёл до сервера. Поведение при сетевом сбое исходного logout, потере связи на другом устройстве и возобновлении приостановленной вкладки ещё не согласовано.

### Вопрос 9 — аккаунт новой вкладки при нескольких входах

Если в браузере уже открыты аккаунты A и B, под каким аккаунтом должна автоматически войти третья вкладка, в которой пользователь вручную открыл адрес GeoService?

Ответ пользователя: «Под тем под которым пользовотель вошел».

Ответ связывает автоматический вход с выполненным пользователем входом, но при двух последовательных входах A и B ещё не определяет, какой из них используется новой вкладкой. Правило последнего входа пока не считается принятым. Механизм реализации не предлагается.

### Вопрос 10 — порядок входа A, затем B

Если пользователь сначала вошёл как A в первой вкладке, затем как B во второй, новая третья вкладка должна автоматически войти как B, а первая после перезагрузки остаться под A?

Ответ пользователя: «Нет должен быть один токен на пользователя».

Предложенная в вопросе комбинация поведения не принята. Прямое требование пользователя: один токен на пользователя. Пока не определено, означает ли это единую авторизацию вкладок одного браузера или один общий токен каждого аккаунта при сохранении нескольких аккаунтов в браузере. Также не определено, о каком виде токена и области его уникальности идёт речь; нельзя автоматически переносить формулировку на access JWT, refresh credential или все устройства.

### Вопрос 11 — сохраняется ли несколько аккаунтов в браузере

В одном браузере по-прежнему должны одновременно работать вкладки под разными аккаунтами A и B, как мы согласовали раньше, или теперь все вкладки должны использовать один аккаунт?

Ответ пользователя: «все вкладки должны использовать один аккаунт».

Принято: в одном браузере все вкладки используют один аккаунт. Это отменяет прежнее решение вопроса 2 о разных аккаунтах во вкладках и его следствия о восстановлении отдельного аккаунта вкладки. Правило последнего входа между одновременно действующими A и B не требуется. Независимость рабочих контекстов разных WorkOrder сохраняется в пределах общей авторизации.

### Вопрос 12 — одновременная работа на нескольких устройствах

Должен ли один аккаунт одновременно работать на нескольких устройствах, например на компьютере и ноутбуке, без завершения предыдущего входа при новом входе?

Ответ пользователя: «Да».

Принято: один аккаунт может одновременно работать на нескольких устройствах; новый вход не завершает предыдущий. Явный выход завершает авторизацию аккаунта на всех устройствах согласно предыдущим ответам. Это уточнение не выбирает технический формат или хранение токенов.

### Вопрос 13 — один WorkOrder в двух вкладках

Как должна вести себя вторая вкладка, если в ней открыт тот же WorkOrder, который пользователь уже редактирует в первой?

Ответ пользователя: «Онадолжна кинуть ошибку что этот WorkOrder уже открыт в другой вкладке».

Принято: вторая вкладка при попытке открыть тот же WorkOrder показывает ошибку о том, что он уже открыт в другой вкладке. Способ обеспечения этого поведения не выбран. Wiki задаёт организационное правило одного окна редактирования наряда, но не заявляет реализованную межоконную блокировку; новый ответ требует продуктового поведения, которое нельзя считать уже реализованным. Допустимость просмотра после ошибки, момент освобождения WorkOrder и восстановление после аварийного закрытия ещё не определены.

### Вопрос 14 — один WorkOrder на разных устройствах

Если этот WorkOrder уже открыт на компьютере, попытка открыть его на ноутбуке под тем же аккаунтом тоже должна завершаться такой ошибкой?

Ответ пользователя: «Нет на другом устройстве редактировать можно».

Принято: на другом устройстве разрешено редактировать тот же WorkOrder; ограничение повторного открытия не является глобальной блокировкой наряда. Это прямое продуктовое уточнение пользователя имеет приоритет над более общим организационным правилом одного окна из Wiki. Оно не отменяет действующие проверки DraftVersionToken, stale rejection и остальные серверные guards. Из разрешения редактировать на другом устройстве не следует разрешение автоматически сливать конкурентные изменения.

### Вопрос 15 — разные браузеры на одном устройстве

Если WorkOrder открыт в Chrome, можно ли одновременно редактировать его в Firefox на том же компьютере?

Ответ пользователя: «Да, в разных браузерах редактировать можно. Запрет только для вкладок одного браузера».

Принято: запрет повторного открытия WorkOrder действует только для вкладок одного браузера. Разные браузеры одного устройства не блокируют друг друга. Механизм идентификации и координации пока не выбран.

### Вопрос 16 — закрытие вкладки с WorkOrder

После обычного или аварийного закрытия вкладки с WorkOrder через какое максимальное время другая вкладка того же браузера должна получить возможность открыть его?

Ответ пользователя: «2 секунды».

Принято: после обычного или аварийного закрытия вкладки с WorkOrder другая вкладка того же браузера должна получить возможность открыть его не позднее чем через 2 секунды. Это отдельный срок от 5 секунд для глобального выхода. Реализуемость и способ проверки аварийного закрытия ещё не установлены; ответ фиксирует целевое требование, а не подтверждённую гарантию текущего браузерного механизма.

### Вопрос 17 — приостановленная вкладка

Если вкладка с WorkOrder остаётся открытой, но браузер приостановил её в фоне, должна ли она продолжать удерживать WorkOrder, запрещая его открытие в другой вкладке?

Ответ пользователя: «Да».

Принято: открытая вкладка продолжает удерживать WorkOrder, даже если браузер приостановил её в фоне. Другая вкладка того же браузера не получает право открыть этот WorkOrder только из-за отсутствия активности первой. Совместимость этого требования с освобождением за 2 секунды после аварийного закрытия необходимо проверить при исследовании механизмов браузера; она пока не доказана. Механизм обнаружения или освобождения не выбран.

### Вопрос 18 — выход при недоступном сервере

Если пользователь нажал «Выйти», когда сервер недоступен, что должно произойти в текущей вкладке до того, как приложение сможет подтвердить выход на всех устройствах?

Ответ пользователя: «Выйти локально и показать сообщение, что выход на остальных устройствах не подтверждён. После восстановления связи завершить выход везде».

Принято: при недоступном сервере выполнить локальный выход, явно сообщить об отсутствии подтверждения выхода на остальных устройствах и автоматически завершить глобальный выход после восстановления связи. Нельзя сообщать об успешном глобальном выходе только по локальной очистке. Способ сохранения и исполнения намерения не выбран.

Текущий `auth.logout` очищает локальное состояние до HTTP-запроса и подавляет его ошибку, не реализуя согласованные уведомление и последующее завершение глобального выхода. Гарантия перехода остальных устройств за 5 секунд применяется после подтверждённого сервером выхода и при ранее согласованных условиях сети/работы браузера.

### Вопрос 19 — незавершённый выход после закрытия браузера

Если после такого локального выхода пользователь закрыл браузер без сети, должно ли приложение при следующем открытии автоматически завершить прежний глобальный выход до восстановления входа?

Вместо ответа пользователь изменил область задачи: «Давай все таки не будем выходить на других устройствах. Вход привязан к конкретному устройству и браузеру».

Это прямое уточнение отменяет глобальный выход, принятый в вопросах 6–8, и глобальное отложенное действие из вопроса 18. Вопрос 19 в прежней формулировке больше не актуален. Входы других браузеров и устройств независимы; рабочие вкладки текущего браузера по-прежнему используют одну авторизацию. Детали неподтверждённого сервером выхода текущего браузера не следует молча переносить из отменённого глобального протокола.

### Вопрос 20 — локальный выход без сети в пределах браузера

Если сервер недоступен, должны ли все вкладки текущего браузера сразу выйти и оставаться на экране входа после перезагрузки, даже если сервер ещё не подтвердил выход?

Ответ пользователя: «Нет Зачем?».

Предложенная в вопросе комбинация немедленного выхода всех вкладок и сохранения экрана входа после reload без подтверждения сервера не принята. Из отрицательного ответа нельзя автоматически вывести ни успешный выход, ни согласие на отложенную операцию. Причина уточнения: текущая локальная очистка при неуспешном logout не доказывает отзыв серверного входа; последующее восстановление может снова авторизовать пользователя.

### Вопрос 21 — неуспешный запрос выхода

Если запрос выхода не дошёл до сервера, правильно ли оставить текущий вход и показать сообщение «Не удалось выйти, попробуйте ещё раз»?

Ответ пользователя: «Да».

Принято: если запрос выхода не дошёл до сервера, сохранить текущий вход и показать «Не удалось выйти, попробуйте ещё раз». Другие браузеры и устройства не затрагиваются. Это заменяет предположение о локальном выходе независимо от результата запроса. Потеря ответа после выполненного сервером выхода не доказывает, что запрос не дошёл; этот технический пограничный случай ещё требует анализа.

### Вопрос 22 — поддерживаемые браузеры

В каких браузерах и на каких устройствах это поведение должно обязательно работать?

Ответ пользователя: «Актуальные версии Chrome, Edge и Firefox на компьютерах и ноутбуках. Мобильные устройства пока не нужны».

Принято: актуальные Chrome, Edge и Firefox на компьютерах/ноутбуках; мобильные устройства не входят в текущий объём. Матрица нужна для проверки автоматического восстановления, межвкладочного ограничения WorkOrder, приостановки вкладок и освобождения за 2 секунды. Конкретные версии фиксируются при проверках; операционные системы не уточнялись. Механизм пока не выбран.

### Вопрос 23 — потеря нового токена после ротации

Если сервер уже заменил токен, но вкладка закрылась или связь оборвалась до получения нового токена, допустимо ли запросить повторный вход, или оставшиеся вкладки должны восстановить доступ без ввода пароля и в этом случае?

Ответ пользователя: «В таком случае допустимо запросить повторный вход».

Принято: повторный вход допустим, если новый токен действительно потерян после выполненной сервером ротации. Это не разрешает повторный вход при штатном одновременном восстановлении вкладок. В текущем `AuthSessionService.refresh_session` прежний токен отзывается и новый создаётся до отправки HTTP-ответа. Фактическое поведение cookie при разных моментах закрытия вкладки пока не воспроизведено; согласованное исключение относится к неполученному новому токену, а не к любому закрытию вкладки.

## Дополнительная проверка кода и браузерных ограничений

После подтверждения требований дополнительно проверена граница существующего logout: `create_access_token` выдаёт JWT без идентификатора браузерной сессии, а `get_current_user` не проверяет отзыв refresh-сессии. Следовательно, очистка UI всех вкладок и отзыв refresh token не обеспечивают немедленный серверный отказ по уже скопированному access JWT. Это существующее свойство, которое необходимо явно показать при сравнении подходов, не выдавая UI-синхронизацию за серверную инвалидизацию access token.

Для текущего объёма техническая блокировка WorkOrder отменена. Наблюдения ниже о местах её возможного подключения сохраняются только как история исследования и не задают работы по реализации.

Проверено после уточнения требований:

- `workOrders.openSelectedWorkOrder` вызывает `openEditVersion`, затем читает workspace и сохраняет маркеры открытия. `restoreOpenedWorkspace` отдельно восстанавливает workspace по маркерам `sessionStorage`. Межвкладочное ограничение должно охватывать оба пути; защита только кнопки открытия не охватит reload.
- `selectWorkOrder`, `clearSelection`, `clearOpenedWorkspace` и `reset` меняют жизненный цикл локального workspace. Область владения WorkOrder нельзя определять только существованием вкладки, не учитывая уход из наряда.
- `requestNavigation` и `prepareLogout` уже учитывают local dirty и recovery отправленных команд внутри одной вкладки. Нельзя обойти эти правила при добавлении межвкладочного выхода; последствия для соседних вкладок необходимо сопоставить с принятой политикой принудительной потери доступа.
- По INF-02 внешний deployment использует единый HTTPS origin; локальный smoke использует localhost. Это имеющийся контекст, а не новое требование инфраструктуры AR-01.

Внешние факты, проверенные по первичным источникам:

- [Chrome Page Lifecycle](https://developer.chrome.com/docs/web-platform/page-lifecycle-api) различает frozen и discarded: приостановленная страница и выгруженная страница имеют разный жизненный цикл; выгруженная страница впоследствии загружается заново. Наличие вкладки в панели не доказывает сохранение исполняющегося документа. Из этого следует необходимость уточнить продуктовое правило для discard отдельно от уже согласованного frozen.
- [W3C Web Locks, рабочий проект спецификации](https://www.w3.org/TR/web-locks/) описывает координацию в пределах общего storage bucket и освобождение при завершении соответствующего контекста. Доступ к API ограничен secure context. Документ не устанавливает универсальный срок освобождения в 2 секунды; соответствие целевому сроку ещё необходимо проверять в поддерживаемых браузерах. Это исследование доступных возможностей, не выбор решения.

Браузерные сценарии закрытия, заморозки, выгрузки и гонки restore пока не запускались. Документация не заменяет такую проверку.

### Вопрос 24 — полная выгрузка страницы браузером

Если браузер полностью выгрузил страницу из памяти, хотя её вкладка остаётся в панели, можно ли освободить WorkOrder, а при возвращении в эту вкладку заново проверять, не занят ли он другой?

Вопрос снят после отмены технической блокировки WorkOrder; выбор поведения удержания/освобождения больше не требуется.

### Уточнение после вопроса 24 — отмена технической блокировки WorkOrder

Пользователь запросил происхождение и точный смысл правила одного окна редактирования. По исходному исследованию и Wiki уточнено: это дисциплина учебной эксплуатации, а не запрет второго просмотра, владение вкладкой или реализованная блокировка.

На вопрос «Вам нужен именно технический запрет открытия второго окна или достаточно оставить организационное правило редактирования?» пользователь ответил: «Нет не нужен».

Принято: технический запрет повторного открытия WorkOrder не нужен. Отменены требования из вопросов 13–17 о межвкладочной ошибке, области блокировки, освобождении за 2 секунды и удержании при приостановке; вопрос 24 о discard потерял актуальность. Исследование браузерного lifecycle выше остаётся справочным материалом и не является обоснованием реализации блокировки. Действующие доменные правила и серверные проверки конкурентных изменений не отменяются.
