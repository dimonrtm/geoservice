## AR-01 — P2: параллельное восстановление двух вкладок завершает одну сессию в UI

Статус 2026-10-28: решена в согласованных границах; локальные gates, итоговый review и re-review исправлений пройдены без открытых замечаний. [Отчёт](2026-10-27-ar-01-browser-session-implementation-report.md):
настоящие Chrome 156/Edge 156/Playwright Firefox 157, реальные ротации и отзыв sid,
status fallback ≤5 s, независимые входы, WorkOrder stale без нового lock.
Native BFCache/OS suspend не подтверждены; fresh lifecycle fence проверен
injected pageshow с реальным status, настоящий history back — с новым document.
Повторный login при фактической потере rotated credential допустим по принятому
дизайну. Ниже сохранены описание дефекта и ссылки исходного ревью до исправления.

Категории: корректность, UX, интеграция auth.

Код: `apps/backend/utility_service/use_cases/services/auth_session_service.py:79–118`, `apps/backend/utility_service/infrastructure/postgresql/repositories/auth_session_repository.py:79–94`, `apps/frontend/src/stores/auth.ts:155–179`, `apps/frontend/src/App.vue:33–36`.

Каждая вкладка при загрузке самостоятельно вызывает refresh. Cookie общий для вкладок, access token хранится в памяти каждой вкладки. Сервер атомарно отзывает старый refresh token и выпускает новый. При двух запросах со старым cookie только один update `revoked_at IS NULL` может вернуть строку. Второй получает 401; frontend очищает локальное состояние и показывает вход, даже если другая вкладка только что успешно восстановила тот же аккаунт.

Сценарий: открыть две вкладки одновременно либо одновременно восстановить их после перезапуска браузера; оба запроса должны уйти до получения первого Set-Cookie. Это не обход защиты от повторного использования refresh token, а отсутствие координации законных клиентов вокруг этой защиты. Отдельная гонка позднего restore в одной вкладке описана в FE-01.

Доказательство: трассировка кода и прошедший существующий unit test `test_refresh_session_rejects_replay_when_rotation_loses_race` в наборе из 418 тестов. Настоящий двухвкладочный браузерный сценарий в этом ревью не запускался.

Исправление: сериализовать refresh между вкладками и повторно читать актуальную cookie через следующий запрос после завершения первого; выбрать поддерживаемый механизм координации с fallback и не отменять серверную защиту replay. Добавить тест двух независимых клиентов с одним cookie, а также закрытия вкладки во время refresh. Критерий: обе вкладки восстанавливаются без ручного повторного login, старый token остаётся непригодным для произвольного replay.

## AR-02 — P2: медленный WebSocket задерживает остальных подписчиков и HTTP-ответ записи

Категории: производительность, доступность, архитектура realtime. Условие: включён `LEGACY_GIS_API_ENABLED`; по умолчанию выключен.

Код: `apps/backend/utility_service/use_cases/services/realtime_connection_manager.py:36–49`, `apps/backend/utility_service/use_cases/services/feature_service.py:134,179,196`, `apps/backend/utility_service/use_cases/services/feature_realtime_publisher.py:15–59`.

Broadcast последовательно ожидает `send_json` каждого клиента без прикладного deadline. Если отправка первому клиенту заблокирована обратным давлением транспорта, следующие не получают событие. HTTP CRUD уже завершил транзакцию, но всё ещё ожидает публикацию перед возвратом ответа. Клиент может получить timeout при фактически выполненной записи. Перехват Exception не ограничивает время ожидания.

Доказательство: `evidence/code-review/realtime_probe.py` запускает настоящий manager с двумя имитациями сокетов. Пока первый ожидает освобождения Event, второй не получает событие и broadcast не завершается. После освобождения порядок доставки `[slow, fast]`. Запуск без сети и БД завершён успешно; это детерминированная проверка порядка await, не сетевой нагрузочный тест.

Исправление: отдельные ограниченные очереди отправки на соединение, deadline и отключение медленного клиента; не ожидать произвольную сетевую доставку на пути ответа уже закоммиченной операции. Ограничить очереди, чтобы не заменить задержку неограниченным ростом RAM. Проверка: один зависший сокет не задерживает второй и HTTP-ответ; события сохраняют порядок на каждом соединении.

## AR-03 — P3: ошибки публикации скрываются без диагностического следа

Категории: качество кода, наблюдаемость. Условие: legacy GIS.

Код: `apps/backend/utility_service/use_cases/services/feature_service.py:243–265`, `apps/backend/utility_service/use_cases/services/realtime_connection_manager.py:45–49`.

Все ошибки publisher подавляются через `except Exception: return`; ошибки отправки приводят только к удалению соединения. При неисправности realtime запись возвращает успех, но ни лог, ни метрика не объясняет отсутствие события у других клиентов. Успех записи после commit корректен; дефект — отсутствие возможности диагностировать потерю уведомления.

Исправление: структурированный warning/метрика с идентификаторами события и слоя без содержимого токенов; различать ожидаемое закрытие клиента и ошибку публикации. Проверка: failing publisher не откатывает запись, но создаёт диагностическое событие.

## Подтверждённые проблемы качества кода

Это наблюдаемые проблемы структуры и сопровождаемости, а не заявления о новых runtime-сбоях. Приоритет P3 означает устранение при развитии затронутых модулей. AR-03 выше также относится к качеству кода и учитывается один раз.

### CQ-01 — P3: доменный слой зависит от инфраструктуры и use cases

**Код:** `apps/backend/utility_service/domain_services/feature_registry.py:8–18`, `apps/backend/utility_service/domain_services/bbox.py:3`.

Registry импортирует конкретные PostgreSQL ORM-модели, а bbox использует исключение из use_cases. Доменный модуль тем самым знает детали внешних слоёв. Это затрудняет изолированное использование доменных функций и делает границу `domain_services` непоследовательной: чистая геометрическая логика и адаптация ORM оказываются под одним названием.

**Рекомендация:** перенести mapping storage table → ORM model в persistence; разместить независимые доменные ошибки рядом с доменной логикой, а преобразование в API errors оставить адаптеру. Проверка: production-модули domain_services не импортируют infrastructure/use_cases; существующие проверки bbox и разрешения типов сохраняют поведение. Это не требование менять формат API или геометрические инварианты.

### CQ-02 — P3: workOrders store совмещает слишком много ответственностей

**Код:** `apps/frontend/src/stores/workOrders.ts:17–31` (зависимости auth/recovery/navigation), `:541–641` (навигация и logout), `:746–877` (recovery host и lifecycle), `:1062–1133` (reset и загрузка списка), `:1448–1484` (отправка команды и проверки сессии).

Store из 1484 строк одновременно координирует загрузку, рабочую версию, локальное редактирование, восстановление, переходы и авторизацию. Изменение одного сценария требует учитывать поколения запросов, sessionEpoch, actor и callbacks других сценариев. Проблема — пересечение ответственностей и неявные связи, а не число строк само по себе. FE-01 отдельно показывает дефект auth continuation; причинная связь именно с размером workOrders не доказана.

**Рекомендация:** выделить координатор переходов и адаптер recovery-host с явными входами/результатами, оставить state рабочей версии в одном месте. Не дублировать pending command между stores. Проверка: сценарии Save → переход, logout при pending Save, поздний readback и смена actor сохраняют текущие гарантии; каждому выделенному модулю не требуется полный store для проверки его правил.

### CQ-03 — P3: use case привязан к деталям PostgreSQL и SQLAlchemy

**Код:** `apps/backend/utility_service/use_cases/services/edit_version_service.py:7–50,69`.

Сервис импортирует конкретные repositories, AsyncSession, ORM User/WorkOrder, persistence rows и geometry codec. Транзакционные сценарии и их данные описаны через адаптер хранения, поэтому изолированные тесты должны подражать деталям этого адаптера. Изменение представления геометрии или persistence rows затрагивает use case. В отличие от CQ-01, здесь проблема не в импортах доменного слоя, а в отсутствии явного контракта между application orchestration и persistence.

**Рекомендация:** при следующем развитии Save выделить минимальные контракты repository/transaction и независимые DTO для реально используемых операций; преобразование EWKB оставить persistence adapter. Сохранить одну транзакцию и действующие lock/replay semantics. Не вводить интерфейс на каждый класс ради формального соблюдения схемы. Проверка: Save/replay/rejection тестируются через контракт, а PostGIS adapter отдельно подтверждает атомарность и конкурентность.

## Архитектурные риски — не отдельные доказанные runtime-дефекты

1. **Realtime manager локален процессу.** `use_cases/deps.py:77–79,161–162` использует `app.state.websocket_connection_manager`. Несколько workers/реплик не разделяют подписчиков; без брокера событие дойдёт только до сокетов процесса записи. В текущем single-worker deployment это ограничение, а не проявленный дефект. Перед горизонтальным масштабированием нужна межпроцессная доставка и проверка двух workers.
2. **Нет гарантии доставки между commit и publish.** Текущий legacy publisher работает после commit без durable outbox. При падении процесса событие теряется. Для нынешнего режима допустимость требует явного контракта best-effort и readback/reconnect; для будущего authoritative workflow нельзя автоматически считать этот канал надёжным журналом.

Полноценное keyboard-редактирование геометрии не включено в дефекты: пользователь явно ограничил D11-Q03 кнопками и диалогами. Аналогично отсутствие будущих review/post, multi-feature editing и новых доменных сценариев не объявляется нарушением принятого Sprint 2.
