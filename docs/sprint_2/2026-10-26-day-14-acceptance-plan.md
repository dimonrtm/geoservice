# День 14: план исполнения приёмки Sprint 2

> Для агента-исполнителя: применять `superpowers:executing-plans` при последовательном исполнении в текущем чате. Шаги отмечаются выполненными только по фактическим результатам. Коммиты не выполняются.

**Цель:** проверить Sprint 2 по AC/DoD/M5 и создать честный acceptance report.

**Архитектура:** существующие suites и API smoke используются без нового runner. M4 и отдельный ручной UI-demo выполняются последовательно в disposable окружениях. Историческое evidence сохраняется отдельно от новых результатов.

**Стек:** Docker Compose, Python/pytest, PostgreSQL/PostGIS, Vue/TypeScript/Vitest, Playwright M4, управление браузером через пользовательский интерфейс.

**Спецификация:** [принятая спецификация](2026-10-26-day-14-acceptance-design.md); [анализ и ответы](2026-10-26-day-14-acceptance-analysis.md).

**Исполнение:** задачи 1–3 выполнены; задачу 4 закрывает последующее ручное подтверждение пользователя после остановки Computer Use; задача 5 отражена в [acceptance report](2026-08-16-sprint-2-acceptance-report.md). Чек-листы ниже сохраняют исходные шаги плана, а не выдают невыполненный агентом UI-проход за выполненный; фактические результаты — в [журнале](2026-10-26-day-14-execution-ledger.md).

## Общие ограничения

- Все обязательные проверки выполняются локально; remote Actions не требуется.
- Fresh означает изначально пустую изолированную БД. Пользовательский volume не удаляется.
- Исправляются только дефекты основного сценария. M4-дефекты обязательного recovery/доступности при работающем основном пути фиксируются как blockers без исправления.
- Zoom 200% явно непроверен, но не блокирует M5.
- Никаких git add/commit/push. Русские документы, UTF-8/LF. Не менять `.obsidian/graph.json`.
- В evidence не сохранять credentials, токены и environment dumps. При sandbox-ошибках применять штатную эскалацию, не обходить ограничения.

## Особые риски проверки

1. Старый image выдаётся за текущий код — задача 1 фиксирует HEAD/dirty state и собирает новый image.
2. DB tests пропущены — задача 1 отдельно подтверждает настоящий DB suite и migration cycle.
3. Restart сбросил БД — задача 2 проверяет manifest и сохранность revision/registry/history.
4. M4 перезаписал исторические артефакты — задача 3 сохраняет исходные bytes и архивирует новый вывод отдельно.
5. Успех API или M4 подменяет ручной demo — задача 4 сохраняет самостоятельное UI evidence без программных mutations.

- [ ] Из корня собрать свежий image: `docker build --target dev -t geoservice-day14-check apps/backend`. Требуется exit 0.

- [ ] Выполнить `infra\db-tests.cmd`. Проверить exit 0, фактический запуск DB integration и migration cycle, успешный cleanup. DB-only skips обычного pytest не засчитывать вместо этого результата.
- [ ] Из `apps/frontend` выполнить `npm.cmd test -- --maxWorkers=2`, `npm.cmd run typecheck`, `npm.cmd run lint`, `npm.cmd run format:check`, `npm.cmd run build`. Зафиксировать каждый результат отдельно; warnings отличать от failures.

## Задача 5. Разбор дефектов и итоговый отчёт

**Вход:** результаты задач 1–4. **Выход:** acceptance report и решение по M5/ingest.

- [ ] Для каждого failure разделить ошибку приложения, проверки и окружения. До исправления основного сценария применить systematic-debugging, установить причину и добавить содержательный regression test; затем минимальное исправление и targeted verification. Не исправлять исключённые пользователем M4-дефекты.
- [ ] Если код изменён, выполнить финальный полный regression и актуализировать затронутый live/UI evidence. Не смешивать успешные результаты разных несовместимых состояний кода. Если код не менялся и проверки достаточны, не повторять их без причины.
- [ ] Создать `2026-08-16-sprint-2-acceptance-report.md`: фактические даты/HEAD/dirty state, AC-01–AC-10 и DoD, команды и ссылки evidence, M5, blockers, ограничения, cleanup. Для каждого обязательного критерия поставить подтверждённый результат либо непроверенное/неуспешное состояние с причиной.
- [ ] Вердикт «принят» разрешён только при выполнении обязательной матрицы. Remote CI и zoom 200% указать как согласованные неблокирующие ограничения. При M4-blocker итог «не принят», даже если основной сценарий прошёл.
- [ ] Оценить необходимость `/ingest repository-change`: только новая устойчивая техническая информация, не результаты приёмки. При наличии прочитать ingest skill и выполнить узкий documentation-only ingest; иначе записать обоснованное «не требуется». Не дублировать планы в agent memory.
- [ ] Обновить `docs/sprint_2/README.md`, проверить `git diff --check`, UTF-8/LF всех новых/изменённых текстовых артефактов, включая untracked. Сверить итоговый status с исходным; оставить изменения unstaged.

## Самопроверка плана

Все разделы спецификации покрыты задачами 1–5. Пять рисков имеют отдельные проверки. Новые product interfaces не вводятся. M4 и UI выполняются последовательно из-за общих портов; API smoke сохраняет штатный startup chain. Чистая БД, restart, baseline proof, неизменность исторического evidence и правила отказа в приёмке отражены явно. Это план, не журнал выполненных проверок.
