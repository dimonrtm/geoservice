# Чеклист реальной проверки с Editor/Reviewer

Дата: 2026-06-23
Статус: черновой чеклист проверки
Расположение: `docs/release_2/geometry_association_conflict`

## Назначение

Чеклист проверяет человеческий слой Release 2 после developer demo.
Синтетическая фикстура может доказать машину состояний (`state machine`) и блокеры, но не доказывает,
что реальные `Editor`/`Reviewer` понимают пакет последствий (`consequence package`),
доверяют формулировкам риска и принимают правильное go/no-go решение быстрее
штатного базового варианта (`baseline`).

## Участники

- 1-2 `Editor`, которые работают с authoritative-изменениями сети.
- 1-2 `Reviewer` или эквивалентная роль.
- Опционально: Data Owner / администратор utility network для полномочий (`authority`) уровня `Critical`.

## Материалы

- Контракт реализации v0.1.
- Канонический сценарий трансформатора/service-device.
- Пример пакета доказательств.
- Пример запуска решения.
- Прохождение штатного базового варианта (`baseline`): `ArcGIS native Conflicts view + SOP + expert handoff`.

## Обязательные вопросы

1. Понимает ли участник за 1-2 минуты, какое сетевое последствие стоит за geometry/association conflict?
2. Видит ли участник разницу между `approve package` и `can post`?
3. Доверяет ли участник вердикту жесткого блокера, если видит dirty trace path, invalid subnetwork или unresolved association delta?
4. Какие доказательства обязательны для `Normal`, `High` и `Critical`?
5. Где проходит граница между `self-resolve`, `send to Reviewer`, `escalate` и `blocked_post`?
6. Кто должен принимать финальное решение для `Critical`?
7. Достаточен ли `delta since previous approval` для повторной проверки (`repeat review`) после stale?
8. Какие формулировки уровня риска (`risk tier`) создают ложную уверенность?
9. Нужен ли sign-off от специалиста при влиянии на service/subnetwork/safety?
10. Какие внешние проверки участник все равно открыл бы после просмотра пакета?

## Желательные вопросы

11. Достаточна ли примерная политика проверки (`sample review policy`) для `Normal`, если жесткие блокеры отсутствуют?
12. Какие поля объекта аудита Reviewer ожидает видеть через неделю после решения (`decision`)?
13. Какая формулировка лучше: `blocked post`, `not ready for post`, `stale approval` или другая?
14. Какие поля кажутся шумом и должны уйти в детали/логи (`details/logs`)?
15. Сравнивает ли участник пакет быстрее штатного базового варианта (`baseline`), или все равно уходит в экспертную передачу (`expert handoff`)?

## Чеклист наблюдений

- Участник правильно называет затронутую association.
- Участник правильно объясняет свежесть trace/subnetwork.
- Участник не трактует `approved` как автоматический `can post`.
- Участник замечает stale event.
- Участник выбирает корректный следующий шаг.
- Участник не пропускает blocker с absolute veto.
- Участник может повторить обоснование (`rationale`) по сводке (`summary`) аудита.

## Критерии прохождения/провала

Критерии прохождения (`Pass`) для mini-round пользовательской проверки:

- оба типа ролей понимают пакет последствий без внешней подсказки;
- ни один участник не выбирает ложно-безопасное действие (`false-safe action`) на hard-block case;
- `Reviewer` различает approval и can-post;
- sidecar-компонент stale приводит к повторной проверке (`repeat review`), а не к слепому post (`blind post`);
- участники называют недостающие evidence (`missing evidence`), если пакет неполный.

Провал (`Fail`) или смена курса:

- формулировка риска воспринимается как зеленое утверждение safe-post (`safe-post claim`);
- Reviewer сразу открывает внешнюю GIS (`external GIS`) для каждого case;
- блокеры (`blockers`) кажутся непрозрачными (`opaque`) и не вызывают доверия;
- `Normal / High / Critical` не совпадают с практикой владения решениями (`decision ownership`);
- объект аудита (`audit object`) не помогает повторной проверке (`repeat review`).

## Выходные материалы

После проверки сохранить RAW notes в `RAW_inputs/meetings/` и выполнить
`/ingest`. Не менять контракт реализации молча: изменения контракта должны
ссылаться на источник проверки.
