# Utility GIS editor: рискованные допущения и порядок проверки

## Контекст

Для варианта использования `Utility GIS editor` самые опасные допущения — не технические детали вроде “карта откроется быстро”, а продуктово-доменные предположения.

Этот сценарий относится к high-risk authoritative editing:

```text
work order
→ named/edit version
→ edit
→ validation / topology check
→ reconcile with Default
→ conflict resolution
→ post to Default
→ authoritative state
```

Пользователь работает с инженерной сетью: линиями, устройствами, узлами, ассоциациями и связанными nonspatial objects.

Ошибка в этом сценарии может привести не просто к плохой карте, а к:

- неверному сетевому состоянию;
- ошибочным trace-результатам;
- потере правок;
- silent overwrite;
- повторному выезду бригады;
- ручной сверке;
- задержке публикации;
- снижению доверия к authoritative network layer.

---

# 1. Самое рискованное допущение

## Пользователю реально нужен branch-like workflow, а не простой live-edit

### Допущение

> `Utility GIS editor` действительно готов работать через `work order → edit version → validation → reconcile → post`, потому что для него безопасность изменений важнее мгновенной публикации.

---

### Почему это самое рискованное допущение

Если окажется, что реальные пользователи хотят просто быстро править общий live-слой, то весь workflow с рабочими версиями, reconcile и post будет восприниматься как лишняя бюрократия.

В этом случае продукт может быть архитектурно правильным, но неудобным и невостребованным.

---

### Что именно проверять

Нужно дать пользователю пройти или хотя бы разобрать сценарий:

```text
Получить work order
→ открыть рабочую версию
→ изменить линию/устройство
→ сохранить edit
→ пройти validation
→ сделать reconcile
→ сделать post
```

---

### Критерий прохождения

Пользователь должен подтвердить не просто “понятно”, а именно соответствие реальной работе:

```text
Да, такой workflow похож на мой реальный рабочий процесс.
Да, отдельная рабочая версия нужна.
Да, post в authoritative state не должен происходить сразу после каждого save.
Да, я понимаю, где моя работа завершена.
```

---

### Почему проверять первым

Если этот workflow не совпадает с реальной работой, остальные проверки теряют смысл.

Нет смысла глубоко проверять validation и conflict resolution, если пользователю вообще не подходит модель работы через edit version и post.

---

# 2. Второе рискованное допущение

## Система сможет защитить сеть от некорректного состояния через validation

### Допущение

> GeoService сможет проверять не только геометрию, но и смысловую корректность инженерной сети: связность, ассоциации, topology rules, dirty areas и пригодность сети для trace.

---

### Почему это рискованно

Для `Utility GIS editor` недостаточно просто сохранить geometry и attributes.

Система должна защищать инженерную сеть от состояния, при котором данные формально записаны, но сеть уже нельзя безопасно использовать для эксплуатации.

Например:

- линия есть на карте, но не подключена к узлу;
- устройство стоит на карте, но не связано с сетью;
- association создана неправильно;
- trace проходит неверно;
- dirty areas остались непроверенными;
- topology формально нарушена.

---

### Что именно проверять

На маленьком synthetic utility dataset нужно подготовить 5–7 намеренно проблемных edits:

```text
1. Линия добавлена, но не подключена к узлу.
2. Устройство стоит на карте, но не связано с линией.
3. Ассоциация создана с недопустимым типом объекта.
4. Удален объект, от которого зависит другой объект.
5. Изменен атрибут, влияющий на trace.
6. Создана dirty area после перемещения узла.
7. После исправления validation проходит успешно.
```

---

### Критерий прохождения

```text
Система находит критические ошибки до post.
Пользователь понимает, что именно сломано.
Пользователь может исправить ошибку без ручного анализа в БД.
После исправления validation проходит.
Trace/связность не ломаются после post.
```

---

### Почему проверять вторым

Даже если branch-like workflow нужен, продукт провалится, если validation не защищает authoritative network layer.

Иначе получится опасная ситуация:

```text
edit сохранен
→ post прошел
→ сеть стала официальной
→ trace и эксплуатационные решения стали неверными
```

---

# 3. Третье рискованное допущение

## Пользователи смогут безопасно разрешать конфликты без silent overwrite

### Допущение

> Когда несколько редакторов меняют один feeder, участок трубы, кабельную линию или устройство, GeoService сможет понятно обнаружить конфликт, показать diff и не допустить тихой перезаписи.

---

### Почему это рискованно

В versioned workflow конфликт обычно проявляется на этапе `reconcile` или `post`.

Опасные ситуации:

- две бригады работают на одном участке сети;
- диспетчер меняет статус оборудования, которое уже редактирует GIS editor;
- другая рабочая версия успевает сделать post в Default раньше;
- один пользователь меняет геометрию, другой — атрибуты;
- один пользователь обновляет объект, другой его удаляет.

Главный риск — не сам факт конфликта, а то, что пользователь не поймет, что произошло, и случайно опубликует неверное состояние.

---

### Что именно проверять

Нужно смоделировать три конфликта двумя пользователями.

#### Конфликт 1. Attribute vs attribute

```text
Пользователь A меняет status устройства.
Пользователь B меняет тот же status в Default.
Пользователь A запускает reconcile.
```

Ожидаемый результат:

```text
Система показывает attribute conflict.
Пользователь видит свою версию и Default.
Пользователь может выбрать правильное значение.
```

---

#### Конфликт 2. Geometry vs geometry

```text
Пользователь A двигает узел.
Пользователь B двигает тот же узел иначе.
Пользователь A запускает reconcile.
```

Ожидаемый результат:

```text
Система показывает geometry conflict.
Пользователь видит обе версии геометрии.
Пользователь понимает, какая геометрия должна остаться.
```

---

#### Конфликт 3. Edit after reconcile

```text
Пользователь A сделал reconcile.
Пользователь B успел сделать post в Default.
Пользователь A пытается сделать post.
```

Ожидаемый результат:

```text
Post не проходит silently.
Система сообщает, что Default изменился после последнего reconcile.
Система требует повторный reconcile.
Изменения пользователя A не теряются.
```

---

### Критерий прохождения

```text
Reconcile находит конфликт.
Conflict view показывает свою версию и Default.
Пользователь понимает тип конфликта.
Пользователь может выбрать правильное решение.
Post не допускает silent overwrite.
Если Default изменился после reconcile, система требует повторный reconcile.
```

---

### Почему проверять третьим

Conflict resolution важен, но его имеет смысл проверять после двух вещей:

1. подтверждено, что пользователю вообще нужен branch-like workflow;
2. подтверждено, что validation защищает сеть от некорректного состояния.

После этого можно проверять безопасность совместной работы.

---

# Итоговый порядок проверки

```text
1. Проверить, что branch-like workflow реально нужен пользователю.
   Риск: строим слишком тяжелый процесс, который не совпадает с реальной работой.

2. Проверить, что validation защищает инженерную сеть от некорректного состояния.
   Риск: edits сохраняются, но сеть становится непригодной для trace и эксплуатации.

3. Проверить, что conflict resolution предотвращает silent overwrite.
   Риск: параллельные правки теряются или приводят к неверному authoritative state.
```

---

# Короткая формулировка

> Сначала проверяем нужность workflow, потом безопасность сети, потом безопасность совместной работы.

Именно в таком порядке, потому что каждый следующий риск имеет смысл только если предыдущий уже подтвержден.

---

# Практическая проверка на synthetic dataset

Минимальный проверочный набор должен включать:

```text
1. Один work order.
2. Одну edit version.
3. Один Default state.
4. 5–10 network features.
5. 2–3 устройства.
6. 2–3 линии.
7. 1–2 junctions.
8. 2–3 associations.
9. Один заранее подготовленный dirty area case.
10. Три заранее подготовленных conflict cases.
```

Такой набор позволит проверить не “все типа работает”, а конкретные рискованные места:

```text
workflow acceptance
validation safety
conflict safety
post safety
authoritative state correctness
```
