# Utility GIS editor: словарь доменной области и описание домена

## 1. Доменная область простыми словами

`Utility GIS editor` — это пользователь, который редактирует **инженерную сеть**: электросеть, водопровод, теплосеть, газовую или телеком-сеть.

Он не просто двигает точки и линии на карте. Его задача — поддерживать карту сети в таком состоянии, чтобы по ней можно было доверенно выполнять эксплуатационные действия:

- трассировку;
-- анализ связности;
- поиск отключаемых участков;
- проверку оборудования;
- публикацию актуального состояния сети;
- передачу данных в downstream-системы.

Проще говоря:

> Пользователь получает наряд на изменение сети, открывает отдельную рабочую версию данных, вносит изменения, проверяет, что сеть не сломалась, сверяет свои изменения с тем, что уже успели сделать другие, разрешает конфликты и только после этого публикует результат в основное состояние сети.

Главная особенность домена: **ошибка здесь опаснее обычной ошибки на карте**.

Если неправильно сохранить дорогу или POI — это неприятно. Если неправильно сохранить инженерную сеть — можно получить:

- неверную трассировку;
- неправильное отключение;
- потерю связи между объектами;
- повторный выезд бригады;
- ручную сверку данных;
- задержку публикации;
- недоверие к authoritative layer.

В одну фразу:

> Домен `Utility GIS editing` — это не CRUD по геометрии, а управляемое изменение инженерной сети через рабочие версии, проверки топологии, обнаружение конфликтов и безопасную публикацию в официальное состояние данных.

## 2. Роли

| Термин | Понятное определение | Пример |
|---|---|---|
| **Utility GIS editor** | Основной пользователь, который редактирует инженерную сеть в ГИС. | Инженер электросетевого участка меняет кабельную линию, трансформатор, выключатель и связи между ними. |
| **Диспетчер** | Пользователь, который работает с оперативным состоянием сети и может передавать редактору задачу или уточнение. | Сообщает, что оборудование заменено или участок сети временно отключен. |
| **Planner / инженер-планировщик** | Специалист, который готовит плановые изменения сети. | Планирует реконструкцию участка кабельной линии. |
| **Reviewer / контролер качества** | Проверяет изменения перед публикацией в основное состояние сети. | Смотрит, не нарушена ли топология и корректно ли разрешены конфликты. |
| **Version administrator** | Управляет версиями, доступами, зависшими рабочими версиями и публикацией. | Закрывает старую edit version после успешного post. |
| **Mobile crew / полевая бригада** | Люди, которые физически выполняют работы на сети и дают фактическую информацию. | Сообщают, что установлен новый шкаф или заменен участок трубы. |
| **Downstream consumer** | Потребитель опубликованных данных сети. | Дашборд, модуль трассировки, отчетность, аварийная система, внешняя интеграция. |

## 3. Основные объекты сети

| Термин | Понятное определение | Пример |
|---|---|---|
| **Utility network / инженерная сеть** | Модель реальной инфраструктуры: линии, устройства, узлы, связи и правила их соединения. | Электросеть района, водопроводный контур, теплосеть квартала. |
| **Network feature** | Пространственный объект сети. Обычно это линия, точка или полигон. | Кабельная линия, труба, задвижка, трансформатор, муфта. |
| **Line / линия сети** | Линейный объект, который соединяет части сети. | Кабель, труба, воздушная линия, оптоволоконный участок. |
| **Device / устройство** | Точечный объект, который выполняет функцию в сети. | Выключатель, клапан, насос, трансформатор, распределительный шкаф. |
| **Junction / узел** | Место соединения элементов сети. | Точка соединения кабелей, узел трубопровода, технологический стык. |
| **Assembly / сборочный объект** | Сложный объект, внутри которого могут быть другие элементы. | Подстанция, шкаф, камера, колодец. |
| **Association / ассоциация** | Непространственная связь между объектами сети. | Устройство находится внутри шкафа; кабель подключен к порту; труба связана с арматурой. |
| **Nonspatial object** | Объект без собственной геометрии, но важный для сети. | Порт, клемма, контакт, внутренняя часть оборудования. |
| **Asset / актив** | Физический объект инфраструктуры, который учитывается как имущество или эксплуатационная единица. | Насос, кабель, опора, счетчик. |
| **Feature attribute / атрибут объекта** | Описание объекта в таблице. | Статус, материал, диаметр, напряжение, дата установки, владелец. |

## 4. Рабочая задача и область редактирования

| Термин | Понятное определение | Пример |
|---|---|---|
| **Work order / наряд** | Конкретная задача на изменение сети. | “Заменить трансформатор ТП-42 и обновить подключенные линии”. |
| **Job / рабочая задача** | Более общий термин для пакета работ, который может включать несколько edits. | Реконструкция участка сети по проекту. |
| **AOI / Area of Interest** | Рабочая область на карте, где пользователь выполняет изменения. | Один feeder, квартал, участок трубы, район подстанции. |
| **Feeder / фидер** | Логический или физический участок сети, питающий потребителей. Чаще термин из электросетей. | Фидер 10 кВ от подстанции до группы ТП. |
| **Edit session / сессия редактирования** | Период, когда пользователь вносит изменения в свою рабочую версию. | Открыл work order, поменял объекты, сохранил, запустил validation. |
| **Edit / правка** | Одно изменение данных. | Изменить статус задвижки, передвинуть узел, добавить кабель, удалить старое оборудование. |
| **Change set / набор изменений** | Группа edits, которые относятся к одной задаче. | Все изменения по одному work order. |

## 5. Версии и публикация

| Термин | Понятное определение | Пример |
|---|---|---|
| **Default version / Default** | Основная версия данных, которая считается текущим официальным состоянием. | То, что видят диспетчеры, аналитики и downstream-системы. |
| **Authoritative state** | Доверенное опубликованное состояние сети. | Состояние после успешного post, validation и проверки конфликтов. |
| **Edit version / рабочая версия** | Изолированная версия, где пользователь вносит изменения до публикации. | Версия `workorder-12345-alexey`. |
| **Named version** | Именованная версия, созданная под конкретного пользователя, задачу или наряд. | `repair-feeder-17-2026-06-06`. |
| **Branch versioning** | Подход, где пользователи редактируют данные в отдельных ветках, а потом согласуют изменения с Default. | Редактор работает в своей версии, затем делает reconcile и post. |
| **Long transaction / длинная транзакция** | Изменение, которое может длиться долго: часы, дни или недели. | Реконструкция сети, которую нельзя сразу публиковать в Default. |
| **Reconcile** | Сверка рабочей версии с Default. Система проверяет, не изменились ли те же объекты у других пользователей. | Пользователь изменил выключатель, а диспетчер уже поменял его статус в Default. |
| **Post** | Публикация изменений из рабочей версии в Default. | После validation и reconcile изменения становятся официальными. |
| **Stale version / устаревшая версия** | Рабочая версия, которая уже не соответствует текущему Default. | Пользователь сделал reconcile, но до post кто-то другой изменил Default. |
| **Close version / закрыть версию** | Завершить рабочую версию после публикации или отмены. | После успешного post версия больше не нужна. |

## 6. Validation и качество сети

| Термин | Понятное определение | Пример |
|---|---|---|
| **Validation / валидация** | Проверка, что изменения не нарушили правила сети. | Проверить, что кабель подключен к допустимому оборудованию. |
| **Topology / топология** | Правила связности и пространственных отношений сети. | Линия должна быть соединена с узлом; труба не должна “висеть в воздухе”. |
| **Validate topology** | Проверка топологии после правок. | После добавления линии система проверяет, корректно ли она соединена с сетью. |
| **Dirty area** | Область, где были изменения и где топология требует проверки. | Пользователь передвинул устройство — вокруг него появилась dirty area. |
| **Network rule / правило сети** | Ограничение, которое говорит, какие объекты можно соединять. | Кабель 10 кВ нельзя напрямую подключить к оборудованию другого класса напряжения. |
| **Connectivity / связность** | Способность сети быть логически соединенной. | От подстанции можно пройти трассировкой до потребителя. |
| **Trace / трассировка** | Анализ прохождения по сети. | Найти всех потребителей, которых отключит авария на линии. |
| **Invalid network state / некорректное состояние сети** | Состояние, при котором сеть формально сохранена, но использовать ее для анализа опасно. | Линия есть на карте, но не подключена логически. |

## 7. Конфликты

| Термин | Понятное определение | Пример |
|---|---|---|
| **Conflict / конфликт** | Ситуация, когда рабочая версия и Default изменили один и тот же объект или связанные данные. | Один пользователь изменил геометрию трубы, другой — удалил эту трубу. |
| **Conflict detection by object** | Конфликт считается по объекту целиком. Если один объект изменили два пользователя — это конфликт. | Пользователь А изменил статус задвижки, пользователь Б изменил ее диаметр. |
| **Conflict detection by attribute** | Конфликт считается по конкретным полям. Разные поля могут не конфликтовать. | Один изменил `status`, другой `comment` — это может быть не конфликт. |
| **Attribute conflict** | Конфликт по атрибуту. | Один поставил статус “active”, другой — “retired”. |
| **Geometry conflict** | Конфликт по геометрии. | Два пользователя по-разному передвинули один и тот же узел. |
| **Update/delete conflict** | Один пользователь изменил объект, а другой удалил его. | Один обновил кабель, другой удалил его как демонтированный. |
| **Conflict view** | Экран, где пользователь видит различия между своей версией и Default. | Слева “моя версия”, справа “Default”, ниже варианты решения. |
| **Resolve conflict / разрешить конфликт** | Выбрать правильный вариант изменения. | Принять свою версию, принять Default или вручную исправить данные. |
| **Silent overwrite / тихая перезапись** | Опасная ситуация, когда изменение одного пользователя незаметно затирает изменение другого. | Статус оборудования изменился без предупреждения о конфликте. |

## 8. Audit, история и доверие

| Термин | Понятное определение | Пример |
|---|---|---|
| **Audit trail / журнал изменений** | История того, кто, когда и что изменил. | Алексей изменил статус выключателя 06.06.2026 в 10:42. |
| **Editor tracking** | Автоматическая фиксация автора и времени изменения. | Поля `created_by`, `created_at`, `updated_by`, `updated_at`. |
| **Lineage / происхождение изменения** | Связь изменения с причиной, задачей или предыдущим состоянием. | Изменение появилось из work order №12345. |
| **Review history / история проверки** | Информация о том, кто проверял изменения и какое решение принял. | Reviewer отклонил post из-за ошибки топологии. |
| **Authoritative layer / официальный слой** | Слой, которому доверяют downstream-системы и пользователи. | Опубликованный слой инженерной сети. |
| **Data steward / ответственный за данные** | Человек или роль, отвечающая за качество и правила ведения данных. | Специалист, который утверждает модель данных сети. |

## 9. Состояния рабочего процесса

| Состояние | Что означает |
|---|---|
| **Draft / черновик** | Пользователь начал задачу, но изменения еще не готовы. |
| **Editing / редактируется** | Пользователь активно меняет объекты сети. |
| **Saved / сохранено в рабочей версии** | Изменения записаны, но еще не опубликованы в Default. |
| **Validation required / нужна валидация** | Есть изменения, которые требуют проверки топологии или правил сети. |
| **Validated / проверено** | Validation прошла успешно. |
| **Validation failed / валидация не прошла** | Найдены ошибки сети, dirty areas или нарушения правил. |
| **Reconcile required / нужен reconcile** | Рабочую версию надо сверить с Default. |
| **Conflicts found / найдены конфликты** | Reconcile обнаружил конкурирующие изменения. |
| **Conflicts resolved / конфликты разрешены** | Пользователь или reviewer выбрал корректные варианты. |
| **Ready to post / готово к публикации** | Validation успешна, reconcile успешен, конфликтов нет. |
| **Posted / опубликовано** | Изменения попали в Default / authoritative state. |
| **Rejected / отклонено** | Reviewer или система не разрешили публикацию. |
| **Closed / закрыто** | Рабочая версия завершена. |

## 11. Доменное описание workflow

Типовой workflow:

1. `Utility GIS editor` получает `Work order`.
2. Система создает или открывает `Edit version`.
3. Пользователь переходит к нужному `AOI`.
4. Пользователь редактирует `Network features`: линии, устройства, узлы, атрибуты и ассоциации.
5. После edits появляются `Dirty areas`.
6. Пользователь запускает `Validation`.
7. Если validation нашла ошибки, пользователь исправляет сеть.
8. Если validation успешна, пользователь запускает `Reconcile`.
9. Если есть `Conflicts`, пользователь открывает `Conflict view` и разрешает их.
10. После успешного reconcile и validation изменения переходят в состояние `Ready to post`.
11. Пользователь или reviewer выполняет `Post`.
12. Изменения попадают в `Default version`, то есть в `Authoritative state`.
13. Рабочая версия закрывается.

## 12. Что НЕ надо называть этим доменом

| Неудачный термин | Почему плохо | Лучше |
|---|---|---|
| **Просто редактирование карты** | Занижает сложность. Здесь важны версии, топология и публикация. | Редактирование инженерной сети |
| **CRUD объектов** | Не отражает reconcile, validation, topology, conflict resolution. | Versioned network editing |
| **Сохранить слой** | Непонятно, сохранено куда: в рабочую версию или в Default. | Save edit / Post to Default |
| **Опубликовать правку** | Может смешивать save и post. | Save в edit version, затем post в Default |
| **Конфликт карты** | Слишком размыто. | Attribute conflict, geometry conflict, update/delete conflict |
| **Ошибка сети** | Может означать интернет, backend или топологию. | Network topology error / connectivity error / validation error |

## 14. Центральная доменная формулировка для GeoService

> `Utility GIS editor` работает не с “картинкой на карте”, а с официальной моделью инженерной сети. Поэтому система должна позволять безопасно изменять сеть в отдельной рабочей версии, проверять топологию, находить конфликты с изменениями других пользователей, показывать понятный diff и публиковать только проверенное состояние в authoritative layer.
