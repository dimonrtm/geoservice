# Utility GIS editor: что считается проблемой после post

## Контекст

Для варианта использования `Utility GIS editor` **проблема после post** — это любая ситуация, когда изменения уже попали в `Default` / `authoritative state`, но потом выяснилось, что опубликованное состояние инженерной сети нельзя считать корректным, безопасным или доверенным.

Это не ошибка во время редактирования. Это хуже: система уже сказала, что `post` прошел, а затем оказалось, что в официальном состоянии сети есть проблема.

Успешный результат для `Utility GIS editor`:

```text
version reconciled
conflicts resolved
post to Default completed
topology validated
dirty areas closed
edit version can be closed
authoritative state is safe to use
```

Проблема после post — это нарушение любого из этих ожиданий уже после публикации.

---

# 1. Потеря или искажение правок

Это ситуация, когда пользователь внес изменения, `post` прошел, но потом оказалось, что часть изменений потерялась, была перезаписана или попала в `Default` неполностью.

## Примеры

```text
после post исчез измененный атрибут;
геометрия вернулась к старому состоянию;
association не попала в Default;
один объект обновился, а связанный объект нет;
часть change set опубликована неполностью;
изменение другого пользователя silently overwritten;
пользователь думал, что публикует один набор изменений, а в Default попал другой.
```

## Почему это критично

В utility-сценарии потеря или искажение правки может привести не только к плохому отображению на карте, но и к неверному состоянию сети.

---

# 2. Некорректная topology / dirty areas после post

Это ситуация, когда `post` прошел, но сеть осталась топологически некорректной.

## Примеры

```text
dirty area осталась незакрытой;
линия не подключена к junction;
устройство визуально есть на карте, но логически не связано с сетью;
association нарушена;
validation считалась успешной, но после post снова появились topology errors;
сеть требует дополнительной топологической проверки;
объект опубликован, но его связи с сетью неполные.
```

## Почему это критично

Для `Utility GIS editor` важно не просто сохранить геометрию и атрибуты. Важно сохранить сеть как связную и пригодную для эксплуатации модель.

---

# 3. Неверные trace-результаты после публикации

Это одна из самых важных категорий проблем.

Проблема после post есть, если сеть выглядит нормально на карте, но аналитика по ней работает неправильно.

## Примеры

```text
trace идет не туда;
trace не проходит через нужный участок;
потребители отключения определяются неверно;
система показывает неправильный upstream/downstream;
аварийный участок влияет не на тех потребителей;
аналитик трассировки сообщает, что сеть стала недостоверной;
операционная система принимает неверное решение на основе опубликованной сети.
```

## Почему это критично

В utility-домене карта — это не только визуализация. Она используется для эксплуатационных решений. Если trace неверный, authoritative state нельзя считать безопасным.

---

# 4. Необнаруженный или неправильно разрешенный conflict

Это ситуация, когда `reconcile/post` формально прошли, но позже выяснилось, что конфликт был пропущен или решен неправильно.

## Примеры

```text
два пользователя меняли один feature, но система не показала conflict;
победила неправильная версия атрибута;
после повторного reconcile история ручного разбора потерялась;
Default изменился после reconcile, но post все равно прошел;
пользователь думал, что принял свою версию, а в Default попала другая;
geometry conflict был скрыт как обычное обновление;
update/delete conflict привел к потере нужного объекта.
```

## Почему это критично

Главный риск совместного редактирования — не сам конфликт, а `silent overwrite`: когда одна правка незаметно затирает другую и неверное состояние становится официальным.

---

# 5. Ручная аварийная коррекция после публикации

Это самый практичный критерий для метрик.

Если после `post` кому-то пришлось вручную исправлять опубликованные данные, значит `post` был проблемным.

## Считать проблемой

```text
rollback опубликованной версии;
ручная правка в БД;
ручная правка через админский инструмент;
повторное открытие work order из-за ошибки;
дополнительный reconcile/post для исправления ошибки;
ручная сверка с нарядом;
ручная сверка с полевой бригадой;
исправление данных после жалобы downstream-потребителя;
экстренное вмешательство reviewer/admin.
```

## Почему это критично

Ручная коррекция после публикации показывает, что система не смогла защитить authoritative state до `post`.

---

# 6. Несоответствие work order / факту выполненных работ

Это ситуация, когда опубликованное состояние не соответствует тому, что должно было быть сделано по наряду или фактическим работам.

## Примеры

```text
по work order нужно было заменить устройство, но в Default осталось старое;
линия должна быть демонтирована, но осталась active;
новое оборудование добавлено, но не связано с существующей сетью;
атрибут статуса не соответствует фактическому состоянию;
полевой акт и опубликованная сеть расходятся;
work order закрыт, но не все объекты изменены;
в Default опубликована неполная реконструкция участка.
```

## Почему это критично

Для `Utility GIS editor` work order — это не просто заметка. Это основание для изменения официального состояния сети.

---

# 7. Downstream-системы получили неверные данные

Проблема после post есть, если ошибка проявилась не в редакторе, а в системах-потребителях.

## Примеры

```text
дашборд показывает неправильный участок сети;
модуль trace дает неверный результат;
отчетность ушла с ошибкой;
диспетчерская система видит неправильный статус оборудования;
интеграция получила неполный change set;
mobile crew видит устаревшее или неверное состояние;
аналитический модуль строит неправильный расчет.
```

## Почему это критично

После `post` данные становятся authoritative. Если downstream-системы получают ошибку, это уже не локальная проблема редактора, а проблема доверия ко всей системе данных.

---

# 8. Что НЕ считать проблемой после post

Не всё неприятное является именно post-проблемой.

| Ситуация | Считать проблемой после post? | Почему |
|---|---:|---|
| Validation нашла ошибку до post | Нет | Система сработала правильно и не пустила ошибку в Default. |
| Reconcile нашел conflict до post | Нет | Это нормальный защитный механизм. |
| Post отказался из-за изменившегося Default | Нет | Это правильное поведение, если изменения пользователя не потеряны. |
| Пользователь отменил work order до публикации | Нет | Данные не попали в authoritative state. |
| Карта медленно открывалась, но данные корректны | Нет | Это performance issue, но не post-проблема. |
| Пользователь недоволен количеством кликов | Нет | Это UX-проблема, но не ошибка опубликованного состояния. |
| Reviewer отклонил изменения до post | Нет | Ошибка была поймана до публикации. |
| Validation потребовала исправить dirty area до post | Нет | Это ожидаемое поведение системы защиты. |
| Reconcile потребовал ручного выбора версии до post | Нет | Это conflict resolution, а не post-проблема. |

---

# 9. Рабочее определение для метрик

## Полное определение

```text
Проблема после post — это любое обнаруженное в течение контрольного окна нарушение корректности, полноты, связности, трассируемости или доверенности данных, которые уже были опубликованы в Default / authoritative state и потребовали rollback, ручного исправления, повторной сверки, повторного work order или вмешательства reviewer/admin/downstream-потребителя.
```

---

## Контрольное окно

Для продуктовых метрик можно взять:

```text
7 дней после post
```

Для MVP или synthetic experiment можно проще:

```text
до следующего validation/reconcile/post цикла
```

---

# 10. Категории для учета в метриках

Для `Rework / Manual Correction Rate` и `Safe Authoritative Post Rate` удобно классифицировать проблемы после post так:

```text
POST_DATA_LOSS
POST_TOPOLOGY_ERROR
POST_TRACE_ERROR
POST_CONFLICT_MISRESOLVED
POST_MANUAL_CORRECTION
POST_WORK_ORDER_MISMATCH
POST_DOWNSTREAM_ERROR
```

---

## POST_DATA_LOSS

Потеря, неполная публикация или искажение change set после `post`.

Примеры:

```text
потерян атрибут;
не опубликована association;
geometry опубликована не в той версии;
change set попал в Default частично.
```

---

## POST_TOPOLOGY_ERROR

Нарушение topology или наличие dirty areas после публикации.

Примеры:

```text
линия не подключена;
junction удален, но зависимые объекты остались;
dirty area не закрыта;
network rule нарушен.
```

---

## POST_TRACE_ERROR

Ошибка, которая проявилась через трассировку или сетевой анализ.

Примеры:

```text
trace не проходит;
trace идет по неверному пути;
неверно определены affected consumers;
неверный upstream/downstream.
```

---

## POST_CONFLICT_MISRESOLVED

Пропущенный или неправильно разрешенный конфликт.

Примеры:

```text
silent overwrite;
выбрана неправильная версия;
post прошел после устаревшего reconcile;
update/delete conflict привел к потере объекта.
```

---

## POST_MANUAL_CORRECTION

Любое ручное аварийное исправление после публикации.

Примеры:

```text
rollback;
ручная правка в БД;
админская коррекция;
повторная сверка с нарядом.
```

---

## POST_WORK_ORDER_MISMATCH

Несоответствие опубликованного состояния исходному work order или факту работ.

Примеры:

```text
замена оборудования не отражена;
демонтированная линия осталась active;
новое оборудование опубликовано без нужных связей.
```

---

## POST_DOWNSTREAM_ERROR

Ошибка обнаружена downstream-системой или потребителем данных.

Примеры:

```text
дашборд показывает неверный статус;
диспетчерская система получила неправильные данные;
отчетность сформирована с ошибкой;
интеграция получила неполный change set.
```

---

# 11. Короткая версия

Для `Utility GIS editor` проблемой после post считается:

```text
1. Потеря или перезапись правок.
2. Некорректная topology после публикации.
3. Неверный trace после публикации.
4. Пропущенный или неверно разрешенный conflict.
5. Ручная аварийная коррекция опубликованных данных.
6. Несоответствие work order фактическому состоянию сети.
7. Ошибка, обнаруженная downstream-системой после получения данных.
```

Самая короткая формулировка:

> Проблема после post — это когда изменения уже стали официальными, но сеть после этого нельзя безопасно использовать как authoritative state.
