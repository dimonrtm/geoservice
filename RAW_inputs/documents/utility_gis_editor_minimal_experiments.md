# Utility GIS editor: минимальные эксперименты для проверки рискованных допущений

## Контекст

Для варианта использования `Utility GIS editor` самые рискованные допущения нужно проверять минимальными экспериментами, а не сразу строить большую систему.

Сценарий относится к high-risk authoritative editing:

```text
work order
→ named/edit version
→ edit
→ validation / topology check
→ reconcile with Default
→ conflict resolution
→ post to Default
→ authoritative state
```

Пользователь работает с инженерной сетью:

- линиями;
- устройствами;
- узлами;
- ассоциациями;
- связанными nonspatial objects.

Успешное завершение сценария — это не просто сохранение объекта, а безопасный `post` в `Default`, validated topology, закрытые dirty areas и отсутствие нерешенных конфликтов.

---

# 1. Допущение: branch-like workflow реально нужен пользователю

## Минимальный эксперимент

**Название:** кликабельный workflow-test без полноценной реализации backend versioning.

**Цель:** проверить, принимает ли пользователь саму модель работы:

```text
work order
→ edit version
→ save edit
→ validation
→ reconcile
→ post
```

---

## Как провести

Сделать не полноценную систему, а тонкий прототип.

Минимальные экраны и действия:

```text
1. Экран списка work orders.
2. Кнопка “Open work order”.
3. Автоматическое создание edit version.
4. Карта с маленьким synthetic utility dataset.
5. Возможность изменить 1 линию и 1 устройство.
6. Кнопка “Save edit”.
7. Кнопка “Run validation”.
8. Кнопка “Run reconcile”.
9. Кнопка “Post to Default”.
10. Финальный статус “Posted to authoritative state”.
```

На этом этапе `validation`, `reconcile` и `post` можно имитировать моками.

Главное — проверить не алгоритмы, а понимание и принятие workflow.

---

## Минимальный dataset

```text
1 feeder
2 линии
2 устройства
2 junctions
1 work order
1 Default state
1 edit version
```

---

## Что наблюдать

Пользователь должен без подробных объяснений понять:

```text
где он редактирует;
почему это не сразу Default;
что значит Save;
что значит Validation;
что значит Reconcile;
что значит Post;
когда работа считается завершенной.
```

---

## Критерий успеха

Эксперимент считается пройденным, если 3–5 представителей роли подтверждают:

```text
Да, такой порядок похож на мой реальный рабочий процесс.
Да, отдельная рабочая версия нужна.
Да, post не должен происходить сразу после каждого save.
Да, я понимаю, что опубликовано, а что еще только в моей версии.
Да, я понимаю, когда work order завершен.
```

---

## Критерий провала

```text
Пользователь ожидает live-edit без версий.
Пользователь не понимает разницу между Save и Post.
Пользователь считает Reconcile лишним шагом.
Пользователь не понимает, зачем нужна edit version.
Пользователь не может объяснить, когда данные стали authoritative.
```

---

## Решение после эксперимента

Если эксперимент провален, не стоит сразу строить сложный branch workflow.

Возможные решения:

```text
1. Упростить workflow до live-edit с soft-lock/conflict warning.
2. Сделать два режима:
   - Operational live-edit mode;
   - Branch/work order mode.
3. Переработать UX, чтобы разница между Save и Post была очевидной.
```

# 2. Допущение: validation реально защищает сеть от некорректного состояния

## Минимальный эксперимент

**Название:** validation trap test на synthetic utility dataset.

**Цель:** проверить, может ли система поймать типовые ошибки инженерной сети до `post`.

---

## Как провести

Собрать маленький dataset и подготовить несколько заранее ошибочных действий.

Пользователь должен внести или получить эти ошибки через UI, запустить validation и понять, что именно сломано.

---

## Минимальный dataset

```text
1 feeder
3 линии
3 устройства
3 junctions
2 associations
1 nonspatial object
1 Default state
1 edit version
```

---

## Проверочные кейсы

### Кейс 1. Disconnected line

```text
Линия добавлена, но не подключена к junction.
```

Ожидаемый результат:

```text
Validation показывает ошибку связности.
Проблемная линия подсвечена на карте.
Post заблокирован.
```

---

### Кейс 2. Device without valid connection

```text
Устройство стоит на карте, но не связано с линией.
```

Ожидаемый результат:

```text
Validation показывает, что устройство не подключено к сети.
Пользователь понимает, какую связь нужно создать.
Post заблокирован.
```

---

### Кейс 3. Invalid association

```text
Создана недопустимая связь между устройством и nonspatial object.
```

Ожидаемый результат:

```text
Validation показывает ошибку association rule.
Пользователь видит оба объекта связи.
Post заблокирован.
```

---

### Кейс 4. Delete dependent object

```text
Удален junction или device, от которого зависит линия/association.
```

Ожидаемый результат:

```text
Validation показывает зависимые объекты.
Система не допускает публикацию разрушенного состояния сети.
```

---

### Кейс 5. Dirty area after geometry move

```text
Пользователь двигает узел.
Система должна пометить область как dirty area.
```

Ожидаемый результат:

```text
Dirty area отображается на карте.
Validation требуется перед post.
После успешной validation dirty area закрывается.
```

---

## Что должна сделать система

```text
1. Не разрешить post при критических validation errors.
2. Показать список ошибок.
3. Подсветить проблемный объект на карте.
4. Объяснить ошибку предметным языком.
5. Дать пользователю исправить ошибку.
6. После исправления пропустить validation.
```

---

## Критерий успеха

```text
>= 80% подготовленных ошибок обнаружены validation.
100% критических ошибок блокируют post.
Пользователь может найти проблемный объект на карте.
Пользователь понимает сообщение validation без чтения логов.
После исправления validation проходит.
```

---

## Критерий провала

```text
Validation ловит только геометрию, но не сетевой смысл.
Post проходит при disconnected line или invalid association.
Ошибка отображается только техническим текстом.
Пользователь не понимает, что исправлять.
Dirty areas не видны или не влияют на post.
```

---

## Решение после эксперимента

Если эксперимент провален, нельзя двигаться к полноценному `post to Default`.

Сначала нужно усилить:

```text
connectivity rules;
association rules;
dirty area detection;
validation result UX;
post blocking rules.
```

Иначе система будет сохранять данные, которые выглядят корректно на карте, но ломают эксплуатационную модель сети.

# 3. Допущение: conflict resolution предотвращает silent overwrite

## Минимальный эксперимент

**Название:** two-editors conflict drill.

**Цель:** проверить, что два пользователя могут параллельно менять один участок сети, а система обнаруживает конфликт, показывает diff и не допускает тихой перезаписи.

---

## Как провести

Нужны два тестовых пользователя:

```text
Editor A
Editor B
```

И один маленький dataset:

```text
1 feeder
2 линии
2 устройства
2 junctions
1 Default state
2 edit versions
```

---

## Сценарий 1. Attribute conflict

### Шаги

```text
1. Editor A открывает work order и edit version.
2. Editor A меняет status устройства с Active на Retired.
3. Editor B меняет status того же устройства в Default или в версии, которая будет запощена раньше.
4. Editor A запускает reconcile.
```

### Ожидаемый результат

```text
Система показывает attribute conflict.
Видно значение Editor A.
Видно значение Default.
Нельзя случайно затереть изменение без выбора решения.
```

---

## Сценарий 2. Geometry conflict

### Шаги

```text
1. Editor A двигает junction на карте.
2. Editor B двигает тот же junction в другую позицию и публикует раньше.
3. Editor A запускает reconcile.
```

### Ожидаемый результат

```text
Система показывает geometry conflict.
На карте видно обе геометрии.
Пользователь может выбрать правильную геометрию или исправить вручную.
```

---

## Сценарий 3. Edit after reconcile

### Шаги

```text
1. Editor A делает reconcile.
2. Editor B после этого делает post в Default.
3. Editor A пытается сделать post.
```

### Ожидаемый результат

```text
Post не проходит.
Система сообщает, что Default изменился после последнего reconcile.
Система требует повторный reconcile.
Изменения Editor A не теряются.
```

---

## Критерий успеха

```text
100% подготовленных конфликтов обнаружены.
Post не допускает silent overwrite.
Conflict view показывает “моя версия vs Default”.
Пользователь понимает тип конфликта.
Пользователь может принять решение без ручного SQL/БД сравнения.
```

---

## Критерий провала

```text
Последняя запись silently wins.
Система показывает общую ошибку без diff.
Пользователь не понимает, какой объект конфликтует.
Post проходит после устаревшего reconcile.
История ручного разбора теряется или не видна.
```

---

## Решение после эксперимента

Если эксперимент провален, нельзя выпускать collaborative editing для utility-сценария.

Сначала нужен минимум:

```text
object version token / row version;
attribute-level diff;
geometry diff;
conflict type classification;
post precondition: reconcile must be fresh;
audit trail for conflict decision.
```

# 4. Итоговая таблица экспериментов

| Порядок | Допущение | Минимальный эксперимент | Что доказываем |
|---:|---|---|---|
| 1 | Пользователю нужен branch-like workflow | Кликабельный workflow-test с work order, edit version, save, validation, reconcile, post | Пользователь понимает и принимает модель работы |
| 2 | Validation защищает сеть | Validation trap test с намеренно сломанными объектами сети | Система ловит topology/connectivity/association ошибки до post |
| 3 | Conflict resolution предотвращает silent overwrite | Two-editors conflict drill | Параллельные edits не теряются и не публикуются без осознанного решения |

# 5. Короткая версия

```text
1. Workflow prototype
   Проверяет нужность процесса.

2. Validation trap test
   Проверяет безопасность сети.

3. Two-editors conflict drill
   Проверяет безопасность совместной работы.
```

---

# 6. Минимальный принцип

Не нужно сначала строить большую систему.

Сначала нужно доказать:

```text
1. Пользователь принимает процесс.
2. Система не ломает сеть.
3. Система безопасно выдерживает параллельное редактирование.
```

Только после этого имеет смысл углублять реализацию branch versioning, reconcile/post, conflict UI и validation engine.
