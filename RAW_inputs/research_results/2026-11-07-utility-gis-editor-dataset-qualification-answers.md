# Ответы на 15 вопросов discovery

Ответы даны агентом через `expert_repson` за условную организацию. Это принятые правила модели, не интервью, результаты запуска приложения или натурная валидация. Основание — [исследование UseCase и реестр 80 внешних документов](2026-11-07-utility-gis-editor-dataset-qualification-research.md). Анализ новых знаний и эти ответы — два артефакта одного исследования с общим корпусом 80 источников. Ссылки S01–S80 и ограничения каждого источника находятся в реестре; основные обоснования ответов дополнительно приведены непосредственно ниже.

Исходный UseCase: [[RAW_inputs/documents/UtilityGisEditorRole]]. Контекст вопросов — паспорт и фактический экземпляр набора, policy EditVersion, fixture, AOI, current/readback и пределы доказательства. Прежние инварианты и SIM-UGIS-POS-001 не изменяются. Все координаты L-003 ниже взяты из исходников синтетической fixture; фактическая БД не опрашивалась.

## 1. Как связать паспортную координатную сетку и настройки приложения?

**Ответ организации.** Паспорт фиксирует условия выбранного набора и основание их выбора. Настройки — способ передать часть условий при создании версии. Persisted GeometryPolicy — фактически сохранённое правило данной EditVersion. Перед упражнением сравниваются все три с реально открытыми данными. Ни один уровень не заменяет другой.

**Обоснование.** Требования к metadata и информационной поставке описывают происхождение данных; операции назначения CRS и преобразования различны. Смысл числа нельзя восстановить только из конфигурации программы. [S28](https://www.usgs.gov/survey-manual/5027-fundamental-science-practices-metadata-usgs-scientific-data) [S36](https://postgis.net/docs/ST_SetSRID.html) [S37](https://postgis.net/docs/ST_Transform.html) [S53](https://assets.watercare.co.nz/media/ai_asset_information_and_data_standard_november_2020_b0f0de2baa.pdf) [S55](https://assets.watercare.co.nz/media/eir_watercare_e057cb8a01.pdf)

**Проверяемое решение.** В ручной карточке для каждого параметра указать ожидаемое значение, источник, фактическое значение и результат сверки. Для synthetic dataset допустимо основание «выбрано при генерации», если известна редакция генерации и проверено соответствие. Для импорта без metadata — «происхождение неизвестно». При несовпадении остановить заявленное упражнение и открыть разбор по существующей процедуре, не перенормализовывать baseline.

**Предел.** Нынешний код принимает resolution из settings. Исследование не объявляет это доказанной цепочкой dataset metadata → policy; остаток FU-2026-10-11-001 сохраняется.

## 2. Можно ли считать default 0.0000001 установленной характеристикой открытого набора?

**Ответ организации.** Нет. Его можно назвать default исходников. Для конкретной EditVersion значение устанавливается чтением её persisted policy; соответствие исходным данным требует отдельной проверки. Default не доказывает происхождение, реальную точность и отсутствие прежнего округления.

**Обоснование.** Документы координатных систем и GNSS показывают различие представления, основания координат и качества наблюдений. Малые числовые шаги не устраняют неизвестность метода. [S45](https://proj.org/en/stable/faq.html) [S73](https://www.ordnancesurvey.co.uk/documents/resources/guide-coordinate-systems-great-britain.pdf) [S76](https://www.ngs.noaa.gov/OPUS/about.jsp)

**Проверка.** Зафиксировать окружение/экземпляр, EditVersion и её policy snapshot. Проверить координаты выбранного before/current по той же сетке и режиму округления, не меняя их. Если параметр совпал с default, записать «совпадает», а не «значение взято из default». Положительный результат относится к данной версии и моменту сверки.

**Контрпример.** Версия создана при другой настройке, затем приложение перезапущено. Новый default не описывает её правила. Диапазоны допустимых XY также не являются точностью съёмки.

## 3. Какие правила действуют после смены настроек для уже созданной EditVersion?

**Ответ организации.** Сохраняется immutable policy snapshot этой версии. Конфигурация нового процесса не переписывает её правила. При необходимости иных условий готовится отдельный допустимый сценарий или версия по существующему процессу; скрытый перенос старого baseline запрещён.

**Обоснование.** Версионирование и provenance позволяют воспроизводить результат только при известной редакции обработки. Даже повторная обработка тех же наблюдений может дать другой результат. [S49](https://www.w3.org/TR/vocab-dcat-3/) [S52](https://www.w3.org/TR/dwbp/) [S80](https://www.ga.gov.au/scientific-topics/positioning-navigation/positioning-australia/geodesy/auspos)

**Проверка.** Сопоставить policy старой версии до/после reopen и отдельно условия новой версии, если она создаётся. Изменение конфигурации само по себе не доказывает изменение данных. Эта процедура — критерий проверки, не утверждение, что тест выполнен.

**Следствие.** Старая версия может быть технически корректной, но не соответствовать новому учебному паспорту. Тогда ограничивается применимость упражнения; историческое сохранение не объявляется ошибочным задним числом. Совпадение координат после смены настроек тоже не означает совпадения правил.

## 4. Как обозначить отсутствующие xyTolerance и сведения о преобразовании?

**Ответ организации.** Не подставлять ноль. Различать «не предусмотрено текущим контрактом», «неизвестно» и «не применимо для конкретной цели с объяснением». Для xyTolerance сейчас корректно первое; для происхождения импортированных координат без сведений — второе.

**Обоснование.** CRS-метка не описывает исполненную операцию. PROJ выбирает операции с учётом условий и ресурсов; региональные модели имеют области применения. [S11](https://proj.org/en/stable/operations/operations_computation.html) [S46](https://proj.org/en/stable/usage/transformation.html) [S57](https://www.ordnancesurvey.co.uk/geodesy-positioning/coordinate-transformations) [S78](https://www.ga.gov.au/scientific-topics/positioning-navigation/positioning-australia/geodesy/australian-geospatial-reference-system/agrstoolsandmodels)

**Проверка.** Если synthetic XY сгенерированы сразу в заданном представлении, документировать эту генерацию и отсутствие операции именно на данном этапе. Если история до импорта неизвестна, отсутствие pipeline в коде не разрешает запись «трансформаций не было». Для позиционной оценки требуются пригодные сведения о применённой операции, включая ресурсы/эпоху, когда они существенны.

**Следствие.** Неполнота positional evidence не становится новым hard guard Save. В карточке можно допустить техническое упражнение и одновременно оставить позиционную пригодность непроверенной. Выбранные слова — ручное описание, не новый серверный enum.

## 5. Достаточно ли карты, если UI не показывает сохранённую geometry policy?

**Ответ организации.** Для полной сверки — нет. Карта подтверждает отображённое представление, но не весь policy snapshot. Нужна связанная с конкретной EditVersion запись доступного read-only источника policy и координат. Отсутствующие в UI сведения нельзя выдавать за увиденные.

**Обоснование.** Формат представления может менять точность вывода; явное описание CRS ответа — отдельная задача API. Внешний пример Content-Crs не означает, что такой контракт уже реализован у нас. [S38](https://postgis.net/docs/ST_AsGeoJSON.html) [S51](https://www.rfc-editor.org/rfc/rfc7946) [S75](https://docs.ogc.org/is/18-058r1/18-058r1.html)

**Проверка.** В ручном отчёте указать источник каждого поля: UI, API, persisted данные или source-code expectation. Последнее не заменяет первые. Не добавлять секреты подключения в отчёт. Если подходящего чтения нет, записать конкретный пробел и ограничить вывод.

**Следствие.** Автоматический UI-паспорт может быть будущей технической задачей. В этом исследовании не проектируется endpoint и не меняется интерфейс. Для текущего доказательства допустима ручная карточка, но она должна содержать фактически полученные значения, а не заполненные по догадке.

## 6. Как отличить два экземпляра synthetic dataset с одинаковым названием?

**Ответ организации.** Название — человекочитаемая метка. Отдельно фиксировать логический dataset/редакцию, экземпляр окружения, фактический ключ набора и выбранную запись. Идентификатор должен быть однозначным в указанном контексте, а не обязательно глобально уникальным сам по себе.

**Обоснование.** MUDDI различает объект, запись и систему; DCAT — логический набор и его представления. [S10](https://docs.ogc.org/is/23-024/23-024.html) [S49](https://www.w3.org/TR/vocab-dcat-3/)

**Проверка.** Сопоставить происхождение экземпляра, его содержимое и ссылки WorkOrder/EditVersion. Полное совпадение геометрии не объединяет два экземпляра; разный локальный ID не обязательно означает другой физический актив. Для synthetic fixture код L-003 — обозначение сценария, а не доказательство внешнего реального актива.

**Контрпример.** Fresh database и старый volume оба имеют `synthetic_utility_feeder_01`; только fresh содержит новую трёхточечную L-003. Подходящий вывод — «проверены разные экземпляры; старый не соответствует этой редакции упражнения». Запрещено назвать оба эквивалентными только по заголовку.

## 7. Что делать, если новый seed содержит три вершины L-003, а старая БД — две?

**Ответ организации.** Остановить именно упражнение с перемещением внутренней вершины в данном экземпляре. Не добавлять вершину в baseline и не переписывать seed-данные во время сверки. Можно подготовить отдельный явно названный набор/сценарий вне этого ограниченного действия.

**Обоснование.** Топологическое равенство допускает различную детализацию линии. Общие precision/grid-операции могут изменить структуру сразу в нескольких местах. [S35](https://docs.qgis.org/3.40/en/docs/user_manual/working_with_vector/editing_geometry_attributes.html) [S39](https://postgis.net/docs/ST_ReducePrecision.html) [S40](https://postgis.net/docs/ST_SnapToGrid.html) [S41](https://postgis.net/docs/ST_Equals.html) [S42](https://postgis.net/docs/ST_OrderingEquals.html)

**Проверка.** Проверить фактическую структуру before/current, число вершин, endpoints, допустимый внутренний индекс и связи. По исходникам новая L-003 — `(65.520,44.820) → (65.525,44.8205) → (65.530,44.820)`. Это ожидание для сверки; оно не переписывает наблюдаемые данные.

**Следствие.** Create-once seed объясняет возможное расхождение и не является ошибкой идентичности сам по себе. «Упражнение недопустимо здесь» не равно «вся БД негодна». Новая fixture требует отдельного явного выбора, а не подгонки текущего объекта ради зелёного результата.

## 8. Как установить соответствие линии с другим ID в другом окружении?

**Ответ организации.** Через явное сопоставление записей с указанием источника и контекста: экземпляр, asset code/назначение, происхождение, структура, endpoints и associations. Совпадение XY — вспомогательное свидетельство, не достаточное условие идентичности.

**Обоснование.** Межсистемный обмен NUAR и IMKL требует согласования схем/представлений; локальный ключ не является универсальным предметным идентификатором. [S07](https://gdsgeospatial.blog.gov.uk/2024/08/13/an-introduction-to-the-nuar-data-model/) [S09](https://gdsgeospatial.blog.gov.uk/2025/11/13/open-sourcing-elements-of-nuar/) [S12](https://www.contractsfinder.service.gov.uk/Notice/Attachment/b1a84db2-857d-427f-908d-a20a3fff82f9) [S64](https://www.geonovum.nl/geo-standaarden/informatiemodel-kabels-en-leidingen-imkl)

**Проверка.** Для обеих сторон указать ключи и основания mapping. Не переносить старый receipt, CommandId или positional assessment на новую запись автоматически. Если связь неоднозначна, остановить утверждение об эквивалентности и выбрать объект заново в рамках подходящего сценария.

**Контрпример.** Импорт продублировал геометрию, но изменил связь линии с устройством. Это не доказанная копия пригодной fixture. Для нашего упражнения важно сохранить не только линию, но и контекст связей; при этом полная сетевая validation остаётся за пределами first-save.

## 9. Нужно ли перепроверять пригодность той же линии после изменения AOI наряда?

**Ответ организации.** Да. Допуск относится к паре «данные и задача» с их состояниями. Новый AOI или иной WorkOrder меняет основание проверки даже при неизменных координатах.

**Обоснование.** Геометрическое покрытие и строгая принадлежность внутренности — разные условия; общая валидность не проверяет задачу. [S43](https://postgis.net/docs/ST_CoveredBy.html) [S44](https://postgis.net/docs/ST_IsValid.html)

**Проверка.** Снова установить актуальный WorkOrder/AOI, покрытие всей линии и положение редактируемой внутренней вершины, остальные действующие ограничения. Не расширять AOI в ходе упражнения ради допустимости candidate. Нельзя выводить eligibility из того, что линия видна на карте.

**Следствие.** Прежний результат остаётся исторически корректным для прежнего scope. Новая проверка не требует автоматического Revert и не объявляет изменение AOI геометрическим дефектом. При расхождении передать вопрос по существующей процедуре применения основания; не изобретать новый транзакционный процесс.

## 10. Что делать, если current уже содержит предполагаемую правку?

**Ответ организации.** Сначала определить ветку упражнения. Для доказательства ненулевого Save нужен пригодный начальный current и новый допустимый candidate. Повторное отправление уже сохранённой геометрии может быть no-op; это отдельный корректный результат, но не доказательство нового движения.

**Обоснование.** Версии и обмен изменениями сохраняют различие исходного состояния и дельты; восстановление данных не устанавливает новую предметную операцию. [S24](https://docs.qfield.org/reference/qfieldcloud/workflow/) [S65](https://merginmaps.com/docs/manage/synchronisation/) [S66](https://merginmaps.com/docs/manage/missing-data/)

**Проверка.** Сравнить baseline, current и candidate по действующей policy до команды. Если задача уже выполнена, зафиксировать «требуемое состояние уже имеется» с основанием. Если нужен именно первый ненулевой Save, выбрать явно подготовленный контекст отдельной процедурой. Не выполнять произвольное обратное движение ради демонстрации.

**Предел.** Revert имеет собственный смысл и условия; он не используется автоматически как reset упражнения. Существующий current не становится baseline. Смена цели после выполнения не разрешает переписать историю доказательств.

## 11. Как доказать изменение, если экранные координаты после округления совпадают?

**Ответ организации.** Сравнить сохранённые координаты достаточной точности и структуру в одном установленном контексте версии. Отдельно показать, что изменена только разрешённая внутренняя вершина, остальные координаты/связи неизменны.

**Обоснование.** Ограничение знаков при сериализации и топологическое сравнение не эквивалентны сравнению структуры сохранённой линии. [S38](https://postgis.net/docs/ST_AsGeoJSON.html) [S41](https://postgis.net/docs/ST_Equals.html) [S42](https://postgis.net/docs/ST_OrderingEquals.html)

**Проверка.** В отчёт включить before/current/candidate в точности, достаточной для принятой сетки, policy и идентификатор состояния. Если предоставляется хеш, указать, что именно и как сериализовано; несовпадение хешей само по себе не показывает разрешённость изменения. Не делать единственным доказательством картинку, округлённые подписи или bbox.

**Контрпример.** Две записи отличаются на один шаг сетки, но UI показывает меньше знаков. Это может быть ненулевой Save при одинаковой подписи. Обратный случай: текст отличается форматированием, а нормализованная геометрия совпадает — не новый результат правки.

## 12. Как сообщать старый replay success, если current уже новее?

**Ответ организации.** Два утверждения рядом: «операция с данным CommandId ранее завершилась таким исходом» и «текущее состояние на момент чтения такое-то». Не заменять current геометрией из старого ответа и не называть исторический результат последним.

**Обоснование.** В системах версий запись, согласование и публикация различаются; provenance связывает результат с породившим его действием. [S48](https://www.w3.org/TR/prov-dm/) [S59](https://pro.arcgis.com/en/pro-app/3.3/help/data/geodatabases/overview/manage-branch-version-conflicts.htm) [S60](https://pro.arcgis.com/en/pro-app/3.5/help/data/geodatabases/overview/reconcile-and-post-edits-to-a-branch-version.htm)

**Проверка.** Сохранить идентичность операции, её результат и отдельно актуальный token/state readback. Если более новая версия возникла между действиями, указать это ограничение. Поздний ответ не доказывает, что более новая правка исчезла. Unknown outcome разрешается существующим recovery-процессом, не новым Save наугад.

**Следствие.** Старый success остаётся полезным доказательством истории, но не основанием позиционной оценки нового current. Last-wins из документации сторонней синхронизации не заменяет правила GeoService. [S32](https://docs.qfield.org/reference/qfieldcloud/jobs/)

## 13. Когда карта и ChangeSet, прочитанные в разное время, образуют согласованное доказательство?

**Ответ организации.** Когда удалось установить их принадлежность совместимому состоянию одной EditVersion и одному baseline. Одного близкого времени чтения недостаточно. Если совместимость не подтверждена, отчёт описывает отдельные наблюдения и не утверждает атомарный снимок.

**Обоснование.** PROV задаёт причинные ограничения использования/порождения; QFieldCloud отделяет обработку изменений от их передачи. Эти модели не дают автоматически согласованного снимка в нашем API. [S23](https://docs.qfield.org/reference/qfieldcloud/system/) [S32](https://docs.qfield.org/reference/qfieldcloud/jobs/) [S74](https://www.w3.org/TR/prov-constraints/)

**Проверка.** Сопоставить контекст и доступные версии/token; при mismatch повторить чтение доступными средствами. Если один ответ не предоставляет нужную связь, зафиксировать ограничение контракта. Отсутствие новых уведомлений само по себе не доказывает неизменность данных. Карта, ChangeSet и baseline не объявляются одной транзакцией.

**Следствие.** Исследование задаёт критерий доказательства, а не новый алгоритм API. Текущие token/reconciliation механизмы описаны в Code_wiki; их наличие не заменяет наблюдение конкретного выполнения.

## 14. Какое заключение допустимо после успешного Save без независимого эталона?

**Ответ организации.** «Техническая правка выполнена в установленном контексте и прочитана обратно» — если это действительно наблюдалось. Позиционный статус остаётся `POSITIONAL_ACCURACY_UNVERIFIED`; topology и эксплуатационная пригодность не подтверждаются.

**Обоснование.** Метрики качества зависят от цели; планы коммуникаций и геометрическая запись не заменяют наблюдения. Сетевые расчёты требуют иных данных. [S30](https://docs.ogc.org/per/17-025r2.html) [S50](https://www.w3.org/TR/vocab-dqv/) [S62](https://www.epa.gov/water-research/epanet) [S63](https://19january2021snapshot.epa.gov/sites/static/files/2020-05/documents/epanet_userss_manual_2.2.0.pdf) [S68](https://www.hse.gov.uk/electricity/information/excavations.htm) [S71](https://www.sla.gov.sg/qql/slot/u143/Newsroom/Circulars/Survey%20Services/Other%20Information/Standard%20and%20Specifications%20for%20Utility%20Survey%20in%20Singapore%20Version%201.0%20-%20Aug%202017.pdf)

**Проверка.** Заключение должно назвать объект/состояние, технический результат, непроверенные свойства и причину ограничения. Нельзя считать величину перемещения величиной исправленной ошибки. GNSS indicator одной точки не покрывает всю линию; повторная обработка того же наблюдения не делает evidence независимым. [S08](https://docs.qfield.org/how-to/navigation-and-positioning/gnss/) [S77](https://nweb.ngs.noaa.gov/OPUS-Projects/user_guide/section4.3.html) [S80](https://www.ga.gov.au/scientific-topics/positioning-navigation/positioning-australia/geodesy/auspos)

**Предел.** SIM-UGIS-POS-001 с прежними T=0.50 m и ограничением u<=0.10 m не меняется. SIM-EVID-001 не относится автоматически к L-003. Чужие tolerances Watercare/ADAC не становятся новыми порогами нашего Save.

## 15. Достаточно ли этого исследования, чтобы закрыть два вопроса metadata/fixture?

**Ответ организации.** Нет. Правила выбора и проверки теперь конкретнее, но фактическое состояние экземпляра не проверено. Это два оставшихся вопроса наблюдения, а не просьба к несуществующим сотрудникам организации.

**Обоснование.** Metadata, lifecycle и версии связывают утверждение с конкретным ресурсом; проверка концептуальной модели не заменяет проверку экземпляра. [S27](https://www.usgs.gov/data-management/data-lifecycle) [S29](https://www.usgs.gov/science-data-management/persistent-identifiers-pids-metadata-faq) [S31](https://docs.ogc.org/per/26-005r1.html) [S52](https://www.w3.org/TR/dwbp/)

**Критерий закрытия metadata.** Есть запись сверки конкретного экземпляра/версии: CRS/оси/единицы, persisted resolution/rounding/version, применимые диапазоны и происхождение. Неподдерживаемые/неизвестные свойства описаны с последствиями для цели. Не требуется выдумывать xyTolerance или полевую съёмку для технической демонстрации.

**Критерий закрытия fixture.** Наблюдались конкретные WorkOrder/EditVersion/feature, baseline и current, подходящая структура/внутренняя вершина, endpoints/associations/AOI и допустимый candidate. Различены ожидание seed и факт БД; определена ветка no-op/ненулевой Save. Один и тот же evidence-пакет может поддержать оба ответа, но каждый вопрос закрывается по своим условиям. Позиционная приёмка остаётся отдельной.

## Ручная карточка проверки экземпляра

Это шаблон состава доказательств, **не заполненный паспорт текущей БД**. Поля не объявляются реализованными API-атрибутами.

| Группа | Что фиксировать | Что не подставлять вместо факта |
| --- | --- | --- |
| Цель | Техническое упражнение, конкретная ветка; отдельно positional scope | Универсальное «данные качественные» |
| Идентичность | Dataset/редакция, экземпляр окружения, локальный ключ, asset designation, mapping | Одно имя слоя или одинаковые XY |
| Контекст | WorkOrder, AOI/его состояние, EditVersion, baseline ref, current token где доступен | Старый screenshot |
| Policy | Ожидаемые и persisted значения с источниками; результат сравнения | Default из settings как факт этой версии |
| Координатное основание | CRS, оси, единицы, origin/domain; операция/ресурсы/эпоха при применимости | «Не было преобразования», если история неизвестна |
| Структура | Тип/размерность, число/порядок вершин, endpoints, associations, разрешённый индекс | Один ST_Equals |
| Правка | Before/current/candidate, намерение, выбранная ветка | Искусственный reset ради демонстрации |
| Исход | CommandId/receipt отдельно от current/readback; согласованность чтений | Старый success как последнее состояние |
| Ограничения | Unknown/n/a с объяснением; positional/topology/operational scope | Отсутствующий допуск как ноль |
| Решение | Допущено для данной цели либо причина недопуска/разбор; время и evidence refs | Заявление о выполненной проверке без evidence |

При изменении экземпляра, версии, AOI, основания или релевантной политики пригодность переоценивается по влиянию. Незначимое изменение оформления карточки не требует нового движения геометрии.

## Аналитическая матрица пограничных случаев

Сценарии ниже разобраны логически, **не исполнялись как тесты**.

| Случай | Ожидаемый вывод |
| --- | --- |
| Паспорт и policy совпали, но экземпляр не установлен | Допуск не доказан |
| Default совпал с числом в отчёте без чтения persisted policy | Проверка версии не выполнена |
| Изменились settings, старая версия сохранила прежнюю policy | Исторические правила сохранены; применимость паспорта оценивается отдельно |
| Нет xyTolerance в контракте | Не ноль; указать отсутствие свойства и цель |
| Неизвестна история импорта | Не заявлять отсутствие трансформаций |
| Два volume имеют одинаковое имя набора | Проверить раздельно |
| Линия топологически равна fixture, но имеет две вершины | Нет eligible внутренней вершины |
| ID изменился после импорта, mapping подтверждён | Можно сопоставлять запись, но receipts/оценки не переносить автоматически |
| AOI изменён, геометрия прежняя | Повторить eligibility |
| Current уже равен candidate | Возможен no-op; ненулевой Save не доказан |
| Подписи XY равны, точные координаты различаются | Проверять persisted структуру и policy |
| Replay старой операции успешен, current новее | Сообщить историю и current раздельно |
| Карта и ChangeSet относятся к разным token | Не составлять единое доказательство |
| Save прошёл, эталона нет | Технический результат; positional unverified |
| Только seed-тесты подтверждают L-003 | Runtime metadata/fixture вопросы остаются open |
