# Ответы на 15 вопросов discovery

Ответы даёт агент через expert_repson от имени условной организации. Это принятые правила моделируемой работы, не реальное интервью. Внешние факты обосновывают выбор, но не предписывают правила GeoService. Общий корпус **78 прочитанных документов** и анализ новизны находятся в [[RAW_inputs/research_results/2026-11-08-utility-gis-editor-verification-research]]. Это тот же анализ, не дополнительный корпус.

Сохранён порядок 15 вопросов discovery о конкретном экземпляре, metadata, fixture и доказательствах упражнения. Названия вопросов ниже кратко пересказывают их предмет. Фактическая БД не проверена; ответы не закрывают два вопроса metadata/fixture и не расширяют реализацию.

## 1. Как установить экземпляр при прежнем имени набора после обновления?

**Решение.** Имя используется для поиска, а допуск привязывается к наблюдаемому экземпляру, редакции данных, WorkOrder и EditVersion. В карточке записываем идентификаторы, происхождение поставки, время чтения и доступный признак редакции. Если отдельного revision нет в контракте, не выдумываем его: указываем доступные признаки и пределы их достаточности.

Паспорт описывает ожидаемый набор. Нужно сопоставить его с открытой копией: структура слоёв, запись L-003, геометрия и policy. Обновлённый seed в Git не доказывает обновление существующего volume. При неустранимой неоднозначности эта ветка упражнения пока не допущена; отдельно подготовленный экземпляр допустим только как явно другая подготовка.

**Основание.** История проекта, dataset/distribution и локальные ключи имеют различный смысл. [R07](https://merginmaps.com/docs/manage/project-history/), [R40](https://www.w3.org/TR/vocab-dcat-3/), [R45](https://www.geopackage.org/spec140/index.html)

## 2. L-003 имеет другие координаты: другая запись или изменённая та же линия?

**Решение.** Сначала сравниваем техническую идентичность записи внутри экземпляра, её контекст и связь с baseline/current; затем — координаты. Label L-003 и пространственная близость недостаточны. При переносе между системами требуется объяснимое сопоставление идентификаторов, включая происхождение таблицы соответствий.

Та же запись может иметь новую геометрию; другая запись может обозначать тот же актив; одинаковая геометрия не доказывает ни того, ни другого. Если соответствие неизвестно, не трактуем расхождение как разрешённую правку и не заменяем baseline. В карточке явно отмечаем неопределённость identity.

**Основание.** QField описывает изменяемость fid; Watercare использует идентификацию для связи систем и полевых активов. [R13](https://docs.qfield.org/get-started/tutorials/advanced-setup-qfc/), [R58](https://assets.watercare.co.nz/media/ai_asset_information_and_data_standard_november_2020_b0f0de2baa.pdf)

## 3. Что действительно известно при SRID 4326?

**Решение.** Это обозначение системы координат в конкретном представлении. Дополнительно устанавливаются соглашение осей интерфейса/хранилища, единицы, допустимые диапазоны, размерность и известная история обработки. В GeoService ожидаются XY и SRID 4326 по коду; состояние выбранной БД нужно наблюдать отдельно.

Нельзя из SRID вывести отсутствие прошлых преобразований, датум исходной съёмки, её точность или истинность координат. GeoJSON использует longitude/latitude; формальное определение CRS и порядок приложения могут различаться. Ошибочно подписанная геометрия не исправляется догадкой или одним назначением SRID.

**Основание.** Различие SetSRID/Transform, осей PROJ и соглашения GeoJSON. [R22](https://postgis.net/docs/ST_SetSRID.html), [R23](https://postgis.net/docs/ST_Transform.html), [R30](https://proj.org/en/stable/faq.html), [R44](https://www.rfc-editor.org/rfc/rfc7946)

## 4. Изменились настройки сетки после создания EditVersion: какие правила действуют?

**Решение.** Для прежней версии сверяем persisted GeometryPolicy, а не подставляем новые settings. Не перенормализуем baseline и не переписываем политику задним числом. В карточке раздельно показываем ожидаемое значение, конфигурационный default, наблюдаемое persisted значение и вывод.

Расхождение может означать законно созданную при прежних настройках версию. Вопрос продолжения определяется целью и принятыми правилами применимости; смена конфигурации сама по себе не делает старое сохранение ошибочным. Если новый сценарий требует иной политики, нужна отдельная явная подготовка.

**Основание.** Документация precision/преобразований показывает зависимость результата от параметров; правило immutability взято из проекта, а не из внешнего стандарта. [R29](https://postgis.net/docs/ST_ReducePrecision.html), [R31](https://proj.org/en/stable/operations/operations_computation.html), [R35](https://gdal.org/en/stable/programs/ogr2ogr.html)

## 5. В контракте нет tolerance или истории преобразования: можно ли принять ноль?

**Решение.** Нет. Различаем неизвестное значение, неподдерживаемое контрактом свойство, обоснованную неприменимость и наблюдаемый ноль. Ноль — значение, требующее источника. «Не применимо» допускается только с объяснением относительно цели.

Отсутствие pipeline не означает, что преобразования не было. Для технического упражнения допустимы явно описанные ограничения, если существенные условия проверены. Для утверждения о позиционной точности отсутствие необходимого основания сохраняет непроверенность. Нельзя заполнять карточку уверенностью вместо данных.

**Основание.** Data dictionary включает missing-data semantics; операции могут зависеть от grids и окружения. [R66](https://www.usgs.gov/data-management/data-dictionaries), [R32](https://proj.org/en/stable/apps/projinfo.html), [R33](https://proj.org/en/stable/usage/transformation.html), [R34](https://proj.org/en/stable/usage/network.html)

## 6. Старая L-003 содержит две вершины: добавить среднюю ради упражнения?

**Решение.** Не добавляем вершину внутри ограниченной правки. Такая линия не подходит для заявленной ветки движения существующей внутренней вершины. Допустим явно подготовленный другой экземпляр или другой сценарий с собственным основанием; это не скрытый ремонт старого baseline.

Проверка ST_Equals может считать геометрию эквивалентной при иной структуре вершин, однако структура существенна для упражнения. Нельзя выдавать подготовку fixture за исправление актива или успешно выполненный Save.

**Основание.** Топологическое и структурное равенство различаются; разбиение дуги — самостоятельная операция. [R24](https://postgis.net/docs/ST_Equals.html), [R25](https://postgis.net/docs/ST_OrderingEquals.html), [R76](https://docs.giswater.org/master/en/docs/giswater/for-users/dialogs/arc-divide.html)

## 7. Подходящая линия находится в другом WorkOrder/AOI: можно ли перенести допуск?

**Решение.** Нет автоматического переноса. Проверяются текущие WorkOrder/EditVersion, разрешённая область, линия и candidate по действующим инвариантам. Геометрическая пригодность не предоставляет полномочия и не расширяет задание.

В карточке различаем AOI задания, область наблюдения и область выполненной проверки. Они могут пересекаться, но не взаимозаменяемы. Успешная проверка только видимой части не называется проверкой всей линии или всех данных.

**Основание.** Survey extent и topology validation extent имеют конкретную область; это разные виды охвата. [R60](https://pw-cdn.watercorporation.com.au/-/media/watercorp/documents/about-us/suppliers-and-contractors/resources/design-standards/spatial-data-standards/s551-spatial-data-standard.pdf?hash=89BDD9F67400853882120EC1306E3239&rev=52ed8b38196e44cb970cada69fd4d06e), [R55](https://pro.arcgis.com/en/pro-app/latest/help/data/utility-network/validate-a-network-topology.htm), [R09](https://docs.vertigis.com/networks/latest/en/editor/vne_jm_working-within-the-job.html)

## 8. Средняя вершина доступна для drag: достаточно ли этого?

**Решение.** Нет. Проверяем, что это разрешённая shape point, не endpoint и не сетевой junction/device, который требуется сохранить. Сверяем endpoints и associations до/после; движение не должно незаметно менять соседние объекты или сетевые отношения.

Визуальное совпадение не заменяет проверку связи. Если задача требует переместить узел, разделить дугу или изменить присоединение, ограниченный Save не используется как обход. Число вершин само по себе не устанавливает семантику.

**Основание.** Connectivity/associations отделены от XY; QGIS topological editing может затронуть соседние геометрии. [R53](https://pro.arcgis.com/en/pro-app/latest/help/data/utility-network/connectivity.htm), [R54](https://pro.arcgis.com/en/pro-app/latest/help/data/utility-network/associations.htm), [R50](https://docs.qgis.org/latest/en/docs/user_manual/working_with_vector/editing_geometry_attributes.html)

## 9. Линия с четырьмя вершинами валидна, но UI поддерживает три: что это означает?

**Решение.** Это ограничение текущего инструмента для данного сценария, а не общая доменная невалидность линии. В заключении указываем «не поддерживается текущим UI» отдельно от нарушений структуры/простоты/связности.

Нельзя удалять вершину, упрощать линию или менять число сегментов ради доступности кнопки. Можно выбрать подходящую fixture либо сформулировать отдельную задачу расширения инструмента. Такая задача настоящим исследованием не принимается к реализации.

**Основание.** Проверки valid/simple имеют определённые свойства и не задают лимит UI в три вершины. [R26](https://postgis.net/docs/ST_IsValid.html), [R27](https://postgis.net/docs/ST_IsSimple.html), [R52](https://docs.qgis.org/latest/en/docs/user_manual/processing_algs/qgis/vectorgeometry.html)

## 10. Current уже совпадает с желаемым результатом: как завершить упражнение?

**Решение.** До действия объявляем ветку: ненулевой Save, no-op или подтверждение уже достигнутого состояния. Если цель — проверить изменение, совпадение current с candidate не доказывает её выполнение. Если цель — установить соответствие заданию, обоснованное отсутствие изменения может быть правильным результатом.

Не сдвигаем объект туда-обратно ради демонстрации. Сравнение выполняется по правилам проекта и существенным структурам, а не только визуально. Итог содержит выбранную ветку и свидетельство сравнения.

**Основание.** Разные предикаты равенства и history требуют различать состояние и действие. [R24](https://postgis.net/docs/ST_Equals.html), [R25](https://postgis.net/docs/ST_OrderingEquals.html), [R07](https://merginmaps.com/docs/manage/project-history/)

## 11. Можно ли соединить отдельные чтения map, changes и baseline в один снимок?

**Решение.** Только если согласованность подтверждается доступным контрактом. Фиксируем контекст версии, записи, доступные токены/признаки редакции и время наблюдений. Серия запросов сама по себе не атомарна.

При несовместимых данных повторяем необходимые чтения или ограничиваем вывод: «совместное состояние не установлено». Отсутствующий токен не заменяем timestamp с вымышленной точностью. Не предлагаем новый endpoint как уже принятое требование. Нужно знать также, не отфильтрована ли часть данных.

**Основание.** Разные представления могут обновляться на разных этапах; delta и скачанный слой проверяются отдельно. [R02](https://www.esri.com/arcgis-blog/products/arcgis-pro/data-management/how-do-utility-or-trace-network-changes-impact-network-diagrams), [R12](https://docs.qfield.org/reference/qfieldcloud/workflow/), [R14](https://docs.qfield.org/reference/qfieldcloud/self_hosted/django_interface/)

## 12. Replay сообщает успех старого Save, но current уже новее: чему доверять?

**Решение.** Оба свидетельства могут быть верны: receipt относится к операции, current — к состоянию на момент чтения. Сначала связываем receipt с command и контекстом; затем читаем актуальные данные. Не заменяем current старым результатом replay и не повторяем старое намерение как новую команду.

Исторический успех не доказывает, что более поздние изменения отсутствовали. Для упражнения уточняем, доказываем ли факт прежней операции или сегодняшнее состояние. При неопределённости используем существующий recovery process.

**Основание.** История, применение изменений и reconcile/post имеют различную временную семантику. [R07](https://merginmaps.com/docs/manage/project-history/), [R10](https://docs.vertigis.com/networks/latest/en/editor/vne_jm_close-jobs.html), [R12](https://docs.qfield.org/reference/qfieldcloud/workflow/), [R56](https://pro.arcgis.com/en/pro-app/latest/help/data/geodatabases/overview/reconcile-and-post-edits-to-a-branch-version.htm)

## 13. Save успешен и линия выглядит правдоподобно: можно ли признать точность и качество?

**Решение.** Можно утверждать только установленный технический результат. Для остальных утверждений нужны свои методы и свидетельства: valid/simple, сетевые отношения, позиционное соответствие, высота, материал, эксплуатационная пригодность не взаимозаменяемы.

При отсутствии пригодного позиционного эталона сохраняем POSITIONAL_ACCURACY_UNVERIFIED. Величина ручного сдвига не равна измеренной ошибке. Статус verified внешнего документа без метода, свойства и охвата не переносится на всю линию. Не меняем SIM-UGIS-POS-001 и не вводим новый hard guard Save.

**Основание.** Watercare различает методы; EPA отделяет калибровку расчёта; Fort Myers ограничивает значение выданных карт. [R59](https://assets.watercare.co.nz/media/as_built_3d_model_specification_2cef742361.pdf), [R19](https://nepis.epa.gov/Exe/ZyPURL.cgi?Dockey=P10113EM.TXT), [R20](https://nepis.epa.gov/Exe/ZyPURL.cgi?Dockey=2000D2C2.TXT), [R73](https://www.fortmyers.gov/DocumentCenter/View/25497/AsBuilt-GIS-Data-Request-Form-Jan-2025)

## 14. После допуска сменились экземпляр, AOI или основание: отменять прежний результат?

**Решение.** Переоцениваем затронутые зависимости и область применимости. Историческое заключение сохраняет свой контекст; оно не автоматически пригодно для нового. Если поменялась только нерелевантная часть источника, повторяем не всё, а необходимые проверки с обоснованием.

Новая неопределённость не является командой Revert. Изменение данных требует отдельного актуального намерения и действующего контекста. Для частичного допуска явно указываем, какая часть остаётся пригодной и что ещё не проверено; общие зависимости могут затронуть весь вывод.

**Основание.** PROV, версия metadata и quality assessment поддерживают прослеживаемость; правило последствий принято условной организацией. [R38](https://www.w3.org/TR/prov-dm/), [R39](https://www.w3.org/TR/prov-o/), [R68](https://www.usgs.gov/data-management/data-quality-assessment-and-review-recommended-practices), [R70](https://www.usgs.gov/data-management/metadata-creation)

## 15. Какие свидетельства действительно закроют вопросы metadata и fixture?

**Решение.** Закрытие требует read-only сверки выбранного экземпляра с прослеживаемым результатом. Для metadata нужны наблюдаемые идентификаторы/редакция, CRS и соглашения хранения/интерфейса, persisted policy, сведения об источнике и явно ограниченная неизвестность истории. Паспорт/default отдельно от наблюдения.

Для fixture нужны baseline/current, candidate заявленной ветки, структура и разрешённая внутренняя вершина, endpoints/associations, WorkOrder/EditVersion/AOI и согласованность чтений. Записываются метод каждой проверки, охваченные объекты/свойства и результат. Отсутствие строки в выборке сначала проверяется на фильтр и контекст.

Позиционное evidence не является обязательным условием закрытия технической пригодности fixture: её позиционный статус остаётся отдельно непроверенным. Изучение кода, успешный тест синтетических данных и интернет-источники не заменяют наблюдения рабочего экземпляра. В этой работе такого наблюдения нет; оба вопроса остаются open.

**Основание.** Metadata и данные проверяются совместно; проверки графа/модели/конфигурации разделены. [R66](https://www.usgs.gov/data-management/data-dictionaries), [R67](https://www.usgs.gov/data-management/data-release), [R68](https://www.usgs.gov/data-management/data-quality-assessment-and-review-recommended-practices), [R70](https://www.usgs.gov/data-management/metadata-creation), [R78](https://docs.giswater.org/master/en/docs/giswater/for-users/dialogs/check-project.html)

## Ручная карточка: минимальный состав

Это шаблон, **не заполненный протокол проверки L-003**. Для всех фактических полей ниже состояние в настоящем исследовании — «не наблюдалось».

| Поле | Что записать |
|---|---|
| Цель | Ненулевой Save, no-op, подтверждение состояния или отдельная оценка |
| Контекст | Экземпляр/редакция, WorkOrder, EditVersion, запись и отображаемый label |
| Предмет проверки | Свойство, объекты/участки, baseline/current/candidate |
| Ожидание | Значение, источник и редакция паспорта/правила |
| Наблюдение | Значение, способ получения, доступный контекст версии и время |
| Метод | Конкретная проверка и её параметры; визуальная/структурная/позиционная не смешиваются |
| Результат | Соответствует; установленное несоответствие; не проверено; обоснованно не применимо |
| Охват и исключения | Что проверено, что не входило; фильтры, доступ, неполная выдача |
| Координатное происхождение | Известная операция/ресурсы или явно неизвестная история |
| Итог | Допуск конкретной ветки, ограничения и условия пересмотра |
| После действия | Исход операции отдельно от актуального чтения и downstream-приёмки |

Это язык ручной процедуры, не схема БД и не новое перечисление API. Поля заполняются только доступными свидетельствами. Неизвестность не подменяется синтетическим нулём или придуманным revision.

## Аналитическая матрица пограничных сценариев

Матрица описывает ожидаемые решения условной организации. Это не протокол исполненных тестов.

| Ситуация | Вывод | Допустимое продолжение |
|---|---|---|
| Имя совпало, экземпляр не установлен | Допуск не доказан | Установить контекст или явно подготовить другой экземпляр |
| В старом volume две вершины | Ветка движения средней вершины не подходит | Отдельная fixture; baseline не чинить |
| Линия имеет четыре вершины | Возможное ограничение UI | Другой пример или отдельная задача расширения |
| Settings новые, persisted policy прежняя | Нужна сверка, не автокоррекция | Работать по действующим правилам версии |
| Tolerance не представлена контрактом | Не ноль | Описать ограничение и его значимость |
| Наблюдались endpoints, середина не проверена | Частичный охват | Не заявлять проверку всей линии |
| Проверка дала zero errors только в extent | Результат ограничен этой проверкой | Не объявлять всю сеть проверенной |
| L-003 не видна из-за фильтра | Нет доказательства отсутствия | Проверить фильтр/слой/контекст |
| Push выполнен, apply job не завершён | Доставка установлена, применение нет | Установить исход обработки |
| Импорт изменил fid/число знаков | Нужна проверка представления и identity | Не переносить допуск по имени файла |
| Current равен candidate | Нет ненулевой правки | Выбрать честную ветку no-op/соответствия |
| Replay старого Save успешен, current новее | Исторический исход и новое состояние совместимы | Не восстанавливать старый UI как current |
| Save успешен, измеренного эталона нет | Технический результат, positional unverified | Передать ограничения |
| Изменён AOI/отозван источник | Переоценка применимости | Не автоматический Revert |

## Решение для ingest

Уточнить существующие [[Wiki/concepts/field_observation_acceptance]], [[Wiki/concepts/assessment_statement_lifecycle]], [[Wiki/concepts/dataset_instance_and_record_identity]], [[Wiki/policies/demo_dataset_qualification_policy]], [[Wiki/specifications/demo_dataset_instance_qualified]] и [[DDD_Wiki/use_cases/prepare_and_check_line_edit]]. Новые понятия не создавать там, где уже сохранены scope, provenance и разделение доставки/приёмки.

Правила приняты для условной организации. Гипотезы автоматизации карточки, нового journal или общей multi-service orchestration в scope не включаются. Два вопроса metadata/fixture, 19 follow-up и stale model health не закрываются. Код, конфигурация, миграции и тесты не изменяются.
