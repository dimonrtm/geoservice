# Release 2 после Ф8

Отвечаю как архитектор enterprise GIS для инженерных сетей, который проектирует workflow-и для authoritative network editing, versioning и audit в utility-среде.

## Исходная рамка решения

Загруженный файл описывает **Utility GIS editor** не как узкую фичу, а как слой над **authoritative network model** с branch versioning, reconcile/post, conflict resolution, полевыми и офисными ролями, а также с явным пробелом в части role model, audit, data governance и product blueprint. Иначе говоря, сам файл полезен как **рамка use case**, но не как готовая спецификация Release 2. Поэтому implementation contract нельзя честно «вынуть» прямо из файла; его нужно собирать из двух источников: из этого use case-фрейма и из доменных ограничений utility network workflow в ArcGIS/utility-практиках. fileciteturn0file0

Доменные документы Esri задают несколько жёстких фактов, которые сильно сужают правильный дизайн Release 2. Во‑первых, edits по geometry, associations, network attributes и terminal configuration создают **dirty areas**; пока topology не validated, analytic operations, включая trace, могут давать результаты, не соответствующие текущему виду сети. Во‑вторых, trace имеет смысл только на валидированной topology, а опция **Validate Consistency** — единственный способ гарантировать, что trace не проходит через dirty areas. В‑третьих, reconcile и post — это разные шаги: reconcile только обновляет edit version и обнаруживает/разрешает conflicts, а post разрешён только если target version не изменился после reconcile; иначе требуется reconcile again. В‑четвёртых, update subnetwork может пометить subnetwork controller как **Invalid**, если обнаружены consistency failures или subnetwork errors. citeturn5view0turn6view3turn9view0turn14view0turn10view0

Это приводит к ключевому выводу: **Release 2 логично фиксировать как decision-support и control layer вокруг reconcile → consequence package → review → post**, а не как новый движок conflict resolution. Такой вывод согласуется и с рынком: mature network-editing продукты комбинируют network model с workflow / work management / version-control слоем, а не пытаются подменить базовый движок сетевой модели. Bentley прямо описывает встроенный utilities GIS, configurable workflow engine и связь с work management, а NextGIS — version control, full history, snapshots, API и on-prem execution как часть collaboration stack. citeturn17view1turn20view1

## Что уже можно фиксировать в implementation contract

**Главное решение Release 2 уже можно зафиксировать.** Первичный decision в Release 2 — это не «conflict resolution» и не full routing engine, а **approval of change package as a pre-post gate**. Иначе: Editor по-прежнему разрешает конфликт в native edit workflow, а Release 2 формирует consequence package и помогает принять human decision о том, можно ли допускать пакет дальше. Routing/escalation — это производный outcome, а не центральная сущность контракта. Такой выбор лучше всего соответствует тому, что reconcile/post у Esri уже отделяет conflict handling от фактического post, а файл описывает пробелы именно в workflow, audit и role boundaries, а не в базовой геометрической операции merge. fileciteturn0file0 citeturn6view1turn14view0turn17view1

**Момент, когда Reviewer получает работу, тоже уже можно фиксировать.** Reviewer должен получать пакет **после reconcile** и после сборки consequence package на снимке, где уже известны Base / Mine / Default различия, association delta и состояние dirty/validation/subnetwork freshness. Если после reconcile остались dirty areas в критическом пути, inconsistent trace или invalid subnetwork, это не «готово к review» в содержательном смысле, а состояние **blocked**. Причина проста: trace и другая аналитика не гарантированно отражают сеть, пока topology не validated, а reconcile сам по себе не означает, что пакет безопасно готов к post. citeturn5view0turn6view3turn9view0turn10view0turn14view0

**Минимальный пакет входа для решения тоже уже достаточно ясен.** Для первого implementation contract минимальный conflict package должен включать:
Base / Mine / Default snapshot; geometry diff; association delta; dirty areas; validation/topology status; trace result с Consistency/Freshness status; subnetwork status там, где подмножество сети зависит от subnetwork semantics; work order / change request id; explanatory comments / history; а field evidence — как обязательный input только для High/Critical или когда без него нельзя объяснить, почему Editor выбрал конкретный resolution. Это вытекает из того, что utility network semantics живут не только в geometry, но и в associations, network rules, containment, attachment, trace behavior и subnetwork status. fileciteturn0file0 citeturn12view3turn11view0turn11view1turn11view2turn10view3turn9view0turn10view0

**Что Reviewer должен увидеть первым, тоже уже можно зафиксировать.** Первый экран пакета должен давать не «красивый diff», а четыре факта в таком порядке:
изменилось ли connectivity/association semantics; есть ли dirty/validation blockers; изменилась ли trace/subnetwork интерпретация; и свеж ли текущий approval snapshot относительно Default. Это важнее, чем raw geometry, потому что Esri прямо показывает: associations моделируют connectivity, containment и structural attachment; containment и internal content могут менять trace outcome; structural attachment обычно не переносит ресурсный flow; dirty areas делают trace ненадёжным; а posting после изменения target version требует reconcile again. citeturn12view3turn11view0turn11view1turn11view2turn6view3turn14view0

**Approve и “можно отправить на post” нужно фиксировать как два разных шага.**
Approve = reviewer согласен с change package и тем, как объяснено сетевое последствие.
Can post = у пакета нет hard blockers, approval не stale, и target/default state не ушёл вперёд после reconcile/approval.
Они не должны сливаться в одно состояние, потому что ArcGIS допускает ситуацию, когда reconcile уже выполнен, но post запрещён, если target version изменился после reconcile; кроме того, dirty areas, invalid subnetworks и inconsistent trace делают «одобрено» и «можно постить» разными по смыслу решениями. citeturn14view0turn5view0turn6view3turn10view0

**Hard blockers для implementation contract тоже уже можно описать без реального пользователя.** В контракт стоит фиксировать как absolute veto: unresolved association delta; dirty areas на trace path или отсутствующий validated topology для требуемой области; invalid subnetwork / update-subnetwork failure для релевантного tier; stale approval после нового reconcile или после обновления target/default state; missing mandatory evidence для High/Critical; unexpected trace impact, который не объяснён или не подтверждён. Эти блокеры опираются на documented behavior utility network: associations влияют на connectivity/containment/attachment semantics, dirty areas делают analytic results inconsistent, а subnetwork update может переводить состояние в Invalid. citeturn12view3turn11view0turn11view2turn5view0turn6view3turn9view0turn10view0

**Stale semantics тоже уже достаточно созрели для контракта.** Всё, что в ArcGIS создаёт dirty areas или меняет смысл trace/subnetwork, разумно считать invalidate trigger для предыдущего approval/package: geometry edits; association edits; network-attribute changes; terminal configuration changes; validation result changes; reconcile against changed target/default; subnetwork status changes. Это не догадка из воздуха: именно эти категории Esri перечисляет как источники dirty areas и inconsistency между edits и network topology. citeturn5view0turn6view3turn14view0turn10view0

**Минимальный audit object также уже можно заморозить.** Туда стоит включить: package id; version ids / snapshot ids для Base-Mine-Default; computed risk tier; blockers list; evidence completeness flags; trace/subnetwork freshness snapshot; decision; actor role; timestamps; stale events; final post outcome; и ссылку на reconcile log / technical log. Это логично и из product side, и из доменных примитивов: dirty areas already store feature/edit/editor context, а Reconcile Versions умеет писать log file с содержимым geoprocessing messages. citeturn5view0turn6view1

## Что остаётся design-гипотезами и что реально блокирует контракт

Есть решения, которые **не стоит притворяться готовыми** до real Editor/Reviewer validation. Самая большая группа гипотез — это **risk tier calibration**. Уже можно зафиксировать саму идею tiering и hard blockers, но нельзя уверенно зафиксировать тонкую границу между Normal / High / Critical, пока реальные пользователи не скажут, где для них проходит линия между «решаю сам», «нужен reviewer» и «нужен профильный специалист». Доменные документы подтверждают, что не всякая association/structure/container change равна по operational effect: structural attachment обычно не является частью resource flow, containment само по себе не несёт поток, но внутренние устройства в контейнере могут менять trace behavior, а connectivity associations напрямую моделируют связь. Значит, rule “любое trace change = Critical” выглядит слишком грубо и пока остаётся гипотезой. citeturn11view0turn11view1turn11view2turn9view0

Вторая группа гипотез — **role authority model**. В частности, ещё нельзя без полевой проверки окончательно зафиксировать:
должен ли High-tier reviewer принимать финальное решение сам или лишь подтверждать proposal Editor; может ли безопасный Normal идти через audit + sample review; кто final owner authoritative state для Critical; обязателен ли specialist sign-off при любом service/subnetwork/safety impact. Файл сам показывает, что текущая документация не разворачивает полноценную модель ролей и governance, а значит эти части сейчас честнее держать как design hypotheses, а не как будто уже «известные требования». fileciteturn0file0

Третья группа гипотез — **UX-формат repeat review и field evidence sufficiency**. Мы можем рекомендовать repeat review показывать “delta since previous approval” плюс one-click access к full package, но нельзя утверждать, что этого достаточно для доверия reviewer. Точно так же нельзя сейчас объявлять жёсткий universal rule, что field evidence обязательно именно в таком-то объёме: это зависит от utility domain, risk tier и от того, насколько убедителен computed consequence package. На рынке collaboration/network platforms действительно важны workflow, history, auditability и work context, но конкретная достаточность evidence — это уже пользовательская калибровка, а не голая доменная инварианта. citeturn17view1turn20view1

Из этого следует важное различие между **open questions вообще** и **open questions, которые реально блокируют implementation contract**. Реально блокируют контракт только пять вещей:
кто владелец финального решения для Critical; какая evidence-matrix обязательна по tier; какие exact events переводят approval в stale; где проходит MVP boundary между read-only decision support и action buttons; и какие интеграции гарантированно доступны в demo/runtime для work order и trace/subnetwork data. Всё остальное — например, sample review policy для Normal, specialist escalation UX, SLA queue, batch review — можно вынести в ADR candidates и не задерживать первый контракт. fileciteturn0file0 citeturn9view0turn10view0turn17view1

## Какие RAW inputs должны появиться после Ф8 и как обновить документацию

После Ф8 должны появиться не только выводы, но и **сырые артефакты**, иначе implementation contract останется narrative-документом без проверяемой базы. Минимальный набор RAW inputs я бы фиксировал так:
fixture checksum / seed; canonical scenario dataset; Base-Mine-Default snapshot ids; computed geometry diff; computed association delta; dirty area snapshot; validation result; trace result with consistency flag; subnetwork status snapshot; blocker list; risk-tier output; decision outcome; stale event log; audit object JSON; timing metrics по package build / evidence load / stale invalidation / audit save. Это напрямую вытекает из доменной природы проблемы: без raw snapshots по dirty areas, trace consistency и subnetwork freshness невозможно воспроизвести, почему пакет был approved, blocked или признан stale. citeturn5view0turn6view3turn9view0turn10view0turn6view1

С существующей документацией **нет жёсткого прямого конфликта**, но есть два важных tension points. Первый: загруженный файл — это use case / market-context документ, а не release-specific spec, поэтому новые решения нужно вносить как **additive design layer**, а не как будто они уже были зафиксированы. Второй: native ArcGIS branch workflow по умолчанию может разрешать conflicts в пользу edit version, тогда как Release 2 вводит отдельный human approval gate перед post. Это не противоречие, но это надо явно описать в документации как **надстройку над native reconcile/post**, а не замену native conflict engine. fileciteturn0file0 citeturn6view1turn14view0

После этого ответа я бы обновил следующие wiki-ноды.
**Release 2 Scope** — чтобы явно зафиксировать, что центральный decision равен approval of change package, а не full conflict engine.
**Consequence Package Schema** — чтобы заморозить обязательные поля пакета.
**Risk Tiers and Veto Blockers** — чтобы отделить contract-ready blockers от validation hypotheses.
**Reviewer Decision Model** — чтобы развести approve, block post, escalate и stale repeat review.
**Audit Object Schema** — чтобы run schema и audit schema не расходились.
**Demo Fixtures and Canonical Scenario** — чтобы Ф8 и implementation contract опирались на один и тот же dataset.
**Real Validation Plan** — потому что часть решений сознательно остаётся hypothesis until user validation. fileciteturn0file0 citeturn5view0turn9view0turn10view0

## Acceptance gates, формат контракта и допустимый demo claim

Перед реализацией я бы ввёл **четыре acceptance gates**.
Первый — **contract gate**: frozen state machine, package schema, blocker semantics и stale triggers.
Второй — **safety gate**: canonical scenario и stale/pre-post sidecar обязаны воспроизводимо показывать hard blockers; unacceptable false-safe case здесь должен быть абсолютным veto.
Третий — **observability gate**: каждый run должен сохранять package id, inputs checksum, blockers, freshness snapshots, decision и audit object.
Четвёртый — **validation gate**: любые claims сильнее “helps explain/detect/block” запрещены до реальных Editor/Reviewer sessions. Такой порядок оправдан доменно: trace consistency, dirty areas, target version drift и invalid subnetworks — documented reasons, по которым система может выглядеть «почти готовой», но быть небезопасной к post. citeturn6view3turn9view0turn10view0turn14view0

**Допустимый demo claim без user validation** я бы формулировал так:
*«В developer demo Release 2 собирает consequence package для utility-network конфликта, делает видимыми hard blockers и помогает сформировать более обоснованное go/no-go решение перед post на synthetic scenario.»*
Это допустимо, потому что оно обещает explanation, blocker visibility и decision support.
**Недопустимая формулировка** выглядела бы так:
*«Release 2 обеспечивает safe post», «снижает ошибки в production», «заменяет reviewer», «доказывает корректность authoritative state».*
Такие claims требуют реального пользовательского и operational validation, а не только synthetic rehearsal. fileciteturn0file0 citeturn6view3turn14view0

**Формат implementation contract** лучше делать не как длинный PRD, а как короткий **ADR-style Markdown contract** с machine-readable appendices. Практически это должен быть один основной документ плюс приложения в YAML/JSON. В основной части — scope, actors, states, events, decision semantics, blockers, stale rules, non-goals, acceptance gates. В приложениях — package schema, audit schema, API/events, fixture manifest, P95 targets и observability fields. Такой формат лучше удерживает границу между тем, что уже фиксируется, и тем, что пока остаётся hypothesis/ADR candidate. Рынок collaboration/network tools тоже показывает, что без явной схемы history/version/workflow быстро появляется разрыв между UX-обещаниями и техническими артефактами. citeturn17view1turn20view1

**Из run schema в audit object нужно переносить не всё, а именно доказательные поля.** Я бы включил: package_id; scenario_id; seed/checksum; source snapshot ids; risk_tier; blockers[]; trace_consistency flag; subnetwork_status; evidence_completeness; actor_role; decision; timestamps; stale_events[]; manual_checks_count; final_post_outcome. А вот низкоуровневые performance counters, технические stack traces и дебажные поля лучше держать в observability/log stream, а не в пользовательском audit object. Это соответствует и доменной стороне, и тому, что reconcile уже умеет писать отдельный log, а dirty areas/trace/subnetwork дают семантические, а не только технические сигналы. citeturn6view1turn5view0turn9view0turn10view0

**Отдельный real validation checklist нужен обязательно.** Причина простая: synthetic demo может доказать воспроизводимость blockers и корректность state machine, но не может доказать, что Editor/Reviewer действительно понимают consequence package быстрее, реже уходят во внешнюю GIS и доверяют risk tier wording. Это именно тот тип знания, которого нет ни в загруженном файле, ни в официальной документации движка. fileciteturn0file0

## Что делать дальше после Ф8 и что остаётся non-goal

**Три следующих шага после Ф8** я бы зафиксировал так.
Сначала — выпустить **implementation contract v0.1** со frozen scope: states, blockers, stale rules, package schema и audit schema.
Затем — собрать **walking skeleton demo** на одном canonical transformer/service-device association case и одном stale/pre-post failure sidecar.
Потом — провести **real validation mini-round** с Editor/Reviewer по отдельному checklist, не меняя базовую архитектуру, а проверяя только risk wording, evidence sufficiency и trust in blocker verdict. Такой порядок минимизирует риск уйти в красивую архитектурную фантазию раньше, чем проверена decision usefulness. citeturn11view0turn9view0turn10view0turn14view0

**Что явно остаётся non-goal** для первого implementation contract:
не строить новый topology engine; не достигать full ArcGIS parity; не делать full in-product conflict editing UI; не делать batch review queue и SLA routing; не делать production-grade on-prem hardening; не обещать authoritative-safe post без real validation. Это следует и из файла, который сам признаёт отсутствие полного product blueprint, и из доменной архитектуры utility network, где correctness держится на базовом network/topology engine, а не на поверхностном reviewer-UI. fileciteturn0file0 citeturn5view0turn9view0turn10view3

**Follow-up’ы стоит разнести на три корзины.**
Нужно **закрыть сейчас**: формат implementation contract, пакет обязательных полей, hard blockers, stale semantics, audit object minimum.
Нужно **объединить**: вопросы про risk tiers, specialist escalation и reviewer authority в один ADR “Decision ownership and escalation matrix”; вопросы про stale approval и repeat review — в один ADR “Freshness and re-review semantics”.
Нужно **оставить long-term**: batch queue, SLA, analytics over many packages, external GIS deep embed, broader non-Esri comparison, storage hardening და enterprise rollout concerns. Иначе Release 2 расползётся раньше, чем будет доказана базовая ценность consequence-first review. fileciteturn0file0 citeturn17view1turn20view1

**Короткий 2-минутный demo narrative** я бы сделал таким.
Editor после reconcile открывает canonical transformer/service-device conflict. Вместо обычного geometry diff он сразу видит: что изменили Mine и Default; какие associations изменились; есть ли dirty areas; свежа ли topology; как поменялся trace; затронут ли subnetwork status. Система не притворяется «всезнающей», а честно показывает одно из трёх состояний: *safe to self-resolve*, *needs reviewer*, *blocked pre-post*. Затем Reviewer открывает тот же package, видит короткое consequence summary и принимает only-one-click decision: approved package, return to editor, or escalate. После этого демонстрируется stale sidecar: Default изменился или пакет был reconciled повторно, прежний approval помечается stale, UI показывает delta since approval, audit фиксирует stale event и final post outcome. За две минуты демонстрация должна доказать одну вещь: **путь от “вижу конфликт” до “понимаю сетевое последствие и следующую безопасную операцию” стал короче и явнее, чем в raw Conflicts/Differences view**. citeturn11view0turn12view3turn6view3turn9view0turn10view0turn14view0

## Итоговая позиция

Если свести всё к одному выводу, то **к implementation contract уже готовы**: scope Release 2 как pre-post decision-support layer; момент handoff после reconcile/package build; minimal package schema; разделение approve и can-post; absolute veto blockers; stale invalidation semantics; minimal audit object; canonical demo with one main scenario plus one stale sidecar. Это уже достаточно опирается на файл и на domain constraints utility network workflow. fileciteturn0file0 citeturn5view0turn9view0turn10view0turn14view0

**До real Editor/Reviewer остаются гипотезами**: точная risk calibration, authority matrix for High/Critical, sample review policy for Normal, evidence sufficiency thresholds, repeat-review UX detail и language of trust. Поэтому правильная формула сейчас такая: **freeze the contract around states, blockers and artifacts; validate the human layer separately; do not overclaim safety.** fileciteturn0file0
