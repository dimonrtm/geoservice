# Ближайший полноценный инкремент после открытия workspace

## Основание для решения

Отвечаю как архитектор корпоративных ГИС для инженерных сетей и workflow‑систем редактирования авторитетной network model.

Загруженный файл трактует целевой сценарий не как обычное веб‑редактирование карты, а как работу с авторитетной моделью инженерной сети: изолированные рабочие версии, reconcile/post, conflict resolution, полевой и офисный контур, а также контроль качества изменений. Это важно, потому что следующий инкремент должен строиться не вокруг “ещё одной формы редактирования объекта”, а вокруг минимально целостного change workflow внутри edit version. fileciteturn0file0

Официальная документация Esri по branch versioning подтверждает ту же основу: work orders и jobs обычно ведутся как отдельные named versions; branch versioning отслеживает insert, update и delete в named version; branch‑versioned data редактируется через web feature layer; reconcile и post работают уже поверх реально сохранённых изменений, а не поверх черновых UI‑состояний. Для utility network аналитические операции зависят от валидной network topology, а dirty areas, associations, network attributes и terminal configuration — это не “второстепенные детали”, а источники последствий для сетевого поведения. citeturn5view1turn5view0turn4view2turn4view3turn8view0turn8view3

## Почему первым должен быть именно persisted edit slice

Branch versioning в ArcGIS строится вокруг дискретной единицы работы — work order, job, project — которая изолируется в named version. После этого система отслеживает реальные insert/update/delete и только затем позволяет reconcile, conflict review и post. Из этого следует довольно жёсткая инженерная логика: пока у workspace нет собственного write path, у продукта есть экран рабочей области, но нет самого “редактирования версии” как доменного действия. citeturn5view1

Поэтому первый полноценный инкремент после открытия workspace — не submit и даже не review‑draft, а **сохранённое изменение существующего объекта**. В практическом смысле это означает: пользователь открывает work order, открывает edit version, вносит изменение в geometry и/или разрешённые атрибуты, сохраняет, а затем сразу получает readback в том же workspace с корректным `operation=updated`, временем изменения, actor, diff summary и обновлённым `base_network_revision`/workspace revision marker. Только после этого уже можно честно говорить о validate, draft evidence и submit. citeturn5view1turn5view0

Выбор именно **update существующего feature** как первого обязательного mutation path тоже не случаен. Для utility network любые изменения geometry, associations, network attributes и terminal configuration порождают dirty areas и могут менять то, что хранится в network topology. Но create/delete и особенно association edit лезут в более дорогие классы последствий: жизненный цикл новых объектов, шаблоны создания, referential effects, container/content relations, rule enforcement и восстановление UI‑состояния после ошибок. Напротив, update existing feature даёт минимально достаточную техническую сложность и при этом уже является “настоящим” utility edit. citeturn4view2turn8view0turn8view3

## Как строить write path, API и модель состояния

Для workspace‑mode я бы не использовал generic `saveFeature/deleteFeature` как публичный контракт. В ArcGIS branch‑versioned data редактируется через web feature layer в контексте конкретной версии, а named version имеет собственные ограничения, права и дальнейший reconcile/post lifecycle. Поэтому внешний контракт должен быть version‑scoped: например, `PatchWorkspaceFeature`, `CreateWorkspaceFeature`, `DeleteWorkspaceFeature`, а позже — `SubmitEditVersion`. При этом внутри реализации совершенно нормально переиспользовать существующий низкоуровневый код изменения geometry/attributes, если он уже есть. citeturn5view1turn5view0

По той же причине новый write path разумнее выделить в отдельный command‑side сервис, а не распухать `WorkOrderRepository`. Сейчас `WorkOrderRepository` уже логически связан с открытием edit version и сборкой workspace aggregate. Команда сохранения должна отвечать за optimistic concurrency, проверку editability, запись changed rows, вычисление `operation`, доменную валидацию черновика и, позднее, подготовку change set для submit. Это отдельная причина завести либо `EditVersionCommandService`, либо `EditWorkspaceRepository`, а `WorkOrderRepository` оставить query‑ориентированным. Такая граница лучше совпадает с file‑трактовкой продукта как workflow вокруг авторитетной network model, а не вокруг простого экранного CRUD. fileciteturn0file0 citeturn5view1

По статусам сейчас выгоднее **не спешить с новыми durable review states**. Если reviewer backend ещё отсутствует, `submitted` и `in_review` будут “красивыми, но пустыми” состояниями. Более практичный шаг — оставить `assigned/in_progress` и `EditVersionStatus=open`, а readiness для следующего шага считать предикатами: есть ли изменения, прошла ли draft validation, есть ли stale marker, заполнен ли editor summary. Когда появится реальный submit endpoint и пакет на review, тогда `submitted` станет честным доменным событием. citeturn5view1turn5view0

Проверку freshness тоже стоит разделить на **informational** и **authoritative** уровни. На открытии workspace полезно показать, совпадает ли его `base_network_revision` с текущим revision маркером Default, чтобы editor сразу видел вероятность устаревания. Но реальный blocking check должен выполняться прямо перед submit, потому что Default может измениться в любой момент: Esri прямо указывает, что изменения в target/default после reconcile и до post требуют повторного reconcile, а utility network re‑creates dirty areas при reconcile и может потребовать дополнительной валидации до следующего шага. citeturn5view0turn4view2

Если выбирать **один следующий endpoint**, то это должен быть version‑scoped PATCH на feature update. С точки зрения ценности он закрывает самую большую техническую дыру: после него уже можно строить draft validation, change set summary и smoke с readback. Напротив, `POST submit-for-review` или `GET review-package-draft` раньше write path будут опираться на искусственные состояния. citeturn5view1

## Как минимально вводить ReviewPackage и Reviewer

`ReviewPackage` не стоит моделировать первым артефактом. Его минимально правильное появление — **после того, как есть persisted change set**. В branch workflows конфликтный и review‑related state в ArcGIS хранится отдельно и может переживать сессии, но review notes очищаются на следующем reconcile/post. Это хороший ориентир: до submit summary/evidence должны жить как draft внутри edit session, а в момент submit превращаться в устойчивый snapshot, который уже можно независимо читать и аудировать. citeturn7view2turn5view0

Поэтому до появления reviewer backend summary и evidence лучше хранить прямо в `EditVersion`: короткий editor summary, список evidence items, maybe attachment refs, поля completeness. Когда появится submit, система создаёт `ReviewPackage v0.1` как **materialized snapshot**: changed features, before/after summary, operation, validation outcome, freshness marker и ссылки на исходные `edit_version_features`. Такой подход одновременно даёт устойчивость для reviewer и не заставляет преждевременно строить отдельный authoring‑aggregate для review до появления change set. citeturn7view2turn5view1

Первый reviewer‑инкремент я бы делал **не как очередь**, а как **detail view одного review package**. Это совпадает и с логикой ArcGIS Conflicts view, который начинается с разбора конкретных конфликтов конкретной named version, и с реальным риском раннего продукта: пока непонятно, достаточно ли объясняется consequence и хватает ли evidence, очередь лишь добавит routing‑слой, не доказав ценность decision surface. Detail‑first slice проще, честнее и полезнее для API stabilization. citeturn7view2

Ассоциации в этом первом reviewer slice должны быть **read‑only evidence**, а не mutation‑поверхностью. Причина прямая: associations моделируют connectivity, containment и structural attachment, создаются и проверяются under network rules, а их изменение влечёт dirty areas и сетевые последствия. До тех пор пока нет отдельного надёжного command path c rule enforcement и ошибками locatability/association rules, reviewer должен их видеть, но не редактировать. citeturn8view0turn4view2

## Что валидировать сейчас и что сознательно отложить

До reconcile, trace и subnetwork management можно сделать вполне полезную **draft validation**, но она должна оставаться честно ограниченной. В минимальный набор входят geometry validity, required fields, доменные значения и subtype/asset type checks, AOI containment, operation completeness и базовая editable‑policy проверка. Всё это полезно до topology engine и не притворяется сетевой аналитикой. Одновременно документация Esri подчёркивает, что network analytic operations полагаются на validated topology, а trace results не гарантируются при наличии dirty areas; более того, subnetwork traces зависят от subnetwork definition, terminal paths и чистого/валидного subnetwork state. Значит, трассировку, subnetwork health и post‑level safety нельзя честно “симулировать” уже на этом шаге как будто они готовы. citeturn4view2turn4view3turn8view1turn8view2turn8view3

Именно поэтому за пределы ближайшего спринта разумно вынести `can_post`, simulated post, полноценный audit object reviewer decision, risk tiers, trace/subnetwork evidence и reviewer queue. Все эти вещи реальны и нужны, но они стоят **после** появления базового persisted change set и draft validation. Иначе команда начнёт проектировать слои, которые в коде будут выглядеть убедительно, но будут стоять на пустом основании. citeturn5view0turn4view2turn8view1turn8view2

Практически это означает такую walking skeleton‑последовательность: открыть “assigned to me”, открыть edit version, изменить один existing feature, сохранить, получить readback и operation summary, запустить draft validation, увидеть readiness flags. Только после этого следующим шагом имеет смысл добавлять submit и snapshot ReviewPackage. С точки зрения smoke‑покрытия приоритет должен получить **edit‑save‑readback**, а не submit‑mock, потому что именно он впервые доказывает, что workspace перестал быть read‑only витриной и стал доменной рабочей областью. citeturn5view1turn5view0

## Итоговое решение для implementation focus

Если свести всё к одному инженерному приоритету, то ближайший вертикальный срез должен быть таким: **workspace → update existing feature in named version → persist `operation=updated` → readback diff → draft validation flags**. Это самый маленький, но уже настоящий кусок utility editing workflow, который опирается и на загруженный файл, и на реальную логику branch versioning и utility network в ArcGIS. fileciteturn0file0 citeturn5view1turn4view2turn4view3

Из этого следуют конкретные архитектурные решения. Сначала нужен version‑scoped write API и отдельный command‑side слой для workspace edits. Первая обязательная mutation — update existing feature, а не create/delete/association edit. Новые review‑статусы пока не добавляются; вместо них вводятся readiness predicates. Draft summary/evidence живут в `EditVersion`, а `ReviewPackage` появляется позже как snapshot поверх persisted change set. Проверка stale/default freshness должна блокировать именно submit, а не только открытие workspace. Associations в первом review — read‑only evidence. Валидация пока ограничивается geometry/form/AOI/policy rules. Всё, что связано с `can_post`, trace/subnetwork safety, risk tiering и полноценным reviewer decision audit, нужно сознательно отложить до следующего слоя, а не подменять фиктивной полнотой. citeturn5view0turn7view2turn8view0turn8view1turn8view2

В более короткой формулировке: **сейчас надо доказать, что workspace умеет создавать настоящий change set; review domain имеет смысл только после этого**. citeturn5view1turn7view2
