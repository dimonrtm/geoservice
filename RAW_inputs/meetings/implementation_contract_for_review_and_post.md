# Решения для implementation contract по review и post в Utility GIS

## Опорная интерпретация домена

Отвечаю как архитектор корпоративных ГИС для инженерных сетей с фокусом на branch versioning, utility network governance и безопасную публикацию изменений в authoritatively managed сети.

Ваш файл трактует Utility GIS editor не как обычный редактор карты, а как редактор **authoritative network model** с branch versioning, reconcile/post, ролями review/approve/publish, топологической связностью и эксплуатационным жизненным циклом work order → edit → review → publish. При этом сам файл прямо признаёт, что модель ролей, data governance и audit в нём пока не доведены до полного продуктового blueprint, поэтому на вопросы ниже нужно отвечать не «по названию релиза», а через **целевую operating model** и **ближайший вертикальный срез**. fileciteturn0file0

В ArcGIS branch versioning есть две принципиально разные модели доступа к Default. Если Default публичный, редакторы могут постить из named versions сами; если Default **protected**, постить в него может только **version administrator**. В той же документации отдельно показан QA/QC-сценарий, где editor заканчивает edits, передаёт version ownership администратору, и именно version administrator завершает reconcile/post в защищённый Default. Это очень сильный аргумент в пользу отделения семантического review от технического PostToDefault. citeturn19view1turn19view0turn19view2

Технически domain риска здесь определяется не самим конфликтом строк/геометрий, а тем, что в utility network изменения в **geometry, associations, network attributes и terminal configuration** создают dirty areas, а dirty areas означают, что topology ещё не отражает актуальное состояние сети; trace через такие участки может дать невалидный результат, а subnetwork update при consistency failures и subnetwork errors может закончиться invalid status. Поэтому в договорённостях по review/post нельзя жить только на diff-экране; нужен package с consequence-aware evidence и строгими veto-условиями. citeturn11view2turn11view3turn22view2turn22view1turn20view1turn9view0

## Роли и ownership post

**Кто владелец PostToDefault в целевой модели.** Рекомендуемый вариант один: **Publisher — отдельная техническая роль**. Reviewer принимает решение о допустимости change package с точки зрения сетевого риска и достаточности evidence. Publisher владеет именно **операцией интеграции в authoritative Default** и отвечает за финальную техническую проверку freshness, blockers и права на post. Data Owner в этой схеме не «жмёт post» и не выполняет reconcile/post как рутинную операцию; его зона — policy, risk matrix и делегирование полномочий. Такая граница лучше всего согласуется и с вашим файлом, где approve/publish разведены как отдельные роли, и с branch versioning-паттерном Esri, где при protected Default пост принадлежит version administrator, а не обычному editor/reviewer. fileciteturn0file0 citeturn19view1turn19view0turn19view2

**Кто фактически выполняет post в ближайшем срезе.** Для ближайшего среза я бы зафиксировал так: **семантически post разрешает Reviewer, а фактически выполняет demo-system action после approval**. Это позволяет не тащить отдельную human-role механику Publisher в самый первый workflow slice, но уже сейчас сохранить правильную границу ответственности: Reviewer не становится владельцем authoritative state, а system action лишь имитирует технического Publisher. В целевой модели этот system action должен быть заменён на отдельного Publisher или Version Administrator. fileciteturn0file0 citeturn19view1turn19view0

**Почему Reviewer не должен одновременно быть Publisher по умолчанию.** Если смешать эти роли, вы теряете важную двухступенчатую защиту: reviewer decision перестаёт быть осмысленным review package verdict и превращается в «сразу влил в Default». Это особенно опасно потому, что в публичном Default у branch versioning нет conflict detection на прямом редактировании, и последний update может просто перезаписать предыдущий. Поэтому безопасная модель — защищённый Default, reviewer approval как семантическое решение и отдельный технический post gate. citeturn19view2turn19view1

**Кто является обязательным вторым контролем по уровням риска.** Для Normal обязательного второго контроля не нужно; для High тоже не нужен обязательный второй контролёр, если evidence полный и Reviewer может принять решение сам; для Critical обязателен **профильный специалист**. Utility-network admin не должен быть стандартным вторым контролем для каждого Critical случая: его надо привлекать только там, где проблема похожа на нарушение rule/configuration/topology governance, а не на доменную semantics-ситуацию. Data Owner тоже не должен быть рутинным вторым контролем; он нужен только для governance override или policy exception. Такая матрица соответствует доменной логике utility network: Critical должен означать возможное изменение service/subnetwork/safety semantics, а это именно профильная, а не административная экспертиза. citeturn20view1turn22view2turn22view1turn9view0

**Матрица полномочий по уровням риска.**

| Уровень риска | Кто принимает основное решение | Обязательный второй контроль | Кто выполняет post |
|---|---|---|---|
| Normal | Reviewer или policy-driven safe path | никто | system action в ближайшем срезе; далее Publisher |
| High | Reviewer | никто по умолчанию | system action в ближайшем срезе; далее Publisher |
| Critical | Reviewer не единолично; решение подтверждается профильным специалистом | профильный специалист | system action в ближайшем срезе; далее Publisher |

Эта матрица опирается на то, что associations и terminal-aware connectivity влияют на traversability, trace и subnetwork behavior, а защищённый Default в Esri-паттерне должен поститься привилегированной role, а не тем же пользователем, кто делал обычное review. citeturn20view1turn15view0turn19view1turn19view0

## Ближайший вертикальный срез

**Что обязательно нужно сделать в ближайшие 14 дней.** В must я бы поставил шесть вещей: **узкий ReviewPackage aggregate**, **минимальный evidence package**, **трёхуровневый risk tier**, **hard blockers с absolute veto**, **stale approval policy на ограниченном наборе событий** и **audit с двумя решениями — approve package и can post**. Без этих элементов получится либо красивый diff-экран без безопасного перехода к post, либо workflow без проверяемого ownership и repeat review. Это напрямую следует из того, что dirty areas, reconcile/post и subnetwork validity уже сейчас делают «простое согласование diff» недостаточным. fileciteturn0file0 citeturn11view2turn18view4turn22view2turn22view1turn19view1

**Что можно отложить.** В later я бы оставил автоматическое routing к конкретным specialist-профилям, rich consequence explanation с несколькими видами traces, delta-only UX для repeat review, sample-review policy для безопасных Normal и полноценный human Publisher desk. Всё это полезно, но не является минимальным контрактом, без которого невозможно построить безошибочную state machine. fileciteturn0file0

**Что нужно сразу считать out of scope.** В out надо явно вынести production-parity topology engine, собственный полнофункциональный conflict resolver уровня native ArcGIS, batch review queue, SLA-механику, сложную оргструктурную маршрутизацию и любые обещания «production-safe post» без реальной валидации на живых пользователях и живой GIS-интеграции. Сам файл прямо говорит, что role model, audit и governance ещё не доведены до полного blueprint, а доменные документы Esri показывают, что уже в native utility network есть много состояний, которые нельзя честно эмулировать в полном объёме быстрым демо. fileciteturn0file0 citeturn22view1turn22view0turn18view1

**Где должна проходить граница вертикального среза.** Ближайший срез должен доходить **до review/post end-to-end**, а не останавливаться на WorkOrder → EditVersion → editing workspace. Иначе вы не проверяете главную гипотезу — что system действительно сокращает путь к уверенному go/no-go решению и не ломает ownership authoritative state. Практически это должен быть такой скелет: work order → named edit version → validation → reconcile → package build → reviewer decision → stale/blocker recheck → simulated post → audit outcome. fileciteturn0file0 citeturn19view1turn18view4turn11view2

**Нужно ли уже сейчас заводить ReviewPackage aggregate.** Да, **сейчас заводим**. Причина простая: stale events, blockers, risk tier, reviewer decision, audit record и pre-post recheck невозможно стабильно реализовать без отдельного агрегата с собственной идентичностью, версией сборки и привязкой к edit version/default snapshot. Если этого не сделать сейчас, state machine быстро расползётся по ad hoc полям на EditVersion, а repeat review и stale invalidation станут неуправляемыми. fileciteturn0file0 citeturn11view2turn18view4turn22view2

## State machine и safety invariants

**Какие canonical states нужны после InProgress.** Для минимальной модели я бы зафиксировал такой линейный путь: **editing → validated → reconciled → ready_for_review → approved_package → post_authorized → posted**. Отдельно как поперечные состояния должны существовать **blocked**, **stale** и **escalated**. Это важнее, чем спорить о деталях naming: вам нужно явно отделить момент, когда edit просто существует, от момента, когда он валиден, от момента, когда он согласован с Default, от момента reviewer decision и от момента технического допуска к post. Такой разрез согласуется и с вашим файлом, где review и publish — самостоятельные этапы, и с branch versioning/utility network ограничениями Esri. fileciteturn0file0 citeturn19view1turn18view4turn18view1

**Что переводит EditVersion в ready_for_review.** Рекомендуемый предикат готовности такой: выполнен **последний reconcile с текущим Default**, нет **unreviewed/unresolved conflicts**, прошла **validation** без absolute veto-ошибок, собран **минимальный evidence package**, заполнен **editor summary/comment**, а package имеет зафиксированный built-from state. Если validation уже вернула hard blocker, состояние должно быть не ready_for_review, а blocked. Это опирается на то, что reconcile с неразобранными конфликтами — риск потери контекста, а dirty areas и validation являются формальным признаком того, что topology ещё не соответствует edit state. citeturn18view4turn18view1turn11view2turn11view3

**Какие failures обязаны сохранять edits и блокировать partial post.** Абсолютные veto cases должны быть такими: unresolved or unreviewed conflicts; validation errors или error dirty areas в затронутой области; stale package или stale approval; изменение Default после package build, требующее нового reconcile; unresolved association delta; trace, который на Validate Consistency падает из‑за dirty areas; invalid/dirty subnetwork при затронутых контроллерах/tiers; missing required evidence для High/Critical; и любое неожиданное trace impact, которое reviewer ещё не классифицировал. Эти случаи нельзя превращать в partial post: Esri прямо указывает, что dirty-area edits не отражены в topology и не должны считаться надёжными для trace, а subnetwork update может закончиться invalid. citeturn18view4turn11view2turn11view3turn22view2turn22view1turn18view3

**Нужно ли разводить approve package и can post.** Да, это должны быть **два разных шага**, а не одно решение. Approve package означает: reviewer считает решение по change package приемлемым и evidence достаточным. Can post означает: прямо сейчас package всё ещё fresh, blockers всё ещё cleared, а technical owner поста может безопасно выполнить PostToDefault. Это разделение — естественное следствие protected Default и того факта, что между approval и фактическим post state сети может измениться. citeturn19view1turn19view0turn11view2

## Evidence, risk и stale policy

**Какой минимальный evidence package нужен сейчас, а что остаётся на потом.** В ближайшем срезе минимум должен включать: идентификаторы **Base/Mine/Default state**, краткий **geometry diff**, явный **association delta**, статус **dirty areas**, результат **validation**, ссылку на **work order**, обязательный **editor summary**, а также trace/subnetwork evidence **только по условию риска**, а не всегда. Если изменение затрагивает association, terminal-aware connectivity, controller-like asset или network attribute, тогда trace fixture и subnetwork status становятся обязательной частью package. На потом можно оставить полные comparative traces, richer subnetwork explanations, внешние GIS-drilldowns и полноформатный ingestion field evidence. Такой минимум соответствует и вашему файлу, и utility network реальности: geometry alone недостаточна, потому что association/terminal/network attribute changes тоже меняют topology semantics. fileciteturn0file0 citeturn11view2turn11view3turn9view0turn20view1turn22view2turn22view1

**Как без настоящего topology engine различать Normal, High и Critical.** Для synthetic demo лучше использовать детерминированную rule-based классификацию. **Normal** — нет association delta, нет terminal-sensitive asset, нет network attribute change, validation clean, dirty areas cleared, trace fixture либо не нужен, либо unchanged. **High** — есть association delta или terminal-adjacent конфликт, но нет подтверждённого изменения trace/subnetwork semantics; reviewer должен принять финальное решение сам. **Critical** — меняется trace path, затронут subnetwork controller/critical device, меняется traversability через terminal/connectivity, появляется invalid/dirty subnetwork, или затронут network attribute, который используется как condition barrier/flow logic. Это соответствует самим utility network механизмам: network rules govern connectivity and associations, traces rely on validated topology, а subnetworks являются topological subsets, критичными для operational behavior. citeturn20view1turn15view0turn22view2turn14view0turn22view1

**Пять простых synthetic-примеров для классификации.** Перенос линии без изменения endpoints/associations и с чистой validation — Normal. Изменение атрибута, не являющегося network attribute, без топологических последствий — Normal. Конфликт around transformer/service device, где есть association delta к terminal-aware connectivity, но trace fixture не меняется, — High. Тот же transformer case, но trace через high-side/low-side меняется или меняется reachable subnetwork behavior, — Critical. Изменение network attribute типа device status/open-closed, который используется для traversability barrier, — Critical. Эти примеры прямо следуют из Esri-документации о terminals/connectivity rules, trace condition barriers и subnetwork semantics. citeturn20view1turn15view0turn22view2turn14view0

**Какие stale events нужно считать обязательными.** Обязательный список такой: новый reconcile; любое изменение Default, затрагивающее package scope; изменение geometry; изменение association delta; изменение network attribute; изменение terminal configuration; изменение validation result; изменение trace/subnetwork freshness; изменение rule/configuration в Default, требующее reconcile; изменение required evidence после approval. У Esri есть очень прямая база под это: geometry, network attributes, associations и terminal configuration создают dirty areas; reconcile пересоздаёт dirty areas в named version; network rule updates не отражаются в existing named versions до reconcile. Значит, как только изменился один из этих факторов, прошлое approval перестаёт описывать текущий state. citeturn11view2turn11view3turn22view3turn18view4

## Contract, integrations и audit boundary

**Какой artifact сейчас приоритетнее.** Приоритетнее **implementation contract v0.1 для review/post slice**, а не продолжение coding только вокруг editor workflow. Причина не в «документ ради документа», а в том, что без зафиксированного ownership PostToDefault, ReviewPackage aggregate, stale policy и blocker semantics вы почти наверняка зашьёте неправильные границы в код и потом будете переписывать state machine. Ваш файл сам показывает, что именно role model, audit и governance ещё не доспецифицированы; значит, следующий шаг должен быть контрактом на этот слой. fileciteturn0file0

**Какие integrations сейчас реально доступны для contract.** По текущему материалу безопасно фиксировать так: **work order data — есть как реальный domain input**; **package API — есть и должен быть first-class**; **audit storage — есть и должен быть реальным persistent storage**; **validation fixture — stub**; **trace/subnetwork fixture — stub**; **реальный PostToDefault against external GIS — пока нет, только simulated/system action**. Это честная граница anti-corruption boundary: файл прямо описывает продукт как слой вокруг authoritative network workflow, но не даёт основания обещать production-grade внешнюю GIS-интеграцию уже сейчас. fileciteturn0file0 citeturn22view2turn22view1turn19view1

**Какие поля должны быть domain audit, а какие telemetry/debug.** В **domain audit** должны жить package_id, work_order_id, edit_version_id, actor, role, decision, decision_scope, rationale, risk_tier, blocker flags, stale events, evidence snapshot checksum, trace/subnetwork freshness verdict и final post outcome. Это то, что нужно человеку и повторному review. В **telemetry/debug** должны жить correlation_id, timings, package build duration, evidence fetch latency, UI render timings, counts of external-check opens, retry counters и технические error details. Subnetwork/history docs Esri отдельно напоминают, что не все system-operations автоматически попадают в геобазную историю; значит, свой audit-объект нельзя подменять одними техническими логами. citeturn22view0turn22view1

**Форма implementation contract.** Практически контракт должен быть коротким и жёстким: state machine, ownership matrix, ReviewPackage schema, blocker policy, stale policy, audit schema, integration boundary и acceptance conditions на canonical transformer/service-device conflict. Если в одном предложении: контракт должен описывать **не все идеальные future-возможности**, а минимальный способ доказать, что consequence-aware package ведёт к осмысленному reviewer verdict и безопасному pre-post gate на synthetic data. Это соответствует и вашему файлу, и ограничениям native utility network workflows, где даже базовые reconcile/validate/subnetwork состояния уже вводят много скрытой сложности. fileciteturn0file0 citeturn18view1turn22view2turn22view1turn19view1

**Финальная формулировка решения.** Если сжать всё до одного архитектурного выбора, он такой: **семантическое approval должно принадлежать Reviewer, технический PostToDefault — Publisher, а между ними должен жить ReviewPackage как отдельный aggregate со stale policy, hard blockers и consequence-aware evidence**. Всё остальное — routing, richer UX, specialist directories, full integrations — можно наращивать позже, не ломая каркас. fileciteturn0file0 citeturn19view1turn11view2turn22view2turn22view1
