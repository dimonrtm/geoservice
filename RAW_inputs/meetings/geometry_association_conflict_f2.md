# Geometry и association conflict в Utility GIS editor

Отвечаю как архитектор utility GIS и сетевых data workflows для инженерной инфраструктуры, с фокусом на branch versioning, authoritative network model и эксплуатационные последствия изменений.

## Опорный вывод

**Primary user в этом конфликте — не publisher/version admin и не профильный инженер, а Editor в именованной версии, который уже сделал изменение и должен решить, можно ли безопасно довести его до authoritative state.** Файл прямо реконструирует Use Case как работу офисного utility GIS editor над авторитетной моделью сети с branch versioning, reconcile/post, conflict resolution и review/publish как частью жизненного цикла. Официальная документация ArcGIS подтверждает, что конфликт появляется и разрешается в контексте named version: при reconcile выявляются конфликты между named version и default, а затем пользователь должен выбрать, какую репрезентацию признавать правильной до post. Version administrator — это скорее роль доступа и публикации, особенно если default защищён; он не является главным “носителем боли” от geometry/association conflict. Профильный инженер нужен уже как эскалация, когда конфликт затрагивает сетевую семантику, а не просто форму объекта. fileciteturn0file0 citeturn8view0turn25view0turn25view1

**Суть боли Editor-а** такая: он видит, что feature изменился, но не получает в одном месте ответ на более важный вопрос — “это только картинка, или я меняю authoritative network behavior?”. Для utility network этого вопроса нельзя решить только по геометрии, потому что последствия живут в connectivity, containment, structural attachment, terminals, network attributes, trace и subnetwork state. В ArcGIS associations вообще не имеют собственного Shape-поля и видны только через специальные режимы, diagrams или synthesized trace geometry; trace при этом опирается на topology cache и может быть ненадёжен, если в области есть dirty areas или subnetwork errors. Именно здесь и возникает потребность в отдельном GeoService/Release 2 слое объяснения последствий. citeturn25view2turn18view0turn21view2turn13view0

## Кто этот пользователь на практике

**Конкретный archetype**, который лучше всего соответствует этому конфликту, — офисный Editor/data steward по распределительной utility-сети с опытом примерно 3–7 лет. Он не настраивает саму платформу как администратор utility network, но достаточно глубоко понимает слои, asset groups/types, named versions, reconcile/post, dirty areas и типовые traces. Его зона обычно — распределительная электро-, газо-, водо- или теплосеть на уровне района/фидера/pressure zone, а типовые work orders — замена трансформатора или service device, перенос service line, исправление as-built после полевых работ, актуализация attachment/containment, исправление терминалов или связности после реконструкции. Такой портрет соответствует файлу, где ядро Use Case — офисные ГИС-специалисты и field crews, работающие над одной authoritative network model с review/publish и work-task логикой. fileciteturn0file0

**Reviewer для него — вторичный пользователь, а version admin и профильный инженер — эпизодические роли.** Reviewer включается, когда нужен второй уровень суждения о риске изменения. Version administrator нужен главным образом потому, что post в default может требовать специальных прав, особенно при protected default. Профильный инженер нужен тогда, когда конфликт выходит за пределы “какую запись оставить” и становится вопросом сетевой логики: корректен ли terminal path, допустим ли subnetwork membership, не изменится ли operational trace, не нарушены ли правила участия features в tier. ## Где и когда возникает conflict

**В календаре рабочего дня conflict чаще всего “становится настоящим конфликтом” на reconcile, но риск начинает накапливаться раньше.** Geometry edits, edits to network attributes, terminal configuration–related edits и association changes создают dirty areas сразу по факту изменения. Валидация затем обновляет topology, и только после reconcile named version подтягивает изменения из default и показывает version conflict. То есть: семантический риск появляется в момент редактирования и validation, а формальный version conflict — в момент reconcile; если же между reconcile и post default снова изменился, post прерывается и reconcile нужно делать заново. citeturn13view0turn15view0turn8view0

**Поэтому честный ответ на вопрос “в какой момент рабочего дня это происходит?” такой:**
Editor впервые чувствует проблему во время своей локальной QA после edit/validate, когда видит dirty areas, rule errors или trace uncertainty;
как version conflict он сталкивается с ней во время reconcile;
как governance problem — прямо перед post, если default успел измениться после reconcile. Это не только “review-stage problem” и не только “post-stage problem”; конфликт проходит через несколько состояний, но кульминация для Editor-а наступает именно тогда, когда нужно принять решение, какую репрезентацию считать authoritative. citeturn15view0turn25view0turn8view0

## Как пользователь сегодня понимает риск и где теряет контекст

**Обычного geometry diff недостаточно, чтобы понять безопасность изменения.** ArcGIS Conflicts view и Differences view умеют хорошо показывать feature geometry и attribute values в вариантах Current, Target и Common Ancestor, но это не гарантирует понимание сетевого последствия. Более того, документация прямо показывает случай, когда геометрия в Conflict Display viewer выглядит одинаково в двух версиях, а решать всё равно нужно по данным и различиям в representation. Дополнительно конфликты могут возникать не только по самому feature, но и потому, что в обеих версиях был изменён topologically related feature или relationship class. Это и есть главный разрыв между “вижу diff” и “понимаю impact”. citeturn21view0turn21view1turn25view0turn20view4

**Чтобы понять, меняется ли только картинка или меняется authoritative network behavior, пользователь сегодня вынужден собирать мысль по частям.** Он смотрит Differences/Conflicts view, затем лезет в Modify Associations или Select Associated Data, потому что associations не живут как нормальные геометрические объекты и не имеют Shape; затем включает View Associations Mode или строит network diagram; затем валидирует topology и запускает trace; а если конфликт касается subnetwork semantics, ещё и проверяет update subnetwork / subnetwork status. Если при этом в зоне есть dirty areas или subnetwork errors, trace уже сам по себе не является полностью надёжным, и уверенность снова падает. citeturn25view2turn14view0turn14view1turn21view2turn25view4

**Что пользователь делает сейчас без GeoService — это не одна команда, а ручная композиция нескольких контекстов.** Обычно это: открыть work order или change request; сравнить Current/Target/Common Ancestor; посмотреть dirty areas и errors; вручную извлечь association diff; запустить trace до и после; иногда обновить subnetwork; затем приложить field evidence, фото, схемы и собственные notes. Файл описывает именно такой класс utility platform, где work execution, field-office sync, attachments и authoritative network model живут рядом, но не обязательно в одном consequence-first review flow. Поэтому без отдельного слоя объяснения пользователь естественно уходит во внешнюю GIS, скриншоты, устные согласования или ручные заметки. Это не “плохая привычка”, а нормальная компенсация недостающего связующего контекста. fileciteturn0file0 citeturn21view0turn25view2turn13view0turn21view2

**Контекст особенно теряется на стыке пяти вещей:** work order и field evidence обычно живут отдельно от самой conflict card; association diff плохо виден без специальных режимов; dirty areas и errors живут в отдельном слое/инспекторе; trace and subnetwork consequence требуют отдельного действия; reviewer comments и change history часто не совпадают по “единице анализа” с тем, что редактор видит на карте. Технически ArcGIS даёт почти все кирпичики, но не собирает их в одно последовательное объяснение “изменение → сетевое последствие → допустимое решение”. Именно этот gap и формирует реальную боль Editor-а. fileciteturn0file0 citeturn21view0turn25view2turn13view0turn19view1

## Конкретный пример конфликта и цена ошибки

**Наиболее показательный пример** — конфликт вокруг трансформатора, service device и линии/association после полевой замены или as-built коррекции.
В версии **Mine** Editor после полевого work order заменяет transformer/service device, двигает его в правильное место, перепривязывает service line к новому terminal path и меняет structural attachment или containment, чтобы модель соответствовала фактическому монтажу.
В **Default** параллельно другой редактор уже поправил тот же device: например, изменил asset type, terminal-relevant attributes, связность с другой линией или контейнеризацию оборудования в составе сборки.
При reconcile конфликт может появиться не только как update-update по самому устройству, но и потому, что в обеих версиях изменены relationship class или topologically related features. Если Editor выберет неверную репрезентацию, визуально карта может выглядеть “почти так же”, но внутренняя connectivity/traversability уже станет другой. Это синтезированный, но полностью правдоподобный сценарий по правилам utility network, а не фантазия вне домена. citeturn6view0turn25view0turn25view3turn21view3

**Что именно может сломаться при неверном resolve:** connectivity между line и device; containment состава оборудования; structural attachment к конструкции; terminal-based path внутри устройства; trace result upstream/downstream; subnetwork membership и, как следствие, status/update subnetworks. Документация Esri прямо говорит, что unsupported rules приводят к ошибкам, а в ряде случаев features оказываются не подключены в topology; trace использует topology cache и не гарантированно точен при dirty areas или subnetwork errors; update subnetwork может провалиться и пометить subnetwork как invalid. Для utility-операций это уже не “конфликт линий на карте”, а риск изменить authoritative behavior сети. citeturn13view2turn15view1turn20view0turn21view2turn25view4

**Самая дорогая ошибка для пользователя — unsafe post неверной association/connectivity, а не просто задержка публикации.** Причина простая: post отправляет изменения в default, после чего они не откатываются как обычный локальный undo; если же из-за неправильного resolve в default попадёт не та connectivity/association, downstream trace, subnetwork state и операционные решения уже будут строиться на неверной authoritative картине. Задержка work order болезненна, но она заметна и обратима. Тихое попадание неверной сетевой логики в default дороже именно потому, что оно выглядит “правдоподобно” и может не сразу всплыть. citeturn8view0turn21view2turn25view4

**Кейс считается простым и рутинным**, когда изменяется только геометрическая аккуратность или оформление, а validation остаётся чистой, associations/terminals/network attributes не меняются, trace не меняется или этот слой вообще не участвует в трассируемой сети.
**Кейс становится опасным**, даже если на карте почти ничего не изменилось, когда есть изменение association, terminal-related path, network attribute, containment/attachment, dirty areas с rule error, либо trace/subnetwork outcome отличается или не может быть подтверждён из-за dirty/invalid state. Официальные документы именно такие признаки и превращают из “рисования” в изменение сети как вычисляемой системы. citeturn13view0turn15view1turn25view2turn25view3turn25view4

**Практическое правило маршрутизации** я бы сформулировал так. “Я могу решить сам” — когда конфликт локальный, validation clean, нет rule errors, нет terminal/subnetwork effect, а field evidence и trace подтверждают ожидаемый результат. “Нужен Reviewer” — когда конфликт уже требует выбора между competing representations named/default или касается association/attribute logic, которую нельзя защитить одним скриншотом geometry. “Нужен профильный специалист” — когда меняются service/subnetwork/safety semantics, возникает unexpected trace impact, invalid subnetwork, terminal ambiguity или требуется административное изменение rule base. Это вывод-синтез, но он жёстко опирается на domain mechanics из docs. citeturn25view0turn15view1turn21view2turn21view3

## Что считается успешным результатом и какие обходные пути уже существуют

**Успешный результат после resolution для такого пользователя — не просто “конфликт закрыт”.** Для него успех выглядит так: выбрана правильная representation; validation в области работ чистая или осознанно принята; association/terminal state консистентны с rules; trace подтверждает ожидаемую traversability; при необходимости subnetwork обновляется без invalid status; reviewer или owner default понимают, что именно approved/post authorized; а в audit или notes остаётся краткая логика решения. Иными словами, цель — не “убрать красное”, а доказать, что post не ломает network behavior. citeturn25view0turn15view0turn21view2turn25view4

**Обходной путь для stale approval уже фактически есть, но он тяжёлый и ручной.** Если default поменялся после reconcile, post может обнаружить новые конфликты и потребовать reconcile заново. Если после reconcile редактор ещё раз валидировал, нужен ещё один reconcile перед post. Если конфликт затянули, повторный reconcile или post может автоматически очистить unreviewed conflict history в пользу edit version. На практике это означает: повторно reconcile, ещё раз пересмотреть Conflicts view, заново прогнать validate/trace, обновить notes и заново синхронизировать reviewer-суждение. Формального понятия “stale approval” в ArcGIS docs нет, но с точки зрения продуктового дизайна именно так stale approval и проявляется. citeturn8view0turn25view0turn25view1

**Фразы, которыми пользователь, скорее всего, описывает эту боль,** звучали бы не как технические названия ошибок, а как языки операционного риска: “не уверен, что это только картинка”, “надо проверить трассу”, “непонятно, что реально уйдёт в default”, “вижу diff, но не понимаю влияние на сеть”, “страшно постить”. Это не прямые полевые цитаты, а исследовательская реконструкция по workflow и domain mechanics; использовать их можно как дизайн-гипотезу, но не как проверенный product claim без интервью с реальными Editor/Reviewer. fileciteturn0file0 citeturn21view0turn25view2turn21view2

## Что должен сделать GeoService, чтобы пользователь стал быстрее и увереннее

**Если свести всё к одному требованию, GeoService должен превратить geometry/association conflict из “сравнения двух состояний feature” в “объяснение изменения authoritative network behavior”.** То есть пользователь должен видеть не только Current/Target/Common Ancestor, но и consequence package: какие associations/terminals изменились, какие dirty areas/errors активны, изменился ли trace, затронут ли subnetwork status, есть ли inconsistency с rules, что подтверждает field evidence, и какой маршрут решения предлагается — self-resolve, reviewer, specialist. Без этого Editor продолжит собирать картину вручную из нескольких панелей и внешних проверок. fileciteturn0file0 citeturn21view0turn25view2turn21view2turn25view4

**Практически это означает такой минимальный пакет для одного решения:**
первым экраном — тип конфликта и affected assets;
сразу под ним — explicit association/terminal diff, а не только geometry diff;
дальше — validation/error state и dirty-area scope;
потом — trace before/after или флаг “trace unreliable because topology/subnetwork state is not clean”;
затем — work order и field evidence snapshot;
и уже после этого — suggested route: можно решить самому, нужен reviewer, нужна domain escalation. Такой порядок соответствует тому, как utility network реально вычисляет последствия: сначала topology/associations/rules, потом trace/subnetwork, и только потом governance decision о post. citeturn13view0turn15view1turn25view2turn21view2turn25view4

**Момент, когда пользователь скажет “теперь я быстрее и увереннее принимаю решение”,** наступит не тогда, когда UI просто красивее покажет diff, а когда для опасных конфликтов он перестанет уходить в внешнюю GIS, отдельные traces, скриншоты и устные подтверждения, а для безопасных конфликтов — перестанет зря эскалировать их из осторожности. Иными словами, цель GeoService — одновременно снизить ложные эскалации и уменьшить риск тихого неверного post. Это и есть самый ценный outcome для Release 2 в таком домене. fileciteturn0file0 citeturn25view0turn21view2turn25view4
