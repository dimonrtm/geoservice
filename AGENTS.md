# Agent Instructions

## Приоритетный режим доменной работы

GeoService — эксперимент по разработке приложения в незнакомой пользователю предметной области с помощью нейросети и интернет-поиска. Реальной организации нет. Агент через экспертную персону `expert_repson` представляет условную организацию: самостоятельно исследует практику, отвечает на доменные вопросы и выбирает обоснованные, согласованные правила её работы.

- Перед discovery, ответами на доменные вопросы, ingest и доменным планированием обязательно читать `docs/agent-memory/decisions/2026-10-13-simulated-domain-organization.md`, независимо от результатов поиска по памяти.
- Этот режим имеет приоритет над противоречащими ему записями памяти, wiki, follow-up и методическими требованиями skills о реальных представителях организации. Более поздние прямые указания пользователя могут изменить режим.
- Не требовать от пользователя реальных ответственных, внутренних регламентов, интервью или производственных измерений. Отсутствие организации не является блокером. Пробелы исследует и заполняет агент; вопросы пользователю касаются целей, масштаба и продуктовых предпочтений.
- Явно различать внешние факты со ссылками, решения условной организации и непроверенные гипотезы. Не выдавать синтетические данные и ответы персоны за реальное интервью, измерения или производственную валидацию.
- Перед выдачей доменного ответа проверить: не переложено ли исследование на пользователя, не запрашиваются ли несуществующие сотрудники или документы, указано ли происхождение существенных решений.
- Режим не отменяет принятые инварианты, границы реализации и правила Git; прежние предложения не становятся автоматически принятыми.

- При разборе технической задачи спринта, уточнении требований, анализе текущего кода, проектировании реализации и проверок опираться на материалы репозитория и ответы пользователя. Внешние источники привлекать для конкретных пробелов, без обязательной квоты.
- Не превращать технический разбор в отдельное доменное исследование и не задерживать его завершение ради набора 75 источников.

Before working in this repository:

1. Read `docs/agent-memory/protocol.md`.
2. Search `docs/agent-memory/file-map.md` and memory entries for context related to the user's request.
3. Read only the memory entries that are relevant to the request.
4. After significant work, decide whether durable memory needs an update.

## Git Operations

Agents must not run `git add`, `git commit`, or `git push` in this repository.
The user alone reviews, stages, commits, and pushes changes. Do not request
approval or elevated permissions for these commands. User approval of a design,
completion of implementation, or a skill instruction requiring a commit does
not override this repository rule. Leave changes unstaged and report them for
the user's review.

## Основные правила архитектуры на бекенде

На проекте применяются Domain Driven Design (DDD) и Clean Architecture.

Это обязательное архитектурное правило для всех задач по бекенду: проектирования, написания и изменения кода, рефакторинга и ревью.

### 1. Как понимать DDD и Clean Architecture

- DDD определяет, как моделировать предметную область: использовать её язык, явно выражать бизнес-правила, инварианты, состояния объектов и границы ответственности.
- Clean Architecture определяет, как разделять код и зависимости: бизнес-логика не должна зависеть от способа доставки запроса, хранения данных или конкретного внешнего сервиса.
- Недостаточно назвать папки `domain`, `use_cases` и `infrastructure`. Проверять нужно фактическую ответственность кода и его зависимости.

### 2. Доменная модель и бизнес-правила

- Использовать согласованные термины из `Wiki/` и `DDD_Wiki/`, сверяя их с принятыми решениями и текущей задачей. Не придумывать другое название для уже существующего доменного понятия.
- Сущность определяется своей идентичностью; объект-значение — значением и правилами его допустимости. Не превращать каждую таблицу или DTO в доменную сущность автоматически.
- Агрегат задаёт границу согласованности. Изменения его состояния должны проходить через операции, сохраняющие инварианты; нельзя обходить эти правила произвольным изменением полей извне.
- Правила допустимых состояний, переходов и сочетаний данных размещать в доменной модели. Доменный сервис использовать для бизнес-операции, которая не принадлежит естественным образом одной сущности или объекту-значению.
- Доменные правила не должны знать о HTTP, FastAPI, SQLAlchemy, сессиях БД, SQL-запросах и конфигурации инфраструктуры.
- Границы bounded contexts определяют смысл модели. Не связывать контексты прямым изменением внутренних объектов друг друга; использовать явно определённые операции и контракты.
- Не добавлять агрегаты, события, фабрики и репозитории только ради шаблона. Каждый элемент должен решать конкретную задачу модели.

### 3. Сценарии приложения — use cases

- Use case описывает прикладное действие: кто его выполняет, какие данные нужны, какие доменные операции вызываются и какой результат возвращается.
- Он координирует загрузку данных, проверку прав на действие, вызов доменной логики и сохранение результата. Бизнес-инварианты не должны существовать только в use case, если их должна защищать сама модель.
- Граница транзакции соответствует атомарному сценарию. Use case управляет её выполнением через принятый в проекте механизм; техническую работу с транзакцией выполняет инфраструктура.
- Use case не должен принимать HTTP request, возвращать HTTP response или выбирать HTTP status code. Результаты и ошибки приложения переводятся в транспортный формат на границе API.
- Для доступа к внешним ресурсам целевой подход — интерфейсы (порты), определённые потребностями внутреннего слоя, и их инфраструктурные реализации.

### 4. API и инфраструктура

- API принимает запрос, проверяет его транспортный формат, получает контекст аутентификации, вызывает use case и преобразует результат или ожидаемую ошибку в ответ.
- Проверка формата запроса не заменяет доменную валидацию: например, корректный формат идентификатора не означает, что переход состояния объекта разрешён.
- В контроллерах не размещать SQL, алгоритмы изменения агрегатов и бизнес-решения. Правила доступа к конкретной прикладной операции нельзя защищать только наличием проверки в одном endpoint.
- Инфраструктура реализует хранение, запросы, внешние интеграции и технические механизмы доставки сообщений. Репозиторий отвечает за загрузку и сохранение данных, а не за выбор допустимого бизнес-действия.
- ORM-модель описывает хранение, DTO — контракт передачи данных, доменная модель — поведение и правила. Не считать эти роли взаимозаменяемыми; вводить отдельные представления там, где смешение создаёт зависимость или мешает защищать инварианты.
- Ограничения БД могут дополнительно защищать целостность и конкурентные изменения, но не заменяют явного выражения бизнес-правил в модели.

### 5. Направление зависимостей

- Целевое направление зависимостей исходного кода: внешние адаптеры зависят от прикладных и доменных контрактов, use cases — от доменной модели, доменная модель — ни от одного внешнего слоя.
- Если use case вызывает хранилище через интерфейс, это не означает, что он должен импортировать конкретную реализацию хранилища. Реализацию подставляет код сборки зависимостей.
- Пакет `infrastructure` не должен зависеть от `use_cases`. Прикладные порты и типы результата принадлежат `use_cases`. Адаптер работает со своими инфраструктурными типами. Если сценарий читает данные из них, прикладной порт описывает нужные поля и операции, а сценарий собирает независимый результат в пределах транзакции. Сборку конкретных реализаций выполнять в фабрике зависимостей.
- Связывание конкретных реализаций выполнять в специально выделенном месте сборки приложения (composition root / dependency factories), а не внутри доменных операций.
- Не маскировать нарушение границ переносом бизнес-логики или инфраструктурных зависимостей в общие `utils` и helper-модули.

### 6. Применение правил к существующему проекту

- Перед изменением проверить `Code_wiki/архитектура/backend.md`, относящиеся к задаче решения и фактический код. Для существующих проверок границ смотреть `apps/backend/tests/test_architecture_boundaries.py`.
- Текущая структура переходная: `web_api`, `use_cases`, `domain_services`, `infrastructure`; часть use cases использует инфраструктуру напрямую. Не выдавать текущее устройство за полное соответствие Clean Architecture.
- Сохранять уже установленные ограничения: `web_api` не импортирует `infrastructure`; `use_cases` не импортирует `web_api`; production-код `domain_services` не зависит от этих пакетов и инфраструктурных фреймворков.
- Наличие старого кода, нарушающего целевые принципы, не является основанием повторять нарушение. При этом эти правила не дают разрешения на массовую миграцию, переименование пакетов или введение новых абстракций вне задачи.
- Если изменение требует пересмотра принятой границы, явно описать конфликт и необходимый объём изменения. Не обходить архитектурные проверки и не расширять задачу скрыто.

### 7. Что проверять при изменениях и ревью

- Понятно ли, к какому контексту и слою относится новый код и почему он находится именно там?
- Выражены ли бизнес-правила явно и защищены ли инварианты на всех путях изменения состояния?
- Можно ли проверить доменную логику без запуска HTTP-сервера, БД и внешних сервисов?
- Отделены ли транспортные ошибки, прикладные результаты и доменные ошибки?
- Нет ли новых зависимостей внутреннего слоя от внешнего или утечки ORM/HTTP-деталей в доменную модель?
- Для изменённого поведения выбирать соответствующие проверки: доменные правила — модульные тесты; координация use case — тесты сценария; хранение и транзакции — интеграционные тесты; API — тесты транспортного контракта.

## Основные правила архитектуры на фронтенде

На фронтенде применяется модульная архитектура по функциональным областям. Для сложных сценариев использовать принципы Clean Architecture, для интерфейса — небольшие Vue-компоненты и composables с понятной ответственностью.

Это обязательные правила для проектирования, написания, изменения и ревью фронтенда. Они задают направление развития существующего приложения на Vue, TypeScript, Pinia и MapLibre; не требуют внедрения FSD, микрофронтендов или полной перестройки каталогов.

### 1. Модули и их границы

- Группировать связанный код вокруг функциональной ответственности: например, авторизация, наряды, рабочее пространство редактирования. Модуль может включать собственные компоненты, состояние, сценарии, API и модели.
- Границу модуля определять по смыслу и жизненному циклу данных, а не по размеру файла. Тесно связанные сохранение, откат и восстановление редактора не обязаны становиться независимыми модулями.
- У каждого модуля должен быть понятный публичный контракт: доступные операции, данные и события. Другие модули не должны произвольно менять его внутреннее состояние или обращаться к деталям реализации.
- Публичный контракт не требует общего `index.ts`, экспортирующего всё содержимое модуля. Открывать только то, что нужно потребителям, избегать циклических импортов.
- Общие сценарии нескольких модулей координировать на уровне приложения или экрана. Не связывать модули взаимными вызовами stores и скрытыми цепочками watchers.
- В общую часть выносить код с действительно общим назначением: базовые UI-элементы, технические адаптеры и утилиты. Не превращать `shared`, `utils` или общие composables в хранилище логики, которой не определили владельца.
- Модули остаются частями одного приложения. Независимые сборки, отдельные контейнеры зависимостей и событийная шина не нужны без конкретного требования.

### 2. Clean Architecture для сложных сценариев

- Отделять правила и координацию сценария от UI и внешних механизмов там, где это помогает управлять сложностью: сохранение и восстановление команд, согласование снимков данных, конфликты версий, жизненный цикл сессии.
- Чистые правила обработки черновика, сравнения и допустимых локальных переходов выражать обычными TypeScript-функциями и моделями. Они не должны зависеть от Vue, Pinia, DOM, HTTP, IndexedDB и MapLibre.
- Прикладной сценарий определяет последовательность действий и результат. Vue-компоненты и composables связывают его с реактивным состоянием и пользовательским взаимодействием; адаптеры выполняют сетевые запросы, работу с хранилищем и картой.
- Внутренняя логика зависит от необходимых ей контрактов, а не от конкретных внешних реализаций. Вводить порт или передавать зависимость аргументом, когда это защищает значимую границу и позволяет независимо проверить сценарий.
- Не создавать обязательную цепочку из interface, repository, use case class, factory и mapper для каждой операции. Для простого чтения списка достаточно API-функции и небольшого store или composable с явным состоянием загрузки и ошибки.
- Не дублировать всю серверную доменную модель на клиенте. Фронтенд отвечает за локальное поведение и обратную связь пользователю; сервер остаётся окончательным источником проверки прав, бизнес-инвариантов и допустимости изменения данных.

### 3. Владение состоянием

- Для каждого состояния определять одного владельца и разрешённый способ изменения. Не поддерживать несколько независимо изменяемых копий одних данных в компоненте, store и объекте карты.
- Различать серверный снимок, локальный черновик, отправленную команду, состояние интерфейса и состояние MapLibre. Черновик и снимок могут существовать одновременно, но их связь, версии и правила обновления должны быть явными.
- Не подменять подтверждённое состояние сервера локальным предположением. Сохранять принятые контракты чтения после записи, повторов и восстановления; обновление снимка не должно молча затирать несохранённый черновик.
- Pinia использовать для состояния, которое разделяют несколько потребителей или которое должно переживать отдельный компонент. Локальное состояние панели, поля или диалога оставлять рядом с его владельцем, если нет причины делать его общим.
- Производные значения вычислять из исходного состояния, а не хранить дополнительные копии и синхронизировать их watchers.
- Browser storage и IndexedDB являются механизмами хранения, а не самостоятельными владельцами бизнес-состояния. Доступ к ним выполнять через определённый механизм с явными правилами записи, восстановления и очистки.
- Для workspace учитывать пользователя, сессию, наряд и рабочую версию. Смена контекста должна инвалидировать относящиеся к прежнему контексту операции и применять принятые правила сохранения или очистки данных.

### 4. Асинхронные операции и восстановление

- Явно описывать значимые состояния операции: ожидание, выполнение, успех, отказ, а при необходимости — неопределённый результат доставки. Не заменять различающиеся состояния одним флагом ошибки.
- Защищать состояние от поздних ответов после смены выбора, версии или сессии. Использовать существующие поколения запросов, идентификаторы и session epoch; отмена HTTP-запроса сама по себе не гарантирует актуальность результата.
- Не считать сетевой сбой доказательством того, что сервер не выполнил команду. Повторы записи и восстановление должны соответствовать действующему контракту идентичности команды и проверки её результата.
- Не запускать автоматическую повторную отправку изменения при новом login, повторном mount или восстановлении соединения, если это явно не разрешено сценарием.
- Watchers использовать для понятной реактивной синхронизации. Значимые команды, например сохранение или удаление, запускать явными действиями, а не как неочевидный побочный эффект изменения нескольких полей.
- Учитывать жизненный цикл подписок, listeners, timers и соединений. Их владелец освобождает ресурсы при завершении своего жизненного цикла; общие ресурсы не должны случайно закрываться одним из потребителей.

### 5. Vue-компоненты и composables

- Компонент отвечает за связную часть интерфейса: отображение, доступность и передачу действий пользователя. Не размещать в шаблоне или обработчике кнопки алгоритм восстановления, согласования версий или хранения команд.
- Размер компонента оценивать по числу ответственностей и сложности понимания, а не по жёсткому лимиту строк. Выделять часть, когда у неё появляется самостоятельный смысл, поведение или жизненный цикл.
- Composable инкапсулирует связную реактивную логику и явно принимает зависимости. Не превращать `useEditor()` или `useMap()` в универсальный объект, управляющий всем приложением.
- Логику, которой не нужна реактивность Vue, оставлять обычной TypeScript-функцией. Не создавать composable только ради префикса `use`.
- Явно различать состояние отдельного вызова composable и общее состояние Pinia. Несколько вызовов не должны случайно создавать независимые копии того, что по смыслу должно быть общим.
- Для взаимодействия компонентов использовать понятные props, события и согласованные операции stores. Избегать скрытого изменения состояния родителя и прямого изменения переданных объектов.
- Переиспользуемые UI-компоненты не должны знать о конкретном наряде, серверном endpoint или store редактора. При этом не делать каждый компонент универсальным: специализированные компоненты сценария допустимы и полезны.

### 6. Границы API, карты и браузерных механизмов

- HTTP-вызовы и обработку транспортного формата держать в API-адаптерах. Проверять внешние данные на границе по действующим контрактам; тип TypeScript сам по себе не проверяет JSON во время выполнения.
- Преобразование транспортных данных в локальные модели добавлять там, где представления действительно различаются. Не создавать mapper для идентичной структуры без причины.
- Технические ошибки переводить в понятное состояние сценария и сообщение пользователю через принятый механизм обработки ошибок. Не раскрывать детали транспорта в чистых правилах редактора.
- Интеграция с MapLibre отвечает за источники, слои, отображение и события карты. Правила изменения черновика, сохранения и разрешения конфликтов не должны жить внутри обработчиков MapLibre.
- Данные для отображения карты получать из состояния приложения. Внутренние sources и layers MapLibre не использовать как единственный источник истины о черновике или серверных данных.
- Изолировать внешние механизмы настолько, насколько это нужно сценариям. Не создавать универсальную обёртку над всем API MapLibre, Axios или браузера ради возможности гипотетической замены библиотеки.

### 7. Применение к текущему коду и проверка изменений

- Перед изменениями сверять `Code_wiki/архитектура/frontend.md`, относящиеся к задаче решения и фактический код. Существующие `components`, `composables`, `stores`, `api`, `contracts`, `domain`, `map` и `auth` не требуют немедленного перемещения.
- Развивать модульные границы постепенно в рамках задачи. Перенос файлов оправдан, если делает ответственность и зависимости понятнее; сам по себе новый каталог не улучшает архитектуру.
- Сохранять уже реализованные гарантии сессий, актуальности ответов, сохранения и recovery. Архитектурная переработка не должна незаметно менять поведение пользователя или протокол взаимодействия с сервером.
- Проверять: кто владеет состоянием, кто может его менять, где выполняются побочные эффекты и что произойдёт при смене контекста во время запроса.
- Чистые правила проверять модульно; сложные сценарии — с управляемыми внешними зависимостями, включая значимые ошибки и порядок завершения запросов; компоненты — через наблюдаемое поведение; адаптеры — на соответствие внешним контрактам.
- Не писать тесты, закрепляющие случайное устройство каталогов или цепочку внутренних вызовов. Архитектурные проверки импортов полезны для явно принятых границ, а поведенческие тесты — для гарантий сценария.
- Перед введением абстракции объяснять, какую текущую проблему она решает. Если небольшая функция, компонент или существующий store обеспечивают те же гарантии проще, выбирать их.

## Основные правила написания кода

Код должен соответствовать принципам SOLID. Паттерны GoF (банды четырёх) и enterprise-разработки применять там, где они решают конкретную задачу. Не допускать оверинжиниринга: сложность решения должна быть оправдана текущими требованиями.

Эти правила обязательны при написании, изменении и ревью кода. Применять их с учётом языка, архитектуры и принятых подходов проекта; они не требуют превращать любой код в иерархию классов.

### 1. Принципы SOLID

- **Single Responsibility Principle — единственная ответственность.** У модуля, класса или функции должна быть связная ответственность и понятная причина изменения. Не смешивать бизнес-решения, доступ к данным, транспорт и форматирование ответа в одном месте. При этом не дробить связную операцию на множество классов без практической пользы.
- **Open/Closed Principle — открытость для расширения и закрытость для изменения.** В местах реальной вариативности предусматривать расширение поведения без постоянного изменения устойчивого общего кода. Не создавать точки расширения для гипотетических требований; обычное изменение функции допустимо, если отдельный механизм расширения пока не нужен.
- **Liskov Substitution Principle — подстановка подтипов.** Реализация интерфейса или наследник должны сохранять обещанное контрактом поведение, включая допустимые входные данные, результат и ошибки. Не использовать наследование, если подтип вынужден запрещать нормальные операции базового типа или неожиданно менять их смысл.
- **Interface Segregation Principle — разделение интерфейсов.** Клиент должен зависеть только от нужных ему операций. Разделять большие интерфейсы по задачам потребителей; не заставлять реализации содержать фиктивные методы или бросать `NotImplementedError` для обязательных операций контракта.
- **Dependency Inversion Principle — инверсия зависимостей.** Высокоуровневая политика должна зависеть от необходимых ей контрактов, а не от деталей хранения, транспорта или внешних сервисов. Конкретные реализации связывать в месте сборки зависимостей. Не вводить интерфейс к каждому классу автоматически: он должен защищать значимую границу или выражать нужный потребителю контракт.

### 2. Применение паттернов

- Выбирать паттерн после определения проблемы. В объяснении решения сначала указывать, какую сложность он устраняет, затем — почему подходит именно этот паттерн.
- Использовать GoF-паттерны при соответствующей потребности: например, `Strategy` для взаимозаменяемых алгоритмов, `Adapter` для согласования внешнего интерфейса, `Factory` для нетривиального создания объектов. Простая функция или конструктор предпочтительнее, если они полностью решают задачу.
- Enterprise-паттерны, например `Repository`, `Unit of Work`, `Specification` или `Outbox`, применять для конкретных требований к хранению, транзакциям, бизнес-правилам или надёжности доставки. Их наличие в каталоге паттернов само по себе не является основанием для внедрения.
- Сначала проверить существующие реализации и соглашения проекта. Не создавать второй механизм для той же задачи без обоснованной необходимости.
- Учитывать цену паттерна: дополнительные типы, переходы между слоями, конфигурацию, тестирование и сопровождение. Польза должна оправдывать эти затраты.

### 3. Простота и защита от оверинжиниринга

- Реализовывать текущие требования и уже принятые ограничения. Не добавлять универсальные движки, плагины, настройки и запасные варианты поведения «на будущее» без конкретного сценария использования.
- Выбирать самое простое решение, которое сохраняет корректность, инварианты и архитектурные границы. Простота не оправдывает смешение слоёв или обход бизнес-правил.
- Создавать общую абстракцию для общего смысла и поведения, а не только из-за похожих строк кода. Небольшое дублирование допустимо, если объединение связывает независимые сценарии и усложняет их изменение.
- Предпочитать композицию наследованию, когда требуется сочетать или заменять поведение. Использовать наследование только при устойчивом отношении подтипов и соблюдении их контрактов.
- Писать функции с понятным назначением, явными входами, результатами и побочными эффектами. Избегать скрытого глобального состояния, неочевидных зависимостей и параметров-флагов, объединяющих разные сценарии.
- Не добавлять слои, классы-обёртки и промежуточные методы, которые лишь перенаправляют вызов и не защищают контракт, границу или самостоятельную ответственность.
- Рефакторинг ограничивать задачей. Улучшать затрагиваемый код, когда это нужно для изменения; не запускать массовую переработку только ради формального соответствия паттерну.

### 4. Что проверять при написании и ревью

- Понятны ли назначение кода и причина выделения каждого нового класса, интерфейса или модуля?
- Соблюдаются ли SOLID и архитектурные границы без механического увеличения числа абстракций?
- Решает ли выбранный паттерн существующую проблему, и нельзя ли решить её проще с теми же гарантиями?
- Не появились ли ненужные точки расширения, дублирующие механизмы или зависимости между независимыми сценариями?
- Можно ли проверить нужное поведение через понятный контракт, не привязывая проверки к внутреннему устройству реализации?

## Окончания строк при записи файлов

Соблюдать `.gitattributes`: текстовые файлы записывать с LF, `.bat` и `.cmd` — с CRLF.
`.editorconfig` не управляет записью из скриптов. На Windows Python `write_text()` /
`open()` без явного `newline` преобразует LF в CRLF. Для обычного текста использовать
`open(path, 'w', encoding='utf-8', newline='\n')` или запись UTF-8 bytes с LF.
После массовой генерации проверять окончания строк изменённых и новых файлов;
`git ls-files --eol` показывает только отслеживаемые файлы. Не обходить ошибки
окончаний строк через `core.safecrlf=false`: исправлять запись и сами файлы.

Create or update agent memory only when both conditions hold:

1. The knowledge is likely to remain useful for at least a week.
2. Existing code, design, plan, runbook, or wiki does not already preserve it, or the memory adds an important explanation of why.

Store decisions with consequences, non-obvious bug root causes, stable patterns, non-obvious file relationships, and unique operational constraints. Do not store task completion, changed-file lists, test logs, sync/ingest/lint results, or summaries of existing plans and wiki nodes. Update an existing entry instead of creating a duplicate. Use `sessions/` only for unfinished handoff or a unique result that fits no decision, pattern, bugfix, or wiki node.

Do not store secrets, full chats, temporary logs, or unverified guesses.

- `DDD_Wiki/` stores the DDD domain model: domains, subdomains, bounded contexts, context maps, aggregates, invariants, state machines, use cases, integration patterns, and model health.

- `memory/` stores live wiki state and LLM-wiki method files.
- `Общие_принципы/` stores reusable discovery and meeting methodology.
- `docs/knowledge-pipeline/README.md` describes the manual pipeline.

Human-readable wiki content, implementation plans, runbooks, follow-ups, and state files must be written in Russian. Do not translate paths, commands, file names, API names, types, identifiers, package names, or code.

Manual wiki workflow:

1. Morning: run `/sync-vision`, check `memory/project-state.md`, check new files in `RAW_inputs/`, then run `/ingest` for new raw inputs.
2. `/discover` без параметров ищет пробелы по всей доменной модели. Из 150 разных кандидатов выбрать 15 открытых вопросов о конкретных рабочих эпизодах. Исключить смысловые повторы и развилки, уже разрешённые принятыми правилами. Выдать только нумерованный список вопросов. `--wide` эквивалентен запуску без параметров. При явном ограничении темы, в том числе через `--context` или `--phase`, выдать до 15 вопросов в её границах. Ответы исследовать по отдельному поручению. При `/ingest` RAW этого исследования сверить цели и результаты из эпизодов с `DDD_Wiki/use_cases/`, включая задачи вне исходной анкеты. [Процесс и критерии отбора](docs/knowledge-pipeline/README.md).
3. Для планирования ближайших 14 дней запускать `/plan-sprint`. Сверить исходное состояние с кодом, `Code_wiki/`, `Wiki/`, `DDD_Wiki/` и конфликтами. Из 150 вопросов выбрать 15, влияющих на цель, объём, порядок работ или приёмку, и задать пользователю все 15 одним нумерованным списком в первом содержательном ответе в чате. При частичных ответах уточнить оставшиеся пункты. Составлять план только после ответов пользователя по всем 15 вопросам, учитывая явно делегированные решения. Из ответов вывести демонстрируемый результат, минимальный сквозной сценарий, календарь, критерии приёмки и допустимое сокращение объёма.
