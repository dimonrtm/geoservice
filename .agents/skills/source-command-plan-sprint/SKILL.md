# /plan-sprint

Начать с результата, который пользователь сможет предъявить к концу спринта. От него вывести минимальный сквозной сценарий, критерий приёмки, задачи и календарь. Команда готовит план и может запускаться независимо от `/discover`. Код в ходе планирования не менять.

## Исходные данные

Перед доменным планированием прочитать `docs/agent-memory/decisions/2026-10-13-simulated-domain-organization.md`. Предметные вопросы исследует агент через `expert_repson`. За пользователем остаются цели, масштаб и продуктовые предпочтения.

- Сверить результат предыдущего спринта и исходное состояние по `memory/project-state.md`, относящимся к цели планам, отчётам о приёмке и проверкам.
- Проверить принятые правила и конфликты по `DDD_Wiki/model_health.md`, `DDD_Wiki/index.md`, `Wiki/index.md`, реестрам вопросов, конфликтов, команд, событий, политик и спецификаций в `Wiki/_registry/`. Для происхождения спорного решения использовать `Vision_wiki/`. Из discovery брать вопросы и ответы, от которых зависит выбранный результат.
- Найти реализацию и точки приёмки по `Code_wiki/index.md`, `Code_wiki/архитектура/data_model.md`, `Code_wiki/архитектура/api_and_realtime.md` и фактическому коду. Использовать точечный `rg`, `git status --short`, `git diff --stat`, относящиеся к сценарию файлы и проверки. Установить, что уже доступно через обычную точку входа пользователя и чего не хватает.

## Цель и способ приёмки

Горизонт по умолчанию — 14 дней. Учесть заданные дату старта, доступное время и ограничения. При неизвестной дате обозначить дни относительно начала спринта и явно отметить допущения.

Сформулировать цель через участника, исходные данные, действие и наблюдаемый результат. Сразу описать, как воспроизвести результат на приёмке. Например, редактор перемещает вершину линии, сохраняет её и после перезапуска видит сохранённую геометрию. Из такого результата следуют и необходимость чтения после записи, и проверка восстановления.

Если цель уже задана, проработать её сразу. Если есть две содержательно разные цели, коротко сравнить их по пользе, необходимым зависимостям и риску. Дать рекомендацию с основанием и указать минимальный проверяемый результат каждого варианта. На выбор пользователя вынести только существенную продуктовую развилку. Когда ключевой приоритет неизвестен, предложенный вариант обозначить как условный.

## 15 решений о спринте из 150 вопросов

Внутренне сформировать **150 вопросов-кандидатов** о достижимости результата. Охватить ценность для пользователя, границы минимального сценария, правила и конфликты модели, доступность данных и API, порядок зависимых задач, миграции и демоданные, проверки, условия демонстрации и возможное сокращение объёма.

Отобрать **топ-15** по тому, насколько ответ меняет состав работ, последовательность, способ приёмки или риск срыва цели. Объединить вопросы, ведущие к одному решению. Для каждого из 15 показать **вопрос → ответ с основанием либо открытая развилка → последствие для плана**. Сгруппировать по смыслу. Полный пул показывать по отдельной просьбе.

Агент сам приводит доступные ответы из кода, проверок, принятых доменных решений и предыдущих ответов. Существенный пробел в проверках оформить как зависимость с критерием готовности. Если решение зависит от продуктового предпочтения, показать пользователю практическую разницу между вариантами. Когда данных достаточно, перейти к плану в том же запуске. Ответ из чата использовать непосредственно. Для нового RAW-файла сначала выполнить `/ingest` по его пути и учесть обновлённую модель. Устойчивое решение из чата можно сохранить в RAW и передать в `/ingest` по явной просьбе.

## План от выбранного результата

1. **Цель и приёмка.** Указать исполнителя сценария, начальные условия, действие, ожидаемый результат и проверку, по которой его можно принять.
2. **Обязательный объём.** Выделить наименьший сквозной сценарий, достигающий цели. Для каждой задачи указать, какой шаг сценария или его проверку она обеспечивает, от чего зависит, какие области кода или модели затрагивает и по какому признаку готова.
3. **Календарь.** Разложить работы по 14-дневной рамке с учётом зависимостей. Для каждой контрольной точки назвать наблюдаемый промежуточный результат и способ его проверить. Явно указать тесты, демоданные и среду финальной приёмки.
4. **Сокращение при задержке.** Назвать сигнал для сокращения, что именно можно отложить и какой сквозной результат останется проверяемым. Если задерживается обязательная зависимость или сокращение лишает сценарий смысла, указать условие пересмотра цели и влияние на приёмку.
5. **Отложенное и открытое.** Кратко перечислить отложенные возможности и причины, нерешённые конфликты, допущения и оставшиеся риски для результата.

План писать по-русски, сохраняя пути, команды и идентификаторы.
