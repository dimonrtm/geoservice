# /plan-sprint

`/plan-sprint` помогает выбрать оптимальные фичи, доработки кода и уточнения модели для ближайшего 14-дневного спринта. Команда не меняет код и не пишет sprint plan без достаточного контекста.

## Обязательный Контекст

Перед вопросами или планом прочитать:

- `DDD_Wiki/model_health.md` - пробелы, конфликты и готовность модели.
- `DDD_Wiki/index.md` и релевантные DDD-ноды.
- `Wiki/index.md`, `Wiki/_registry/questions.md`, `Wiki/_registry/conflicts.md`, `Wiki/_registry/commands.md`, `Wiki/_registry/domain_events.md`, `Wiki/_registry/policies.md`, `Wiki/_registry/specifications.md`.
- `Code_wiki/index.md`, `Code_wiki/архитектура/data_model.md`, `Code_wiki/архитектура/api_and_realtime.md` и другие релевантные технические ноды.
- `memory/project-state.md`.
- Текущий код через точечный `rg --files`, `git status --short`, `git diff --stat` и релевантные файлы, если план зависит от реального состояния реализации.
- Существующие release/sprint документы, если они релевантны текущему плану.

## Шаг 1. Зафиксировать Рамку Спринта

- Длина спринта по умолчанию: 14 дней.
- Уточнить, есть ли заданная команда, capacity, дата старта, release goal или обязательные внешние ограничения.
- Если этих данных нет, использовать осторожные допущения и явно отметить их в вопросах.

## Шаг 2. Исследовать Модель И Код

Сопоставить:

- текущую доменную модель в `Wiki/DDD_Wiki`;
- открытые конфликты и низкий confidence;
- текущую модель данных и API из `Code_wiki` и кода;
- release/sprint документы;
- пользовательские ответы в чате или новых raw-файлах.

Не планировать фичу, если она зависит от unresolved conflict, не отмеченного в рисках.

## Шаг 3. Сгенерировать 150 Candidate Questions

Внутренне сгенерировать 150 вопросов для выбора оптимального состава спринта. Кандидаты должны покрывать:

- ценность для пользователя и release goal;
- фичи, которые лучше всего подтверждают core domain;
- доработки кода, которые снижают риск реализации;
- data model/API gaps;
- bounded context и aggregate risks;
- команды, события, политики и спецификации, которые должны появиться в коде;
- тесты, acceptance criteria и демо-сценарии;
- зависимости, миграции, seed/demo data, observability и rollout;
- конфликты модели, которые блокируют планирование;
- технический долг, который мешает 14-дневному результату.

## Шаг 4. Выбрать Top 15

Оценить каждый вопрос по критериям:

- насколько ответ меняет состав спринта;
- насколько снижает риск неверной фичи или неверной модели данных;
- насколько влияет на последовательность работ;
- насколько связан с unresolved conflict;
- насколько быстро пользователь может ответить;
- насколько важен для 14-дневного результата.

Показать пользователю только top 15, сгруппированные по смыслу. Для каждого вопроса указать, какое решение по sprint scope он разблокирует.

## Шаг 5. Обработать Ответы

Пользователь может ответить прямо в чате или положить ответ новым файлом в `RAW_inputs/`.

- Если ответ в чате достаточен для планирования, использовать его в текущем `/plan-sprint`.
- Если ответ нужно сохранить как устойчивое знание, попросить положить его в `RAW_inputs/` или, по явной просьбе пользователя, создать source summary и запустить `/ingest`.
- Если ответ уже лежит новым файлом в `RAW_inputs/`, сначала выполнить `/ingest` для этого файла, затем повторить планирование с обновленной моделью.

## Шаг 6. Сформировать Sprint Plan

После ответов или при явно принятых допущениях подготовить:

- sprint goal;
- выбранные фичи и почему они выбраны;
- невыбранные фичи и причина откладывания;
- 14-дневный календарь;
- backlog items с acceptance criteria;
- code areas;
- domain model updates;
- тесты и проверки;
- риски, конфликты и fallback;
- список вопросов, которые остались открытыми.

План писать на русском языке. Пути, команды, API, идентификаторы и имена файлов не переводить.

## Ограничения

- Не менять код как часть `/plan-sprint`.
- Не создавать sprint plan, который игнорирует `DDD_Wiki/model_health.md` и `Wiki/conflicts/`.
- Не выдавать все 150 вопросов, если пользователь явно не попросил.
- Не считать `Vision_wiki` канонической моделью: использовать как legacy/source слой.
- Не подменять `/ingest`: новые raw-ответы должны обрабатываться через `/ingest`.
