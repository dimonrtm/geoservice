# /ingest

## Выбор режима

Перед ingest прочитать `docs/agent-memory/decisions/2026-10-13-simulated-domain-organization.md`. Обычный `/ingest` обрабатывает источники в `RAW_inputs/`. Для технического знания из репозитория предусмотрены `repository-snapshot` и `repository-change`, которые записывают результат в `Code_wiki/`.

В отдельно поставленной задаче доменного исследования, когда готовы RAW с ответами, разбором эпизодов или выводами, обработать эти файлы через `/ingest` и оформить решения по сценариям в той же задаче. Если пользователь просил только собрать или проанализировать материалы, завершить работу на указанном результате. Самостоятельный `/discover` заканчивается выдачей вопросов. Если список вопросов позднее явно передан на `/ingest`, учесть вопросы как открытые, сохранив прежние статусы уже решённых вопросов.

Перед ingest прочитать `Wiki/index.md`, нужные `Wiki/_registry/*.md`, `DDD_Wiki/index.md`, `DDD_Wiki/model_health.md`, `Vision_wiki/index.md`, `Code_wiki/index.md`, `RAW_inputs/index.md`, если он есть, `memory/llm-wiki-method.md` и `memory/project-state.md`.

Если путь не указан, сканировать `RAW_inputs/` и выбирать только новые добавленные файлы, которые еще не встречаются как processed source в `RAW_inputs/index.md`, `Wiki/`, `DDD_Wiki/`, `Vision_wiki/`, `Code_wiki/` или `memory/project-state.md`. Старые уже обработанные raw-файлы второй раз автоматически не читать. Если старый raw-файл изменился, похож на новую версию уже обработанного документа или конфликтует с wiki, показать неоднозначность и ждать подтверждения пользователя.

Обрабатывать любой новый raw-файл, а не только файлы с вопросами или ответами. Ответы на discovery уточняют `Wiki/`, `DDD_Wiki`, `Wiki/conflicts/` и `Wiki/questions/`. Ответы на sprint planning использовать как input для `/plan-sprint`; если в них есть устойчивое доменное знание, также уточнять `Wiki/DDD_Wiki`.

Из каждого источника извлекать DDD-понятия, когда для них есть основания: ubiquitous language, domain, subdomain, core/supporting/generic classification, bounded context, context map, upstream/downstream, partnership, shared kernel, customer/supplier, conformist, anti-corruption layer, open host service, published language, separate ways, big ball of mud, entity, value object, domain service, application service, repository, factory, module/package, aggregate, aggregate root, consistency boundary, invariant, command, domain event, integration event, policy/process manager/saga, specification, business rule, constraint, eventual consistency, idempotency, transaction boundary, optional CQS/CQRS/read model.

Сначала обновлять канонический доменный слой `Wiki/`: `glossary`, `concepts`, `actors`, `external_systems`, `entities`, `value_objects`, `commands`, `domain_events`, `system_events`, `policies`, `specifications`, `conflicts`, `questions`. Затем обновлять `DDD_Wiki/`: `domains`, `subdomains`, `bounded_contexts`, `context_map`, `aggregates`, `state_machines`, `invariants`, `use_cases`, `integration_patterns`, `model_health.md`. После этого обновлять `Vision_wiki/` как legacy/source слой и `Code_wiki/` только для технического знания.

В конце обновить `RAW_inputs/index.md`, `Wiki/index.md`, `Wiki/_registry/*.md`, `DDD_Wiki/index.md`, `DDD_Wiki/model_health.md`, при необходимости `Vision_wiki/index.md`, `Code_wiki/index.md` и `memory/project-state.md`. Если lint падает только на старых RAW-файлах без frontmatter, не править RAW в рамках ingest.

`/ingest` превращает сырой источник в атомарные wiki-ноды с источниками, связями и follow-up'ами. Он не должен менять код, конфигурацию, миграции или тесты.

## Шаг 1. Определить Объект Ingest

- Если пользователь указал путь, работать с ним.
- Если путь не указан, проверить `RAW_inputs/` и найти новые или измененные файлы, которых еще нет в обработанных source-записях `RAW_inputs/index.md`, `Vision_wiki/chats/`, `Vision_wiki/index.md`, `Code_wiki/index.md` или `memory/project-state.md`.
- Если новых RAW-кандидатов нет, ничего не менять и коротко сообщить, что ingest не выполнен; предложить явно указать путь, выполнить `/ingest repository-snapshot` или `/ingest repository-change`, если это подходит к ситуации.
- Если найдено 1–5 однозначных RAW-файлов, обработать их в одном запуске. Для самостоятельных источников пройти шаги 2–8 по очереди. Для связанных материалов одного исследования сначала прочитать и классифицировать каждый файл, затем выполнить общую сверку сценариев по всему исследованию. Сохранить ссылки и отметку об обработке для каждого RAW. Итоговую проверку и отчёт по решениям выполнить один раз после записи всех результатов.
- Если найдено больше 5 RAW-кандидатов, показать список, сгруппированный по папкам `RAW_inputs/`, и попросить подтверждение: обработать все, выбрать часть или начать с одного файла.
- Если есть неоднозначность, не запускать batch без подтверждения. Неоднозначность: непонятен тип источника, файл слишком большой для надежного прохода, неясно, поступил ли новый источник или другая версия уже обработанного документа, есть возможный конфликт с существующей документацией, либо источник содержит потенциальные секреты/персональные данные.

## Шаг 2. Классифицировать Источник

- Встречи, документы, переписку и исследования классифицировать по содержанию. Доменное знание направить в `Wiki/` и `DDD_Wiki/`, технические выводы — в `Code_wiki/`. Для встреч и переписки сохранить связь с исходным материалом по шагу 6.
- Уже существующее состояние репозитория - первично фиксируется агентом через `/ingest repository-snapshot` в `Code_wiki/`.
- Значимые изменения репозитория - фиксируются агентом через `/ingest repository-change` в `Code_wiki/состояние_проекта/`.

## Режим `repository-snapshot`

`/ingest repository-snapshot` нужен для первичной или периодической инвентаризации уже существующей кодовой базы, даже если файлы не менялись. Это обзор текущего состояния репозитория, а не diff.

Когда вызывать:

- при первом наполнении `Code_wiki` для существующего проекта;
- после крупных внешних изменений, если агент не видел их как `repository-change`;
- когда `Code_wiki` пустая или явно отстает от реальной структуры проекта.

Порядок:

1. Прочитать `README.md`, `AGENTS.md`, `docs/agent-memory/file-map.md`, `memory/project-state.md`, `Code_wiki/index.md`.
2. Построить карту репозитория через `rg --files`, исключая `.git/`, `.obsidian/`, `node_modules/`, `dist/`, `build/`, `.venv/`, `__pycache__/`, временные файлы и саму wiki, если она не является объектом обзора.
3. Найти ключевые входные точки и конфигурацию: `pyproject.toml`, `requirements*.txt`, `package.json`, `docker-compose*.yml`, `Dockerfile*`, `alembic.ini`, `vite.config.*`, entrypoints backend/frontend, scripts, tests и миграции.
4. Читать файлы порциями и извлекать только устойчивые знания: архитектурные области, сервисы, API, модели данных, dev setup, build/deploy, правила стиля, тестовые стратегии, риски и follow-up'ы.
5. Создать или обновить технические ноды в `Code_wiki/архитектура/`, `Code_wiki/dev_setup/`, `Code_wiki/сборка/`, `Code_wiki/deployment/`, `Code_wiki/правила_и_стиль/`, `Code_wiki/глоссарий/`, `Code_wiki/состояние_проекта/`.
6. Создать или обновить журнал snapshot'ов в `Code_wiki/состояние_проекта/repository_snapshot.md`: дата, область обзора, прочитанные источники, созданные/обновленные wiki-ноды, пробелы и follow-up'ы.
7. Обновить `Code_wiki/index.md` и `memory/project-state.md`.
8. Запустить `python scripts/lint-wiki.py --root .`.

Ограничения:

- Не пытаться индексировать весь репозиторий дословно. Snapshot фиксирует знания и структуру, а не копирует код.
- Не писать секреты, значения `.env`, токены, пароли и персональные данные.
- Не менять код, конфигурацию, миграции или тесты как часть snapshot.
- Если обзор большой, делить на области: backend, frontend, infra, scripts, docs.

## Режим `repository-change`

`/ingest repository-change` вызывается только если завершённая работа содержит
новое устойчивое техническое знание, которое требуется отразить в
`Code_wiki`.

Завершение плана, размер задачи, количество изменённых файлов, запуск тестов и
commit сами по себе не являются триггерами.

До вызова режима определяется только наличие нового устойчивого технического
знания. Конкретные ноды и операция create/update заранее не задаются:
`Repository Change Ingest` определяет их самостоятельно.

Порядок:

1. Определить новое устойчивое техническое знание и его проверяемые источники.
2. Прочитать только нужные части `git status --short`, `git diff --stat` и
   точечные diffs, чтобы проверить факты.
3. Изучить релевантные ноды и индекс `Code_wiki`, затем определить, какие ноды
   нужно создать или содержательно обновить.
4. Создать или обновить выбранные ноды без пересказа плана, временных шагов и
   полного списка файлов.
5. Добавить в активный реестр
   `Code_wiki/состояние_проекта/repository_change_ingest.md` по одной строке
   на содержательно изменённую ноду: дата, нода, причина и источник.
6. Не создавать запись для правок только индексов, live state, самого реестра
   или других служебных файлов pipeline.
7. Обновить `memory/project-state.md` только если изменился живой статус
   проекта; не добавлять туда историю завершённых задач.
8. Запустить `python scripts/lint-wiki.py --root .`.

Если нового устойчивого технического знания нет, режим не вызывается и пустая
запись не создаётся. Pre-commit не проверяет и не запускает repository-change
ingest. Триггер не привязан к commit.

Ограничения:

- Не создавать запись только о выполнении plan/task/tests.
- Не перечислять code files и verification logs в активном реестре.
- Не создавать строку реестра для изменений только index/state.
- Не изменять legacy history до подтверждённой cleanup-задачи.

## Шаг 3. Читать Источник Порциями

- Большие файлы читать блоками.
- Транскрипты разбирать по смысловым кускам.
- Не пытаться поглотить большой источник одним проходом, если теряется точность.
- Не выдумывать факты, которых нет в источнике.

## От эпизода к сценарию

В доменном исследовании, интервью или подборке практиков до распределения материала по вопросам discovery разобрать все указанные источники и содержательные эпизоды. Один рассказ может описывать несколько работ разных участников. Для каждой самостоятельной цели установить инициатора, повод, принятое решение, получателя и наблюдаемый результат. Где исход неизвестен, указать это. Стандарт или руководство может подтверждать ограничение, а статус выполненной работы требует свидетельства исполнителя.

Сверить каждую цель с каталогом `DDD_Wiki/use_cases/_info.md`, основным ходом, развилками и условиями завершения ближайших сценариев, правилами Wiki и прежними решениями по кандидатам. Сравнивать действие, полномочия и результат для получателя. Несколько эпизодов одной цели объединить с сохранением ссылок. Уже описанную работу связать с действующей страницей. Дополнительное подтверждение сохранить в обзоре источника. Если автор исследования предложил как кандидата уже полностью покрытую цель, явно отметить «уже покрыт», назвать совпадающий результат и сослаться на существующий раздел.

### Решить судьбу каждого кандидата

В том же доменном `/ingest` агент через `expert_repson` самостоятельно принимает решение по каждому кандидату, включая цели вне анкеты discovery. Опираться на границы долгосрочной модели GeoService, действующие инварианты и свидетельства практиков. При совместной обработке анализа и ответов одного исследования принять одно решение на цель с учётом обоих файлов. При повторной обработке переиспользовать страницу и прежнее решение. Если новые сведения меняют выбор, указать, что изменилось и почему.

| Решение | Действие агента |
| --- | --- |
| Принят | У участника GeoService есть собственное решение, получатель и проверяемый результат, который не покрыт действующим сценарием. Создать полноценную страницу в `DDD_Wiki/use_cases/` и добавить её в каталог. |
| Включён как вариант | Цель и результат уже покрыты, но новое условие меняет ход работы. Дополнить конкретный раздел действующего сценария условием, действием и исходом. Дать ссылку на раздел. |
| Уже покрыт | Для названного в исследовании кандидата совпадают действие, условия и результат. Указать действующий раздел и эпизод, подтвердивший его. |
| Отложен | Указать конкретный пробел в основании или новую ответственность, от которой зависит выбор, и условие повторного рассмотрения. |
| За границей модели | Назвать владельца решения в смежной службе и сведения, которые GeoService ей передаёт или получает. |

Для принятой страницы использовать принятые в DDD_Wiki метаданные (`type: use-case`, `status: active`, источник, уверенность и связи). Описать цель, триггер, исполнителя и получателя, предусловия и входы, основной ход, существенные альтернативы, границы ответственности и применимые инварианты. Указать проверяемый результат и привести рабочий пример с ожидаемым исходом. [Пример принятого сценария](../../../DDD_Wiki/use_cases/triage_map_correction_request.md).

В обзоре исследования или существующем реестре решений сохранить для каждого кандидата ссылку на эпизод с указанием места, ближайший use case и совпадение или различие, выбранный исход и его причину. Если близкого сценария нет, явно указать это. Для принятого и варианта дать ссылку на каноническую страницу или раздел. Связать решения с каталогом и обзором источников. Сохранить покрытие каждой записи корпуса. Отделить наблюдение участника, решение условной организации и остающуюся гипотезу. Принятие относится к доменной модели. Объём релиза и факт реализации проверяются отдельно. [Пример решений по одному исследованию](../../../DDD_Wiki/use_cases/candidates/_info.md).

## Шаг 4. Извлечь Факты

Для каждого факта определить:

- `source` - путь к RAW/source или ссылка на repository-change entry.
- `type` - concept, decision, entity, risk, assumption, followup, solution, technical note.
- уверенность - verified, inferred или hypothesis.
- связи - какие wiki-ноды нужно связать wikilinks.

## Шаг 5. Разнести По Wiki

Применить порядок обновления из раздела «Выбор режима». Для конфликтов обновить `Wiki/conflicts/` и связанный follow-up. В `Vision_wiki/` хранить происхождение продуктовых решений и материалы источника. Для технических решений использовать соответствующий узел или ADR в `Code_wiki/`.

## Шаг 6. Создать Summary Источника

Для meeting/document/chat источника создать или обновить `Vision_wiki/chats/YYYY-MM-DD-<source>.md`:

- контекст источника;
- главные тезисы;
- решения;
- конфликты;
- follow-up'ы;
- цитаты, если они короткие и важные;
- links на созданные ноды.

## Шаг 7. Обновить Индексы И State

Обновить затронутые индексы `Wiki/`, реестры `Wiki/_registry/` и `DDD_Wiki/`.

- `RAW_inputs/index.md` - отметить обработанный источник.
- `Vision_wiki/index.md` - добавить ссылки на важные новые ноды.
- `Code_wiki/index.md` - добавить ссылки на важные технические ноды.
- `memory/project-state.md` - обновить последний `/ingest`.
- `Vision_wiki/decisions/followups/index.md` - сохранить открытые вопросы и конфликты.

## Шаг 8. Проверить

Для доменного исследования сверить все выделенные цели с решениями. Каждому кандидату соответствует один обоснованный исход, каждая принятая страница доступна из каталога, каждый вариант описан по указанной ссылке. Завершить исследовательский ingest после этой сверки. В отчёте перечислить принятые сценарии со ссылками и объяснить остальные решения либо дать ссылку на их разбор по каждому кандидату. Если самостоятельных кандидатов нет, зафиксировать этот вывод и указать, что уже покрыто или уточнено.

Запустить:

```powershell
python scripts/lint-wiki.py --root .
```

## Ограничения

- Исходные материалы в `RAW_inputs/` только читать. Отметки об обработке записывать в `RAW_inputs/index.md`.
- Не менять код, конфигурацию, миграции и тесты как часть `/ingest`.
- При доменном ingest дополнять действующие сценарии принятыми вариантами, обновлять каталог и решения по кандидатам. Исторические свидетельства сохранять. Содержательные противоречия с прежними решениями фиксировать в конфликте и follow-up. Оперативные статусы, реестр, Current Discovery Queue и project-state обновлять по установленным ответам и протоколам.
- Post-ingest correction разрешен только после `/ingest` и только для конфликтов из `Vision_wiki/decisions/followups/index.md`, связанных с `Code_wiki`.
- Wiki-контент писать на русском языке; пути, команды, API, идентификаторы и имена файлов не переводить.

## Прирост модели и очередь после discovery-ответов

При ingest исследования отделять новое правило/понятие/исключение, изменение прежнего решения и дополнительное подтверждение известного. Новый URL и новая формулировка сами по себе не требуют новой ноды или повторного открытия вопроса. Если доменного прироста нет, зафиксировать подтверждение в source-summary и не добавлять косметические дубли в канонические узлы.

Ответы и фактические протоколы сопоставлять с активной Current Discovery Queue в `DDD_Wiki/model_health.md`, реестром вопросов и следующим действием в `memory/project-state.md`. Обновлять саму очередь: закрытый пункт со ссылкой на основание больше не является следующей темой. Непроверенная реализация/БД остаётся отдельной технической задачей, не повторным вопросом о принятом правиле. Историю и RAW не переписывать; новые независимые вопросы не закрывать по аналогии.

Для следующего discovery использовать смысловой фильтр `.agents/skills/source-command-discover/SKILL.md`. Принятие модели и проверка runtime имеют разные основания.
